# Z2 — in-process sandbox after fork, and the root cause of Z1's `wait4` ECHILD

**Research prototype, Zygote track step Z2.** Only `research/zygote-proto/**` and this file
changed. No crates, no product engine, no fixtures. Every ART run went through
`tools/art-runtime/run-exclusive.sh --task Z2 -- tools/guarded.sh --mem 8G --time 900 -- …`;
scratch stayed in `.cache/z2-*`; no leftover `bwrap`/`dalvikvm64`/`z2*` processes.

Raw logs: `.cache/z2-logs/{diag.log,run-n{1,2,5}.log}`. Machine-readable snapshots:
`research/zygote-proto/evidence/Z2-N{1,2,5}.json` (rollups + grouped mappings; the full
`smaps` was not committed).

---

## 0. Verdict

| question | answer |
|---|---|
| Why did `wait4` fail with `ECHILD` inside ART? | **Not ART and not bwrap.** The prototype's JNI shim declared the entries as if the Java methods were *instance* methods. Every `Nat` method is `static native`, so JNI passes `(JNIEnv*, jclass)` first: `waitPid(pid)` actually called `wait4(JNIEnv_low32, …)`, and `waitPidOpt(pid, options)` called `wait4(JNIEnv_low32, …, jclass_low32)`. `SIGCHLD` was `SIG_DFL` all along. |
| Is it fixed? | **Yes.** `wait4` now returns the child's real status: `exit=7`, `terminated_by_signal=15`, `exit=0`, in one parent (below). |
| Does the in-process sandbox work unprivileged? | **Yes for user/mount/PID namespaces, private mounts, seccomp and a capability drop.** `setresuid` to a *distinct* uid is **impossible** unprivileged: only one uid is mappable in the parent user namespace (`setresuid(10000) → EINVAL`). No fake uid split is claimed. |
| Child A cannot see child B's private file | **Pass**, raw `ENOENT` in every child (N=5). |
| A child cannot read the zygote's private dir | **Pass**, raw `ENOENT` (tmpfs over `/data/zygote-private`). |
| Seccomp blocks a chosen syscall | **Pass**: `ptrace`, `mount`, `unshare`, `fork` each return `-EPERM` after setup; `PR_GET_SECCOMP=2`. |
| Does the sandbox break CoW? | **No.** The boot image and pre-fork heap are still one physical copy. Total Σ Pss grows **3.6 MiB per child** (N=1→N=5) versus Z1's 3.0 MiB; ~2.5 MiB of the difference is the two sandbox helper processes this topology needs. |
| 5 GCs + 4×20 000 monitors still work? | **Yes**, in all five N=5 children (`ms=[1,1,1,1,1]`, `contended=80000/80000`). |
| `fork→ready` with the sandbox | **20–28 ms** (Z1: 14–19 ms); sandbox setup itself is **2–3 ms**. |

## 1. `wait4` ECHILD: root cause and fix

### 1.1 What the hypotheses said

The Z1 write-up guessed `SIGCHLD = SIG_IGN` / `SA_NOCLDWAIT`. The measurements say no:

```text
diag_masks before SigIgn=0000002000000007 SigCgt=0000004e400084f8 SigBlk=0000000080001204
diag_sigchld before action=0x0          # handler 0 = SIG_DFL, flags 0
diag_reset rc=0 action_after=0x0
diag_parent forked=10 immediately WNOHANG ret=0 status=0x0        # child alive and waitable
diag_child pid=10 ppid=2 SigIgn=0000002000000007 action=0x0
diag_parent t+300ms WNOHANG ret=0 status=0x0
diag_child exiting 3
diag_parent blocking_wait ret=10 status=0x300 exit=3 sig=0 core=0
diag_parent wait_any ret=-10(errno=10) status=0x0                 # correct: no children left
diag_parent WALL_WNOHANG ret=-10(errno=10) status=0x0
```

`SIGCHLD` is not in `SigIgn` (bit 17), not in `SigCgt` and not in `SigBlk`; the disposition is
`SIG_DFL`. A plain C probe under the *identical* bwrap argv forks and `wait4`s correctly, and
a 7-thread probe under bwrap does too. So neither bwrap, the PID namespace, nor ART's signal
handling is the cause.

### 1.2 The actual cause

The first diagnostic run had two values that could not both be kernel facts:

```text
diag_parent immediately WNOHANG ret=-22(errno=22)     # wait4 with WNOHANG = EINVAL
diag_parent blocking_wait ret=-10(errno=10)           # wait4 without options = ECHILD
...
sandbox_rc ... 5:mkdir_private=0 13:uid_before=0 15:pid_in_ns=0
iso_private_dir path=/data/data/pkg-1 exists=false
iso_sibling_dir_exists=false iso_data_listing=[pkg-784363760]
```

- `784363760` (`0x2EC070F0`) is the low 32 bits of the `JNIEnv*`.
- `sandboxRc(slot)` returned 0 for every slot because `slot` was the same pointer.
- `waitPidOpt` got the pointer as `options` → `EINVAL`; `waitPid` got it as `pid` → `ECHILD`.

Every method in `Nat.java` is `static native`. JNI passes a hidden `JNIEnv*` and `jclass`
before the Java arguments; `shim/z1fork.c` omitted them. The shim's no-argument calls
(`fork`, `getpid`, `nanos`) worked, which is why Z1 only saw the wait failure.

### 1.3 Fix

`shim/z2fork.c` now declares the hidden parameters on every entry point that takes Java
arguments, e.g.

```c
EXPORT jlong Java_dev_acos_z1_Nat_waitPid(void *env, void *cls, jint pid);
EXPORT jint  Java_dev_acos_z1_Nat_spawnSandboxed(void *env, void *cls, jint tag);
```

Verified with the same diagnostic plus the parent's real status collection (§3.3). The two
`ECHILD` observations in Z1 are therefore **prototype bugs, not Zygote or ART properties**, and
the `wait4`-is-unusable blocker from Z1 §5.3 is closed.

## 2. Sandbox sequence (AOSP order) and what works unprivileged

Child topology per session (the zygote's direct child is `A`):

```text
zygote --fork--> A  comm z2ns    unshare(NEWUSER) + maps, unshare(NEWNS), unshare(NEWPID)
                 A --fork--> B  comm z2init  PID 1 of the new PID namespace:
                                   private mount propagation, tmpfs mounts, proc mount
                   B --fork--> C comm z2app   PID 2, the ART app:
                                   seccomp -> capset(drop all) -> setresuid
                 B waits C and writes C's raw wait status to a pipe
                 A waits B, reads the status, re-raises a signal death or exits with the code
```

`A` stays in bwrap's PID namespace so the zygote can `wait4` it and observe a real
`WIFSIGNALED` status. `C` is PID 2, not PID 1, because a PID-namespace init ignores fatal
signals from its own namespace (a self-`SIGTERM` test would be a lie otherwise).

Order and results from `sandbox_rc` (one real N=1 child; all offsets are KiB/errno):

```text
sandbox_rc 0:userns=0 1:mntns=0 2:pidns=0 3:mount_private=0 4:tmpfs_data=0
           5:mkdir_private=0 6:tmpfs_zygote=0 7:proc=0 8:seccomp=0 9:capset=0
           10:setresgid=0 11:setresuid_other=-22 12:setresuid=0
           13:uid_before=1000 14:gid_before=984 15:pid_in_ns=2 16:reaper_pid=0
sandbox_ids pid=2 ppid=1 uid=0 euid=0 gid=0 threads=7
sandbox_ns mnt=mnt:[4026533822] pid=pid:[4026533825] user=user:[4026533264]
           net=net:[4026533587] ipc=ipc:[4026533522] uts=uts:[4026533521]
           cgroup=cgroup:[4026533585] time=time:[4026531834]
sandbox_seccomp status=2 ptrace_rc=-1 mount_rc=-1 unshare_rc=-1 fork_rc=-1
```

| step | mechanism | unprivileged? |
|---|---|---|
| user namespace | `unshare(CLONE_NEWUSER)`, `setgroups=deny`, uid_map `0 <outer uid> 1`, gid_map `0 <outer gid> 1` | **yes**; exactly one uid/gid can be mapped |
| mount namespace | `unshare(CLONE_NEWNS)` after NEWUSER (CAP_SYS_ADMIN in the new userns) | **yes** |
| private propagation | `mount(NULL, "/", NULL, MS_REC\|MS_PRIVATE)` | **yes** |
| per-child app data | `mount("tmpfs", "/data/data", …)`; `mkdir /data/data/pkg-<tag>` | **yes** |
| hide the zygote's private dir | `mount("tmpfs", "/data/zygote-private", …)` | **yes** |
| PID namespace | `unshare(CLONE_NEWPID)` then fork; `mount("proc","/proc","proc",…)` in PID 1 | **yes** |
| seccomp | raw `prctl(PR_SET_NO_NEW_PRIVS,1)` + `prctl(PR_SET_SECCOMP, 2, &prog)` with a 40-syscall `SECCOMP_RET_ERRNO\|EPERM` blocklist | **yes** (and installed while the process still has CAP_SYS_ADMIN in its own userns, as AOSP does) |
| capability drop | `prctl(PR_CAPBSET_DROP, 0..40)` + `capset` zero | **yes** |
| uid/gid split | `setresgid(0,0,0)`; `setresuid(0,0,0)` | **no distinct uid**: `setresuid(10000,…) → -EINVAL`. The app is uid 0 inside its own user namespace, i.e. still the single outer uid. This is a namespace identity, not a privilege boundary. |
| seccomp blocklist | `ptrace mount umount2 pivot_root chroot unshare setns fork vfork bpf keyctl add_key request_key process_vm_readv/writev kexec_* *_module open_by_handle_at name_to_handle_at iopl ioperm userfaultfd perf_event_open swapon/off reboot sethostname/domainname acct settimeofday clock_settime adjtimex clock_adjtime syslog vhangup mknod/at` | filter returns `EPERM` (not `SIGSYS`), and `kill`, `clone` (threads), `mmap`, `futex`, `nanosleep` stay allowed |

The filter is a **blocklist**, not AOSP's allowlist. A product must adopt AOSP's per-arch
`seccomp_policy` allowlist; this one exists to prove enforcement.

## 3. Isolation evidence per child (raw)

### 3.1 Files

Each child gets a private, anonymous tmpfs at `/data/data` with only its own package
directory; the zygote's private directory is over-mounted with an empty tmpfs. A child writes
its own secret first, then probes the sibling and the zygote.

N=1 (the parent's own read, before any fork):

```text
parent_private path=/data/zygote-private/secret.txt read_n=22 data=zygote-secret pid=<zygote>
iso_private_dir path=/data/data/pkg-1 exists=true canWrite=true
iso_own_file wrote=true read_n=11 data=tag=1 pid=2
iso_sibling path=/data/data/pkg-2/secret.txt errno=2(ENOENT)
iso_zygote path=/data/zygote-private/secret.txt errno=2(ENOENT)
iso_sibling_dir_exists=false iso_data_listing=[pkg-1]
```

N=5, every child (1…5) is the same, with its own name and listing:

```text
iso_private_dir path=/data/data/pkg-<n> exists=true canWrite=true
iso_own_file wrote=true read_n=11 data=tag=<n> pid=2
iso_sibling path=/data/data/pkg-<other>/secret.txt errno=2(ENOENT)
iso_zygote path=/data/zygote-private/secret.txt errno=2(ENOENT)
iso_sibling_dir_exists=false iso_data_listing=[pkg-<n>]
```

| test | result | raw |
|---|---|---|
| own private dir writable and readable | **pass** | `wrote=true read_n=11 data=tag=<n> pid=2` |
| sibling's file | **pass** (invisible) | `errno=2(ENOENT)` |
| zygote's private file | **pass** (invisible) | `errno=2(ENOENT)` |
| sibling directory enumerated | **pass** | `iso_data_listing=[pkg-<own>]` only |
| namespace ids differ per child | **pass** | `mnt=[4026533822/…] pid=[4026533825/…] user=[4026533264/…]`; net/ipc/uts are bwrap's, shared by design |

### 3.2 Seccomp

```text
sandbox_seccomp status=2 ptrace_rc=-1 mount_rc=-1 unshare_rc=-1 fork_rc=-1
```

`status=2` is `PR_GET_SECCOMP` reporting a filter; the four `-1`s are `-EPERM` from the
blocked syscalls. `getpid` still works (pid 2), `clone` for threads still works (7 threads,
4 contending workers), so the filter is not a blanket denial.

### 3.3 Exit status collected by the parent through `wait4`

N=5, after the 6 s hold:

```text
reaped child=8  pid=8  exit=7 status=0x700
reaped child=15 pid=15 terminated_by_signal=15 core=0 status=0xf
reaped child=24 pid=24 exit=0 status=0x0
reaped child=43 pid=43 exit=7 status=0x700
reaped child=57 pid=57 terminated_by_signal=15 core=0 status=0xf
late_fork_reaped child=101 pid=101 exit=0 status=0x0
```

The signal case is forwarded honestly: the app (PID 2) dies of `SIGTERM`, PID 1 writes the raw
status to the pipe, the zygote's direct child (`A`, a normal process) re-raises `SIGTERM`, so
the zygote observes `WIFSIGNALED`/`WTERMSIG=15`, not a synthetic exit code.

Two things to read carefully:

1. **Pss totals are not monotonic at N=2** because `Pss` apportions each shared page over the
   number of mappers and the snapshot has 7 vs 4 vs 16 processes. The robust number is the
   N=1→N=5 slope, not a single row.
2. The extra **3.6 − 3.0 = 0.6 MiB/child** is almost entirely the two helper processes this
   PID-namespace topology needs (their Pss grows ~2.5 MiB/child, but they also pull shared
   Pss away from the zygote; the zygote+app slope is 1.2 MiB/child). The helpers are ART forks
   and map the same ~80 MiB address space; their `Private_Dirty` is **8 KiB each**, so they do
   not copy the boot image or the pre-fork heap. `Σ Rss` is a misleading 1.17 GiB at N=5 for
   the same reason; `Σ Pss` is the number that matters.

The four mappings from Z1 are unchanged in the app: boot-image group `PrivDirty 44 KiB`,
`dalvik-zygote space` 32 KiB, app region live bitmap ~2 MB private, pre-fork heap shared
`Shared_Dirty ≈ 61 MiB` per app. Namespaces and mounts do **not** break CoW: they add page
tables and the private 3.1 MiB region-space bitmap already present in Z1, not copied image
pages.

## 5. GC, threads, timing

Every N=5 child (and the late tag=99 child):

```text
gc pid=2 n=5 ms=[1,1,1,1,1] gc_requested=5 heap_used_kb=20598 heap_total_kb=26726 threads=7
threads pid=2 n=4 contended=80000 expected=80000 ms=6..8 threads=7
ready pid=2 tag=1..5 mode=forked fork_to_ready_ms=20..21 threads=7
```

So the sandbox survives 5 full GCs + finalization and 4 threads × 20 000 monitor acquisitions
in every child, exactly as in Z1. The zygote forks a late sixth child after all five, also
sandboxed (`late_fork_reaped child=101 exit=0`).

| | Z1 | Z2 |
|---|---:|---:|
| `fork→postForkChild` | 1 ms | 5 ms |
| sandbox setup (inside the child) | — | **2–3 ms** |
| `fork→ready` | 14–19 ms | **20–28 ms** |

The +6–9 ms is the two extra forks, three `unshare`s, six mounts, the BPF install and the
capability drop; the workload itself (20 MiB, 5 GCs, 4 threads) is still ~13–18 ms.

## 6. Remaining security gaps for a security review

1. **No uid/gid separation.** Unprivileged, only one uid is mappable, so `setresuid` cannot
   move the app to a distinct uid (`-EINVAL`, measured). The app is uid 0 in *its own* user
   namespace, which is the same outer uid as the zygote. Everything that normally follows
   from a uid boundary (file DAC, `/proc` ownership, `kill`) is therefore not enforced by uid;
   it is enforced by the private mount namespace + seccomp + the capability drop.
2. **A blocklist, not AOSP's allowlist.** 40 blocked syscalls is a proof, not a policy. A
   product must ship AOSP's per-architecture `seccomp_policy` allowlist and its `SECCOMP_RET_*`
   choices (AOSP kills on some, errnos on others).
3. **No SELinux / no Landlock.** The mount hiding is the only filesystem boundary; before
   seccomp is installed the child has CAP_SYS_ADMIN in its userns and could undo mounts (app
   code cannot run then, but a compromised native constructor before setup could).
4. **No cgroup/`RLIMIT` work** beyond what `guarded.sh` puts on the whole run; per-child CPU,
   memory, pids and `PR_SET_DUMPABLE`/core-dump policy are unset.
5. **Two helper processes per child** double the process count and each keeps the whole ART
   address space mapped (large `Σ Rss`, small `Pss`). A product variant that makes the app
   PID 1 avoids one fork but loses the honest `SIGTERM` test; the reaper design needs a cost
   decision.
6. **`execve` is not blocked**, so a child can re-exec any binary reachable in the guest root
   with the same uid. In this sysroot there is no `bwrap`, but a product must decide whether
   app `exec` is allowed (AOSP allows it) and then ensure the seccomp/uid/SELinux combination
   still contains it.
7. **Constructors before seccomp.** The app's native libraries are mapped before the sandbox
   is installed (the ART child is already running); this prototype installs seccomp before the
   post-fork Java entry, but a product that loads app code first would need a different seam.
8. **Inherited `SigIgn`/`SigCgt` state** is ART's (many signals ignored/caught); SIGCHLD is
   `SIG_DFL` and fine, but the signal disposition is not reset wholesale for the app.
9. Unmeasured: CPU cost at N>5, teardown of a hung child, `-Xint`, cold preload without an
   image, and a real (non-empty) framework-init workload.

## 7. Reproducing

```bash
research/zygote-proto/build.sh
# one locked hold: diagnostic + N=1/2/5 snapshots
tools/art-runtime/run-exclusive.sh --task Z2 -- tools/guarded.sh --mem 8G --time 900 -- \
  research/zygote-proto/z2-suite.sh

# or individually
tools/art-runtime/run-exclusive.sh --task Z2 -- tools/guarded.sh --mem 8G --time 120 -- \
  research/zygote-proto/run.sh diag
tools/art-runtime/run-exclusive.sh --task Z2 -- tools/guarded.sh --mem 8G --time 600 -- \
  python3 research/zygote-proto/measure.py --n 2 --hold 6000 --preload 800
```

`run.sh` still runs the *same* bwrap argv as the product launcher; the sandbox under test is
the in-process one in the forked child, not a second `bwrap`.
