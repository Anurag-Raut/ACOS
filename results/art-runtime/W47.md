## 1. Root cause (AOSP-first)

Stock `AlertDialog` width is **not** a dialog constant. It is the framework's
`WRAP_CONTENT` window plus the `DecorView.onMeasure` minimum
(`frameworks/base/core/java/com/android/internal/policy/DecorView.java:705-800`):

```java
availableWidth = TypedValue.applyDimension(DIP,
        res.getConfiguration().screenWidthDp, metrics);
tv = isPortrait ? mWindow.mMinWidthMinor : mWindow.mMinWidthMajor;
min = tv.getFraction(availableWidth, availableWidth);   // 0.95 * 1078.875
if (width < min) width = min;                           // 1024, not 940
```

The 940 px the scenario asserts is the dialog **content** (`1024 - 2*42` px
insets), so the window must be 1024 px. The theme values in the image's
`framework-res.apk` are:

```
dialog_min_width_major  default 65%, (large) 55%, (xlarge) 45%
dialog_min_width_minor  default 95%, (large) 80%, (xlarge) 72%
```

The pre-fix guest resolved `mMinWidthMinor` to **72%**: a temporary probe of the
live dialog `DecorView`/`PhoneWindow` (scenario `w27-dialog-window`) printed

```
cfg w=411 h=842 sw=411 dpi=420 px=1080 dens=2.625
LayoutParams -2x-2 (WRAP_CONTENT)
mMinWidthMinor type=6 (FRACTION), value 0.72  (getFraction(1080,1080)=777.6)
mMinWidthMajor type=6 (FRACTION), value 0.45
```

0.72 * (411 dp * 2.625) = **776.79 → 776 px**, exactly W40's measured width;
content was `776 - 2*42 = 692`, exactly the failing `[194,…][886,…]`.

The guest's display configuration itself was correct (`411x842 dp`, `1080x2209`
px, density `2.625`). The qualifier was wrong because the **launch
`Configuration` had no `screenLayout`**:

1. `LaunchMain.buildBindApplicationRequest()` (and
   `currentAndOverrideConfig()`) built a `Configuration` with density/dp/
   orientation but left `screenLayout = 0` (SIZE_UNDEFINED / LONG_UNDEFINED /
   LAYOUTDIR_UNDEFINED).
2. `ActivityThread.handleBindApplication` → `ResourcesManager` →
   `AssetManager.nativeSetConfiguration` therefore received `screenLayout = 0`.
3. `ResTable_config::match` with no valid size qualifier accepted the
   `(xlarge)` variants, so `dialog_min_width_minor` became 72% instead of the
   default 95%. This is a **general resource-selection bug**, not a dialog
   rule; the same mechanism affects every `-large`/`-xlarge` qualified resource.
4. `DecorView` then measured 776 px for the `WRAP_CONTENT` dialog.

`acos-wm`'s `reference_merged_configuration` also carried an invalid
`screen_layout = 0x1a` (size nibble `0xa`), so the WMS copy was wrong too even
though the bind-time guest config was what the live run used. Both are fixed
from one AOSP-derived value.

## 2. Fix

* `crates/acos-wm/src/wms.rs`:
  * `screen_layout_for_dp(long_dp, short_dp)` reproduces AOSP
    `Configuration.reduceScreenLayout` size/long thresholds and sets
    `LAYOUTDIR_LTR`; for the measured `842x411 dp` portrait display it returns
    `0x62` (`SIZE_NORMAL | LONG_YES | LAYOUTDIR_LTR`).
  * `REFERENCE_SCREEN_LAYOUT = 0x62`, used by
    `reference_merged_configuration` instead of `0x1a`.
* `crates/acos-services/src/wms.rs`: re-export `REFERENCE_SCREEN_LAYOUT` so the
  launcher uses the same value.
* `crates/acos-art/src/launch.rs`: forwards it to the guest as
  `ACOSLAUNCH_SCREEN_LAYOUT` (one env assignment; the surrounding W48 heap
  edits in this shared file are not part of W47).
* `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java`:
  `displayConfiguration()` is the single builder for both the bind request and
  the launch-item `current` configuration. It sets `screenLayout` from the
  host value, with the measured `0x62` as fallback. No dialog special case and
  no hardcoded 940.

With `screenLayout = 0x62`, the default `dialog_min_width_minor = 95%` is
selected: `0.95 * 1078.875 = 1024.93 → 1024` px window, 940 px content.

## 3. Unit test and negative check

`reference_screen_layout_is_normal_long_not_xlarge` (in
`crates/acos-wm/src/wms.rs`):

* asserts `REFERENCE_SCREEN_LAYOUT == 0x62`, size `SIZE_NORMAL`, long
  `LONG_YES`, layoutdir `LAYOUTDIR_LTR`, and **not** `SIZE_XLARGE`;
* negative check: the two pre-fix values `0x1a` (WMS) and `0x00` (guest bind
  config) are different and have no `SIZE_NORMAL` nibble, so they cannot
  satisfy the assertion;
* checks the AOSP thresholds for SMALL/LARGE/XLARGE so the helper is not a
  one-value table.

Runtime negative evidence (pre-fix, before the change): the probe above shows
`mMinWidthMinor = 0.72` and a 776 px window; the post-fix live tree shows the
1024 px stock window. Full details in
`results/art-runtime/evidence/W47-prefix-probe.txt`.
