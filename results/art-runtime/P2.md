# P2 — M5 screenshot, part 2: no `md5sum` fork, one file pass, hash over a trusted channel

**Result in one line.** A warm screenshot goes **30.0 → 24.4 ms p50** (−18.7 %,
n=20, every sample fresh), the **PNG bytes and `content_hash` are unchanged
character for character**, and the `md5sum` fork+exec is gone. The target of
≤ 20 ms p50 was **not** reached; §6 says exactly what is left and why.

Time box: 60 minutes was the brief; this task ran over it (see §8). No push, no
merge.

Stages 5's three sub-rows are now *concurrent*, so they no longer add up: the
encoder runs on a second thread and hands over 1 MiB chunks that the main thread
writes and hashes in one pass each.

### 1.1 In-process MD5 instead of a fork (`crates/acos-render/src/md5.rs`)

`content_hash` is `md5(PNG bytes)`, so it must stay exactly that. The launcher
used to fork `md5sum` and read the finished 9.5 MB file back (9.63 ms in D-M5's
80 ms frame; 9.47 ms here). It now streams the bytes it is writing through a
hand-written, fully unrolled RFC 1321 MD5:

* no new external crate (the workspace has no `md5`/`md-5` dependency in the
  build graph of these crates; the pure-Rust `md-5` in `Cargo.lock` belongs to
  `acos-vm` and is slower than `md5sum`, D-M5 rank 4), and no subprocess;
* the digest is fed the *exact* bytes that go to the file, so the value is
  identical by construction, and the file is traversed once for the hash instead
  of twice (write, then `md5sum` re-read);
* measured throughput **918 MB/s** on generic x86-64 (10.4 ms / 9.5 MB),
  **1058 MB/s** with `-C target-cpu=native`; `md5sum`'s own hash is ~1.2 GB/s.
  This is why the win is the *overlap*, not the hash rate — see §6.

### 1.2 One file, one pass (`crates/acos-art/src/launch.rs`)

* The encoder is now a sink (`encode_png_rgba_into`): signature/IHDR, the zlib
  stored blocks, Adler-32, the IDAT chunk and IEND are emitted in order instead
  of being assembled in three intermediate 9.5 MB buffers (`zlib`, `crc_input`,
  `out`). The IDAT CRC is folded in as the bytes are emitted (`Crc32Stream`,
  slice-by-8), and the IDAT length is computed up front.
* `capture_c1` → `encode_write_and_hash`: the encoder runs on a scoped thread and
  sends 1 MiB chunks over a bounded channel; the main thread writes each chunk
  and updates the MD5 in the same pass, then joins. The channel is bounded (4)
  so peak RSS does not grow with the frame; the sender is moved into the encoder
  thread so the drain loop terminates when the encoder returns.
* The launcher still writes exactly **one durable artifact** per frame in
  `art-frames/live-frames/` and still reports `frame_seq`, `md5`, `png`,
  `png_bytes` and the C1 evidence fields in the same reply shape.

### 1.3 No redundant read/hash in the daemon (`crates/acos-cli/src/engine/`)

* `ArtSession::capture_frame()` returns a frame's identity **and the artifact
  path** instead of the bytes. `serve` copies that artifact to the caller's path
  with `fs::copy` (kernel-side) and reports `bytes`/`md5` from the reply, so the
  daemon no longer reads 9.5 MiB and writes it again (the old
  `read_png` + `fs::write` pair). The trait `screenshot()` keeps returning bytes
  for callers that need them (verifier, scenarios).
* `FrameArtifact` (O2) is now bound from the launcher's own digest over the
  session's control channel — the same channel that already carries `frame_seq`
  and the frame path — instead of re-reading and SHA-256-ing the file at bind
  (5.3 ms on every tree reply). The claimed digest is only trusted when it is a
  well-formed 32-hex MD5 **and** the file on disk has exactly the claimed size;
  otherwise the engine hashes the file itself. `load()` still proves size + hash
  before serving any pixel, so a missing, truncated or altered artifact is a
  structured `FRAME_ARTIFACT_UNAVAILABLE` (`RENDER_IO`) error, never stale
  pixels.

### 1.4 Trace

`P2_TRACE=<path>` (or D-M5's `DM5_TRACE`) appends the per-stage lines; inert when
unset. New/converted events: `art.capture_composite`, `art.encode_filter`,
`art.encode_stored`, `art.encode_adler32`, `art.encode_crc32`,
`art.encode_idat_chunk`, `art.png_encode` (pipeline span), `art.png_write` (file
writes, cumulative), `art.md5_file` (hash, cumulative), `cli.serve_shot_write`.

| `acos-art/src/png_checksum_tests.rs::the_streamed_encoder_writes_the_same_file_as_the_pre_p2_encoder` | 1080×2209, compared against a **verbatim copy of the pre-P2 encoder** (framing included, not just the checksums) |
| `acos-cli/…::a_launcher_claimed_digest_is_bound_and_still_proved_on_load` | a launcher-claimed digest binds, **altered bytes are refused on load**, a size mismatch re-binds what the engine can prove |
| (existing O2) `frame_artifact_loads_lazily_and_verifies_its_hash`, `…_missing_file_is_a_structured_error`, `a_held_session_loads_its_bound_frame_…`, `reset_replaces_the_bound_frame_artifact` | still green, updated to the MD5 identity |

The `png_checksum_tests` change matters: the old oracle handed the *shared*
encoder body two oracle checksums, which cannot see a missing chunk type. While
writing this task a 4-byte-eaten IDAT header (`"IDAT"` not re-emitted by the
streaming path) passed every pre-existing test and hung the resume gate; the
verbatim pre-P2 encoder oracle now catches exactly that class of bug.

## 6. What is left, measured

After: 24.4 ms = C1 composite 10.25 + pipelined encode/write/hash 12.58 +
caller-copy 1.20 + IPC/serve ~0.4.

| rank | remaining | p50 | note |
|---|---|---:|---|
| 1 | **C1 composite** | **10.25 ms** | of which `hash_pixels` 7.0 (FNV-1a over 41.7 MB + non-zero scan, `acos-services/src/surface_client.rs`), memfd read 1.3, blit 1.5. **Out of scope for P2**; the word-at-a-time FNV proposal in D-M5 rank 3 would remove ~6 ms and is the single biggest remaining lever |
| 2 | **MD5 over 9.5 MB** | **10.45 ms** | the hash bounds the pipeline: this implementation runs at 918 MB/s (generic x86-64) while `md5sum`/OpenSSL reach ~1.19 GB/s. An OpenSSL-class MD5 (8.0 ms) would cut ~2.4 ms off the block; adding `-C target-cpu=native` alone gives 1058 MB/s but is not a portable default |
| 3 | encoder thread (filter + stored blocks + CRC32 + Adler-32) | 8.25 ms | overlapped with (2) but competing for memory bandwidth; a pclmul CRC32 (~1 ms instead of ~3) would shrink it under the hash and stop it from squeezing the MD5 thread |
| 4 | caller `fs::copy` of the artifact | 1.20 ms | kernel-side; a hard link would be free but would make the caller's file and the evidence artifact one inode, which the evidence trail must not allow |
| 5 | 1 MiB chunk handoff copy | ~1 ms of (3) | a scoped zero-copy double buffer (borrowed slices + `Mutex`/`Condvar`) would remove it |

**Not built (item 3 of the brief):** the optional `format: "raw"` RGBA path. It
is additive and independent of the PNG contract, but it needs its own API
surface, its own freshness/geometry rules and its own docs in
`docs/AGENT_API.md`; there was no time to measure it honestly, so nothing was
added. `docs/AGENT_API.md` is therefore unchanged.

## 7. Rules this task kept

* `wait_for_settled_observation` (P1's file area) untouched; `LaunchMain.java`
  untouched; `hash_pixels` untouched; nothing Zygote-related touched.
* `frame_seq` stays monotonic and bound to the capture: `capture_frame()` only
  advances `seen_seq` after the reply names the frame, and a non-advancing
  sequence is still `STALE_FRAME`. The artifact is still verified (size +
  content hash) before any pixel is served, and a bound frame with a missing or
  altered file is still `FRAME_ARTIFACT_UNAVAILABLE`.
* One durable PNG artifact per frame on disk, exactly as before; the caller's
  copy is a separate file (a copy, not a link), so evidence cannot be mutated
  through the caller's path.
* Scratch under `.cache/` only; every build/test/ART run through
  `run-exclusive.sh` + `guarded.sh`.

## 8. Time

The 60-minute box was exceeded (≈3 h wall, including two ART hangs traced to the
missing `"IDAT"` type and to a channel-deadlock where the sender was borrowed
rather than moved into the encoder thread; both are now covered by the tests in
§4). The measurements above were all taken inside `run-exclusive.sh`
acquisitions; the host stayed under 25 % used RAM and the run-exclusive log
records each acquisition.
