## 2. The general rule for an unknown service (documented, not hidden)

Stock behaviour is: `IServiceManager.checkService(name)` returns **null at once**
and `getService(name)` returns null *after* the client-side 5 s retry loop. ACOS
keeps both exactly as stock — a missing name still answers null immediately from
the host — and the fix for the launch stall is to **publish the service** instead
of shortening the guest's loop. Consequences, recorded so the next agent does not
re-diagnose them:

* any framework service the guest asks for with `getService` and that ACOS does
  not publish costs the guest up to 5 s per lookup, by design (that is what the
  same code does on a device whose service is genuinely absent);
* the launcher's 12 s resume budget (W25 §blocker 4) is therefore still the
  second-order issue for slow apps, and `ACOSLAUNCH_RESUME_MS` remains requested
  from the `acos-art` owner — **unchanged here** (acos-art is not W26's);
* `waitForService(name)` (the AIDL callback form) is likewise answered from the
  same table; a published name returns on the first callback.

## 6. Residuals / next walls (ranked)

1. **`android.content.IntentFilter` parcelable codec** — blocks the *debug* APK's
   `DevSupportManagerBase` init (release builds never take this path, which is why
   W25's release row is green). Smallest next action: `parcelable.rs` spec from
   the image's `IntentFilter.writeToParcel`, plus a fixture from the same call.
2. **Launcher `activity-alias` resolution** (W25 §blocker 3) — still open; the
   diagnostic APK is what W26 used. A concurrent agent has added
   `crates/acos-services/src/manifest_resolve.rs` (a one-line `mod` in `lib.rs`,
   not mine); it does not change the launcher path yet.
3. **Launcher's fixed 12 s resume budget** (W25 §blocker 4) — unchanged, still a
   one-line request for the `acos-art` owner. With sensorservice published it is
   no longer the binding constraint for this APK.
4. **`createSensorEventConnection` / `createSensorDirectConnection`** are named
   gaps. Unreachable with an empty sensor list; a real reply needs `BitTube`/fd
   delivery, which is a separate (deliberate) design decision.
5. **`Sensor` flatten layout** is not modelled — only the empty-list reply is
   byte-exact. If a scenario ever needs a non-empty sensor list, model
   `Sensor::flatten` from `libsensor.so` first.
6. **Shared `target/debug` profile**: the guest runs were made with
   `CARGO_PROFILE_DEV_DEBUG=0`; the tree was rebuilt afterwards with the default
   dev profile (debuginfo restored, `acos` 234 MB / `acos-art` 100 MB) and the
   counter row re-verified on that binary (7.08 s, pass).
7. **`lib.rs`**: not edited by W26 (the only change there is W27's
   `manifest_resolve` mod line, left untouched).
