# W60 — who SIGKILLs a launching ART guest

Time box: 60 min, started 2026-11-12T06:31Z. Host clock is +05:30; journal lines
below are quoted in local time and converted to UTC.

## 1. Result

**No host-level killer delivered the SIGKILL.** In the W50 §7.3 / W55 / W57
signature the guest dies **122–135 ms after `bwrap` starts**, with the *guest
scope* peak at **85.6–86.1 MiB** (bwrap only, no dalvikvm), the launcher's
`--die-with-parent` then SIGKILLs the guest. That is not an OOM, not earlyoom,
not systemd-oomd and not `guarded.sh`'s group kill: it is the kernel's
`PR_SET_PDEATHSIG` path firing because **the `acos-art` launcher itself ended
during startup**. In the pre-W55 code (the binary W57 actually measured — see
§4) that launcher death is misclassified as `GUEST_EXITED … signal 9`, which is
why "who SIGKILLed" was never nameable: the signal is real, but it is the
*consequence* of a launcher-side startup failure, not an external kill.

Reproduction of exactly that signature, on demand, with the W57 binary:
```
acos-art: io: No such file or directory (os error 2)
```
→ the just-spawned scope is torn down with signal 9 in ~120 ms and the session
is reported `GUEST_EXITED`. (Here the missing file was W57's deleted worktree
`GUEST_SOURCE` path; any early launcher error produces the same shape.)

### 2.2 Every host-level killer is ruled out

* **earlyoom**: `journalctl` 11:20–12:05 local contains only the hourly
  `mem avail:` reports (`mem avail: 45522 of 49800 MiB (91.41%)` at 11:40:55
  local = 06:10:55Z). No `low memory!` / `sending SIGTERM` line. `/etc/default`
  is `-r 3600 -n`; the only kill on the host is `pid=92933 python3` at
  10:34:02 local, an unrelated 46 GB leak.
* **systemd-oomd**: `inactive (dead)` (disabled).
* **kernel OOM**: `journalctl -k` for the windows has no `Out of memory` /
  `Killed process`.
* **systemd scope stop**: no `Killing process … with signal SIGKILL` line. A
  scope that systemd stops logs it; here the scope ends because its main
  process (bwrap) exited.
* **`guarded.sh` / `run-exclusive.sh`**: the failing reps were *inside* the
  guard; `guarded`'s trap only runs on guard exit (after the rep failed), and
  its group is the outer scope's, while each guest is in its own group.
  `run-exclusive.sh` only holds a flock and never signals.
* **the systemd scope memory limit / `memory.events`**: the guest scope peaks at
  86.1 MiB against `memory.max=2G` and `MemoryOOMGroup=yes`, so no
  `memory.events:oom_kill` is possible; `RunCgroup::sample()` reads
  `memory.events` and `memory.peak` and reports `oom_kills=0` (S5 design).
* **ramguard**: `results/tmp/ramguard.log` has no kill in the window (last
  memory-pressure kill 10:34:02 local, again the 46 GB python).
* **the kill logger**: with `killwatch.so` preloaded into the whole
  `acos serve` tree (sender pid/comm + `cgroup.kill` writes), every SIGKILL in
  a healthy 5-session rep is `comm=acos-art`, `kill(-<guest scope pid>)` during
  **teardown**. No other sender exists — and in the failing shape there is no
  sender at all in the tree, only the kernel's parent-death signal.

## 3. Why the guest sees signal 9

`bwrap` is started with `--die-with-parent`; when the launcher that spawned it
ends, the kernel delivers SIGKILL to bwrap (and its pid-ns init). bwrap then
re-exits `128+9`, and the pre-W55 `ArtSession` classified that as
`GUEST_EXITED … signal 9`. That is the exact trace:

```
launcher (acos-art) exits early
  └─ bwrap  --die-with-parent  ← SIGKILL from the kernel at ~122 ms
       └─ dalvikvm64            ← dies with the pid-ns init
```
The 86 MiB peak is bwrap alone: dalvikvm never got far enough to be charged.

## 4. Why W57 was still exposed

W57 measured `.cache/w57-target/release/acos` built from **bab06c6 (W53)**; the
report says so ("so the shared tree's W54/W55/W56 edits are not in the binary").
`bab06c6` predates both W55 (`f6408c5`, launcher-exit classification + stderr
tail + relaunch) and W56 (`63720f2`, scoped cleanup kills). Confirmed:

```
git merge-base --is-ancestor f6408c5 bab06c6   # false: W55 is not in W57's binary
git diff --stat bab06c6 HEAD -- crates/acos-cli/src   # art.rs +482, serve.rs +276, failure.rs +40
```
On HEAD the same event is classified from the launcher's own exit status and
stderr (`failure::classify_child_exit`, W55), so it is no longer an unexplained
`GUEST_EXITED`.

## 5. Before/after rate and reproduction attempt

* **Before** (W57 report, binary bab06c6): **2 failed N=5 reps / 9** (2/45
  launches died at launch, 122–135 ms in).
* **After** (HEAD `b5e01b7`, release binaries), W60 harness under
  `run-exclusive.sh` + `guarded.sh --mem 8G`:
  * 12 consecutive N=5 reps = **60 launches, 0 `GUEST_EXITED`**;
  * 3 × 20 `acos_reset` cycles = **60 resets, 0 `GUEST_EXITED`**;
  * a second control run of the **pre-W55 binary** (bab06c6 built in a worktree,
    `.cache/w60-target`) gave 15 N=5 reps = **75 launches, 0** and 4 × 20
    resets = **80, 0**. So the current host/state does not reproduce the 4 %
    launch death at all; with 0/135 the residual rate is ≤ ~2 % (rule of three),
    which is why the report relies on the journal + scope accounting above
    rather than a fresh kill.

Reproduce/attribute (kept in `tools/art-runtime/w60/`): `repro.py` (N fresh
sessions/rep, full descendant lineage + lifetimes), `reset.py` (reset cycles),
`killwatch.c` (`kill`/`tgkill`/`killpg`/`cgroup.kill` logger preloaded into the
daemon tree). Both keep scratch, never `/tmp`.

## 6. Conclusion and next action

The named sender of the guest's SIGKILL is the **kernel's parent-death signal
through `bwrap --die-with-parent`, triggered by the launcher ending during
startup** — not earlyoom, systemd-oomd, the kernel OOM killer, the systemd scope,
`guarded.sh` or the serve relaunch path. The launcher-side cause is already
classified on HEAD (W55); the remaining work, if a launcher-side startup error
recurs, is to surface its stderr in the *launch* reply rather than only in the
session's error envelope — the harness in §5 already records it when it happens.
