## 5. Requests (outside W44 ownership; precise)

### 5.1 W42 — `parcelable.rs` `VAL_MAP` allocation (gate 1 blocker)

`crates/acos-services/src/parcelable.rs:2567` (inside `read_dynamic`, `val::MAP`):

```rust
let mut entries = Vec::with_capacity(size as usize);
```

`size` is a guest `int32`; a 256 KiB peer frame can say `i32::MAX` and reserve
34 GiB before any element is read. `read_bundle` reaches this at `:2159`
(`Intent` extras are one caller). Bound it by the remaining payload (each entry
needs at least two 4-byte `writeValue` tags) **before** the allocation:

```rust
let size = size as usize;
if size > parcel.remaining() / 8 {
    return Err(ParcelError::BadLength { len: size, max: parcel.remaining() / 8 }.into());
}
let mut entries = Vec::with_capacity(size.min(1024));
```

Add a negative test: a `Parcel` with `VAL_MAP` + `size = i32::MAX` returns
`BadRequest`/`BadLength`, never allocates; a small valid map still decodes.

### 5.2 W42 — `cursor.rs` same class

`crates/acos-services/src/cursor.rs:357`: `Vec::with_capacity(size_usize)` from
a guest `CursorWindow` `size` (`u32`). Cap by `parcel.remaining()` or a named
`MAX_CURSOR_WINDOW_BYTES` before allocating; negative test with `size = i32::MAX`.

### 5.3 acos-cli engine (W40/W42 boundary) — scenario `activity` is ignored

`crates/acos-cli/src/engine/art.rs::ArtSession::start` always launches the
manifest MAIN/LAUNCHER (`acos-art launch --apk … --until activity-resumed`);
`LaunchRequest.activity` is never forwarded. W44 worked around it by building
one APK variant per hostile activity (see `fixtures/build-hostile-probe.sh`).
Request: forward the requested component to the guest
(`LaunchMain`/`acos-art launch` need an activity argument) or document that
ART scenarios can only launch the manifest launcher; until then, non-launcher
activities need a variant APK as above.
