## 1. Real activity tokens (the `token 0x0` wall)

Root cause as measured in W31 §3 and confirmed here: the launch `ClientTransaction` was
marshalled by the guest and sent over the peer's byte pipe, so `mActivityToken` had to be
`null` — `Parcel.marshall()` refuses a parcel that contains a binder object ("Tried to
marshall a Parcel that contains objects"). Every `ActivityClientRecord.token` was therefore
`null`, and the first `IActivityClientController` callback (Gaten's `finish()`) answered
`illegal state in atms: no activity for token 0x0`.

Changes (all in files I own):

* `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java`
  * `watch()` builds the same framework `ClientTransaction` (`LaunchActivityItem` +
    `ResumeActivityItem` via the image's own `obtain(...)`), but with a **real
    `new android.os.Binder()`** as `mActivityToken`, and hands it to the real
    `IApplicationThread.scheduleTransaction` on the local app-thread binder
    (`scheduleLocal`). Marker:
    `ACOSLAUNCH MARK schedule-transaction-delivered activity=… token=binder:<hash> transport=local-iapplicationthread`.
    The framework's `TransactionExecutor` runs it on the main thread (`EXECUTE_TRANSACTION`
    159 still appears in the `Looper` trace), so nothing about the item execution changed —
    only the token and the transport.
  * the marshalled builder remains, unused, as the byte-level reference for a future
    host-side delivery (it cannot carry a token; §5).
* `crates/acos-services/src/atms.rs`
  * `adopt_activity(token)`: on the first `activityResumed`/`activityIdle`/`activityPaused`/
    `activityStopped`/`activityDestroyed`/`finishActivity` for an unknown, non-zero token
    while the process is attached, create the record. Adoption is limited to **guest-owned
    Java binders** (the peer's `JAVA_TAG`, bit 32 — `GUEST_JAVA_BINDER_TAG`) or to a launch
    the host recorded; an arbitrary number and `0x0` still return the structured
    `no activity for token …` error. The synthetic `FIXTURE_ACTIVITY_TOKEN` record is
    dropped so the real Activity is the only one this process owns. Log:
    `ActivityManagerAdopt token=0x… activity=…` (protocol event + launcher stderr).
  * `finish_activity` also pops `AmsState`'s task stack, so the record below the finished
    Activity becomes the top (what the guest's destroy+resume returns to).
* `crates/acos-services/src/ams.rs`
  * `adopt_launch_token(real)`: binds the pending launch the host recorded under its
    placeholder token to the real guest token (rewrites `activities[].token` and
    `tasks[].activities`), and removes it from `pending_launches` — the guest materialised
    it, it is not work the runtime still owes.
* `crates/acos-services/tests/w38_activity_token.rs` (**new**, 3 rows, real fixture APK):
  guest-tagged token adopted + fixture record dropped + `finishActivity` resolves;
  `startActivity` record rebound to the real token (class from the launch, task stack
  rewritten, pending emptied, finish empties the task); arbitrary/zero tokens still error.

## 2. The second Activity: record host-side, deliver the stock items

Two things had to be true for the live path, and both now are:

1. **The host must be able to resolve the launch.** The ATMS state starts with an empty
   `ManifestDb`, so the decoded `startActivity` answered `START_NOT_FOUND` even for a
   declared target. Flagged minimal `crates/acos-art/src/launch.rs` edit (the only host-side
   launcher change; listed here as required): after `install_package_from_apk`, seed the
   shared `AtmsState.ams.manifests` from the same APK through the new
   `AtmsService::seed_manifest_from_apk`. Live: `startActivity` now records the launch and
   replies `START_SUCCESS`.
2. **The delivery must carry a binder token.** The peer's `acos.launch` channel holds exactly
   one framework-marshalled `ClientTransaction` (`peer.rs::take_launch_delivery`) and
   `Parcel.marshall()` cannot carry the token, so a host-side delivery of a token-bearing
   transaction is not possible on that ABI (§5 names the exact missing pieces). The guest
   therefore delivers **what AMS would send next**, using the framework items:

   * `LaunchMain.installStartActivityGuard`: a `startActivity*` call with an explicit
     component is (a) forwarded to the real `IActivityTaskManager` binder, so the request is
     decoded and recorded host-side (W35) and the host's `START_SUCCESS` is the gate — a
     non-zero result is returned unchanged and **nothing is launched**; then (b) the guest
     pauses the top (`PauseActivityItem`, its own transaction because a transaction carries
     one token) and delivers `LaunchActivityItem(app intent incl. extras)` +
     `ResumeActivityItem` for a **new `Binder` token**. Requests with no explicit component
     keep W27's structured `UNSUPPORTED_ANDROID_API` (no Intent resolution host-side), and a
     failed delivery returns `START_CANCELED` (2) — never a fabricated success.
   * `LaunchMain.startStopWatcher`: once the new Activity is resumed and its first
     traversal has run (200 ms), deliver `StopActivityItem(showWindow=false)` for the
     Activity it replaced — the stock `onStop`, which the launch transaction alone never
     reaches.
   * `LaunchMain.startFinishWatcher`: when that Activity's `Activity.finish()` has set
     `mFinished` (the `IActivityClientController.finishActivity` call has already succeeded
     host-side), send `DestroyActivityItem(finished=true)` for it and then
     `ResumeActivityItem` for the Activity below it (the executor cycles
     `ON_STOP → ON_START → ON_RESUME`, so `Main.onStart` runs again).

## 5. Residuals and the exact next missing pieces

**5.1 Host-driven delivery of the second transaction (the packet's literal shape).**
Today the host *records* the launch and the *guest* delivers the stock items. What a
host-driven delivery still needs, precisely:

1. `acos-binder-peer`: the `acos.launch` path holds one `ClientTransaction`
   (`peer.rs::launch_txn`, `take_launch_delivery`) and `frame_from_parcel` maps only guest
   binders (`JAVA_TAG`); a host-minted activity-token binder sent to the guest and echoed
   back in `activityResumed` has no reverse mapping (`java_wire` returns `None` →
   `UNSUPPORTED_ANDROID_API`, `peer.rs:857-905`). Needed: a per-transaction delivery queue
   keyed by app-thread binder + a host↔guest binder echo table.
2. `acos-services::codec::build_request("android.app.IApplicationThread", …)` must encode
   `android.app.servertransaction.ClientTransaction` with `FieldOp::Binder` for the token and
   `FieldOp::Interface` for `mActivityClientController`, plus the `ActivityInfo` the guest
   currently builds (`parcelable.rs` has the item specs; the binder fields are the gap).
3. `Parcel.marshall()` throw site: `LaunchMain.buildScheduleTransactionRequest`
   (`p.marshall()` → "Tried to marshall a Parcel that contains objects"). The in-process
   path avoids it; a host-built parcel would not.

**5.2 Visibility is approximated, not AMS `nowVisible`.** The stop is delivered 200 ms after
the new Activity is resumed, i.e. after `handleResumeActivity` and its first traversal, not
after AMS observes the window as visible. A faithful version keys on the new window's first
C1 frame (host `launch.rs::interactive_serve` / the WMS `relayout`→buffer order) and sends
`StopActivityItem` from there; the observable lifecycle on the fixture is already the stock
one (`Main.onStop` before `Second.finish`, `Main.onStart` again on return).

**5.3 C1 draws a destroyed window.** After Finish, `frames/11.png` == `frames/8.png`
(the destroyed Activity's composite) while `tree/11.json` has only Main. The tree/assertion
path is correct; `crates/acos-services/src/surface_client.rs` must clear a layer's stored
buffer when the window is removed/destroyed (not my file, not touched).

**5.4 Adoption label race.** If a `startActivity` is recorded *before* the first Activity's
`activityResumed` arrives (Gaten does this: `LauncherActivity.onCreate` → `finish()` +
`startActivity(MainActivity)`), the first adopted token takes the queued pending launch's
class label while the second gets `activity`. Tokens, task stack and finish are correct; only
the host's diagnostic class label can be swapped. The AIDL callback carries no class, so a
precise fix needs the guest to name its token (a new diagnostic host call), not a heuristic.
