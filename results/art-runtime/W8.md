## 1. The captured parcels

Both parcels are the *whole* request as the peer received it: 72 bytes of
`writeInterfaceToken` (`[0xc2000004][-1]["TSYS"][27][UTF-16 android.ui.ISurfaceComposer]`)
followed by the transaction body. C1's decoder starts at body offset 0. The two parcels
share a common prefix to body 40 and differ in binder identity from there.

the tag here and is therefore 8 bytes long relative to the image from that point on.

## 3. Verified: `BufferData` and `GraphicBuffer` on the wire (from `blast_txn_1028.bin`)

Body offsets (fixtures README has the full table). The tail anchors:

```
472 blurRegions count (0)
476 StretchEffect (40 bytes)
516 bufferCrop Rect
532 destinationFrame Rect (0,0,1080,2209)
548 isTrustedOverlay
552 dropInputMode
556 hasBufferData = 1
560 Parcel::writeParcelable marker = 1
564 BufferData.flags = 7
568 hasBuffer = 1
572 GraphicBuffer flattened size = 88  (13 header words + 9 transport ints = 22 words)
576 fd count = 1
580..668 the 22 words; word0 = 31 30 42 47
668..692 the BINDER_TYPE_FD object (fd 14)
692 hasFence = 1
696..708 Fence flatten (size 4, 0 fds)
708 frameNumber = 1
716/740/764 releaseBufferListener / releaseBufferEndpoint / cachedToken (3 handles)
788 cachedBufferId = 0x200000000  (== GraphicBuffer idHi=2, idLo=0)
796 hasBarrier, 800 barrierFrameNumber, 808 producerId = 1
812 TrustedPresentationThresholds: marker 1, size 16 (counts itself), 12-byte payload
832 TrustedPresentationListener: marker 1, binder, int32
```

So `BufferData` **is** r75-shaped, and `GraphicBuffer::flatten` is r75-shaped
(`[size][fdCount][13 header + transport ints][fds]`). Two real image-vs-tag deltas that
matter to the decoder:

1. **The magic is byte-reversed**: the flatten's first word in the image is
   `31 30 42 47` (uint32 `0x47423031`), while the tag's `buf[0] = 'GB01'` compiles to
   `0x31304247` (bytes `47 42 30 31`). C1 checks the tag value and would reject the image.
2. **`TrustedPresentationThresholds` is an AIDL parcelable whose size word counts
   itself** (`readFromParcel` rejects `size < 4` and then `setDataPosition(start + size)`),
   so the payload is `size - 4` bytes, not `size`. C1 skips `size`.

## 4. The remaining mismatch: 4 trailing words after `TrustedPresentationListener`

Both parcels end the layer state the same way, e.g. the 700-byte one (body):

```
504 TPL presence marker = 1
508..532 TrustedPresentationListener binder (24-byte BINDER object)
532 one word, = 0 in both parcels   <-- not in r75
536 callbackId (-1)
540 currentHdrSdrRatio (1.0f)
544 desiredHdrSdrRatio (1.0f)
548 cachingHint = 1
552 displayCount = 0, 556 stateFlags = 0, 560 applyToken (handle), ..., 624 mergedCount = 0 (end)
```

**Both parcels now consume exactly** under this model (1028: `END 956 of 956`; 700:
`END 628 of 628`, both with `displayCount == 0` and an object at `applyToken`), i.e. the
image's `TrustedPresentationListener` area carries **one extra zero word** between the
listener binder and its `callbackId` (r75 writes `binder, callbackId` only). Everything
from body 316 (end of the 16-float identity `colorTransform`) through `hasBufferData`,
the whole `BufferData` + `GraphicBuffer` + fd + fence, and the trailing parcelables then
parses field for field in r75 order. The extra word's *meaning* is not needed to decode
(one literal `read_int32`), but it is not yet explained by the image's
`TrustedPresentationListener::readFromParcel` disassembly (`readNullableStrongBinder`
then a single `readInt32`), so record it as an image-only word rather than inventing a
name for it. Re-verify with the exact-consumption assertion below before writing code.
