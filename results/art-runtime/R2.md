# R2 — an APK's own native libraries on real ART, through the normal app path

**Both fixtures answer the question in the affirmative, and neither one dies in the loader.**

- **hello-jni: 12/12, byte-for-byte the V1 report.** The APK's `classes.dex` is
  loaded by a `PathClassLoader` whose *library search path is the extracted
  `lib/x86_64`*, the app class's static initialiser runs the APK's own
  `System.loadLibrary("hellojni")`, and every native method the fixture uses
  (`NewStringUTF`, primitive args, `int[]`, native→Java static + instance
  callbacks, `RegisterNatives`-in-`JNI_OnLoad`, `ThrowNew`) returns exactly the
  values `scenarios/hello-jni.yaml` asserts. The app's own `Log.i` calls need
  **exactly one** framework-JNI registration (`register_android_util_Log`) — an
  84-line `LD_PRELOAD` shim (of which ~15 lines are the registration call), and
  nothing else.
- **rn-hello: the whole library closure loads, `JNI_OnLoad` runs, and RN's
  merged JNI registration completes** (12 pre-merged libs → 11 registered, then
  4 → 3) with **no Activity, no zygote, no `system_server`, no `/dev/binder`**.
  The first blocker is **not** the loader, not a missing symbol, and not the
  image's bionic: it is RN's own Java-side gate, `SoLoader.init() not yet
  called`, thrown from `YogaNative`'s `static { SoLoader.loadLibrary("yoga") }`.

- Owner / date: R2 (experimenter), 2026-11-11. Time-box 60 min; **hard stop at
  ~80 min**, no blocker hit — the runs are green, so nothing was escalated.
- Constraints honoured: nothing committed; only `research/art-feasibility/r2-native/`
  and this report written; `crates/` untouched (acos-art read for reference
  only, nothing copied into it); every ART command through
  `tools/guarded.sh --mem 4G --time 300`; one ART process at a time; scratch on
  disk in `.cache/art-exp-r2/` (its own `ART_DATA`, so `/data/app/...` is not
  shared with other agents); no sudo; host RAM 17/60 GB before, peak well under
  the guard.
- Depends on **E1A** (sysroot + `artroot.sh`), **E2D** (default-namespace
  `dlopen` of `libandroid_runtime.so`; the "one shim, not two" rule),
  **E1C** (the `clns` namespace is inherited from `LD_LIBRARY_PATH` — a host
  leak to avoid).

```bash
research/art-feasibility/r2-native/scripts/build.sh    # javac + d8 + NDK shim + /data/app layout
research/art-feasibility/r2-native/scripts/run.sh all  # hello-raw, hello, rn (3 ART processes, 1.6 s)
```

| artefact (`research/art-feasibility/r2-native/`) | what it is |
|---|---|
| `java/dev/acos/r2/R2Main.java` | the ladder: build the app classloader → touch the app class → call the app's natives → print the fixture report → check the scenario's exact strings |
| `java/dev/acos/r2/Nat.java`, `native/r2shim.c` | the one shim: preload constructor `dlopen`s `libandroid_runtime.so` (default namespace, `RTLD_GLOBAL`) and a JNI bridge that calls its exported `register_*` entry points |
| `java/dev/acos/r2/RnLoader.java` | `System.loadLibrary` from a loader whose search path is the APK's `lib/x86_64` (see §4.1 — this is the whole trick) |
| `scripts/r2root.sh` | `artroot.sh` + an isolated `ART_DATA` and an explicit `LD_LIBRARY_PATH` |
| `scripts/build.sh`, `scripts/run.sh` | build; run under `tools/guarded.sh` |
| `.cache/art-exp-r2/logs/{hello,hello-raw,rn,all}.log` | raw evidence (guest stdout + the logshim'd `LOG(n)` stream) |

## 1. How the namespace for `/data/app/...` has to be set up (asked explicitly)

Nothing is configured by hand: build the classloader the way `LoadedApk` does and
libnativeloader does the rest. Measured line from the `hello` run:

```
LOG(3) nativeloader: Configuring clns-2 for other apk . target_sdk_version=34,
       uses_libraries=ALL,
       library_path=/data/app/~~r2hello==/dev.acos.fixtures.hellojni-1==/lib/x86_64,
       permitted_path=/data:/mnt/expand
```

The recipe, and each part in the AOSP source (`art/libnativeloader`, `bionic/linker`):

| step | how | why / source |
|---|---|---|
| 1. the classloader | `new PathClassLoader(base.apk, <extracted lib/x86_64>, parent=null)` | `librarySearchPath` becomes the namespace's `library_path`; `parent=null` = boot classloader, i.e. what `LoadedApk` uses for the app classloader. **Not** the harness/dex classloader — a `clns` namespace is per classloader |
| 2. the namespace | created lazily on the first `System.loadLibrary` **from a class that classloader loaded** | `library_namespaces.cpp:287` — `clns-<n>`, `kAlwaysPermittedDirectories="/data:/mnt/expand"` appended to `permitted_path` (`:229`), so `/data/app/...` is reachable by construction |
| 3. parent namespace | `FindParentNamespaceByClassLoader` (`:460`) walks the parent chain; with `parent=null` there is none, so `android_create_namespace` gets `nullptr`, and bionic substitutes the *caller's* namespace (`linker.cpp:2475`) — libnativeloader's, i.e. `system`. (Not separately observable here; what *is* measured is the consequence: the app namespace resolves `liblog.so`/`libandroid.so`, which only the system-namespace link can provide.) | this is why an app namespace can `dlopen("liblog.so")` without anything extra |
| 4. exposed system libs | `app_ns->Link(&system_ns, default_public_libraries())` (`:341`) = `/system/etc/public.libraries.txt` + the NDK list | `liblog`, `libandroid`, `libEGL`, `libGLESv2`, `libc`, `libm`, `libdl`, `libjnigraphics` … are in it. **`libandroid_runtime.so` is not** — that is the whole reason a shim is needed at all |
| 5. `target_sdk_version` | set **before** the first load: `VMRuntime.setTargetSdkVersion(34)` | without it the log says `target_sdk_version=0`, which is *more* permissive (`<=30` gets the extended list, `:173`). Measured: only the number in the log changes for these fixtures, but a product must set it or RN-class apps silently get libs they would not get on device |
| 6. `LD_LIBRARY_PATH` | **must be clean** (`/data/lib` here) | E1C §1: with `LD_LIBRARY_PATH` inherited from the host, `clns-1` is configured with `/opt/cuda/lib64:/tmp/.mount_Paseo…` as its search path. Reproduced verbatim before the fix; it also silently is *the* library path of the `-cp` classloader |

**Shim needed: one, small, and only for framework JNI registration.** The app
library itself needs *no* shim: `libhellojni.so` has `DT_NEEDED` = `libc.so`,
`libdl.so` only, both public, and loads with `BIND_NOW` so the successful load
proves every symbol resolved.

something the native loader can provide.

## 3. What breaks on the way, and what it costs

### 3.1 `System.loadLibrary` is caller-classloader-scoped (the one conceptual trap)

First attempt called `System.loadLibrary("jsi")` from the *harness* class
(loaded by the `-cp` dex classloader). Result:

```
FAIL loadLibrary("jsi") :: UnsatisfiedLinkError: dlopen failed: library "libjsi.so" not found
```

Not a file-system problem — `DexPathList.nativeLibraryDirectories` for the app
loader already contained the right directory. ART uses the namespace of the
classloader that loaded the **calling** class (`Runtime.loadLibrary0`), so the
app's libraries were looked up in the harness namespace, which has no search
path into `/data/app/...`. Fix: invoke from a class loaded by a classloader whose
`librarySearchPath` *is* the app's `nativeLibraryDirectory` (`RnLoader`, §4.1).
This is also why a real app's natives always land in the right namespace "for
free": the app classloader is the caller.

### 3.2 An app's own `Log.i` needs framework JNI registration (the only shim)

`hello-raw` (no shim) gives, from the *fixture's own Java callback*:

```
FAIL callBack :: UnsatisfiedLinkError: No implementation found for
     int android.util.Log.println_native(int,int,String,String)
```

`android.util.Log`'s natives live in `libandroid_runtime.so`, which is not a
public library and is therefore invisible from an app namespace. The cheapest
shim is one registration, `register_android_util_Log` (84 lines of C here, of which ~15 are the registration itself,
`native/r2shim.c`): an `LD_PRELOAD` constructor `dlopen`s `libandroid_runtime.so`
with `RTLD_NOW|RTLD_GLOBAL` **in the default namespace** (E2D §2.2 — a `clns`
library cannot `dlsym` it, so the JNI bridge must live in the same `.so`,
otherwise it is one shim too many), and Java calls
`System.load("/data/lib/libr2shim.so")` + `Nat.register("register_android_util_Log")`.
Note this is *not* hello-jni-specific: **any** app that logs from Java — i.e. an
overwhelming majority — needs this same one-liner, so it belongs in the ACOS
"run an app's Java" substrate, not in a fixture.

### 3.3 `new MainActivity()` off the app path fails for a framework reason

```
RuntimeException: Can't create handler inside thread Thread[main,…] that has not
called Looper.prepare()      (Activity's field initialisers → HostCallbacks → Handler)
```
…and `onCreate(null)` reached through an `Unsafe`-allocated instance dies at
`ActivityInfo.parentActivityName` (null `mActivityInfo`: the field
`ActivityThread.attach` sets). Both are consequences of "no `ActivityThread`",
not of JNI. `Looper.prepare()` + the message-queue registration would fix the
first (E2D rung 3) and buys nothing for the second. The harness therefore
allocates the instance with `sun.misc.Unsafe` — documented, and it changes nothing
about the JNI results (the natives touch no instance state; the two
`callbackResult`/`voidResult` fields they *do* touch are the fixture's own).

## 4. rn-hello (React Native, x86_64) — closure, `JNI_OnLoad`, first blocker

**2.607 ms**).

### 4.1 What the loader needed that a plain `System.loadLibrary` does not

`System.loadLibrary` must be called *from* a class loaded by a loader whose
library search path is the app's native library dir (see §3.1). The harness
uses a second `PathClassLoader(guest.dex, <apk>/lib/x86_64, parent=appCl)`
(`RnLoader`) — the same arrangement an app's secondary classloader has (RN's
`SoLoader` itself resolves APK-shipped libs that way). One measured trap on the
way: the **4-argument `DexClassLoader(dexPath, optimizedDirectory,
librarySearchPath, parent)`** ctor kept the library dir in its second
(positional/optimized) slot and silently dropped it — the loader then reported
`nativeLibraryDirectories=[/data/lib]` and every load failed with `couldn't
find "libjsi.so"`. Use the 3-argument `PathClassLoader` ctor.

### 4.2 The first blocker for RN, and its cheapest fix

`SoLoader.init()` has not been called, and the RN Java classes refuse to load
their own libraries without it (`YogaNative.<clinit>` → `SoLoader.loadLibrary` →
`IllegalStateException`). This is a **Java-side** gate, and it is cheap:

- **Cheapest fix (~0.5 d):** call `SoLoader.init(context, 0)` with a stub
  `Context` whose `getApplicationInfo()` carries `sourceDir=<base.apk>` and
  `nativeLibraryDir=<lib/x86_64>` (the same stub-services approach P2a already
  uses for `IWindowManager`). SoLoader then finds both sources it needs
  (`ApplicationInfo.sourceDir` + native lib dir) and every `SoLoader.loadLibrary`
  in RN's Java code goes back to the same `System.loadLibrary` path proven above.
- **Alternative that avoids SoLoader entirely:** the native side is *already*
  fully initialised by these six explicit loads, and the merged registration has
  already run — so for a "native-only" RN bring-up, the missing piece is only
  Java-side `static` initialisers; a stub `SoLoader` class earlier on the
  classpath would do it, but that is a harness-shaped hack, not a product.
- **Not a blocker, and worth saying explicitly:** `fbjni` init, the merged
  `JNI_OnLoad`, `libc++_shared` resolution, `libandroid.so` (NDK), and Hermes'
  library presence all **worked on the first attempt**. Nothing in the native
  closure needed a single line of ACOS code.

### 4.3 What was *not* tested (deliberately)

- No `Activity`, no `Application`, no `ActivityThread`, no `Looper` (so no
  `onCreate`, and hence no `assert_log onCreate` line for hello-jni).
- No Hermes runtime creation, no JS, no `CatalystInstance`, no `ReactHostImpl` —
  the brief caps this at "cheap". Since the blocker is a Java static-init gate
  rather than the loader, the next real questions (Hermes VM init, `ReactHost`)
  are also Java/subsystem work, not loader work.
- No `SoLoader` stub was built: it is the named next step, not this experiment.

## 5. What this changes for ACOS

1. **"An APK's own `.so` loads and runs on real ART" is now measured, not
   assumed** — for a plain JNI fixture *and* for the heaviest closure in the
   fixture set. The remaining Phase 5/6 work on this axis is *not* the loader.
2. **The app-side contract is small and quotable:** `PathClassLoader(base.apk,
   <lib dir>, parent=boot)` + `VMRuntime.setTargetSdkVersion` + a clean
   `LD_LIBRARY_PATH` ⇒ libnativeloader builds the right `clns` namespace with the
   right `permitted_path` *by itself*. ACOS's own VM should reproduce exactly
   these four facts (§1) rather than the `linkerconfig` file.
3. **`register_android_util_Log` is table stakes.** Any app whose Java logs —
   effectively all of them — needs `libandroid_runtime.so`'s `Log` natives. In
   ACOS that is either "serve the framework JNI" or "ACOS's own `android.util.Log`
   with a native implementation"; the experiment shows it is one symbol, not a
   subsystem.
4. **The RN wall is `SoLoader.init`, i.e. an `Application`/`AssetManager`
   question** — the same wall P2a hit for `hello-views` (stub `Context` +
   service peer), one layer earlier. Budgeting note: the RN path's *native* risk
   is now ~0; the Java/`Context` risk is the one that repeats
   (`SoLoader`, `AssetManager`, `ReactHost`).
5. **Determinism/speed:** three ART processes (one of them `dlopen`ing 10 MB of
   RN) run in **1.59 s** wall clock under the guard, so this whole class of
   experiment is cheap enough to put in CI as a regression gate for the app
   path.

## 6. Honest caveats

- x86_64, Android 14/API-34 sysroot, `dalvikvm64`, one process at a time. The
  arm64 fixtures were not touched (no arm64 ART process in this experiment).
- The report text is produced by calling the fixture's natives in `onCreate`'s
  exact order, not by running `onCreate`; that is the one honest difference from
  a device launch (§2.1). The two `Log.i` lines the scenario asserts on *are*
  produced by the fixture's own Java code inside the JNI callbacks.
- Instances are created with `sun.misc.Unsafe.allocateInstance` (§3.3) — a
  harness device, documented, and irrelevant to the JNI findings.
- `permitted_path=/data:/mnt/expand` is libnativeloader's hard-coded app
  allowance (`kAlwaysPermittedDirectories`), so this experiment says nothing
  about `/mnt/expand` or about SEAndroid (there is none here).
- `rn` exits 1 by design: the failing check is the Yoga call that names the
  blocker. Everything up to it is green.
- The `target_sdk_version=0` vs `34` difference was measured only as the log
  field plus the public-library list; neither fixture changed its result.
