# P12 — event-only strict settle, per-session animations, bounded settle timeouts

Branch `perf-p12-event-only-anim` (off `main`). Owner decisions of 2026-11-12:
(A) remove the quiet strict rule; (B) give the agent a per-session animation
switch, default **on**; plus (C) every settle verb accepts a bounded
`settle_timeout_ms` and a timeout still returns the latest tree/frame identity.
All ART runs used real ART, the API-34 image, the release binary, and the
host-wide ART lock (`tools/art-runtime/run-exclusive.sh --task P12`).

## 1. What changed

### A. Strict settle is event-only

* `crates/acos-art/src/launch.rs`
  * deleted `strict_settle_event()` and the `ACOS_STRICT_SETTLE` forwarding into
    the guest sandbox;
  * `wait_for_settled_observation` now dispatches every `strict` request to
    `wait_for_event_settled`; the 150 ms quiet loop is reachable only from
    `fast` as its documented `quiet-fallback` (owner: "`fast` settle is
    unchanged");
  * tree replies always label `bound:"strict-event"`, `strict_rule:"event"`;
  * if `ACOS_STRICT_SETTLE` is still set, it is ignored and logged once
    (`acos-art: ACOS_STRICT_SETTLE is ignored: strict settle is event-only
    since P12`);
  * `ACOS_STRICT_SETTLE_HORIZON_MS` / `ACOS_STRICT_SETTLE_CONFIRM_MS` are kept
    and forwarded unchanged.
* `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java`
  * deleted `settleEventEnabled()` and the env read; `checkSettle` runs on
    every probe sample. There is no quiet branch left.

### B. Animations flag (default `on`, `off` = three Android animation scales at 0)

Surfaces:

| surface | shape |
|---|---|
| `acos-art launch` | `--animations on|off` |
| `acos verify` | `--animations on|off` (overrides the scenario) |
| `acos launch` | `--animations on|off` (ART session via `--keep`; the in-process Rust VM refuses `off` honestly, since it has no framework animators) |
| MCP / `acos serve` `acos_launch` | `"animations":"on"|"off"` |
| scenario YAML | top-level `animations: off` |

Mechanism (the real framework's two delivery points for
`animator_duration_scale`):

* `crates/acos-services/src/animation.rs` (new) holds the per-session scale;
  `WmsState::current_animator_scale()` answers it, so
  `IWindowManager.getCurrentAnimatorScale()` reports `0.0` when off (the same
  value a device's WMS computes from `Settings.Global`).
* The guest applies the same scale with
  `ValueAnimator.setDurationScale(0.0)` (reflective, because it is @hide and the
  guest compiles against the public `android.jar`). That is exact the call
  `WindowManagerGlobal`/`IWindowSessionCallback.onAnimatorScaleChanged` makes on
  a device, so `ValueAnimator`, `ObjectAnimator`, `StateListAnimator` and the
  native `RenderNodeAnimator` (ripple) all see it.
* ACOS's WMS runs no server-side window/Activity transition animations, so
  `transition_animation_scale`/`window_animation_scale` have no ACOS-side
  duration to scale; app-side transition animators use the same
  `ValueAnimator` scale. There is no `SettingsProvider` in the guest; the WMS
  answer plus the guest `ValueAnimator` scale is the equivalent path.
* The guest reports the applied state in every `ACOSPROBE` line
  (`"animations":{"on":…,"scale":…,"applied":…}`); the launcher makes the
  guest's report authoritative and puts `animations:"off"|"on"` on **every**
  protocol reply. `verify` writes it into `engine.json` and the verdict.
* Launch-time only. A relaunch of a live serve session with a different
  `animations` value is refused (`INVALID_ARGUMENT`, "animations is
  launch-time"); destroy and relaunch. There is no mid-session toggle (owner
  allowed documenting this).

### C. `settle_timeout_ms` on every settle verb

* `crates/acos-art/src/launch.rs`: `settle_timeout_ms` (1..=600000, default =
  the verb's existing deadline) bounds strict/fast settle for input and tree
  requests.
* On timeout the agent-facing reply is a real observation: `ok:true`, the latest
  `tree`, the latest C1 frame identity (capture fields when a buffer exists),
  `settled:false`, `bound:"timeout"`, `settle.reason` (the guest's reason) and a
  `warning`. The old `NO_FRESH_FRAME` failure remains only when the guest has
  produced no probe sample at all.
* **Verifier split (review correction):** `acos verify`/scenario steps treat a
  timed-out strict settle as a step failure (`Status::Timeout`, code `TIMEOUT`).
  The latest tree/frame and `settle.reason` stay in the step evidence, but no
  assertion runs on a screen that is still changing. `acos_assert` refuses
  `settled:false` too; only `acos_observe`/`acos_observe_tree` and frame-only
  observe return it for inspection. `settle_timeout_ms` changes the deadline,
  never the outcome.
* Plumbing: MCP `acos_launch`/`acos_reset`/`acos_observe`/`acos_observe_tree`/
  `acos_tap`/`acos_text`/`acos_key`/`acos_action`; CLI
  `acos session observe|tap|key|text --settle-timeout-ms`; scenario
  `tap`/`type`/`key`/`launch`/`reset` steps (`settle_timeout_ms`), carried
  through a new `Backend::set_settle_timeout` no-op default.

### D. Docs

`docs/AGENT_API.md` §8.6.1/§8.6.2/§8.6.3 now describe event-only strict; new
§8.6.4 "Screenshot any time, animating screens, and `settle_timeout_ms`" states
that frame-only `acos_observe`/`acos observe --screenshot` is an immediate
capture with no settle wait and that `settle:"fast"` trees are immediate; new
§8.6.5 documents `animations:"on"|"off"` and when not to use `off`.

P11 settle-lab corpus, same default (`p11-*.yaml`, animations on):
**12/12 match their expectation, `false_passes=0`,
`unexpected_failures=0`** (`p11-corpus-default.txt`).

Every strict input reply now reports `settle.pixels_changed:true|false`
against the pre-action capture. The gate evidence shows the point: the first
`w54` tap (focus into the name field) settles with
`pixels_changed:false, settled:true, bound:"strict-event"` and passes, while
`form`'s later tap reports `true`. A tap with **no draw after the action**
still times out (`reason:"no-draw-after-action"`); the regression test
`timed_out_settle_step_is_a_timeout_never_a_pass` proves verify maps that to

`p11-*` suite: 10 of 12 are green in both animation modes (anim, delay40,
delay200, chain, dialog, activity, list-smooth, layout-transition, rapid-taps,
progress-timeout now non-pass). Two are green with animations **on** and fail
with animations **off**:

| gate | on | off |
|---|---|---|
| `p11-delay1000` | pass 5/5 | wait_for TIMEOUT |
| `p11-background` | pass 5/5 | wait_for TIMEOUT (even with a text wait_for) |

`p11-progress-timeout` is a non-pass `TIMEOUT` with animations **on** (the
ProgressBar never stops), which is the gate's negative control. With animations
off the bar stops, so that case is the passing `p12-progress-anim-off`
counterpart instead.

**Finding (new, P12b/P12 exposure):** with animations on, the framework's
~0.9 s press/elevation animator kept the strict settle alive long enough that a
150 ms background-thread UI post and a 1000 ms `postDelayed` landed *before* the
reply. With animations off the tap settles in ~180 ms, and the later update was
not observed by `wait_for` polling within 3–5 s (the tree stayed `bg-wait` /
`delay1000-wait`; no C1 store appeared). This points at the main-looper's
delayed-message dispatch when the guest is otherwise idle (the probe/refresh
messages keep the looper awake but timers do not fire), not at the settle rule:
the same 40 ms/200 ms cases pass because they are inside the settle horizon.
Follow-up: H6/idle-CPU work should measure main-looper timer dispatch while the
session is idle. Until then, treat `animations:off` as bounded to state changes
caused synchronously or by already-queued messages in the 256 ms horizon.

`scenarios/p11-progress-timeout.yaml` stays `expectation: non_pass` (animations
on): the tap's strict settle times out and `acos verify` fails it as
`TIMEOUT`, so the negative control measures the verifier's no-false-pass rule.
`scenarios/p12-progress-anim-off.yaml` is the animations-off passing counterpart
(6/6). This split was the P12 review's blocking correction.

### 3.1 Adopted pixel-guard decision (recorded for the owner)

The review rebase (`main` `1f21ea7`, GR1 routing/geometry + Z7) first ran the
gates with P11's pixel guard **on**: counter, w22, w15 and `T03-render-good`
passed, but **w54, w42 and form-validation failed as `TIMEOUT`** at taps that
change no pixels (first focus into an EditText with no IME/cursor change). This
was latent while `verify` accepted settle timeouts as passes.

Owner/orchestrator decision (2026-11-12): **flip the default to guard off.**
A strict settle already requires (a) a probe newer than the action floor,
(b) the guest reporting no pending framework work, (c) a draw at/after the
action publish, and (d) the 24 ms same-draw confirmation. Those prove the frame
is from after the action; “the pixels must differ” only adds false timeouts.
Guard-off plus verify-timeout-is-`TIMEOUT` is never more permissive than main:
everything it passes, main already passed.

Implementation:

* default: guard off; `ACOS_STRICT_SETTLE_PIXEL_GUARD=on` restores P11's guard
  for experiments (no other behaviour change).
* every strict input reply and every verify input step states
  `pixels_changed:true|false` against the pre-action capture. It is evidence,
  not a failure rule (`GR2`'s W5 “tap must change state” remains a separate
  opt-in).
* tests: `settled_tap_with_identical_pixels_reports_pixels_changed_false`
  (a post-action draw with identical pixels settles and verify records
  `pixels_changed:false`); `timed_out_settle_step_is_a_timeout_never_a_pass`
  now uses `reason:"no-draw-after-action"` and asserts a `TIMEOUT` step/verdict.
* evidence: `gates-on-after-rebase.txt` (guard-on experiment, 3 red),
  `gates-on-guard-off.txt` (all green), `gates-on-default.txt` (shipped
  default, all green), `p11-corpus-default.txt` (0 false passes).


## 4. Measurements (n=30 taps per mode unless noted)

Counter fixture, `v2-art-counter` steps 4/7/9 (tap → settled in-guest tree + C1
capture; the step duration includes the bound frame capture):

| animations | n | p50 | p95 | min | max |
|---|---:|---:|---:|---:|---:|
| on | 30 | **1010.0 ms** | 1031.5 ms | 994 | 1032 |
| off | 30 | **182.0 ms** | 201.6 ms | 170 | 205 |

That is a **5.5× reduction**; the remaining ~180 ms is the bound C1 capture
(~78 ms) plus tree parse/serve round trip, not the settle wait. The settle-only
target of "tens of ms" is not proven by this step-level number; a settle-only
breakdown needs the P11 serve harness (not run here for time).

Indeterminate `ProgressBar` (settle-lab, `p11-progress-timeout`):

| animations | tap step | settle |
|---|---:|---|
| on | 3098 ms | strict timeout (`settled:false`); the agent reply keeps the latest tree, verify fails the step as `TIMEOUT` |
| off | **205 ms** | settled: the bar stops drawing at animator scale 0 |

So **animations off does stop the indeterminate ProgressBar** and strict settles
on it; `p12-progress-anim-off.yaml` passes 6/6.

False passes on the full P11 settle-lab corpus under the shipped default
(animations on) are **0/12** (`p11-corpus-default.txt`), with 0 unexpected
failures. The animations-off corpus was not re-measured (the P11 harness predates
the per-request `animations` plumbing); the animations-off evidence here is the
per-scenario gates, including the two delayed-update findings above.

## 5. Remaining risks

* The `p11-background`/`p11-delay1000` animations-off failures are a real
  observation gap for updates scheduled *after* a fast settle; documented above
  as a main-looper/idle follow-up, not papered over.
* `animations` is launch-time only; the guest applies it before the first
  traversal, and the serve API refuses to change it on a live session.
* No `SettingsProvider`: app code that reads
  `Settings.Global.animator_duration_scale` directly will still see the default.
  The framework's own animator path is correct.
* C1 captures are still charged to input steps (~78 ms), so the counter tap
  step cannot reach tens of ms even with the settle wait removed. A
  settle-only measurement (serve + `settle` object) is the honest next metric.
* The animations-off change was not exercised on the physical phone; the
  mechanism is Android's own scale, but parity is not measured.
* Fast mode's 150 ms fallback remains by owner instruction; only `strict` lost
  the quiet rule.
