# P10 — the in-guest UI tree probe is event-driven

Worktree `perf-p10-event-probe`, branch of `a69465d` (main, P3b/P3d merged).
Time box 60 min (measurement ran longer: the shared ART lock was queued behind
P9/Z4/Z5 work for long stretches). Guest: `LaunchMain.java`; host: one settle
helper in `launch.rs`. No change to the 150 ms quiet rule or to the fast rule.

The probe walk is now driven by the view tree itself: layout, draw, window
attach/detach and focus change mark a dirty bit; the probe thread coalesces the
burst into **one** sample after the frame and keeps a **250 ms** poll as the
fallback. Idle work drops 5x and the post-tap sample arrives in ~12 ms instead
of waiting for the 50 ms cadence. Strict and fast tree semantics are unchanged.

## 2. Design

`crates/acos-art/guest/java/dev/acos/art/LaunchMain.java`

* **Dirty marking (§P10, `:571-665`)** — `markTreeDirty()` bumps a volatile
  `sViewGeneration`, records `sDirtyAtMs`, sets an `AtomicBoolean` and wakes the
  probe thread. `watchRoot(View)` registers, once per root:
  `ViewTreeObserver.OnGlobalLayoutListener`, `OnDrawListener`,
  `OnWindowAttachListener` (attached **and** detached) and
  `OnWindowFocusChangeListener`. `watchProbeRoots(decor)` registers the Activity
  decor plus every root `windowViews()` reports (dialogs/menus/popups), so a
  window add/remove is observed too. Listeners **never walk and never
  serialise**; registration failures fall back to the poll. `:1527` still calls
  `startLiveProbe` at the same point (activity-resumed).
* **One coalesced walk (`startLiveProbe` `:695-860`)** — the probe thread now
  emits a sample only when:
  * a host `PROBE` line arrived (`cause="wake"`, the existing P3b fast-tree
    channel; immediate, unaffected by the debounce), or
  * the tree is dirty, has been quiet for `P10_PROBE_DEBOUNCE_MS` (default
    **8 ms**, < one frame at 60 Hz) and the previous sample is at least
    `P10_PROBE_MIN_GAP_MS` (default **25 ms**) old (`cause="dirty"`), or
  * the previous sample is `P10_PROBE_FALLBACK_MS` (default **250 ms**) old
    (`cause="poll"`).
  A burst of draw callbacks therefore coalesces; the fallback means a missed
  event can only delay a sample, never stop it. While the main thread is busy
  the thread waits (no 1 ms spin).
* **Same line, plus cause (`emitProbe` `:899-1000`)** — every emitted probe has
  the existing `seq`, `time`, `windows`, `tree` (nodes/budget/truncated),
  `emit_us`, and now `cause` (`dirty|wake|poll`) and `view_generation`. New
  window roots are registered from this main-thread callback at `:974`.

`crates/acos-art/src/launch.rs`

* `wait_for_settled_observation` (`:2244`) takes `guest_stdin` and, in **strict**
  mode only, asks for one sample at entry (`:2272-2279`). The 150 ms quiet rule,
  the generation/sequence floors and the pixel filter are byte-identical.
* After the quiet window, if the newest sample predates the last C1 store
  (`!probe_after`), the host requests one sample (`:2308-2317`, throttled to one
  request / 20 ms) instead of waiting for the slow fallback. This is the only
  way the strict invariant (“a probe sample after the LAST store”) survives the
  removal of the 50 ms poll; it is the same `PROBE` wake P3b already used for
  fast trees, and it never changes what “settled” means.
* Call sites pass the existing guest stdin: tree handler `:2859`, input handler
  `:3203`.

Why the strict entry wake is harmless and needed: with event-driven probes an
**idle** screen emits nothing, so a strict tree would otherwise wait for the
250 ms fallback (151 → up to 250 ms). One entry wake gives a sample in ~2 ms,
keeping M7 strict at 151.77 ms. Fast mode deliberately does **not** take the
entry sample: its baseline is the pre-action tree, and an entry sample can
already be the post-input state.

## 4. Probe latency and idle cost (n=20, one held session each)

`before` is `a69465d`; `after` is this branch. Same host, same method.

| | before | after |
|---|---:|---:|
| idle samples / 6 s | 119 | 24 |
| idle walks/s | **19.83** | **4.00** |
| idle causes | (no field) | poll 24 |
| tap-probe time p50 | 20.30 ms | **11.97 ms** |
| tap-probe time p95 | 49.22 ms | **21.42 ms** |
| tap-probe time max | 49.22 ms* | 24.47 ms |
| post-tap probe cause | (no field) | **dirty 20/20** |
| fresh count 20/20 | yes | yes |

\* The before cohort’s max IS the 50 ms cadence: the 50th-percentile sample is
20 ms old on average and the p95 is one full period. After, the probe is tied to
the frame: 12 ms p50 (the 8 ms debounce + main-thread scheduling) and 21 ms p95
(one 25 ms min-gap collision). The `P10_PROBE_*` knobs are read from the
environment (`envLong`), default 8/25/250 ms.

Under a continuously animating tree the min-gap caps dirty probes at ~40/s
instead of one per draw (60/s); it can never be “one walk per draw callback”.

## 5. M7 strict / fast and freshness (n=20 each, counter, 1 warm-up discarded)

| mode | before p50 / p95 | after p50 / p95 | good |
|---|---:|---:|---:|
| strict | 151.77 / 152.04 ms | **151.77 / 152.05 ms** | 20/20 |
| fast | 0.20 / 0.23 ms | **0.26 / 0.32 ms** | 20/20 |

20 post-tap reps: fast tree count == post-tap count **20/20**; strict tree count
== post-tap count **20/20**; no fast tree returned the pre-tap count in either
run. Fast is 0.06 ms slower at p50 — one extra main-thread registration/wake
path on an otherwise idle screen, inside the previously measured 0.2–0.3 ms
noise band; strict is unchanged to 0.01 ms, which is the important one (the
150 ms rule is untouched).

## 6. M4 warm launch (P7 harness, verified reference, n=20)

| | before | after |
|---|---:|---:|
| launch p50 | 461.43 ms | 476.07 ms |
| launch p95 | 481.58 ms | 485.26 ms |
| verified (count 0 tree + reference md5) | 20/20 | 20/20 |

**This is +3.2 % p50 and I do not have a clean explanation for it.** The strict
settle is unchanged in isolation (M7 strict 151.77 both), `verify_tree` after
each launch is 151.6 vs 151.9 ms, and the extra probe at settle entry is ~2 ms
of guest work. A second interleaved cohort was invalid: it ran while other
agents’ ART jobs saturated the host and produced 469.8 ms (after) vs 701.3 ms
(before) with p95 828/956 ms. So the direction of the 14.6 ms is not proven;
the number to quote is “M4 unchanged within host noise, +3.2 % in the cleaner of
two cohorts”. I did **not** get a third clean cohort before the time box.
