# W1 — the launcher's 16.3 MiB capture working set: returned on free, no knob

**Status: done, measured with real ART.** Every `acos-art` launcher used to retain
**16.3 MiB** of freed screenshot buffers in a glibc worker-thread arena after its first
`screenshot`/`tree`; at N=5 a launcher was **20.07 MiB** Pss. Now the same launcher is
**3.60 MiB** mean at N=5 (**7.38** at N=1), the marginal per-session cost falls by
**16.46 MiB**, **with no environment variable**, byte-identical PNGs (`39d1e4e3…` initial,
`9f3406c1…` after the tap, before and after), all five pixel gates green and the negative
control failing as it must. M5 warm screenshot latency is unchanged within host noise
(paired p50 **−1.1 %**, p95 **−4.3 %**; the quietest pair is **+1.6 % / +3.4 %**).
`cargo test --release -p acos-cli -p acos-art -p acos-services --offline` is green (rc=0,
64 × `test result: ok`).

- Owner: W1 implementer agent, branch `perf-w1-capture-mem`, base `c125e26`.
- Code: `crates/acos-art/src/launch.rs` (allocator default + PNG encoder stream) and
  `crates/acos-art/src/png_checksum_tests.rs` (one new oracle test). No other product

- Evidence: `results/art-runtime/evidence/W1/` (raw memory JSONs, latency JSONs, gate logs,

## 1. What changed

### 1.1 The allocator default (the fix)

`launch()` already had ZM2's env-gated `ACOS_ART_MALLOC_*` controls. It now installs
`mallopt(M_MMAP_THRESHOLD, 128 KiB)` unconditionally at the very start of `launch()`,
before any thread or buffer exists, and only then lets the env knobs override it
(`ACOS_ART_MALLOC_MMAP_THRESHOLD_KB`, `…_ARENA_MAX`, `…_TRIM_THRESHOLD_KB`,
`ACOS_ART_TRIM_AFTER_CAPTURE` all still work). glibc then services the 9.9 MiB
`read_buffer_pixels` / composite `canvas` / PNG `filtered` allocations with `mmap` and
**`free` returns them to the OS** instead of leaving them committed in the encoder
thread's arena. `mallopt` also clears glibc's dynamic threshold bit, so a 9.9 MiB free
cannot raise the threshold again. No env var is needed on the product path.

### 1.2 The last frame-sized copy is gone

`encode_png_rgba_into` no longer builds the `filtered` Vec (`(row+1) × height`, 9.93 MiB
for the counter frame). The stored-block deflate walker reads the logical filtered stream
— a zero filter byte then one pixel row, with `stride - width` pixels skipped — straight
out of `rgba` in 64 KiB blocks, folding each piece into the IDAT CRC and an incremental
Adler-32 in the same pass. The chunk framing, stored-block boundaries, checksums and file
bytes are unchanged: the old buffered encoder is still the `#[cfg(test)]` oracle, and a new
test also covers `stride > width` and a pixel buffer short of its last rows.

### 1.3 Step 2 (reuse one canvas per launcher) — considered and rejected

Retaining one 9.9 MiB canvas + one 9.9 MiB readback buffer per launcher would *keep* ~20 MiB
resident to avoid allocation churn, exactly the opposite of this task's target
(N=5 mean ≤ 6 MiB). With the one-time mmap threshold there is no steady-state frame buffer
at all, and ZM2 measured the capture itself getting cheaper (the buffers are `mmap`/
`munmap`'d instead of paged through an arena), so the reuse step was not implemented.
Note: `surface_client.rs` lives in `crates/acos-services` (the brief said `acos-art`); its
capture buffers are untouched.

## 4. M5 screenshot latency

Harness: the D-M5 fresh-socket probe (`results/art-runtime/evidence/D-M5/probe.py`, copied
here because the committed copy computes `REPO` two levels too high for this layout;
`evidence/W1/probe.py` differs only in that `REPO` constant). Held warm `acos serve
--engine art`, counter.apk, `--samples 30/40 --warmup 5`, every sample a fresh request.
Both binaries measured in **alternating rounds** because other host work was landing
during the window (some rounds show 30–70 ms outliers in *both* binaries).

| round | binary | n | p50 (ms) | p95 (ms) |
|---|---|---:|---:|---:|
| a | before | 30 | 27.58 | 32.46 |
| a | after | 30 | 24.34 | 25.18 |
| b | before | 30 | 23.63 | 62.87 |
| b | after | 30 | 24.61 | 29.33 |
| c | before | 40 | 25.34 | 29.49 |
| c | after | 40 | 24.40 | 32.00 |
| d | before | 40 | 24.22 | 29.90 |
| d | after | 40 | 27.44 | 30.37 |
| **median of rounds** | **before** | — | **24.78** | **31.18** |
| **median of rounds** | **after** | — | **24.51** | **29.85** |
| | | | **−1.1 %** | **−4.3 %** |

The quietest single pair (round a; both at the ~24 ms floor) is p50 24.34 vs 27.58 and
p95 25.18 vs 32.46 (after better). Compared with the separate quiet baseline probe
(23.96 / 24.36), the clean after run (24.34 / 25.18) is **+1.6 % / +3.4 %**. All are
inside the +10 % budget; no latency regression was found. The stage table also shows the
encoder not slower on a quiet pair: composite 10.2 vs 11.2 ms, encode 12.8 vs 13.8 ms,
write 0.9 vs 1.4 ms, MD5 10.7 vs 11.5 ms (after vs before in round a).

Raw: `evidence/W1/latency/*.json` + `summary.txt`.

## 7. Caveats

- Host noise: other agents' builds/tests were running outside the ART lock; four
  alternating latency rounds were taken and compared per round. The raw JSONs contain the
  noisy rounds so the comparison can be redone (`latency/summary.txt`).
- The probe copy in `evidence/W1/probe.py` has one changed line (`REPO`); nothing else.
- The capture-buffer attribution is by size/alignment, the encoder thread and ZM2's
  allocator-only reproduction, as in ZM2 §6 — no heap profiler was used.
- `ACOS_ART_MALLOC_*` and `ACOS_ART_TRIM_AFTER_CAPTURE` remain usable for measurement;
  `TRIM_AFTER_CAPTURE` is now redundant. The production path calls `mallopt` once, always.
