# D1 — API-34 `DisplayInfo` parcel codec, served by `ServiceHost`

**Status: done in `acos-services`. The codec now writes the API-34
`DisplayInfo.writeToParcel` field order byte for byte, `ServiceHost` serves it
for `IDisplayManager.getDisplayInfo`, and six new tests prove it (hand-built
expected bytes + a hand-written transcription of the framework's
`readFromParcel`, `data_avail() == 0`). `cargo test -p acos-services` is green
(11 test binaries, 0 failures) and `cargo clippy -p acos-services --all-targets`
is clean. Work is uncommitted, as instructed; no ART run was made.**

## 1. What was wrong

`crates/acos-services/src/display.rs` described a 21-field pre-API-34 layout
(`displayId, logicalWidth, …`) and `parcelable.rs` filled the gaps with
`IgnoredNamed` placeholders. The framework's own reader desynchronised on the
first such placeholder (`DisplayCutout.readCutoutFromParcel → bad array
lengths`), which is why `results/art-runtime/P4a.md` §7.1 recorded the codec as
pre-API-34 and §7.2 added the guest-marshalled reply template seam.

## 2. The exact API-34 write order (image-verified)

`DisplayInfo.writeToParcel` (`DisplayInfo.java:587-647`) has **51 `Parcel.write*`
sites** plus two element loops; `readFromParcel` (`:520-584`) mirrors them
one-for-one. The served reply is **260 bytes**: 4 (`writeNoException`) + 4
(`writeTypedObject` marker) + 252 (`DisplayInfo`).

Nested shapes, transcribed from the same tag:

- `DisplayAddress` — `writeParcelable` writes the runtime class name
  (`DisplayAddress$Physical`) then `writeLong(mPhysicalDisplayId)`. ACOS serves
  `null` (no physical display id), so only the `-1` name is on the wire.
- `Display.Mode` — `writeInt mModeId, mWidth, mHeight; writeFloat
  mPeakRefreshRate; writeFloatArray alternativeRefreshRates; writeIntArray
  supportedHdrTypes`. **Image vs tag:** `android-14.0.0_r75` `Display.java:2375`
  also writes `mVsyncRate`; the image's
  `classes4.dex:Landroid/view/Display$Mode;->writeToParcel` has six `Parcel`
  calls and **no** `writeFloat(mVsyncRate)`. ACOS follows the image (the image's
  reader is what must stay in sync) — verified with
  `examples/scan-parcelables`.
- `DisplayCutout$ParcelableWrapper.writeCutoutToParcel` (`DisplayCutout.java:1462-1483`)
  — variant marker `-1` null / `0` `NO_CUTOUT` / `1` geometry; the geometry is
  `writeTypedObject(mSafeInsets)`, `writeTypedArray(mBounds.getRects())`
  (count + per-element presence marker + `Rect`), `writeTypedObject(waterfall
  Insets)`, 4 ints, `writeFloat(density)`, `writeString(cutoutSpec)` (UTF-16),
  int, 2 floats, `writeIntArray(sideOverrides)`.
- `DisplayShape` — `String8, int, int, float, int, int, int, float`.
- `SurfaceControl$RefreshRateRange` — two floats.
- `RoundedCorners`, `DeviceProductInfo`, `HdrCapabilities`, `DisplayShape`,
  `layoutLimitedRefreshRate`, `thermalBrightnessThrottlingDataId` are served
  `null`; `thermalRefreshRateThrottling` is the **empty** `SparseArray` the
  framework's own `DisplayInfo()` constructor installs (count `0`, not `-1`).

`supportedModes` / `supportedColorModes` / `userDisabledHdrTypes` are written as
`writeInt(length)` + elements, *not* `writeTypedArray` (the framework loops over
`Mode.writeToParcel` directly), and `readFromParcel` mirrors that with
`Display.Mode.CREATOR.createFromParcel`.

## 3. Implementation

| file | change |
|---|---|
| `crates/acos-services/src/parcelable.rs` | new `FieldOp::Cutout` (writes/reads `writeCutoutToParcel`) and `FieldOp::CountedNested` (`writeInt(count)` + bare payloads, for `supportedModes`); the `DisplayInfo` spec is now the full 51-field API-34 table; new specs `Display$Mode`, `DisplayShape`, `SurfaceControl$RefreshRateRange`, `Insets`; `writeSparseArray` accepts the empty array (`0`) as well as null (`-1`); `pub const DISPLAY_INFO_CLASS` |
| `crates/acos-services/src/display.rs` | `DisplayInfo` now models the API-34 value (`layerStack`, `displayGroupId`, nominal app bounds, `defaultModeId`, `supportedModes`, `supportedColorModes`, `physicalXDpi/Y`, vsync/presentation nanos, `committedState`, `ownerUid`, brightness, `userDisabledHdrTypes`, `minimalPostProcessingSupported`, `cutout`); new `DisplayMode`, `DisplayCutout`/`CutoutGeometry`; `to_parcelable` writes in framework order, `from_parcelable` reads by the same indices; `DisplayOverride` also updates the mode and the physical dpi |
| `crates/acos-services/examples/scan_write_calls.rs` | prints the collapsed `Parcel.write*` sequence the DEX verifier sees (the tool that caught the `Mode` image/tag difference) |

`ServiceHost` needed no change: the `acos-aidl` table already lists
`getDisplayInfo → TypedObject("android.view.DisplayInfo")` (code 1), so the new
field table is what the host now writes.

## 5. Guest reply templates that can now be deleted (not edited here)

`crates/acos-art` (P4b-r owner) — **delete the display template**:

1. `guest/java/dev/acos/art/LaunchMain.java:112-114` — the
   `buildDisplayInfoReply()` call, the
   `pushReplyTemplate("android.hardware.display.IDisplayManager", 1, display)`

2. `guest/java/dev/acos/art/LaunchMain.java:658-688` — `buildDisplayInfoReply()`

   hook and the `displayinfo-field` fallback at `:961`).
3. The `getInstrumentationInfoAsUser` (`:120`) and `getApplicationInfo`
   (`:116`) templates **stay**: they are P4b-r's §4 blocker, not this codec.

Consumers of the seam (other owners, listed for the hand-off, not edited):

- `crates/acos-binder-peer/src/peer.rs` — `launch_display_reply` (`:159`), its
  accessor (`:310-312`), the assignment in the `LAUNCH_PUSH_REPLY` handler
  (`:772`) and the replay branch at `:543-556`. The generic
  `launch_reply_for` path (`:513-525`) stays for the instrumentation/application
  templates. Until these are removed the peer still prefers the guest bytes
  (`launch_reply_for` is checked *before* the host dispatch), so the new codec is
  proven here but not yet on the launch path.
- `crates/acos-runtime/src/display_java.rs` (Q2b) — `owns_method("getDisplayInfo")`
  and the `display_info()` materialisation become unnecessary; `getOverlaySupport`
  still needs its Java object/native.

Value differences to expect when the template goes away (accepted, and closer to
the device): the template's `DisplayInfo` never sets `renderFrameRate` (the field
name it probes, `refreshRate`, does not exist — see the `displayinfo-field`
error path), and leaves `supportedModes` empty, so `Display.getRefreshRate()`
was `0` on ART. The served codec reports `renderFrameRate = 60.000004` and one
`Display.Mode(1, 1080, 2400, 60.000004)`, so the refresh rate becomes the
reference value.

## 6. Residual risks / next steps

1. **No ART run in this task** (constraint), so the "framework reads it back"
   half is proven against the framework *source* order plus the image DEX, not
   against a live `DisplayInfo.CREATOR`. The natural next check is P4b-r/Q2b's
   `displayinfo-read-back` marker after deleting the template (the probe already
   exists in `LaunchMain`).
2. The variant-`1` cutout geometry is transcribed from `android-14.0.0_r75`;
   the image's `writeCutoutToParcel` could not be scanned branch-by-branch
   (the scanner collapses the `variant == 1` arm). ACOS serves `NO_CUTOUT`
   today, so nothing on the launch path depends on it; if a phone override ever
   needs the hole-punch cutout, verify that branch on ART first.
3. `DisplayInfo` is still `Verification::Prefix` for the DEX oracle (scanner
   loop collapse). The literal table test is the guard; extending the scanner to
   keep loop counts would let it be `Full`.
4. `SparseArray` support is still empty-only (`0`) or null (`-1`); a non-empty
   `thermalRefreshRateThrottling` remains a structured `UnsupportedParcelable`
   rather than silently wrong bytes.
5. `DisplayInfo::from_parcelable` does not surface the fields ACOS serves as
   `null` (`address`, `deviceProductInfo`, `hdrCapabilities`, `roundedCorners`,
   `displayShape`, `layoutLimitedRefreshRate`,
   `thermalBrightnessThrottlingDataId`) — they are validated only by the
   byte-exact test.
