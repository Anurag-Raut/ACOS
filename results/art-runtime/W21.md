## 1. Wall 1 — the link line was the wall; `asset=no-asset` was a fixture bug

### Fix

`tools/build-apps.sh` compiled `nativehello.c` with no NDK libraries. The packet
expected hand-made empty soname stubs because "real NDK libs are not available
at build time"; measurement says otherwise: NDK 27.1.12297006 ships API-26 ABI
stubs that carry the right `DT_SONAME` and export the stubs
(`libandroid.so`, `libjnigraphics.so`, `libnativewindow.so`). The link line is
therefore the stock one:

```
clang -shared -fPIC -O2 -landroid -ljnigraphics -lnativewindow -o libnativehello.so …
```

The rebuilt `.so` records

```
(NEEDED) libandroid.so  (NEEDED) libjnigraphics.so  (NEEDED) libnativewindow.so  (NEEDED) libdl.so  (NEEDED) libc.so
```

and the launch resolves every symbol from the image's real libraries — no
preload, no `RTLD_GLOBAL`, no soname stub of our own (W20 rejected that as a
stock-parity fake pass and it was not needed).

`hello-jni` (JNI/libc only) and `native-hostile` (libc/JNI only) reference no
`android/*` NDK API: `grep -rl 'android/' fixtures/apps/*/jni` matches only
`native-hello`. Their link lines are correct as built and were not changed.

### The next wall was a fixture bug, not ACOS

With the link fixed, W20's `asset=no-asset` reproduced once and was explained:
`AssetManager2::Open(filename)` prepends `"assets/"` (tag r75,
`base/libs/androidfw/AssetManager2.cpp:554`), so the fixture's
`AAssetManager_open(mgr, "assets/hello.txt", …)` asked for
`assets/assets/hello.txt`. On a real device it fails the same way. The fixture
now passes `hello.txt`, with the AOSP line quoted in the source comment.

Live result (shared `target/debug/acos-art`, `--until activity-resumed`):

```

AcosFixture: asset=hello-acos!!
AcosFixture: bitmapPixels=12
AcosFixture: bitmapPixel11=ff112233
AcosFixture: frame=1
```

That is all three NDK seams plus the JNI string return, through the real
`libnativehello.so` loaded by the image's `libnativeloader`.

## 2. Wall 2 — the priority limit: adapter in, mount wall named

### The adapter (what changed)

`crates/acos-art/shim/artshim.c` (LD_PRELOAD-ed first in every guest) now also
defines `setpriority`:

* `prio < 0` → call `setpriority(which, who, 0)` and return success; log once
  `AcosPriority: setpriority(-4) clamped to 0 (host RLIMIT_NICE is below stock
  init.rc's 40; guest-only adapter, W21)`;
* `prio >= 0` → the same raw syscall as bionic's wrapper, with `errno` set via
  the guest's `__errno` (a *weak* undefined symbol, so the same shim still loads
  on a host libc for tests).

Why this is sound and minimal: the image's `androidSetThreadPriority` only needs
`setpriority` to succeed; the interposition point is the same one that already
serves `__system_property_*`/`__android_log_*` (preload precedes libc in the
global lookup order); nothing is added to the host, no capability is taken,
seccomp/Landlock are unchanged and stay fail-closed. The honest cost is
recorded everywhere: the guest thread runs at nice 0 instead of -4, and the log
says so. It is not a general "swallow EPERM" switch: only negative priorities
are clamped, and any other failure still returns -1 with errno.

W20's `apply_init_rlimit_nice()` mirror is kept; on a host with the stock limit
it already gives the real behaviour and the adapter never fires.

Teeth: `crates/acos-art/tests/priority_adapter.rs` builds the real shim,
compiles a probe that calls `setpriority(-4)`, and asserts (a) the baseline
without the preload is refused on this hard-limit-0 host, (b) with the preload it
succeeds and prints exactly one clamp note, (c) a non-negative priority is
forwarded untouched and prints nothing. Passes (23:07:39Z).

`ReactRootView` has **no children**, 20 s after resume, and still none after a

```
  5:ReactRootView@1080x2209+0+0}

```

`scenarios/w21-rn-hello.yaml` (launch → tap → `wait_for "Hello ACOS"` 8 s →
assert) ends in a truthful `TIMEOUT` (`status: timeout`, step 3, 8 s of polling);
`scenarios/w15-rn-hello.yaml` still ends in `ELEMENT_NOT_FOUND`.

The first ERROR after the JS entry is libandroidfw `Invalid resource ID
0x0000000b.` (twice, empty tag) from `AssetManager2::FindEntry`
(`is_valid_resid(0xb)` is false: no package/type bits), then INFO
`System.exit called, status: 0`. Two candidate causes, in the order to test:

1. **The UI batch never runs.** Paper's mount goes through `UIManagerModule` →
   `UIImplementation` → `UIViewOperationQueue`, dispatched by RN's
   `DispatchUIFrameCallback` on `Choreographer`. The probe says no layout was
   requested at all, which fits a queued batch that no frame ever drains.
   Cheapest test: in-guest gdb/log at `UIManagerModule`'s
   `ReactChoreographer.postFrameCallback` and at `UIViewOperationQueue.dispatchViewUpdates`
   (or a guest probe that logs `mBatches`), on the same 20 s hold.
2. **A silent `createView` failure** (the `0xb` lookup). Cheap test: gdb at
   `AssetManager2::FindEntry` with `resid == 0xb`, one backtrace names the
   caller; that also explains whether `0xb` comes from a themed-attr lookup
   during `ReactTextView`/AppCompat construction.

Both are inside the launcher/guest probe, not in W19-owned code.
