## 1. What was actually wrong (two contract breaks, both first-deviation)

W10 recorded "the image's BLAST never returns a slot (allocations == stored frames)". That
framing was wrong, and the measurement that killed it is the first line of §3: with the old
pool depth the reverse callbacks **do** arrive and `BufferQueueConsumer::releaseBuffer`
**is** called for every stored frame. Slots were being returned; what was missing is that
BLAST **acquires** frames it never submits, and those acquires are only released through two
stock contract details ACOS got wrong.

1. **The completion stats named the wrong frame.** `SurfaceStats.eventStats.frameNumber` was
   the buffer the transaction *replaced*. Stock SF sends the frame it *latched*
   (`Layer::setTransactionCompletedListeners`: `handle->frameNumber = mDrawingState.frameNumber`)
   and puts the replaced buffer in `previousReleaseCallbackId`. BLAST uses both:
   `transactionCommittedCallback` erases `frameEventStats.frameNumber` from
   `mSyncedFrameNumbers` (and only then flushes the shadow queue), and `transactionCallback`
   releases every submitted buffer **older** than it (`currFrameNumber > key.framenumber`).
   With the one-behind number, neither could happen: merged/dropped frames kept their
   acquired buffers forever and the pool starved at exactly `2 + maxAcquired`.
2. **The client strips buffers it has already sent, and C1 ignored the reference.** The
   image's `SurfaceComposerClient::Transaction::cacheBuffers()` clears `BufferData::buffer`
   for a `GraphicBuffer` id already in the client's `BufferCache` and sends a
   `client_cache_t` instead (`hasBuffer == false`, `cachedBuffer.id` **is** the GraphicBuffer
   id, the token is the client's own `ITransactionCompletedListener`). The app recycles its
   slots, so from the third frame on **most** frames arrive this way: 213 of 215 in a live
   run. C1 stored only the inline ones, so the app's pixels never advanced even though it
   drew (the click listener fired: `AcosCounter: increment value=1`).

Both are needed: (1) makes the pool cycle, (2) makes every frame's pixels reach the capture.

## 2. The fix (source)

* `crates/acos-services/src/surface_client.rs`
  * the completion delivery now writes `eventStats.frameNumber = <latched frame>` and
    `previousReleaseCallbackId = <replaced buffer>` (comment in `apply_layer_state` records
    both readers, `transactionCallback` and `transactionCommittedCallback`);
  * the replaced buffer is released through exactly **one** path, as stock SF does: inside the
    completion stats when the transaction registered completion callbacks, otherwise a
    standalone `onReleaseBuffer` (the `callReleaseBufferCallback` case);
  * a bounded (16 entry, drop-oldest) **id→memfd cache** resolves `client_cache_t`
    references; a miss keeps the previous stored frame (never a blank frame);
  * `ACOS_W5_BUF` now also prints the decoded `BufferData` shape
    (`has_buffer/cached_id/producer`) and which release path was taken.
* `crates/acos-services/src/compositor_client.rs` — `DEFAULT_MAX_ACQUIRED_BUFFERS` back to
  **2** (stock-like; see the notebook row for `calculateMaxAcquiredBufferCount`).
  `ACOS_MAX_ACQUIRED_BUFFERS` stays as an explicit measurement override
  (`ACOS_MAX_ACQUIRED_BUFFERS=24` still reproduces the old behaviour).
* `crates/acos-services/tests/surface_client.rs` — the old test *asserted the bug*
  (`event frame == 1` for a frame-2 transaction, plus a duplicate `onReleaseBuffer`). It now
  asserts the stock contract, and two new tests cover the cache path and the fallback release.
* `docs/IMAGE_ABI_NOTEBOOK.md` — four W11 rows (both contract facts, the small stock pool,
  the single release path).
* `results/art-runtime/evidence/W11-frames-driver.py`, `W11-frames.json`, `W11-verify.json`,
  `W11-allocations.txt` — the acceptance evidence, reproducible from the commands in §5.

## 6. Residuals and the next wall

1. **The launcher captures logd** (`LaunchResult.logs`, ALOGW/ALOGE with tags):
   `BLASTBufferQueue`, `BufferQueueProducer` and framework errors are now readable in every
   run without gdb. Worth using before any future graphics probe.
2. Buffer-cache entries are keyed by `GraphicBuffer` id, which the shim never reuses, so a
   stale entry cannot resolve to a different buffer. The cache holds 16 fds (dups of the same
   memfds, no extra pages) and never grows; the client's cache is 4096 entries, so ours can
   miss under a pathological run — a miss keeps the last frame and is visible as a flat
   `buffer_generation`, never a blank frame.
3. `latchTime` in the stats is synthesized (`now_ns`), so `updateFrameTimestamps` runs with an
   artificial latch; it feeds frame-timeline telemetry only, never a release decision.
4. No presentation: the evidence is stored buffers + the guest's allocation counter, which is
   what ACOS can honestly claim. A phone-parity capture of the same tap sequence is the next
   evidence step, not a correctness gap in this fix.
5. `ACOS_MAX_ACQUIRED_BUFFERS` (1..=64) remains as an explicit override; W12's session bench
   may set it, and it must not be used to paper over a release bug again.
6. Pre-existing red tests are unchanged (the Rust-VM launch path ones W10 listed); nothing in
   this packet touches them.
7. Memory: the guest now allocates **2** 1080×2209 buffers (~19 MiB) instead of up to 26
   (~247 MiB); the launcher's RSS in the acceptance run stayed under the 512 MiB scenario
   budget with no pool-depth workaround in play.
