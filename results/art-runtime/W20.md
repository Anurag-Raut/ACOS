## 1. Wall 1 — native-hello: the namespace is fine, the fixture's link line is not

### Measurement (first error, unchanged by W20 code)

`acos-art launch --apk fixtures/build/apps/native-hello.apk --until
activity-resumed`:

```
java.lang.UnsatisfiedLinkError: dlopen failed: cannot locate symbol
"AAssetManager_fromJava" referenced by "/data/app-lib/x86_64/libnativehello.so"
  at java.lang.Runtime.loadLibrary0
  at dev.acos.fixtures.nativehello.NativeHelloApp.onCreate(NativeHelloApp.java:41)
```

The packet's hypothesis ("the app namespace lacks the public NDK library set")
is **rejected by measurement**. The image's own `libnativeloader` reports:

```
InitDefaultPublicLibraries for_preload=0: libandroid.so:…:libjnigraphics.so:…:libnativewindow.so:…
Configuring clns-2 for other apk /data/app/native-hello.apk. target_sdk_version=34,
uses_libraries=, library_path=/data/app-lib/x86_64
```

`libnativeloader` already links `clns-2` to the `default` namespace with that
exact set; `libandroid.so` in the image exports
`AAssetManager_fromJava@@LIBANDROID`. What the app's `.so` lacks is a
`DT_NEEDED` entry: `readelf -d` shows only `libdl.so` and `libc.so`, while the
dynamic symbol table has unversioned `AAssetManager_*` and
`AndroidBitmap_*` undefined symbols — i.e. `tools/build-apps.sh` compiled the
fixture without `-landroid -ljnigraphics -lnativewindow`.

This is stock bionic's contract, not an ACOS gap: linked-namespace shared libs
decide where a **soname may be loaded from**; relocation symbol lookup uses
`SymbolLookupList(global group, DT_NEEDED local group)`
(`bionic/linker/linker.cpp:1789`). The image's `Initialize` preloads the public
set with `0x1002` = `RTLD_NOW|RTLD_NODELETE` (disassembly at `0xf2d0`), not
`RTLD_GLOBAL`, so they are not in the global group either.

### Proof of mechanism (scratch APK only; no repo/app edit)

The **same APK**, with only `DT_NEEDED libandroid.so:libjnigraphics.so:libnativewindow.so`
added to its x86_64 library (`patchelf`, under `.cache/`), launches through the
same path and produces the app's real output:

```
outcome=ok application_created=True activity_resumed=True
AcosFixture: nativeHello=hello-from-native
AcosFixture: asset=no-asset
AcosFixture: bitmapPixels=12
AcosFixture: bitmapPixel11=ff112233
AcosFixture: frame=1
```

So the launcher, namespace, linker config, JNI registration and sandbox need no
change for the linker wall. `asset=no-asset` is a **new, genuine next wall**:
the JNI-side `AssetManager2` view of the APK does not resolve
`assets/hello.txt` even though the Java asset manager/resources are live (the
fixture opens the path `assets/hello.txt`; native `AAssetManager_open` takes an
APK-relative path, and this one is not found). That is in the guest's
AssetManager/native hand-off, not the linker.

### Smallest correct action

Add `-landroid -ljnigraphics -lnativewindow` (or omit the NDK seams) to the
native-hello link line in `tools/build-apps.sh` — **outside this packet's
ownership**; request to the integrator. Do **not** preload the public libs into
the guest or force `RTLD_GLOBAL`: that would make ACOS accept an APK that a
stock phone rejects, i.e. a fake pass by the parity rule. hello-jni (which only
needs libc/JNI) already reaches its real JNI output in the live tree:
`stringFromJNI=Hello from native C`, `add(20,22)=42`,
`sumArray([1,2,3,4,5])=15`, `javaCallbackResult=42`,
`throwFromJNI caught=thrown from native`.

## 2. Wall 2 — rn-hello: the first error is `RLIMIT_NICE`, not Hermes or the bundle

Launch is healthy: `application=…MainApplication`, `SoLoader` initialises 4 SO
sources, the merged RN JNI libraries register (11 + 3 methods), the activity
resumes, `ReactRootView` is attached. With `ACOSLAUNCH_HOLD_MS=20000` the guest
stderr carries the chronologically first fatal error:

```
Exception in thread "create_react_context" java.lang.SecurityException:
No permission to set the priority of 17
  at android.os.Process.setThreadPriority(Native Method)
  at com.facebook.react.ReactInstanceManager.lambda$runCreateReactContextOnNewThread$2(ReactInstanceManager.java:1219)
```

Framework path: `android_os_Process_setThreadPriority` →
`androidSetThreadPriority` → `setpriority(PRIO_PROCESS, tid, -4)`; EACCES is
turned into `SecurityException` (`base/core/jni/android_util_Process.cpp:537`,
`core/libutils/Threads.cpp:299`). The React context thread dies before any JS
runtime exists, so the tree stays at `ReactRootView` with no children and no
`ReactNativeJS` log (78 logd entries total).

Stock gives this right in `init.rc`:

```
# set RLIMIT_NICE to allow priorities from 19 to -20
setrlimit nice 40 40
```

This host's session has hard `RLIMIT_NICE = 0` (`/proc/self/limits`), and a
user-namespace `CAP_SYS_RESOURCE` cannot raise a hard limit (the kernel checks
the initial user namespace; measured: `raise failed: not allowed to raise
maximum limit`). The launcher cannot get a real device's behaviour for free.

### What W20 changed (owned: `crates/acos-art/src/watchdog.rs` + spawn sites)

* `apply_init_rlimit_nice()` mirrors `init.rc`'s `RLIMIT_NICE=40` in every guest
  `pre_exec` (`launch`, `session`, `app`, `run/verify` launcher): on a host
  started with the stock limit it is stock behaviour with no other change; on
  this host it is a refused no-op and never fatal.
* `note_guest_priority_gap(route)` prints, once, that the host cannot supply
  the limit and what will fail, so the wall is visible in the run log instead
  of only in a guest thread's stack:
  `acos-art: launch: guest RLIMIT_NICE 0 < init.rc 40: Process.setThreadPriority(THREAD_PRIORITY_DISPLAY) will throw SecurityException …`
* One regression test pins the stock constant (40) and that the call/gate are
  safe on a host that refuses the raise.

### Smallest next action (needs an owner/infra decision, not guest code)

Run the ART engine (or the whole `acos` invocation) with a stock-equivalent nice
limit — e.g. a system service/scope with `LimitNICE=40`, or the equivalent of
`init.rc` on the runner (needs CAP_SYS_RESOURCE in the initial user namespace).
Then the next first error should be observable in the same 20 s hold run. A
permissive shim that swallows `setpriority` EACCES was **not** done: faking the
kernel result would change app-visible semantics and count as a fake pass.

Secondary observation (not yet the blocker): SoLoader logs
`couldn't find DSO to load: libappmodules.so` and `Failed to recover` before
the Hermes JNI load. The APK ships no `libappmodules.so`; the load attempt is
survivable at this point (activity resumed, later JNI registration proceeds),
but it is the next thing to classify once the context thread lives.

## 6. Residuals / next walls (precise)

1. **native-hello link line (not owned).** `tools/build-apps.sh` must add
   `-landroid -ljnigraphics -lnativewindow` to the `nativehello.c` link. The
   launcher/namespace/linker need no change; the scratch proof is in §1. A
   preload/`RTLD_GLOBAL` workaround is rejected as a stock-parity fake pass.
2. **native AssetManager2 sees no APK assets.** With the DT_NEEDED proof,
   `readAsset` returns `no-asset` for `assets/hello.txt` while the Java
   resources/frames are live. Guest-side AssetManager hand-off (Java object →
   native `AssetManager*` → `AssetManager2::Open`) is the next investigation.
3. **rn-hello host nice limit.** `RLIMIT_NICE` must be ≥24 for the guest
   (stock init.rc 40). This host's hard limit is 0 and cannot be raised without
   CAP_SYS_RESOURCE in the initial user namespace; the launcher now mirrors and
   reports it. Once lifted, re-run the 20 s hold and read the new first error
   (`libappmodules.so` is the likely next one).
4. **Engine bounds space (S8, unchanged).** hello-jni's live tree has the full
   JNI report but `hello-jni.yaml` still selects a window-local `bounds`
   ([0,147,…] vs the display-space [0,275,…], +128), so that scenario still
   fails on the selector, not on the launch.
