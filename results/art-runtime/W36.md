## 1. Item 1 — the dialog window was always walked; the *line* was invalid, not the probe

W32's conclusion ("the guest probe throws on the second root; `emitProbe` swallows it") is **rejected as
stated** and replaced by two measured defects, both fixed:

1. **Missing root separator (the real wall).** `emitProbe` appended every root into one `StringBuilder`
   without a comma. A one-window sample was valid; the first two-window sample became
   `...}]}]}]}{"class":...` — invalid JSON. `drain_stdout_lines` then dropped it (and every later
   two-window line), so `latest_probe` froze at the last single-window sample while the guest kept
   sampling. W32's "probe_seq 83 → 83" is exactly this. Fixed by building each root in its own buffer and
   joining with a comma; a throw can no longer leave a partial object in the array.
2. **The 128 KiB line cap.** Even valid two-root samples can exceed it (a full Gaten tree is ~110 KiB,
   two windows more). Raised to **8 MiB**, read whole, and an oversized/invalid line is **counted and
   named on stderr**, never silently skipped. `windows` is now carried inside the sample tree.

`emitProbe` also reports every failure: `ACOSPROBE-ERROR {"seq","phase","window","error","stack"}` on
stdout **and** stderr (outer sample catch, per-window catch, decor fallback). No probe throw is swallowed.

**Proof (launch path, `.cache/w36/tap2`, 02:21Z):** after the Show-dialog tap the probe sample has
`window_count:2`, `windows:[main, window-2#1]`, 37 nodes, `android:id/message` = `"Are you sure?"`,
`android:id/button1` = `"OK"` with dialog-frame-relative bounds `[534,318][702,460]` and screen bounds
`[686,1294][854,1436]`; after a **dialog-local** tap at `(618,389)` the status becomes
`"Dialog confirmed"` and the window count returns to 1. Evidence:
`results/art-runtime/evidence/W36-dialog-tree.json`.

**Session path:** `AppMain.dumpTree` (used by `SessionMain.publishFrame`) now emits the same forest:
`WindowManagerGlobal.getWindowViews()`/`mViews` in z-order, Activity decor first labelled `main`, each
node carries `window` + `bounds_on_screen`, top level has `windows`, `node_budget`, `truncated`. The
session guest compiles (`acos-art session` javac step reached the runtime, no javac error). `acos verify`
actually uses `launch --interactive`, so the launch probe is the path the scenarios exercise.

**What still fails (`w27-dialog-window`, 02:32Z):** steps 0–5 pass (launch, Show-dialog, log, message,
OK button); step 6 (the OK tap) fails `ASSERTION_FAILED` with status still `"Idle"`. The engine derives
one `input_offset` from the first node (Activity: `[0,128]`) and subtracts it from every target, so the
dialog's OK centre is sent as `(770,1237)` to the dialog's InputChannel whose local centre is `(618,389)`
(dialog frame origin `[152,976]`). The local-coordinate tap proves the tree/input path itself works.
This needs the acos-cli per-window offset in §4.2; no acos-art change can repair a single offset that the
caller applies globally.

## 4. Requests (precise; owners elsewhere)

### 4.1 `TREE_TRUNCATED` instead of `ELEMENT_NOT_FOUND` (acos-protocol + acos-verify)

1. `crates/acos-protocol/src/error.rs`: add a variant next to `ElementNotFound`
   ```rust
   /// A selector matched nothing in a tree the probe reported as truncated.
   TreeTruncated,
   ```
   add `ErrorCode::TreeTruncated => "TREE_TRUNCATED",` in `as_str` (~line 297), and a hint arm
   (~line 466): *"The tree was truncated at the node budget; the node may exist beyond the sampled prefix.
   Raise `node_budget` or narrow the selector; this is not proof the node is absent."*
   `crates/acos-verify/src/native.rs::input_error` (line ~399) must treat it like `ElementNotFound` for
   the `Flatten` path but **not** as a retryable stale-ref.
2. `crates/acos-verify/src/assertions.rs`: give `element_missing` the observation (or add
   `fn missing_code(observation: &SessionObservation) -> ErrorCode`):
   ```rust
   let code = if observation.tree.truncated { ErrorCode::TreeTruncated }
              else { ErrorCode::ElementNotFound };
   ```
   and use it at the missing-selector sites (lines ~79/109/180/265: `element_missing`,
   `eval_text`, `eval_bounds`, `eval_count`). `executor.rs` ~727 passes the same `observation` it already
   holds to `element_missing("wait_for", …, &observation)`.
3. Test with teeth (acos-verify): a tree with `truncated: true` and no matching node returns
   `TREE_TRUNCATED`; the identical tree with `truncated: false` returns `ELEMENT_NOT_FOUND`.

### 4.2 Per-window input offset (acos-protocol + acos-cli; W34)

The probe now gives everything needed: each node has `window`, `bounds` (window-local) and
`bounds_on_screen`. `probe_input_offset` (`crates/acos-cli/src/engine/art.rs:224`) returns the **first**
node's delta and `ArtSession::tap` applies it to every window.

Minimum change:
* `crates/acos-protocol/src/ui.rs` `UiNode`: add `pub window: String` (default `""`) and serialise it;
* `crates/acos-cli/src/engine/mod.rs::ui_node_from_json` (~line 1016): copy
  `value.get("window").and_then(Value::as_str).unwrap_or("")`;
* `crates/acos-cli/src/engine/art.rs`: replace `probe_input_offset` with
  `probe_window_offsets(&Value) -> HashMap<String,(i32,i32)>` keyed by the node's `window` string
  (`screen.left - bounds.left`, `screen.top - bounds.top`); keep the map on `ArtSession`;
* `crates/acos-verify/src/native.rs::selector_center` return the matched node's `window` and call a new
  `ArtSession::tap_in_window(window: &str, x: i32, y: i32)`; `tap_in_window` subtracts that window's
  offset (falling back to the first/global offset only when the label is empty).
* Acceptance: `scenarios/w27-dialog-window.yaml` passes 9/9 strictly; the dialog OK tap is sent as
  `(618,389)` to the dialog channel for screen `(770,1365)`; existing single-window rows must be
  byte-identical in behaviour (`v2-counter`, `w19-form-behavior`, `two-activity`).

### 4.3 W31 R2 activity-token adoption (acos-services `atms.rs`; W35)

`pub fn adopt_activity(&mut self, token: u64, activity: &str)`: when the process is attached and a
`IActivityClientController.activityResumed`/`activityIdle` arrives with a non-zero token that has no
`ActivityRecord`, create/adopt one (replacing the `FIXTURE_ACTIVITY_TOKEN` record in the real-launch case,
keeping fixture lifecycle tests untouched), log `ActivityManagerAdopt token=0x… activity=…`, and let
`finish_activity` succeed and mark it finished. Unit test: resumed with `0x77` → `finishActivity(0x77)`
succeeds; a second finish and an unknown token still return the structured error.
The `acos-art` side (in-process `IApplicationThread.scheduleTransaction` + a real `new Binder()` token,
W31 §3 A) is intentionally **not** shipped until this lands, because alone it only converts `0x0` into an
unknown token.
