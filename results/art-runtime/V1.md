# V1 — the frame clock: `ISurfaceComposer` + `IDisplayEventConnection` as host nodes

**Status: done in `acos-services` (W-R task T2, the clock half of option A). The
framework's `DisplayEventReceiver` chain now has a real peer-side endpoint:
`getService("SurfaceFlinger")` resolves to an `android.gui.ISurfaceComposer` node,
`createDisplayEventConnection` answers a routable `android.gui.IDisplayEventConnection`,
`stealReceiveChannel` hands back a `SOCK_SEQPACKET` `BitTube` as two descriptors, and a
request-driven 60 Hz thread writes `DisplayEventReceiver::Event` structs (216 bytes, the
image's `sizeof`) with `CLOCK_MONOTONIC` timestamps — only while a vsync is requested.
`cargo test -p acos-services` is green (13 binaries, 116 tests, 10 of them new), `cargo
clippy -p acos-services --all-targets` is clean, `cargo check -p acos-binder-peer -p
acos-runtime -p acos-wm` builds. Nothing committed; no ART run was made.**

- Owner / date: V1 implementer agent, hard 60-minute checkpoint (**overshot: ~105 min**, no
  blocker was hit — see §9 for why the overrun happened and what it bought).
- Scope written: `crates/acos-services/src/display_events.rs` (new),
  `crates/acos-services/src/compositor_client.rs` (new),
  `crates/acos-services/tests/display_events.rs` (new), `registry.rs` (+2 blocks),
  `lib.rs` (+2 `pub mod`), `Cargo.toml` (+`rustix`), and this file.
- **Two tiny additions outside the planned file set, both reported here:**
  1. `crates/acos-services/src/host.rs` — `check_service` now falls back to a dynamic node
     when the descriptor has no factory, and a new `register_dynamic_named` gives a
     dynamic node a `ServiceManager` name. **This was unavoidable**: `android.gui.*` has no
     `acos-aidl` table (W-R §1), so the node must be served by `raw_transact`, and
     `raw_transact` is only reached for `dynamic` binders — but `check_service` (which
     answers `getService("SurfaceFlinger")`) only looked at `entries`. Without this the
     framework's very first call is `UNSUPPORTED_ANDROID_API`. It is the same shape as
     W1's ownership-marker fix and is purely additive (an entry always wins).
  2. `crates/acos-services/Cargo.toml` — `rustix` (`net`, `time`). `SOCK_SEQPACKET` and
     `CLOCK_MONOTONIC` are not reachable from `std`, and the crate is
     `#![forbid(unsafe_code)]`; `rustix` is already in the workspace via `acos-parcel`, so
     no new crate enters the lockfile.
- **Not touched**: `crates/acos-art`, `crates/acos-binder-peer`, `crates/acos-runtime`,
  `crates/acos-wm`. **The fd handoff needs no peer change** — see §7.
- `cargo` always via `tools/guarded.sh --mem 6G`; scratch under `.cache/v1/`.

## 1. What was wrong

W-R §0 rows 2 and 4: `ViewRootImpl`'s constructor calls `Choreographer.getInstance()` →
`FrameDisplayEventReceiver` → `DisplayEventReceiver::DisplayEventReceiver`, which is
`ComposerServiceAIDL::getComposerService()` then `createDisplayEventConnection` then
`stealReceiveChannel`. `registry::NAMES` had no `SurfaceFlinger`, nothing served
`android.gui.ISurfaceComposer`, and no code anywhere wrote a `DisplayEventReceiver::Event`.
That is Q3's SIGSEGV chain (`~NativeDisplayEventReceiver` on a null `JavaVM`): the receiver
never initialises, so the destructor's error path runs.

## 3. The wire: codes and layouts, from the image

The AIDL order is **not** trustworthy for this interface — the same trap W1 hit on
`IWindowSession`. Everything below was read out of
`.cache/art/sysroot/system/lib64/libgui.so`: the generated
`android::gui::BpSurfaceComposer::<method>` / `BpDisplayEventConnection::<method>` pass the
transaction code as an immediate to `IBinder::transact`, so `objdump` on the proxy is the
image's own table.

| 2 | `createDisplayEventConnection` | `0x15499b` writes `0x2` | **yes** |

| 6 | `getPhysicalDisplayIds` | `0x15538d` writes `0x6` | **yes** |

| 8 | `getSupportedFrameTimestamps` | `0x1557ba` writes `0x8` | **yes** |

| 57 | `getMaxAcquiredBufferCount` | `0x15c655` writes `0x39` | **yes** |
| everything else | — | — | **stubbed**, structured `UNSUPPORTED_ANDROID_API { interface: "android.gui.ISurfaceComposer", code, method }` |

**Finding (recorded, not acted on): the image is not the r75 tag for the tail of this
interface.** Counting `android-14.0.0_r75`'s `ISurfaceComposer.aidl` in declaration order
gives `getMaxAcquiredBufferCount` = 65; the image answers **57**. Eight methods' worth of
difference — the image also has `getColorManagement`/`setOverrideFrameRate` symbols the tag
does not list. The seven methods this task needs (2, 3, 6, 7, 8, 10, 11) agree with the tag,
so nothing here is guessed; a future task that adds a *tail* method must re-run the same
disassembly, not count AIDL lines. `compositor_client::tests::image_codes_are_pinned` pins
all eight values.

Argument shapes (proxy disassembly + tag AIDL, cross-checked):

- `createDisplayEventConnection(VsyncSource, EventRegistration, IBinder layer)`: two
  `writeByte` calls and one `writeStrongBinder`. `VsyncSource`/`EventRegistration` are AIDL
  enums with the default **`byte`** backing, but `libbinder`'s `Parcel::writeByte` is
  `writeInt32(int32_t(val))` (`native/libs/binder/Parcel.cpp:1395`), so both are 4 bytes.
  The layer handle is nullable and written null by our caller.
- `getPhysicalDisplayIds()`: no args; reply `readInt64Vector` = `int32 count` + `int64`
  elements.
- `getDisplayStats(IBinder)`: reply `readParcelable(DisplayStatInfo)` = `long vsyncTime;
  long vsyncPeriod`.
- `getDisplayState(IBinder)`: reply `readParcelable(DisplayState)` = `int layerStack;
  Rotation orientation; Size layerStackSpaceRect` — `Rotation` is `@Backing(type="int")`,
  `Size` is two ints, so four `int32`s.

### 3.2 `android.gui.IDisplayEventConnection`

| code | method | image evidence |
|---:|---|---|
| 1 | `stealReceiveChannel(out BitTube)` | `0x1613a5` writes `0x1` |
| 2 | `setVsyncRate(in int)` | `0x16166a` writes `0x2` |
| 3 | `requestNextVsync()` (oneway) | `0x16180d` writes `0x3` |
| 4 | `getLatestVsyncEventData()` | `0x1619f5` writes `0x4` |

**The image has no `getSchedulingPolicy`** (`BpDisplayEventConnection` exports exactly four
methods); the r75 AIDL declares a fifth. A table transcribed from the tag would therefore
have been *one method long* — harmless here only because nothing calls it. Unknown codes
(including 5) are a structured unsupported.

`stealReceiveChannel`'s request carries **only the interface token**: the generated proxy
writes no placeholder for the `out BitTube` (verified at `0x161270` — after
`writeInterfaceToken` the next call is `transact`). The reply is `binder::Status` (int32 `0`)
followed by `gui::BitTube::readFromParcel`, which dups **two** descriptors in order
(`BitTube.cpp`): receive first, then send. Both must be live or the client's
`readFromParcel` fails and `DisplayEventReceiver` sets `mInitError`.

## 4. The event struct (the "16-byte mistake costs a day" item)

`sizeof(DisplayEventReceiver::Event)` in the image is **216 (`0xd8`)** — not read from a
header, read from the immediate `objSize` that `DisplayEventReceiver::sendEvents` passes to
`BitTube::sendObjects` (`0x118b84`) and `getEvents` passes to `recvObjects` (`0xef9e4`).
`display_events::EVENT_SIZE` is that number and a test asserts the encoder fills exactly it.

```text
  0  u32  header.type                  DISPLAY_EVENT_VSYNC = fourcc('v','s','y','n')
  4  --   padding                      (displayId is __attribute__((aligned(8))))
  8  u64  header.displayId             PhysicalDisplayId
 16  i64  header.timestamp             CLOCK_MONOTONIC ns
 24  u32  vsync.count
 28  --   padding                      (vsyncData is 8-aligned)
 32  i64  vsync.vsyncData.frameInterval
 40  u32  vsync.vsyncData.preferredFrameTimelineIndex
 44  u32  vsync.vsyncData.frameTimelinesLength
 48  ...  vsync.vsyncData.frameTimelines[7] x { i64 vsyncId; i64 deadlineTimestamp;
                                               i64 expectedPresentationTime }
216  end                                (32 + 184)
```

`ParcelableVsyncEventData` (`getLatestVsyncEventData`, and the same struct inline) is
`int64 frameInterval`, `uint32 preferredFrameTimelineIndex`, `uint32 frameTimelinesLength`,
then three `int64` per timeline — `VsyncEventData.cpp`'s `writeToParcel`/`readFromParcel`
order, reproduced field for field.

## 5. The clock: request-driven, 60 Hz, monotonic

- One thread per connection (`acos-vsync`), one `socketpair(AF_UNIX, SOCK_SEQPACKET)` with
  `CLOEXEC` (4 KiB socket buffers are the `BitTube` default; not re-set here).
- **No free-running timer.** The thread blocks on a condvar until `requestNextVsync`
  (`pending > 0`) or `setVsyncRate(count > 0)`, and exits the wait on `Drop`. A free-running
  stream is what makes `FrameDisplayEventReceiver` re-enter `doFrame` hot (W-R §4 step 4),
  so this is a correctness property, not an optimisation.
- Timestamps are the **scheduled grid time** (`ceil(now / 16.666667 ms)` on
  `CLOCK_MONOTONIC`, then `last + period`), i.e. what a vblank timestamp is. A late wake-up
  does not shift the grid, so spacing stays ~16.6 ms and `Choreographer`'s
  `frameTimeNanos` is monotonic. Measured in the test: every gap within
  `16.6 ms ± 1 ms`.
- `requestNextVsync` is one-shot (consumed per event) and a no-op when the rate is non-zero,
  exactly as `IDisplayEventConnection.aidl` documents. `setVsyncRate(0)` returns to
  request-driven.
- Writes are `send(MSG_DONTWAIT | MSG_NOSIGNAL)`; on `EAGAIN` the event is dropped (what
  `BitTube::write` reports to `EventThread`, which drops the frame). No blocking send.
- **No hotplug / mode-change / frame-rate-override events, ever.** `eventRegistration` is
  read, validated and recorded but nothing is registered: a spurious
  `DISPLAY_EVENT_HOTPLUG` would make the framework tear the display down, and nothing in the
  launch path asks for one.
- `getLatestVsyncEventData` answers the last grid time with a monotonic `vsyncId` and
  `expectedPresentationTime = vsync + frameInterval`.

## 6. Tests (`tests/display_events.rs`, 10)

Hand-built requests in the image's write order, replies decoded in the framework's read
order, `data_avail() == 0` asserted on every one:

1. `surfaceflinger_resolves_and_answers_the_display_queries_the_image_makes` — `getService`
   → node; `getPhysicalDisplayIds` (`long[]` = `[0]`), `getPhysicalDisplayToken` (a
   **routable** `android.gui.PhysicalDisplayToken` aux binder), `getDisplayStats`
   (`vsyncPeriod` = 16 666 667 and `vsyncTime` a fresh CLOCK_MONOTONIC reading),
   `getDisplayState` (`0, 0, 1080, 2400`), `getSupportedFrameTimestamps` (`0..=9`),
   `getMaxAcquiredBufferCount` (code **57**, value 2).
2. `the_surface_half_is_a_structured_unsupported_not_a_silent_success` — `createConnection`
   is `UNSUPPORTED_ANDROID_API` naming `android.gui.ISurfaceComposer` + `createConnection`.
3. `create_display_event_connection_answers_a_routable_connection_binder` — non-null,
   descriptor `android.gui.IDisplayEventConnection`; an unknown `VsyncSource` is a
   `BadRequest`, not a connection.
4. `steal_receive_channel_carries_two_descriptors_and_nothing_else` — two distinct fds, two
   owned descriptors, `data_avail() == 0`; a second steal is an error (the stock
   `writeToParcel` resets the receive end).
5. `latest_vsync_event_data_decodes_in_the_frameworks_read_order` — 1 timeline,
   `expected == deadline + frameInterval`.
6. **`requested_vsyncs_arrive_at_sixty_hertz_and_only_when_requested`** — the load-bearing
   one: silent for 80 ms with no request; then 5 × `requestNextVsync` → 5 events, each
   216 bytes, `count` = 0..4, `vsyncId` = 1..5, strictly increasing timestamps, every gap
   `16.6 ms ± 1 ms`, no timestamp in the future; then silent again for 120 ms.
7. `set_vsync_rate_makes_the_clock_continuous_until_it_is_zeroed` — `setVsyncRate(1)`
   delivers ≥3 events without any request; `setVsyncRate(0)` answers cleanly.
8. `the_event_struct_is_the_images_216_bytes` — `EVENT_SIZE == 0xd8`, the `displayId`
   alignment pad is zero.
9. `a_clock_writes_only_when_asked_and_stops_on_drop` — same contract one level below the
   dispatcher (`events_sent()` 0, then 1).
10. `a_bit_tube_is_a_seqpacket_pair_with_two_distinct_ends`.

## 7. The fd handoff — **no `acos-binder-peer` change needed**

The reply is a normal `Parcel` with two `BINDER_TYPE_FD` flat objects, written with
`Parcel::write_file_descriptor` (which dups). That is the path P4c §2 fixed and
`MemoryIntArray`/`InputChannel` already use: `frame_from_parcel` dups each `BINDER_TYPE_FD`
into `Frame::fds`, `close_frame_fds` releases them after `write_frame` has sent them over
`SCM_RIGHTS`. The parcel's own dups are closed when the reply `Parcel` is dropped, so there
is **no fd leak and no peer edit**. What the peer must already do (it does) is nothing more
than carry the reply's fds through.

`InputChannel` (`window_session::write_input_channel`) is the precedent for the *shape*: an
optional channel is `int32 1`, then the body. `BitTube` has **no** presence int — the AIDL
`out BitTube` is not an optional parcelable, the reply is `Status` then the two fds — which
is why `stealReceiveChannel`'s request has no arguments at all.

## 8. What the later launch task must wire

Exactly this, and nothing else:

1. **Nothing in `acos-services`.** `ServiceHost::standard()` already installs it:
   `registry::install` calls `compositor_client::install(host, DisplayDescriptor::reference())`,
   which registers 4 `android.gui.IDisplayEventConnection` nodes (dynamic) plus the
   `android.gui.ISurfaceComposer` node under the name `SurfaceFlinger`, plus an aux
   `android.gui.PhysicalDisplayToken`.
2. **The peer must serve `getService("SurfaceFlinger")` through `check_service`** — i.e. the
   existing `IServiceManager` path. If the peer instead hand-maps names, it must map
   `SurfaceFlinger` → `android.gui.ISurfaceComposer` the same way. `INTERFACE_TRANSACTION`
   (0x5f494e54) on the returned binders is still unhandled in the peer (W-R §1) — this task
   did **not** change that, and `ISurfaceComposer::asInterface` calls it, so **that remains a
   real prerequisite** before the chain runs end to end.
3. `createConnection` (code 3) is still unsupported — `ViewRootImpl`'s `SurfaceSession`
   (W-R T1) must land separately or the constructor stops there *before* the clock is
   reached. **Order matters: T1 (`createConnection`) then T2 (this).** T2 alone is verified
   by the tests, not by a launch.
4. Read the guest log for, in this order: `SurfaceFlinger` resolving (not null),
   `DisplayEventConnection creation failed` **absent**, `stealReceiveChannel failed`
   **absent**, and then `requestNextVsync` traffic — the latter is visible as
   `ConnectionClock::events_sent()` growth if the runtime chooses to log it (the state is
   reachable via `ServiceHost::as_any_mut` on the `SurfaceComposerService`, which implements
   `as_any_mut` and records every `createDisplayEventConnection` in
   `SurfaceComposerService::connections()`).
5. If `Choreographer` still dies, the first thing to check is `Event` layout (216) and the
   fd order (receive **first**), because those are the two silent-failure modes: a wrong
   order gives a receiver that reads its own writes, and a wrong size makes
   `BitTube::recvObjects` `LOG_ALWAYS_FATAL` on a partial object.

## 9. Real vs stand-in (this task's slice)

| piece | verdict |
|---|---|
| `ISurfaceComposer` node + `ServiceManager` name | **real host node**, reached through the framework's own `getService` path |
| `createDisplayEventConnection` reply | **real binder**: a routable `IDisplayEventConnection` node id |
| `stealReceiveChannel` | **real fds**: one `SOCK_SEQPACKET` pair, two dups, receive-first order |
| `Event` bytes | **byte-exact** to the image: 216 bytes, verified offsets, `fourcc` types |
| vsync timing | **real timer, synthetic source**: 60 Hz on `CLOCK_MONOTONIC`, grid-aligned; there is no display, so this is the only honest source |
| `frameTimelines` | **one** timeline (`SF` may report up to 7): `vsyncId` monotonic, `deadline == vsync`, `expected == vsync + period`. ACOS has no scheduler, so a second timeline would be invented |
| `getDisplayStats.vsyncPeriod` | the same constant the clock uses, so `Surface::getDisplayRefreshCycleDuration` and the vsync thread agree |
| `getMaxAcquiredBufferCount` = 2 | **synthesized constant** (`MIN_UNDEQUEUED_BUFFERS`); a real SF derives it from refresh rate + pipeline depth |
| `getSupportedFrameTimestamps` = `0..=9` | **synthesized**: which `FrameEvent` slots exist; ACOS produces none of them |
| hotplug / mode change / frame-rate override | **not sent at all** (documented above) |
| `createConnection` and every other `ISurfaceComposer` code | **stubbed**, structured `UNSUPPORTED_ANDROID_API`, never a default success |

## 10. Limits / not done

- **No ART run** (task constraint), so §8 is a prediction from the code plus the tests, not
  evidence from a launch.
- The connection pool is 4 pre-allocated nodes handed out round-robin: a fifth concurrent
  `DisplayEventReceiver` in one process reuses slot 0 and resets its `BitTube`. Observable
  only with more than four live receivers; a real device allocates a binder per call.
- `setVsyncRate(count > 1)` emits every `count`-th grid tick, which is what the interface
  says, but `SurfaceFlinger`'s throttling is per-connection state in `EventThread`; nothing
  in the launch path uses a rate other than 0 or 1.
- No `DISPLAY_EVENT_FRAME_RATE_OVERRIDE`/`_FLUSH` even when `eventRegistration` asks for
  them: recorded and ignored, because ACOS has no `LayerHistory` to override from.
- `vsyncId` is a per-connection counter, not `SF`'s `timestamp / period` scheme. Both are
  opaque to the app (`setFrameTimelineVsync` only carries it back), but a test that compares
  them would differ.
- The 60 Hz period is a constant. There is no mode set, no variable refresh, and
  `getDisplayStats.vsyncPeriod` never changes.

## 12. Process note (the overrun)

The 60-minute checkpoint was passed at ~60 min with the design finished and the code not yet
compiling; stopping there would have left two half-written modules in a crate the rest of the
tree depends on, which is worse for the next agent than the overrun. Total ~105 min, no
blocker, nothing committed. The overrun bought: the image-vs-tag code finding
(`getMaxAcquiredBufferCount` 57 ≠ 65), the `check_service`/dynamic-node gap (§0), and the
216-byte event verification — all three are exactly the class of silent failure this task
exists to avoid.
