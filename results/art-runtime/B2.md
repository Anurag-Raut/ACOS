# B2: heap facts, and a shared boot image without fork

Owner: arm (b) of the three-arm comparison (`docs/decisions/2026-11-12-zygote-shared-art.md`).
Measurement only: no product code changed, no `crates/**` edit. Time box: 60 min.
Scratch: `.cache/b2/`. Every ART run went through
`tools/art-runtime/run-exclusive.sh --task B2 -- tools/guarded.sh --mem 8G --time 600-900 -- …`.

## 0. Answers

**Heap.** ART installs its **own C++ defaults**, not the served `dalvik.vm.*` values:
`Runtime.maxMemory()` = **256 MiB**, `totalMemory()` = **2 MiB**, `Runtime.getTargetHeapUtilization()`
= **0.75**, `getMinimumHeapSize()` = 0, `getTargetSdkVersion()` = 10000. The served table is
already the stock API-34 one (`heapstartsize 8m`, `heapgrowthlimit 192m`, `heapsize 512m`,
`heapminfree 512k`, `heapmaxfree 8m`, `heaptargetutilization 0.75`), but nothing converts it to
flags because ACOS bypasses `AndroidRuntime::startVm`. So the *effective* limits are 2 MiB initial /
256 MiB growth limit / 256 MiB hard cap — the served 192m/512m are dead text, and the
`-Xms 8m` the product thinks it serves is not applied either.

**Live after GC.** A booted guest's CC region space collapses to a **1.2–2.4 MiB floor** after a full
explicit GC (probe, same boot configuration). A counter session holds **38.95–39.04 MiB** resident
region space at idle (D-M2). The guest has no GC hook (`System.gc` / `VMRuntime` are not reachable
from the launcher's argv and no `ACOSLAUNCH_*` variable triggers one), so a forced GC *inside a live
counter* was not possible without product code. Estimate: the 39 MiB is dominated by **live** objects
(Activity + framework graph), with a GC floor of ~1–2 MiB of boot-time objects; garbage resident at
idle is at most a few MiB, not tens.

**Would stock `dalvik.vm.*` values reduce residence?** The values are already stock — passing them
again changes nothing. Making them *take effect* would mean synthesising `-Xms/-Xmx/-XX:…` in
`launch.rs`: `-Xms 8m` would *raise* the initial region space by ~6 MiB, and `-XX:HeapGrowthLimit=192m`
would cap the heap 64 MiB below ART's current default 256 MiB, causing earlier GCs. Net estimate for
the counter: **−2 to −6 MiB region space per session at best**, against a possible relaunch cost from
the larger initial heap. It does not touch the 26.3 MiB image cost.

**Uncompressed image, no fork.** Feasible with stock tooling: `.cache/art/sysroot`'s own
`dex2oat64` built a version-108 uncompressed image (**50.64 MiB** of `.art`, **120.87 MiB** of `.oat`,
173 MiB total) in 5.3 s. But **file-mapping alone does not help**: measured per session, boot-image
mappings:

| image | Rss | Pss | Private_Dirty | Shared_Clean |
|---|---:|---:|---:|---:|
| LZ4 (default), N=2 | 26.29 | 26.29 | **26.29** | 0.00 |
| LZ4 (default), N=5 | 26.29 | 26.29 | **26.29** | 0.00 |
| uncompressed, relocated, N=2 | 50.22 | 50.03 | **49.84** | 0.38 |
| uncompressed, relocated, N=5 | 50.22 | 49.91 | **49.84** | 0.38 |
| uncompressed + `-Xnorelocate`, N=2 | 38.56 | 25.69 | **12.71** | 25.74 |

MiB per session. The uncompressed image is worse than LZ4 unless relocation is disabled: ART maps it
at a **random base** (ASLR), and relocation writes make essentially the whole image private
(49.8 of 50.2 MiB). With `-Xnorelocate` the image maps at its recorded base **0x70000000**, pages stay
file-backed and `sum(Pss)` converges to the file size (51.2 ≈ 50.6 MiB for two sessions), and private
dirty falls to **12.71 MiB/session** — still runtime writes, not relocation. Net saving vs the LZ4
default is **13.6 MiB per session (−52 % of the image cost)**, but only with a fixed base.

**Launch time.** spawn→"image mapped and region space touched": default N=2 0.084/0.112 s, N=5
0.093–0.212 s; uncompressed-relocating N=2 0.089/0.120 s, N=5 0.153–0.271 s. No measurable gain
or loss (within run-to-run noise); the image load is not the launch bottleneck.

**ASLR implication.** The win is *entirely* an ASLR policy decision: `-Xnorelocate` (a fixed image
base, no image address randomisation) is required. With default ASLR the shared image is strictly
worse than the compressed status quo.

**Counter verification.** Not possible without product code: the served path (`launch.rs`) has no
`-Ximage` seam at all (only `launcher.rs run/render-app` auto-loads `<data>/img`), so a counter
session cannot be pointed at the new image. The image test therefore ran the probe class through the
product's own `acos-art run --image`, which uses the same sysroot, property table, preloads, seccomp
and sandbox. `acos verify scenarios/v2-art-counter.yaml` was **not** run with the image.

## 1. Heap facts

Probe: `research/b2/HeapProbe.java`, built and run by `tools/art-runtime/b2/probe-heap.sh`
(throwaway; nothing added to the product). It runs through `acos-art run` so it gets the same
sysroot, the same `Props::for_launch()` table, the same `LD_PRELOAD` shims. It reads its own
`/proc/self/smaps` and reflects `dalvik.system.VMRuntime`.

Default (stock) configuration, `--image none`, one session:

```
maxMemory        268435456  (256 MiB)
totalMemory        2097152  (2 MiB)
freeMemory         2011104
VMRuntime.getTargetHeapUtilization  0.75
VMRuntime.getMinimumHeapSize        0
VMRuntime.getTargetSdkVersion       10000
```

`dalvik.vm.heapgrowthlimit` is served as `192m` and `dalvik.vm.heapsize` as `512m`
(`crates/acos-art/src/props.rs`), yet `maxMemory()` is 256 MiB: the growth limit is ART's compiled
default, and `-Xmx` is not applied at all. That is the expected consequence of bypassing
`AndroidRuntime::startVm` (`.cache/aosp/base/core/jni/AndroidRuntime.cpp:831`): the property table
is only ever read by the shim, never parsed into runtime flags.

### Region space and GC

The CC region space reserves 512 MiB (`heap.cc:642`, `heap.h:140`; `Size` in smaps), of which the
probe had **2.00 MiB resident** at start, **2.26 MiB** immediately after
`Runtime.gc()` + `runFinalization()` + `gc()`, and **1.16 MiB** after a second GC 1.5 s later (the
first GC's mark stacks are still resident in the first sample). Read: the GC floor of a booted
framework-loaded guest is ~1–2 MiB; almost all of a counter session's 39 MiB region space is live
state, not uncollected garbage.

Counter sessions at idle (D-M2, same host, same fixtures) are 38.95–39.04 MiB resident region space.
A forced GC inside a live counter was not reachable: `LaunchMain`/`SessionMain` have no `System.gc`
hook and forward only `ACOSLAUNCH_PROBE`, `ACOSLAUNCH_FRAME_PROBE`, `ACOSLAUNCH_HOLD_MS`,
`ACOSLAUNCH_LIVE_PROBE`, `ACOSLAUNCH_RESUME_MS`, `ACOSLAUNCH_SCREEN_LAYOUT`. Forcing one would have
required editing the guest, which this experiment forbids.

### Effect of the stock `dalvik.vm.*` values

They are already the table (`props.rs: DEFAULT_*`). Passing them through the existing
`ACOS_ART_HEAP*` seam would be a no-op. What would change residence is making them *effective*
(`-Xms`, `-XX:HeapGrowthLimit`, `-XX:HeapMinFree/MaxFree`):
- `-Xms 8m` (vs ART's 2 MiB default) grows the initial region space by ~6 MiB;
- `-XX:HeapGrowthLimit=192m` (vs 256 MiB default) triggers GC 64 MiB earlier: for a counter whose
  live set is ~39 MiB this is maybe −2 to −6 MiB of resident garbage, at the cost of more GCs;
- `-XX:HeapMinFree=512k`, `-XX:HeapMaxFree=8m` tune the GC trigger band (small effect);
- `-XX:HeapTargetUtilization=0.75` is already ART's default.

Estimate: at best a few MiB per session, and only by adding flag synthesis to `launch.rs` — i.e. a
product change, not an environment change.

## 2. Uncompressed boot image, no fork

### Tool and build

Stock only, nothing downloaded:
`.cache/art/sysroot/system/apex/com.android.art/bin/dex2oat64` (the sysroot's own, image version 108).

`acos-art build-image` hardcodes `--image-format=lz4` (`crates/acos-art/src/main.rs:551`), so
`tools/art-runtime/b2/build-uncompressed.sh` reproduces that exact dex2oat invocation — same
sysroot, same device `BOOTCLASSPATH` (35 jars), `--base=0x70000000`, `--instruction-set=x86_64`,
`--oat-file=/data/img/x86_64/boot.oat` — in a bwrap mini-Android root of the same shape as the
product's sandbox, changing only `--image-format=uncompressed`. Output `.cache/b2/image/`.

```
dex2oat took 5.274s (34.203s cpu) (threads: 32)
35 × .art  50.64 MiB   (LZ4 sysroot images: 17.53 MiB)
35 × .oat 120.87 MiB
dir total 173 MiB          (disk had 142 GiB free; well under the 2 GB stop)
```

Two APEX modules are mounted by the product sandbox under a different module name than their APEX
payload directory (`com.google.android.configinfrastructure` →
`/apex/com.android.configinfrastructure`); the first build got them wrong, dex2oat skipped two jars,
and the runtime then **silently fell back to imageless running** ("Could not create image space …
Attempting to fall back to imageless running") instead of failing. After matching the product's
mount mapping the image loads. That silent fallback is worth knowing for any future image work.

### Method

`tools/art-runtime/b2/measure-image.py`: N concurrent `acos-art run --image <dir>` sessions of the
probe (default = ART's `/system/framework/x86_64/boot*.art`, LZ4; uncompressed = `-Ximage` via the
product's documented `--image` seam). Readiness is host-side (guest process exists, image mapped,
region space touched — `acos-art run` buffers guest stdout until exit), then `/proc/PID/smaps` is
grouped into `image_file` (file-backed `.art`), `image_anon` (`[anon:dalvik-…boot….art]`, the LZ4
decompression) and `region_space`. Sessions are killed and checked for survivors (none).

### Results (MiB per session unless noted)

| variant | N | image Rss | image Pss | Private_Dirty | Private_Clean | Shared_Clean |
|---|---:|---:|---:|---:|---:|---:|
| default LZ4 (`image_anon`) | 2 | 26.29 | 26.29 | 26.29 | 0 | 0 |
| default LZ4 (`image_anon`) | 5 | 26.29 | 26.29 | 26.29 | 0 | 0 |
| uncompressed, relocated (`image_file`) | 2 | 50.22 | 50.03 | 49.84 | 0.00 | 0.38 |
| uncompressed, relocated (`image_file`) | 5 | 50.22 | 49.91 | 49.84 | 0.00 | 0.38 |
| uncompressed + `-Xnorelocate` | 2 | 38.56 | 25.69 | 12.71 | 0.11 | 25.74 |

(The default variant also has ~0.04 MiB/session of `image_file` Shared_Clean — the compressed image
headers read from `/system/framework/x86_64/*.art`; the data itself is the 26.3 MiB anon copy.)

Totals at N=5 for the default: `image_anon` 131.45 MiB Rss = 5 × 26.29, Pss = Rss → no sharing at all,
matching the advisor's 26.3 MiB/session decompression cost (`image_space.cc:999`, `:1055`).

Uncompressed, relocating: base addresses are random and different in every session
(examples: `boot.art` at 0x6f66a000, 0x70c7a000, 0x6fe6f000, 0x70b79000, 0x6fa55000, 0x6f40c000),
so ART relocates the image per process; **~49.8 MiB/session becomes private dirty** — strictly worse
than the LZ4 baseline. With `-Xnorelocate` (tested with `tools/art-runtime/b2/run-norelocate.sh`,
stock `dalvikvm64` in the same mini-root) `boot.art` maps at exactly **0x70000000** in both sessions,
`Shared_Clean` is 25.74 MiB/session, `sum(Pss)` ≈ file size (51.37 vs 50.64 MiB), and private dirty
drops to **12.71 MiB/session**. That residue is runtime writes into image objects (class
initialisation, interned strings, resolved entries), not relocation: relocation alone was
49.84 − 12.71 ≈ 37.1 MiB/session.

### Launch time

spawn → readiness, seconds (concurrent launches, so later sessions include contention):

| variant | N=2 | N=5 |
|---|---|---|
| default LZ4 | 0.084, 0.112 | 0.093, 0.128, 0.158, 0.185, 0.212 |
| uncompressed (–Ximage, relocated) | 0.089, 0.120 | 0.153, 0.185, 0.214, 0.242, 0.271 |

No significant difference (+5–7 % at N=5, inside the noise of a 60–90 ms cold path whose launch
budget is dominated by the guest's own startup). The image format is not a launch-time lever.

### ASLR policy

The saving requires a **fixed image base**: ART's `-Xnorelocate` (no image ASLR). Without it every
session relocates ~37 MiB of image pages and the uncompressed image costs ~24 MiB more private
memory per session than LZ4. With it, the image is shared (`Shared_Clean` 25.7 MiB/session, unique
Pss ≈ file size) but image address space is predictable. That is the security trade to weigh —
and note it is only reachable if the served path learns to pass ART flags at all (today it passes
none).

### Counter verification

Not run with the image. `acos serve` → `launch.rs` has **no** `-Ximage` handling (grep: the only
`-Ximage` production is `launcher.rs:201-203`, used by `run`/`render-app`), and the guest argv is
built in `launch.rs:550`. Routing the image into a counter session would need a product change
(argv flag or a `-Ximage` env seam), which this experiment forbids. `acos verify
scenarios/v2-art-counter.yaml` was therefore not exercised against the uncompressed image; its
status is **unverified**, not passed.

## 3. Blockers

1. **No flag synthesis**: the served path passes no `-Xms/-Xmx/-XX:Heap*` (startVm bypassed), so the
   heap seam and any image/ASLR flag would need `launch.rs` work. This is the single blocker for
   both Part 1's "make stock values effective" and Part 2's `-Xnorelocate`.
2. **No image seam on `serve`**: `-Ximage` exists only on `run`/`render-app`; counter sessions cannot
   be pointed at an image without a product change, so counter verification is not possible now.
3. **No forced-GC hook** in the guest: `live vs garbage` inside a live counter is an estimate, not a
   measurement.
4. **Uncompressed images are 2.9× larger on disk** (50.64 vs 17.53 MiB of `.art`; 173 MiB including
   `.oat`) — fine for one image, but it multiplies if per-app images are ever added.

## 4. Reproduce

```bash
# heap facts (probe under the product's own ART path)
tools/art-runtime/b2/probe-heap.sh [--garbage-mib N]

# uncompressed image (stock sysroot dex2oat64, image version 108)
tools/art-runtime/run-exclusive.sh --task B2 -- \
  tools/guarded.sh --mem 8G --time 900 -- tools/art-runtime/b2/build-uncompressed.sh
# -> .cache/b2/image/x86_64/{boot.art,boot.oat,...}

# N-session boot-image measurement (default LZ4 vs uncompressed)
tools/art-runtime/run-exclusive.sh --task B2 -- \
  tools/guarded.sh --mem 8G --time 600 -- \
  python3 tools/art-runtime/b2/measure-image.py --image uncompressed --n 5
# -> .cache/b2/measure/*.json

# fixed-base (-Xnorelocate) check
tools/art-runtime/run-exclusive.sh --task B2 -- \
  tools/guarded.sh --mem 8G --time 300 -- \
  tools/art-runtime/b2/run-norelocate.sh --hold-ms 800
```
