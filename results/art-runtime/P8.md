# P8 — startup prewarm of the ART launch working set

Time box: 60 min (started 2026-11-12T16:05Z local / 11:05Z UTC; the
`framework.jar` investigation below overran it by ~25 min — checkpointed and
reported rather than cut short).

**Verdict: kept.** `acos serve` now reads the ART launch working set into the
host page cache on a background thread. A first launch after the working set
was evicted costs **638.4 → 481.6 ms p50** (p95 654.3 → 494.7, n=12, all
verified), i.e. within **+10 ms** of a warm launch (M4 471.6 ms) even though the
launch races the prewarm. The daemon's own ready time is unchanged
(**1.84 ms** p50, P7 1.9). Verification semantics are untouched: 48/48 rows
verified, 0 false passes, the gate scenario passes 11/11.

## 2. What is warmed, and where the list comes from

`crates/acos-cli/src/prewarm.rs` derives the list from the same sources
`acos-art`'s launch path reads; there is no snapshot of P7's `fincore` output.

| launch input | derived from |
|---|---|
| boot image `boot.art/.oat/.vdex` | `launch.rs::resolve_shared_boot_image`'s rules: `ACOS_SHARED_BOOT_IMAGE` when it holds `x86_64/boot.art`, else `<sysroot>/system/framework/x86_64/` + `system/framework/boot.vdex` |
| `dalvikvm64`, `libart.so`, `libartbase.so`, `libnativehelper.so` | the ART APEX under `<sysroot>/system/apex/*/` (the mount name need not equal the host dir) |
| `libandroid_runtime.so` | `<sysroot>/system/lib64/` |
| guest dex, `LD_PRELOAD` shims, binder driver | `<data>/app/launch-guest/classes.dex`, `<data>/app/libacosart.so`, `<sysroot>/shim/libacoshw.so`, `<data>/shim/libartshim.so`, `<data>/lib/libacos_binder_driver.so` |
| `BOOTCLASSPATH` jars | `<data>/system/environ/classpath` (`derive_classpath`), guest `/system/…` and `/apex/<mount>/…` mapped into the sysroot; falls back to `<sysroot>/system/framework/*.jar` when a fresh data dir has no classpath file yet |
| fonts | `<sysroot>/system/etc/fonts.xml`, `<sysroot>/system/fonts/fonts.xml` and the files the first `sans-serif` family names (what `ensure_system_fonts` + `Typeface.DEFAULT` read) |

Resolution mirrors `ArtRoot::resolve` (`ACOS_ROOT`/`ACOS_ART_SYSROOT`/
`ACOS_ART_DATA`, then `.cache/art/{sysroot,data}`), so a `--sysroot`-less
worktree resolves the same files the launch does.

### 2.1 The finding that mattered: `framework.jar` *is* read

P7 listed `framework.jar` in the eviction set but measured **0 resident pages**
for it, so it looked irrelevant. It is not: it is 38.2 MiB and it dominates the
cold launch. Direct `acos-art` spawns with `ACOS_ART_STAGE_TIMING` (n=2 each,
same lock and host, stages in `run/` metadata below):

| state | ready line (spawn → guest ready) | what was read into cache first |
|---|---:|---|
| warm (no eviction) | 171.2 / 177.5 ms | — |
| evicted, nothing warmed | 349.3 / 358.4 ms | — |
| evicted, **everything except** `framework.jar` warmed (46.9 MiB) | 303.1 / 300.4 ms | boot image, libs, `dalvikvm64`, every other jar, APK |
| evicted, `framework.jar` + boot image + libs warmed (47.2 MiB) | **191.7 / 177.5 ms** | + `framework.jar` |
| evicted, everything warmed (120.4 MiB incl. all APEX jars + fonts) | 172.0 / 178.8 ms | + APEX jars, fonts |

So warming all of P7's 8.2 MiB resident set recovers only ~55 ms; the remaining
~120 ms is `framework.jar`, whose pages do not stay in the cache after the
launch (hence P7's 0) but are read during it. Its read order is therefore:
boot image → ART libs → `dalvikvm64` → guest dex/shims → **`framework.jar`** →
fonts → the platform `system/framework` jars smallest-first → the APEX/mainline
jars. The last two groups are where the 64 MiB cap bites; platform jars come
before mainline jars because the boot image preopts the mainline set and the
platform jars are exactly what P7 measured as resident (telephony-common, ext,
voip-common, ims-common, framework-graphics).

## 3. Non-blocking, bounded, logged, opt-out

* **Background thread** named `acos-prewarm`, spawned in `serve.rs` *after*
  `UnixListener::bind` + the privacy/banner setup and *before* the accept loop.
  It holds no lock the loop takes, is detached (it dies with the process) and a
  thread spawn failure only logs. Daemon ready: 1.84 ms p50, unchanged.
* **Bounded**: default cap **64 MiB** (`ACOS_PREWARM_MAX_MB`, `0` disables);
  files that do not fit are skipped and logged. On this image it warms
  **63.7 MiB in 37 files**, skipping 15 (mostly 0.4–2.8 MiB APEX jars).
* **Page cache only**: plain `read(2)` through one reusable 256 KiB buffer.
  No `mlock`, no `mlockall`, no `MAP_POPULATE`, no `O_DIRECT`, no writes.
* **Logged** (one line per daemon start, plus the skip list):
  `acos serve: prewarm: warmed 37 files, 63.7 MiB in 118 ms (cap 64.0 MiB, 15 skipped, 0 missing, 0 read errors)`
  — 118 ms from a fully-evicted cache, 2 ms when the cache is warm.
  `ACOS_PREWARM_VERBOSE=1` logs every warmed file.
* **Opt-out**: `ACOS_NO_PREWARM=1` (also `true`/`yes`/`on`) logs
  `prewarm: disabled by ACOS_NO_PREWARM` and does nothing else. Documented in
  `docs/AGENT_QUICKSTART.md`'s serve/daemon section, not `SECURITY.md`: the
  knob only causes read-only reads of files the launch reads anyway, as the
  daemon's own uid; it cannot widen the guest's surface, cannot write, cannot
  lock memory and is not on any verdict path. It does not run for
  `--engine rust-vm` (no ART working set).
* **No verification semantics change**: it is not called from launch,
  observation, settle or assert code; the daemon's replies are byte-identical
  to before (48/48 verified, gate 11/11).

### Memory

Page cache is reclaimable, so the cost is not resident memory of the daemon:

| | daemon VmRSS |
|---|---:|
| socket ready, prewarm off / on | 9.8 MiB / 10.5 MiB p50 |
| after the prewarm finished | **12.0 MiB p50** (+1.5 MiB over its own ready RSS) |
| M4 daemon (steady state: ready 9.9 MiB, after a 2 ms warm-cache prewarm) | 11.0 MiB |

The +1.5 MiB is the 256 KiB read buffer plus the resolved path list; the
63.7 MiB are file pages, `fincore`-visible and reclaimable, and are the same
files the first launch would otherwise read from disk.

## 6. Not done / next

* **The APK is not prewarmed** (it is per-launch, not known to the daemon). Its
  196 KB is 1–2 ms; the honest fix would be a per-APK prewarm on the first
  `acos_launch` for that APK, which is a different (launch-path) change.
* **`framework.jar`'s 38.2 MiB read** is the bulk of the 63.7 MiB. It is
  bounded and reclaimable, but a cheaper option exists: P7 §7 #3/#6 (Zygote /
  no-PNG tree replies) are orthogonal, and a future Zygote core would keep these
  pages resident by construction (Z4/Z3 own that seam — not touched here).
* **A cold daemon start on a cold build cache (S0)** was not measured (P7 §8's
  reason: it needs a build-cache wipe other agents depend on). The prewarm adds
  118 ms of background I/O there, off the ready path.
* Not measured: the same cohort at N>1 concurrency (P5 owns M9); the prewarm is
  one thread per daemon and could be revisited if N=10 daemons start together,
  since the page cache is shared but the reads are not deduplicated.
