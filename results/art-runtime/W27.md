## 1. Activity-alias launcher resolution (W25 blocker 3)

`aapt2 dump badging` reports no `launchable-activity` for an alias-only launcher. The
Gaten debug APK declares three `<activity-alias>` entries (`LauncherIconSystem`
disabled, `LauncherIconLight` enabled, `LauncherIconDark` disabled), all targeting
`com.gaten.app.LauncherActivity`. `acos-art launch` now resolves MAIN + LAUNCHER
from the **parsed binary manifest** (`PackageParser` rules), not from badging.

New `crates/acos-services/src/manifest_resolve.rs`:

* candidates are `<activity>` **and** `<activity-alias>` with
  `android.intent.action.MAIN` + `android.intent.category.LAUNCHER`;
* `android:enabled="false"` on the component or `<application>` excludes it;
* an alias must name a declared `targetActivity` (missing target / missing
  attribute are structured errors, as in stock `parseActivityAlias`);
* alias label/icon override the target's; an unset alias label falls back to the
  target label, then to the application label in the guest;
* deterministic choice with several enabled launchers: **enabled aliases first,
  then enabled activities, each in manifest declaration order**; all enabled
  candidates are recorded in `LauncherActivity::candidates`. Rationale: an alias
  exists to be the themed launcher entry.

The guest now receives both the alias component (Intent + `ActivityInfo.name`)
and `ActivityInfo.targetActivity`; stock `ActivityThread.performLaunchActivity`
replaces the component with the target class before instantiating it. `session.rs`
uses the same resolver. `acos-art launch` reports the resolution in
`activity` + `activity_target`; the old "declares no launchable activity" path is
gone and every failure carries a code (`LAUNCHER_NONE`, `LAUNCHER_DISABLED`,
`LAUNCHER_ALIAS_NO_TARGET`, `LAUNCHER_ALIAS_TARGET_MISSING`,
`LAUNCHER_MANIFEST_UNREADABLE`).

Real-APK evidence (`evidence/W27-gaten-alias-launch.json`, 00:34:57Z):

```
activity        = com.gaten.app.LauncherIconLight
activity_target = com.gaten.app.LauncherActivity
code            = NO_ACTIVITY_RESUMED     (not "no launchable activity")
timeout_ms      = 45000
```

The run now reaches `Application.onCreate`, then the alias target's own
`LauncherActivity.onCreate` calls `finish()`; the next wall is
`IActivityClientController.finishActivity` → `illegal state in atms: no activity
for token 0x0` (the guest carries no AMS activity token). That is an AMS/token
wall, not launcher resolution.

`acos inspect` is still CLI-owned: `crates/acos-cli/src/main.rs` and
`crates/acos-apk/src/manifest.rs::launcher_activity()` ignore aliases. Request:
have `inspect` call `acos_services::manifest_resolve::launcher_activity` (or add
alias support to the `acos-apk` model). No CLI/protocol/apk files were edited.

## 2. Configurable 12 s resume budget (W25 blocker 4)

`LaunchMain.watch` uses `sResumeMs` instead of the hardcoded `12000`:

* `ACOSLAUNCH_RESUME_MS` is forwarded by `acos-art` into the guest sandbox and
  clamped to 1 s…600 s; explicit caller value wins.
* The default comes from the APK shape (`manifest_resolve::launch_budget`):
  ordinary apps **12 000 ms** (unchanged); multidex (≥ 8 dex) **or** ≥ 64 MiB of
  native libs **45 000 ms** — documented in code. Gaten debug (31 dex, ~108 MiB
  `.so`) gets 45 s; counter/rn-hello get 12 s.
* Both the resumed and not-resumed markers record the effective `timeout_ms`;
  `LaunchResult` gains `timeout_ms` (serialized as `timeout_ms`, `null` unless the
  outcome is `NO_ACTIVITY_RESUMED`), and the guest prints
  `ACOSLAUNCH MARK resume-budget ms=…`.

Evidence:

* default Gaten debug: `timeout_ms=45000` (`W27-gaten-alias-launch.json`);
* `ACOSLAUNCH_RESUME_MS=3000` Gaten debug: `timeout_ms=3000`
  (`W27-gaten-resume-3000.json`);
* counter and rn-hello with `ACOSLAUNCH_RESUME_MS=1000` both resume, and their
  guest `activity-resumed.marker` contains `timeout_ms=1000`
  (`W27-counter-resume1s.json`, `W27-rn-resume1s.json`) — the guest, not only the
  host, used the override.
* No run reached an actual 12 s/45 s deadline after W26's sensor-service change
  (all current apps resume in < 0.5 s); the deadline value is proven by the
  marker + result fields, the timer arithmetic is a one-line `now + sResumeMs`.

## 3. Multi-Activity: structured unsupported instead of a silent exit

W22's `multi-activity` tap on Send died because the guest sent
`IActivityTaskManager.startActivity` with a `TypedObject(android.content.Intent)`
and the AMS/parcelable side rejects it
(`no parcelable codec for android.content.Intent`). That codec lives in
W26-owned files (`parcelable.rs`/`ams`/`atms`), so W27 did **not** change it.

Instead the guest installs a read-only `IActivityTaskManager` dynamic proxy
(the cached `ActivityTaskManager.IActivityTaskManagerSingleton`): every method
delegates to the real binder; `startActivity*` logs one
`ACOSUNSUPPORTED {"code":"UNSUPPORTED_ANDROID_API","call":…}` line and returns
`START_SUCCESS` without fabricating an Activity. The host parses that marker
(`drain_stdout_lines` → `ProbeState`) and the session's gesture returns
`UNSUPPORTED_ANDROID_API`, naming the call, while the guest stays alive.

`scenarios/multi-activity.yaml` step 7 now:

```
status = unsupported
code   = UNSUPPORTED_ANDROID_API
error  = the app called android.app.IActivityTaskManager.startActivity and the
         launcher has no multi-Activity path; the guest stayed alive and no
         Activity was fabricated
```

(`evidence/W27-multi-activity.json`, 00:58:15–00:58:35Z; step JSON under
`W27-artifacts/multi2/steps/07-tap.json`). This is the packet's permitted
fallback, never a silent `INTERNAL` guest exit. Full second-Activity launch is
the stated next wall: implement the Intent codec (W26) and deliver a second
`scheduleLaunchActivity` transaction.

## 4. Dialog/PopupWindow/Menu window tree probe (W22 residual, step 23)

`emitProbe` now samples the **window forest**, not only the Activity decor:

* `WindowManagerGlobal.getWindowViews()` (fallback: the private `mViews` list),
  AOSP order (oldest/bottom first, newest/top last), Activity decor labelled
  `main`;
* every node carries a `window` label (Activity `main`, otherwise the
  `WindowManager.LayoutParams.title` or `window-<type>#z`) and already carried
  `bounds` (window-local) + `bounds_on_screen` (display space);
* per-window node budget, one bad window never suppresses the others.

The code compiles and the existing single-window scenarios are unchanged, but
**no second window can be observed yet**: the first non-Activity
`WindowManagerGlobal.addView` blocks the app main thread. Measured with manual
live sessions (same guest code):

| gesture | result |
|---|---|
| `dialog-menu`, tap Show dialog | `AcosDialog: dialog_shown`, probe_seq **42 → 42** over 2 s (main thread stopped), `mViews` has no dialog root |
| `dialogs-menus`, tap Popup menu | probe_seq **11 → 11**, no menu root |
| control: tap Toast (no second window) | probe_seq **43 → 63**, main thread alive |

The new `scenarios/w27-dialog-window.yaml` therefore fails at step 4
(`ELEMENT_NOT_FOUND` for `android:id/message`) with steps 0–3 green
(`W27-dialog-window-2.json`; `W27-artifacts/dialog2/tree/3.json` has only the
main window). This isolates W22's step-23 residual to the **window-attach/relayout
host path**, not the probe walk. Next action (outside acos-art): make
`IWindowSession.addToDisplayAsUser`/`relayout` complete for a dialog/PopupWindow
root (`crates/acos-wm` / `acos-services/src/window_session*.rs`, WMS owner);
then the same probe will list the new root without further changes.

## 8. Residuals / next walls

1. **`acos inspect`** still reports `launcher_activity=null` for alias APKs
   (acos-cli + acos-apk owned elsewhere). Request in §1.
2. **Gaten alias target** reaches its own `finish()` and hits
   `finishActivity: no activity for token 0x0`; the guest carries no AMS activity
   token. Next: give the launch transaction/`ActivityClientRecord` a real token
   (AMS/ATMS owner), then the splash can finish and hand off to `MainActivity`.
3. **Full second-Activity launch** needs the `android.content.Intent` parcelable
   codec (W26) plus delivery of a second `scheduleLaunchActivity` item; the
   structured fallback is in place meanwhile.
4. **Dialog/PopupWindow window attach** blocks the main thread before any probe
   can see it; the probe forest is ready, the WMS host path is not. Reproduce
   with `scenarios/w27-dialog-window.yaml`.
   The guest `startActivity` proxy also covers a *splash redirect during
   onCreate*: it keeps the guest alive and logs `ACOSUNSUPPORTED`, but the
   interactive startup loop does not yet turn a pre-`ready` marker into a
   startup failure, so such an app could be observed on its splash. Remove the
   proxy when W26 lands the Intent codec and a second transaction is delivered.
5. No real app currently takes > 12 s to `onResume`, so the 12 s/45 s default was
   not observed firing after W26's sensor change; the budget is proven by the
   guest marker/result and by the 1 s/3 s overrides.
