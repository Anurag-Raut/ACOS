# P7 — ACOS M3 (cold start) and M4 (warm launch) on real ART

Time box: 60 min, started 2026-11-12T15:44Z. **Diagnosis only.** No `crates/`
change: every number below comes from the release binaries' own verbs plus
traces that already exist and are inert when unset (`ACOS_ART_STAGE_TIMING`,
`ACOSLAUNCH_GUEST_STDOUT_FILE`).

## 1. Result

Both rows are measurable, and neither is noisy once its **state** is defined:

| Metric | State | p50 | p95 | n | spread (p95−p5)/p50 | verdict |
|---|---|---:|---:|---:|---:|---|
| **M4** warm launch → first correct frame | `acos serve` up, **app not running**, page cache warm (one launch+destroy before the cohort) | **459.4 ms** | **476.4 ms** | 24 (24/24 verified) | **7.7 %** | measured, not noisy |
| **M3** cold start → first correct frame | **nothing running**; page cache warm from the previous ACOS run | **462.7 ms** | **472.3 ms** | 12 (12/12 verified) | **6.8 %** | measured, not noisy |
| **M3** … same, page cache **evicted** | nothing running; boot image + libs + jars' resident pages dropped (7.3–8.3 MiB, verified 0 left) | **660.9 ms** | **677.3 ms** | 12 (12/12 verified) | **4.3 %** | measured, not noisy |

* **ACOS has no analogue of the emulator's 13.16 s boot.** `acos serve` is ready
  in **1.9 ms** (p95 2.0). ACOS "cold" is therefore *only* launch + whatever the
  page cache lost: M3(warm cache) − M4 = **+3.3 ms**, i.e. daemon spawn.
* The row that was labelled **"noisy"** was not noise: it is a **state
  ambiguity**. Re-reading the boot image and the ART libs from disk costs
  **+198 ms** (+42.8 %); it is systematic (spread 4.3 %) and reproducible in
  12/12 reps. Per MiB of evicted working set that is ≈ 27 ms/MiB.
* The row that was **"not measured"** is now 459 ms and, by the project's own
  15 % spread gate (`benchlib.is_noisy`), **not noisy**. One 540 ms outlier in
  24 pulls the raw max/min range to 22 %; the p5..p95 spread is 7.7 %.
* For comparison: stock emulator M3 17.84 s / M4 1,242 ms; legacy ACVM M3
  3.62 s / M4 1.25–1.34 s. ACOS M4 is **2.7× faster than the emulator's** and
  **2.7–2.9× faster than legacy ACVM's**.

## 2. Definitions (P6's, as closely as ACOS allows)

**P6's definitions, copied verbatim in intent**

* P6 M3: emulator start → `sys.boot_completed` → `am start -W` → poll raw
  screencaps until the app region is pixel-identical to a **verified** count-0
  reference; tree re-read afterwards.
* P6 M4: warm system, `am force-stop` before each rep → wait for the launcher →
  `am start -W` → poll screencaps until the same reference matches; tree re-read
  12/12.

**ACOS definitions used here**

| | M3 | M4 |
|---|---|---|
| Start state | **nothing running**: no `acos`, no `acos-art`, no ART, no daemon | `acos serve` daemon already up and warm; **app not running** (previous session destroyed) |
| Trigger | spawn `acos serve` → send `acos_launch` | send `acos_launch` |
| End | the **first frame byte-identical to the verified reference**, returned *inside the launch reply* | same |
| Verification | (a) the launch reply's tree reports `count = "0"` and the 12-node set; (b) a **post-frame** `acos_observe_tree` re-reads `count = "0"` | same |
| Reference | captured once per session, accepted only when the live tree read `0` **and** two consecutive settled captures had the same PNG md5 (`39d1e4e3633d98d76b992edb4b250a78`) | same |
| n | 12 (12 verified), plus 12 for the evicted-cache variant | 24 (24 verified) |

**Unavoidable differences from P6** (all of them make the ACOS number smaller
or larger in a stated way):

1. **No OS boot leg.** P6 M3 = 13.16 s boot + 4.67 s first-launch. ACOS has no
   OS to boot: namespaces and the guest are created per launch, so its whole
   cold leg is the 1.9 ms daemon spawn. The comparable ACOS quantity to P6's
   "boot alone" row does not exist and is not fabricated.
2. **No status bar / nav strip.** ACOS's frame is the app's window only
   (1080×2209), so "pixel-identical" needs no crop and no tolerance: the compare
   is **exact PNG md5 equality**. P6 had to crop 130 top + 60 bottom px and
   allow 0.05 %.
3. **The frame is fetched, not screencapped.** P6 polled `adb exec-out
   screencap` (~200 ms per poll), so its M4 is an upper bound with 200 ms
   granularity. ACOS's `acos_launch` reply already contains the settled,
   verified frame, so there is no poll granularity in the number: the frame's
   own `captured_at` equals the reply time to within **0.4 ms** (p50 459.0 vs
   459.4 ms). Zero polls were needed in 24/24 and 12/12 reps.
4. **ACOS's launch is stricter.** `acos_launch` settles *and* verifies before it
   replies (`ensure_bound_tree`, `serve.rs:484`), so 284 ms of the 459 ms is
   evidence production. P6 timed force-stop → a *settled-looking* frame; its
   tree re-read and total-time check were outside the M4 clock.
5. **No `am force-stop` equivalent is counted.** The warm state is produced by
   `acos_destroy` between reps (75.0 ms p50, outside the measurement), which is
   the same thing P6 did with `am force-stop` + waiting for the launcher.

## 3. What "warm" means in ACOS (the question in the brief)

Four states exist and only one is P6's "warm":

| State | What is warm | ACOS launch p50 |
|---|---|---:|
| S0 nothing has ever run on this host | binaries cold, `.cache/art/build-cache` cold (clang/javac/d8 rebuilt), image cold | **not measured** — needs a build-cache wipe that would corrupt other agents' runs; `build_cache.rs` records ≈ 1.9 s of compiler work for that case |
| S1 nothing running, page cache warm (a previous ACOS run happened) | page cache, build cache | **462.7 ms** (M3 as measured) |
| S2 nothing running, page cache evicted | build cache only | **660.9 ms** (M3 evicted variant) |
| S3 daemon up, app not running | page cache + daemon + build cache | **459.4 ms** (M4) |

So: **a held `acos serve` daemon is *not* what makes M4 fast** — it is worth
3.3 ms. What makes a launch fast is the **page cache** (198 ms) and the
**build cache** (≈1.9 s, S0 only). The report's "warm" for ACOS M4 should be
defined as S3 (daemon up), with the note that S1 measures the same thing to
within 1 %: a daemon that has already launched once is the only state that
matters.

Consistency check from the same run: on the live session, `{"cmd":"tree"}`
cost **250.7 ms** as the first command after `ready` and **175.4 ms** as the
second (150 quiet + 25 capture + ~0.4). A separate `acos_observe_tree` through
the daemon costs **177.0 ms** (p95 180.4, n=24) — so serve dispatch + reply is
**≈1.6 ms**, not a factor.

Read the table as: **175 ms is real Android work** (spawn, ART init, framework,
Application, Activity, first draw), **≈285 ms is ACOS's own evidence
production** (150 ms fixed quiet + up to 100 ms of 50 ms-cadence probe waiting +
25 ms capture + 10/15 ms poll quanta).

## 6. Noise analysis (why M3 was "noisy")

| Hypothesis | Verdict | Evidence |
|---|---|---|
| page cache (boot image / libs not resident) | **CONFIRMED, and it is the dominant term** | evicting 7.3–8.3 MiB of resident pages (fincore-verified to 0) adds **+198 ms**; 12/12 reps, spread only 4.3 % — systematic, not random |
| boot image decompress per session | **part of #4 in the ladder, not a noise source** | the boot image is decompressed into private memory in every session (26.3 MiB private, `D-M2-MEASURE.md`); it is a constant 51.6 ms phase, measured 8/8 within 4 % |
| first JIT / profile warm-up | **no**: there is no cross-launch JIT state to warm | each launch is a fresh guest with an empty app-data dir and no profile; the work lands inside phases 7–9 and is a constant, not a spread |
| build cache cold (compilers) | **not measured, and it is S0 only** | one-time ≈1.9 s per `build_cache.rs`; it was warm for all of these runs and P7 did not wipe a shared cache |
| host contention | ruled out for these runs | loadavg1 3.5 → 2.99 recorded per rep; the lock was held; no other ART run overlapped |
| measurement method | ruled out | the frame's own `captured_at` and the client reply agree to 0.4 ms p50; 0 polls needed in 36/36 reps |

So the earlier "noisy" M3 label was a **state label**, not a measurement
problem. The honest fix for the versioned table is to print M3 as
`0.46 s (page cache warm) / 0.66 s (page cache cold)` instead of one number, or
to define M3 as M4 + 3.3 ms and say why (no OS boot in ACOS).

## 7. Ranked avoidable costs

Saving is per warm launch (M4 = 459.4 ms), from the measured ladder. "Zygote"
is `docs/decisions/2026-11-12-zygote-shared-art.md` (Z1/Z2 done, **Z3 running**);
"pool" is a pre-warmed spare-process pool, which is an **architecture change and
needs owner approval** — nothing here proposes to build it.

| # | Cost | ms | % of M4 | How to remove | Saving | Risk | Owner |
|---|---|---:|---:|---|---:|---|---|
| 1 | **150 ms hard-coded quiet window** in the strict settle | ~150 (+ up to 50 of probe/store alignment) | 33 % | settle on **frame-sequence facts** (a C1 store after the last input, no store for k frames, probe newer than the store) instead of wall-clock quiet; keep the strict mode's meaning | 150–200 | medium: verification semantics — needs the owner-blessed "settled" definition and P1's fast/strict split kept intact | **P1/P3 follow-up** |
| 2 | **probe cadence 50 ms** (`LaunchMain.java:641`) — the settle must see a probe after the last store and a store after that probe, so it can wait two periods | ~65–100 | 14–22 % | event-driven probe (`OnGlobalLayout`/`OnDraw`, P3 §4.2) or a probe pushed on each C1 store | 65–100 | medium: new guest code, needs the same freshness proof; P3b is already on this | **P3b** |
| 3 | **boot-image load/decompress + ART init in the guest** (phase 4) | 51.6 | 11 % | **Zygote**: fork from a pre-initialised core (Z1 measured fork→ready **14–19 ms** vs 79 ms cold); or B3's shared uncompressed image for the 13.6 MiB part | 35–50 | **removes with Zygote** (Z3 running); B3 arm (b) is opt-in and needs the owner's ASLR decision | **Z track (Z3/Z4)** |
| 4 | **bwrap sandbox + cgroup scope + exec** (phase 3) | 20.7 | 4.5 % | **Zygote**: fork inside the already-sandboxed child (Z2: sandbox setup 2–3 ms after fork) — or **pool**: keep N pre-spawned, pre-sandboxed, pre-init guests idle | 18–20 | **Zygote removes it**; a pool is an architecture change (owner approval) and costs idle RSS per spare | **Z track / owner** |
| 5 | **`Application`/framework init** (phase 7) | 48.1 | 10.5 % | **Zygote**: preloaded framework classes are inherited copy-on-write; Z1's bare child shows the mechanism, Z3 must prove it for a real APK | 20–40 (app-specific, unproven) | **partly removable with Zygote**; needs Z3/Z4 evidence before any claim | **Z track** |
| 6 | **C1 capture for a tree reply** (clone 12 + PNG 8 + write 1.7 + md5 11) | ~25 | 5.4 % | the launch/tree reply needs only frame **identity** (generation, frame_number, fnv1a), not the PNG — P3 §4.1 already established this | 12–25 | low (identity fields already exist; P2 is in the same area) | **P2 / P3 follow-up** |
| 7 | **page cache cold: re-read 7.3 MiB of boot image + libs** | 198 | — (M3 only) | have the daemon read the image once at start (`posix_fadvise(WILLNEED)`) or keep the files resident; a Zygote core keeps them resident by construction | 198 | low (a 7–40 MiB read at daemon start; must not be done under load) | **unassigned (P-track)** |
| 8 | **first draw + traversal** (phase 9) | 17.5 | 3.8 % | nothing: real Android work (a real `ViewRootImpl` traversal and a real C1 store) | 0 | — | — |
| 9 | **Activity create/resume** (phase 8) | 17.2 | 3.7 % | nothing: real framework work | 0 | — | — |
| 10 | **host prep** (13 stages: linkerconfig, classpath, dex, 3 shims, apk-stage …) | 4.1 | 0.9 % | already 0 on the cache-hit path; a cold build cache is the only expensive case and is S0 only | ≤4 | low | — |
| 11 | **`acos serve` spawn (the M3 leg)** | 1.9 | 0.4 % | nothing worth doing | 0 | — | — |

Sum of what is realistically removable **without** an architecture change:
#1 + #2 + #6 ≈ **240–325 ms** off 459 ms → **≈135–220 ms** warm launch, with the
strict verification preserved. #3 + #4 + #5 (**≈85–110 ms**) are what the
**Zygote** track would remove on top, and they overlap with #1/#2 only in the
sense that both shorten the same 459 ms. A pre-warmed **spare pool** would
remove roughly #3 + #4 (≈70 ms) but not #5, and needs owner approval; it is
**estimated only, not measured**.

Nothing in the Zygote or pool direction was measured by P7; those numbers are
Z1's published result and the ladder above, clearly marked as estimates.

## 8. Not measured, and why

| Item | Why |
|---|---|
| S0 (nothing has *ever* run: cold build cache) | requires wiping `.cache/art/build-cache`, which other agents' launches depend on; the cost (≈1.9 s of clang/javac/d8) is recorded in `build_cache.rs`, not re-measured |
| A **global** page-cache drop (`/proc/sys/vm/drop_caches`) | needs root; P7 used `posix_fadvise(DONTNEED)` on 44 named files instead and proved it with `fincore`. That drops 7.3–8.3 MiB of the launch working set, not the whole cache |
| The emulator/legacy rows | out of scope (P6 and `BENCHMARKS.md` own them); quoted only |
| Concurrency (M9) and the agent loop | P5 owns those; M4 here is one held session at a time |
| An M4 variant with a pre-warmed spare process | it does not exist in the product; only estimated (§7) |
| `acos verify` cold one-shot as an M3 alternative | not the agent path (W57 already established that held-session verbs are the comparable state), and it bundles a scenario run, not a launch |
