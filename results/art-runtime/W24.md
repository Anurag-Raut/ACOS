## 1. What changed

### 1.1 The Activity title is the manifest label (AOSP `PackageParser` fields)

Stock `ActivityThread.performLaunchActivity` titles the window with
`r.activityInfo.loadLabel(pm)`. `ActivityInfo.loadLabel` reads
`nonLocalizedLabel`, then `labelRes` (`pm.getText(pkg, labelRes, appInfo)`), then
`applicationInfo.loadLabel(pm)`, and **only then** falls back to `name` — the
component FQN. The live guest set neither label field, so the walk ended at the
FQN (`dev.acos.fixtures.counter.MainActivity`).

* `crates/acos-services/src/pms.rs` — new `LabelSpec { res, literal }`,
  `ManifestLabels { application, activities: Vec<(fq_name, LabelSpec)> }` and
  `manifest_labels(apk)`, built from the same `acos_apk` manifest
  `PmsState::from_apk` installs. Semantics are `PackageParser`'s: a literal
  `android:label` wins and clears `labelRes`; a `@string/…` reference becomes
  `labelRes`; an activity with no label stays **unset** (so it falls through to
  the application label instead of inheriting a copy or the class name).
* `crates/acos-art/src/launch.rs` — reads the labels and passes
  `app labelRes, app literal, activity labelRes, activity literal` as guest argv.
* `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java` —
  `buildAppInfo()` sets `ApplicationInfo.labelRes`/`nonLocalizedLabel`;
  `buildActivityInfo()` sets `ActivityInfo.labelRes`/`nonLocalizedLabel`. No
  view-level title hack: the framework's own `loadLabel` → ActionBar title path
  produces the text.

### 1.2 The live guest loads the image's immutable framework RROs

On a device, `AssetManager.createSystemAssetsInZygoteLocked` loads
`framework-res.apk` **plus** one
`ApkAssets.loadOverlayFromPath(idmap, PROPERTY_SYSTEM)` per immutable overlay
idmap from `OverlayConfig.getZygoteInstance().createImmutableFrameworkIdmapsInZygote()`;
its native `createIdmap` `fork/exec`s `/system/bin/idmap2 create-multiple`.
`AssetManager.Builder.build()` always starts from `getSystem().getApkAssets()`,
so overlays applied to the system `AssetManager` reach every app `Resources`.

The base image's `framework-res.apk` says `bool/config_buttonTextAllCaps = ()
true`; the product overlay `PixelConfigOverlayCommon.apk` says `false`, and
`style/TextAppearance.DeviceDefault.Widget.Button` binds
`textAllCaps=@bool/config_buttonTextAllCaps`. The live launch guest had no
overlays, so it legitimately resolved `true` and Material drew `INCREMENT`;
the tree text stayed `Increment` (the W18 "tree vs glyphs" trap).

* `crates/acos-art/src/launch.rs` — provisions the static overlays with the
  existing `app::provision_overlays` (the image's `idmap2`, unchanged; the same
  code `render-app` and the older session path use), prints the diagnostics, and
  passes the `/data/overlay/*.idmap` list to the guest.
* `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java` —
  `applySystemOverlays()` runs before any framework `Resources` exists: it takes
  `AssetManager.getSystem()`, appends `ApkAssets.loadOverlayFromPath(idmap,
  PROPERTY_SYSTEM)` for each idmap, and `setApkAssets(..., true)`. All stock
  framework classes; an unusable idmap is reported and skipped
  (`ACOSLAUNCH MARK overlay-skipped …`), never silently faked.

### 1.3 Two spaces a pixel verifier must not mix (documented, not a code change)

* The probe tree is **display space**; a C1 frame is **window space**. The
  counter `id/inc` is `[42,368,273,494]` in the tree and `[42,240,273,366]` in
  `frames/1.png` (Δy = 128 = the status inset). W24's first crop measured
  "RESET" where it expected "INCREMENT" for exactly this reason.
* The 1080×2209 frame is the **configured** display's window:
  1080×2400 @ 420 dpi, status inset 128, nav inset 63 → 2209 = 2400−128−63
  (`Geometry::default`, matching the repo's API-34 x86_64 reference:
  decor `[0,0][1080,2337]`, nav `[0,2337][1080,2400]`). W18's "83 px nav inset"
  was the phone's 108 px status bar mixed into ACOS's 128/63 configuration.

## 6. Residuals / next walls

1. **todo-list step 12 (new wall, reached only now):** tapping the `milk` list
   row does not remove it. The live tree is correct (row `[42,561,1038,687]`,
   reference-identical) and the tap is sent at its centre; no `AcosTodo: remove
   item=` line exists in logcat, so the click never ran (not a stale sample).
   AOSP `AbsListView.onTouchUp` (tag `core/java/android/widget/AbsListView.java`
   ~4220–4265) posts `mTouchModeReset` with
   `ViewConfiguration.getPressedStateDuration()` and runs `performClick.run()`
   from that runnable **only if** `!mDataChanged && !mIsDetaching &&
   isAttachedToWindow()`; a suspect is `isAttachedToWindow()`/`mDataChanged` in
   the offscreen window path, untested. This is outside the W24 five items; the
   scenario stays unchanged (it is a real fidelity difference, not a bad
   expectation). `w15-todo-dogfood`/`list-adapter`/`list-scroll` still pass —
   none of them clicks a ListView item.
2. **Density is still 420 dpi vs the phone's 400.** `verify` scenarios pin
   1080×2400 @ 420; the whole-frame SSIM (0.9778) is dominated by the 5 % scale,
   not by layout. Changing it would change every reference expectation, so it
   stays; the density-normalised SSIM (0.9768) shows the same residual.
3. **No phone capture in W24** — every phone number above comes from the
   existing W175-A capture (`W18-phone-reference`, labelled historical). The
   phone's post-tap/reset/text-input states still have never been captured.
4. **Overlay provisioning depends on `.cache/boot/android-34/overlays`**
   (`tools/extract-bootclasspath.sh`) and `.cache/art/sysroot/system/bin/idmap2`
   (both present). When they are missing the guest prints
   `ACOSLAUNCH MARK overlays none …` and renders the un-overlaid framework — an
   honest fallback, but a verification run then legitimately shows `INCREMENT`.
   `tools/art-sysroot.sh` was therefore not changed; the sysroot does not carry
   `/product/overlay` (stock `OverlayConfig` would find nothing there anyway
   without OMS/idmap generation inside the guest).
5. **`acos-art launch` (non-interactive) gets the same fixes** (same
   `launch.rs`/`LaunchMain`), but W18's `acos launch` failure
   (`UNSUPPORTED_BACKEND … first_frame`) was not re-checked here.
6. The app's own `ApplicationInfo`/`ActivityInfo` are still assembled by the
   guest rather than served whole by `PmsState` (labels now come from the same
   parsed manifest); an activity-level `android:theme` is still read from the
   application theme (`launch.rs` passes one theme id).
