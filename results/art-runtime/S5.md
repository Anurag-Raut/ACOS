## 1. Memory cgroup: mechanism, fail-closed proof, config

### 1.1 What the host supports (measured, not assumed)

| mechanism | result |
|---|---|
| direct cgroup v2 delegation (`mkdir` under the launcher's own cgroup, write `memory.max`) | **NO** — `mkdir` succeeds, but the child directory has **no controller files** and the parent's knobs are root-owned (`memory.max: Permission denied`), so no limit can be written. A child moved into it cannot be limited. |
| `systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0 -p TasksMax=…` | **YES** — the transient scope has `memory.max` equal to the request and `memory.swap.max=0`, read back from `/sys/fs/cgroup<path>/memory.max`. |
| `MemoryOOMGroup=yes` | **NOT SUPPORTED by this host's systemd** (`Unknown assignment: MemoryOOMGroup=yes`). Probed at startup; when absent the run still gets the mandatory memory ceiling, only the group-kill refinement is dropped. |
| `bwrap --preserve-fds` | **absent** in the installed bubblewrap 0.13.1 (matters for the seccomp design, §2). |

`crates/acos-art/src/cgroup.rs` therefore uses `systemd-run --user --scope` and nothing else. There
is no `ulimit -v` fallback: an ART process under `RLIMIT_AS` dies with
`Scudo ERROR: internal map failure (NO MEMORY)` (S1 §2), which is why the guarded.sh fallback must
never be the ART ceiling.

### 1.2 How a run is proven limited before the guest starts

```
systemd-run --user --scope -q --same-dir \
  -p MemoryMax=<ACOS_ART_MEM_MAX> -p MemorySwapMax=0 [-p MemoryOOMGroup=yes] -p TasksMax=<n> \
  -- /bin/sh -c 'cat /proc/self/cgroup > "$1" || exit 90; shift; exec "$@"' sh <run>/cgroup <bwrap …>
```

The scoped shell records the run's **own** cgroup before `exec`ing bwrap. The launcher reads that
file, resolves `/sys/fs/cgroup<path>/{memory.max,memory.swap.max,pids.max}` and compares them to the
request (`RunCgroup::confirm`). If the file never appears, or the values do not match, or the path is
still the launcher's own cgroup, the run is **killed and refused** with
`Error::CgroupUnavailable` (`MEMORY_CGROUP_UNAVAILABLE: …`). `memory.peak` and
`memory.events:oom_kill` are sampled during the run and reported in the run diagnostics:

```
cgroup: memory.max=2048MiB swap=0 pids.max=512 peak=1MiB oom_kills=0 (/sys/fs/cgroup/…/run-pNNN.scope)
```

### 1.3 Defaults and knobs

| knob | default | meaning |
|---|---|---|
| `ACOS_ART_MEM_MAX` | `2G` (2 GiB) | hard `memory.max` for one run; accepts bytes / `K`/`M`/`G`. `0` or a parse error is a **fail-closed error**, never "unlimited". |
| `ACOS_ART_PIDS_MAX` | `512` | `pids.max` (ART's ~20 threads plus guest forks); `0` is refused. |

These are in addition to the existing launcher RSS watchdog (`ACOS_ART_RSS_MAX`, default 2048 MiB),
which stays as the launcher-side backstop. A watchdog trip is reported as `HOST_MEMORY_LIMIT`; a
cgroup OOM kill is *also* reported as `HOST_MEMORY_LIMIT` and names the scope + limits.

## 2. seccomp: where the filter goes, and why

### 2.1 Three placements were tried; two failed on evidence

1. **`bwrap --seccomp FD`.** Works (the raw `struct sock_filter[]` format is accepted; a length
   prefix is rejected with "must be multiple of 8"; a `RET_TRAP` program was verified to kill the
   guest with `SIGSYS` = exit 159). But bwrap applies the program **before it `exec`s the guest**, so
   an `execve` denial kills bwrap itself, and dropping `execve` from the policy only to satisfy the
   installer was not acceptable. Rejected as the *installer*.
2. **`acos-seccomp-guard` (Rust `cdylib`) preload.** Not loadable in the ART guest: its dynamic
   linker is **bionic**, and a glibc-linked Rust `cdylib` is rejected. (The arm64 qemu route is a
   glibc process, which is why this guard works there.) Rejected.
3. **Freestanding C `LD_PRELOAD` constructor in the guest** — adopted. Same shape as
   `shim/artshim.c` (`-nostdlib -ffreestanding`, raw x86_64 syscalls), compiled on demand into
   `<data>/seccomp/` and bound read-only into the run. It installs the host-assembled program with
   `seccomp(SET_MODE_FILTER, TSYNC)` from its constructor: after bionic has finished loading the
   process, before ART's `main` and any JNI code. One `LD_PRELOAD` line is assembled from every
   source (`guard` first, then shim / route libraries) because bwrap keeps only the **last**
   `--setenv` of a key — a duplicate silently dropped the guard during bring-up.

### 2.2 Policy (`crates/acos-art/src/seccomp.rs`)

A deny-list carried over from `acos-sandbox`'s audited filter, assembled by a classic-BPF builder in
Rust (90 instructions; unit-tested: every escape syscall present, every ART need absent):

* denied unconditionally: `ptrace`, `process_vm_{readv,writev}`, `process_madvise`, `kcmp`,
  `mount`, `umount2`, `pivot_root`, `chroot`, `unshare`, `setns`, the whole new mount API
  (`fsopen`/`fsconfig`/`fsmount`/`fspick`/`move_mount`/`open_tree`/`mount_setattr`),
  `open_by_handle_at`/`name_to_handle_at`, `io_uring_{setup,enter,register}`, `userfaultfd`, `bpf`,
  `perf_event_open`, `kexec_load`/`kexec_file_load`, `init_module`/`finit_module`/`delete_module`,
  `reboot`, `keyctl`/`add_key`/`request_key`, the `setuid`/`setgid` family + `capset`/`setgroups`,
  the pidfd family, `kill`/`tkill`, `lookup_dcookie`, `quotactl`, `swapon`/`swapoff`, `syslog`,
  `acct`, and (x86) `ioperm`/`iopl`/`modify_ldt`;
* `clone`: denied only when `flags & CLONE_NEW*` is non-zero (thread creation keeps working);
  `clone3` returns `ENOSYS` so bionic falls back to the filtered `clone`;
* `personality`: `PER_LINUX` and the read-only query only;
* `socket`/`socketpair`: `AF_UNIX` only (every other family returns `EACCES`);
* deliberately **allowed** (ART needs them and they are not escapes): `mmap`/`mprotect` incl.
  `PROT_EXEC` (JIT), `memfd_create`, `madvise`, `futex`, `prctl`, `rseq`, `open*`/`stat*`,
  `epoll`/`eventfd`/`poll`, clocks, `sched_*`, `getrandom`, `execve` (see below).

Two deliberate differences from the `acos-sandbox` filter, both forced by where it runs:

* `execve`/`execveat` are **not** denied. The program is installed inside the guest, so denying exec
  would only prevent the guest from starting a helper *inside its own mount view*, which is not a
  host escape (the new image inherits the filter, mounts, cgroup and namespaces). The required deny
  list for this route does not include exec.
* `tgkill`/`rt_*sigqueueinfo` are **not pid-argument-filtered**: the program is assembled by the
  **host**, before the guest exists, so the guest's pid is unknowable. `kill`/`tkill` stay denied;
  the guest pid namespace (`--unshare-pid`) is what bounds signalling.

### 2.3 Deny action and the logging finding

Denials return **`EACCES`** (`SECCOMP_RET_ERRNO`). A `SECCOMP_RET_TRAP` + SIGSYS-handler design was
implemented first (handler writing `DENY syscall=<nr>` to `/data/out/seccomp.log`) and **rejected on
evidence**: the handler installed from the preload constructor is not in effect when the denial
fires. A probe that installs its own SIGSYS handler sees the trap and the correct syscall number
(`ptrace` = 101); the same probe without that handler dies of `SIGSEGV` and nothing is logged.
`SECCOMP_FILTER_FLAG_LOG`/the audit log need `CAP_SYS_ADMIN`, which a bwrap userns does not have, so
there is no kernel-side audit channel. Denials are therefore logged **by the guest**: the guard
records the installed policy (`OK guard=active insns=90` in `<run>/out/seccomp.log`, fail-closed if
absent) and the adversarial probe records the denied syscall and errno in the run's stdout/stderr,
which the launcher captures. Residual: a denial by malicious native code is silent to the host (it
is *denied* but not attributed).

Fail-closed paths: guard artefacts missing ⇒ `SECCOMP_UNAVAILABLE` error before spawn; guard build
fails ⇒ same; the stub exits 126 if the blob cannot be read or the kernel rejects the filter; the
launcher returns `Error::SeccompUnavailable` when `OK guard=active` never appears — except when the
watchdog or the cgroup already killed the run (that is reported as `HOST_MEMORY_LIMIT`, not as a new
error).

## 3. Landlock inside the guest: not implemented — why bwrap binds suffice

S1 §5 #6 asked for a Landlock ruleset applied in the guest constructor after bwrap's mounts. This was
**not implemented**, for two reasons:

1. **Ownership/expiry.** The only in-guest code hook on this route is the freestanding preload stub.
   `acos-sandbox`'s Landlock builder is private to that crate (`linux/landlock.rs`, no
   `install_deferred_*` export), and adding one is outside this checkpoint's file ownership. A second
   hand-written Landlock ruleset in `acos-art` would be exactly the "two copies of one policy"
   problem ADR-0022 forbids.
2. **No new exposure to close.** S4 already made the run's filesystem view the whole story: shared
   inputs are `--ro-bind`ed, the only writable paths are the per-run root (`/data/{out,task,tmp,
   app-data,dalvik-cache,misc}` and the run's socket dir), `/data` itself is a fresh tmpfs, and the
   pre-S4 escapable paths are gone. S2 measured that `/proc/<pid>/root`, `cwd` and `fd` are denied
   inside bwrap's userns, so there is no host-root path view to filter, and this checkpoint's seccomp
   denies the Landlock bypasses (`open_by_handle_at`, `name_to_handle_at`, the mount API). What
   Landlock would add is defence in depth if the mount view were ever widened again.

Recommended follow-up (owner decision): export `install_deferred_landlock(roots)` from
`acos-sandbox` and call it from the same preload stub, with the run root as the only rw grant.

### 4.1 The three new adversarial proofs (`tests/sandbox_s5.rs`)

| test | what it proves |
|---|---|
| `refuses_to_run_when_no_cgroup_can_be_created` | a fake `systemd-run` on `PATH` makes `RunCgroup::prepare` return `Error::CgroupUnavailable` whose text carries `MEMORY_CGROUP_UNAVAILABLE` — the run is refused, not downgraded to `ulimit -v` |
| `allocator_bomb_is_oom_killed_inside_the_scope_and_the_host_is_untouched` | a Python allocator bomb (`bytearray(8 MiB)` loop) in a 128 MiB scope is OOM-killed: `memory.events:oom_kill ≥ 1`, peak stays ≤ 192 MiB, the process exits abnormally, **host `MemAvailable` moves < 512 MiB**, and no process survives in the scope |
| `fork_bomb_is_bounded_by_pids_max` | an sh fork bomb under `pids.max=24` never exceeds 24 processes, then the scope is emptied by `cgroup.kill` |
| `forbidden_syscall_is_denied_and_logged_in_the_guest` | a native probe run **in the real bwrap guest view** (host libc bound in, guard preloaded) calls `ptrace(PTRACE_TRACEME)` and gets `-1/EACCES` (`probe: DENIED ptrace errno=EACCES`), exits 0, and the run's `out/seccomp.log` contains `OK guard=active` |
| `default_memory_limit_is_two_gib` | the default is 2 GiB, not "unlimited" |

`RunCgroup::kill()` (`cgroup.kill`, falling back to a `SIGKILL` per `cgroup.procs` pid) is also used
by the launcher on timeout and on a failed cgroup proof: killing the `systemd-run` client does **not**
reap a scope, which the fork-bomb test demonstrated before the helper existed.

## 5. Residual risks and what is *not* covered yet

1. **Only the `run`/`verify` route is wired.** `app.rs` (`render-app`), `session.rs` and `launch.rs`
   belong to other checkpoints/owners this round; they still run without a per-run cgroup and without
   the guest seccomp filter. The counter render is therefore unchanged partly because it does not take
   this path. **This must not be read as "render-app is safe for untrusted APKs yet."** The builder
   surface (`Sandbox::seccomp_guest`) and `RunCgroup` are route-agnostic; wiring them is a small,
   mechanical follow-up in those three files.
2. **Denials are denied but not attributed.** `EACCES` has no kernel audit trail without
   `CAP_SYS_ADMIN`; a rogue `.so` gets a clean failure, and the host learns nothing unless the guest
   reports it. A `SECCOMP_RET_USER_NOTIF` supervisor in the launcher (listener fd handed over before
   the exec) is the proper fix; it also re-enables a per-syscall log.
3. **`memory.oom.group` is unavailable on this host's systemd.** The memory ceiling is still hard;
   an OOM kill targets the allocating process inside the scope, and the group-kill/`--die-with-parent`
   pair still ends the run. On a newer systemd the probe enables it automatically.
4. **The guard's evidence file is guest-writable** (`<run>/out/seccomp.log`): it proves the policy was
   installed and shows what the guest chose to report, not a tamper-proof audit log.
5. **`execve` is allowed in the guest.** A rogue APK can run other binaries from the sysroot inside
   its own mount view (still filtered, still cgrouped, still namespace-isolated); it cannot leave.
6. **Latency is unchanged, memory overhead is one scope per run** (`systemd-run` client + the
   scope's own `memory.current` accounting). The cgroup scope itself costs ~0 ms in the measured
   path; the launcher RSS backstop (`ACOS_ART_RSS_MAX`) remains necessary for the launcher process,
   which is *not* inside the guest scope.
7. **`acos-art run` exit codes on structured errors**: `SECCOMP_UNAVAILABLE` exits 2, but an earlier
   `MEMORY_CGROUP_UNAVAILABLE` bring-up run printed the error and exited 0. `main.rs` is not owned
   here; the error is structured and on stderr, but the exit-code consistency should be fixed where
   `main.rs` is owned.
