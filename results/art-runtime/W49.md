## Interpretation (hand-written, not generated)

**The loop was measured, but no task reached a verdict.** Every one of the 48
executed iterations (2 apps x 2 runs x 12 loops, warm-ups included) stopped at
the same launch stage: `on_resume` reached, `first_frame` blocked. The counter
and form-validation launches spend a real 688.9 / 728.5 ms p50 booting the app
process, then `IWindowSession.addToDisplayAsUser` fails inside the guest client
stub:

```
android.os.BadParcelableException: Parcel data not fully consumed, unread size: 796
  at android.view.IWindow$Stub.onTransact
  at android.view.IWindowSession$Stub$Proxy.addToDisplayAsUser
  at android.view.ViewRootImpl.setView
  at android.app.ActivityThread.handleResumeActivity
```

so `WindowManagerGlobal` has no root view and there is no tree, frame, tap,
typed text or screenshot. The exact stack is stored in
`runs[*].steps[0].events_evidence` and `steps[8].log_evidence` in the JSON.
Four apps were probed and all failed identically (`counter`, `form-validation`,
`hello-views`, `todo-list`). The `PASS` latency rows above with `ok rate 0%` are
therefore **fast error paths**, not working verbs; the functional gates
(`runtime:tree_reached`, `runtime:task_reaches_verdict`) are `FAIL`, and the
overall gate is `FAIL`.

The failure is deterministic across binaries: the 04:30 run used a release
build from the 04:15 tree (sha256 `93ea1b3dbe5be9b9`) and the 04:33 run was
rebuilt at 04:32 with the in-progress W47 `Configuration.screenLayout` change
in `crates/acos-wm/src/wms.rs` / `crates/acos-services/src/wms.rs` (sha256
`4ffe8a5a1f50722c`). Both fail with the same 796-byte unread parcel, so the
screenLayout fix does not address this blocker.

The daemon is also not on the product engine: `acos serve` builds a
`SessionBackend`/`AgentSession` (the Rust VM path, `engine:
acos-native-session`). It has no engine selector, and `acos_launch` ignores an
`engine` argument. `crates/acos-cli/src/engine/art.rs` is reachable only through
`acos verify --engine art`; **0 ART requests were possible through serve**. This
is why the agent path cannot inherit the ART path's working window.

### Cross-check against the ART path (W48, same host window)

The concurrent W48 run (`results/bench/d2-20261112T042524Z.json`, UTC
04:25:24) exercised `acos verify --engine art` on `counter.apk` with the same
scenarios under the same host lock: its N=1 cohort passed 1/1 and its suite
summary records `suite_verified_good: 2` (T01/T02). So the ART product path
reaches a real frame on this host while the serve agent path reaches none. The
blocker is the serve launch path, not the host, the fixture, or the scenario.

### Smallest next actions (P0, for the owner/orchestrator)

1. Wire the serve agent path to the ART engine (`acos_launch` takes an engine
   selection, or serve defaults to ART), so the measured agent loop is the
   product loop. Today the benchmark can only measure the Rust VM path.
2. Fix the `IWindow` callback parcel the WMS sends to the client stub (the
   client reads 796 bytes fewer than the server wrote). Until then no serve
   app, on either engine, can produce a tree.
3. Add a server-side `assert` (or expose `capture`/`screenshot` as session
   verbs). Today assert costs an extra `acos_observe_tree` round-trip and the
   screenshot is a side effect of `acos_observe`.

Once (1)+(2) land, rerun the exact command below; the gates and the JSON schema
need no change.
