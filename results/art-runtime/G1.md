## 1. What was promoted

`research/art-feasibility/t0-gralloc/gralloc_memfd_shim.c` (T0 probe) →
**`crates/acos-art/shim/gralloc_shim.c`** (product shim, 22 exports):

```
ctors      GraphicBufferMapper::{C1,C2}, GraphicBufferAllocator::{C1,C2},
           GraphicBufferMapper::preloadHal
allocate   GraphicBufferAllocator::allocate (8-arg and 9-arg), ::free
transport  GraphicBufferMapper::getTransportSize, ::importBuffer,
           ::importBufferNoValidate, ::freeBuffer, ::isSupported
lock       ::lock, ::lockAsync(32-bit usage), ::lockAsync(64/64), ::unlock,
           ::unlockAsync
metadata   ::setDataspace, ::setSmpte2086, ::setSmpte2094_40, ::setCta861_3
```

Signatures are the **image's**, re-verified this round against
`.cache/art/sysroot/system/lib64/{libui,libgui}.so` (`nm -D`, raw mangled names,
2026-11-11): all 22 exist verbatim in the image, including the four metadata
setters that only `libgui.so` references (`readelf -rW libgui.so`). `getPlaneLayouts`
/ r75's `optional<LockResult>` lock path are **not** in the image, so T0 §1.3 still
holds and no r75-shaped overload is implemented.

Three things the promotion fixed relative to the T0 probe (all were T0 residual
risks, not new features):

1. **Lifetime / double free.** Every handle the shim allocates *or imports* is in
   a mutex-guarded registry (`ptr → fd,size`). `allocator::free` and
   `mapper::freeBuffer` share one release path; whichever libui reaches first
   unmaps, closes the fd and frees the block, and the second becomes a no-op
   instead of a double free. A pointer outside the registry is treated as
   "already released", never dereferenced.
2. **Metadata no longer guesses.** The handle carries **9 ints** (w,h,stride
   px,format,usage lo/hi,layers,bpp,**dataspace**) and `getTransportSize` reports
   `(1, 9)`; `GraphicBuffer::flatten` writes exactly those ints and one fd, so
   `unflatten`'s size/`getTransportSize` agreement (which is a hard `BAD_VALUE`
   check in the image) is exact. `setDataspace` stores into that int; the HDR
   setters accept and drop (§7).
3. **Thread safety.** Registry, mapping table and handle table are under one
   `pthread_mutex` (BLAST queues a buffer from a different thread than the one
   that locked it). T0 was single-threaded by construction.

`tools/art-sysroot.sh` now builds it as a sysroot artifact:

```

<out>/shim/gralloc_shim.hash   (sha256 of the source, hash-stamped, idempotent)
READY: hw_shim=yes             (and it lands in MANIFEST.txt like every other file)
```

`--no-shim` opts out. Verified: `tools/art-sysroot.sh` run → `hw_shim=yes`,

## 2. Item (1) — the memfd survives flatten → unflatten **across processes**

`research/art-feasibility/g1-gralloc/probe_flatten.c`, run via
`tools/guarded.sh --mem 4G --time 300 -- research/art-feasibility/g1-gralloc/run.sh flatten`
(`G1_FULL_CHAIN=1` also exists: same probe with the guest's whole preload chain).

The carrier is SCM_RIGHTS instead of binder, and that is deliberate: what
`Transaction::setBuffer` does is `GraphicBuffer::flatten` into a Parcel plus an fd
that libbinder turns into `BINDER_TYPE_FD`; SCM_RIGHTS is the same kernel object
hand-off (`dup` + `struct file` share), and the shim never sees the carrier. The
byte stream (`getFlattenedSize`/`getFdCount` → `flatten`) and the reconstruction
(`importBuffer` + `getTransportSize`) are the image's own code.

```
[g1-flatten] parent: GraphicBuffer 64x48 RGBA_8888 via stock libui + shim
ACOSHWC[gralloc]: allocate: 64x48 fmt=1 layers=1 12288 B (256 B/row)
[g1-flatten] parent: initCheck = 0
[g1-flatten] parent: pattern written, bytesPerStride = 256
[g1-flatten] parent: getFlattenedSize = 88      <- 13 words + 9 ints, ×4
[g1-flatten] parent: getFdCount = 1
[g1-flatten] parent: flatten rc = 0
[g1-flatten] parent: sendmsg bytes = 104
[g1-flatten] child: SCM_RIGHTS fds = 1
[g1-flatten] child: flattened bytes = 88
ACOSHWC[gralloc]: importBuffer: dup'd fd, 64x48 stride=64
[g1-flatten] child: unflatten rc = 0
[g1-flatten] child: initCheck = 0
[g1-flatten] child: pixels read back OK (same memfd, other process)   <- every pixel
ACOSHWC[gralloc]: mapper:freeBuffer
ACOSHWC[gralloc]: release: closed memfd, freed 12288 B metadata
[g1-flatten] child: fd count before dtor = 74 / after dtor = 74       <- no fd leak
[g1-flatten] parent: child exit = 0
[g1-flatten] parent: own buffer still intact (fd shared, not moved)   <- still readable
[g1-flatten] PASS: flatten(proc A) -> SCM_RIGHTS -> unflatten(proc B) -> pixels OK
== exit=0
```

That is all four sub-claims of item 1: flatten in A, unflatten in B, B reads the
pixels A wrote, and **A's buffer is still valid afterwards** (so the fd was
shared, not moved — the lifetime model the header documents), with no fd leak
across `importBuffer`'s `dup` / libui's `native_handle_close` of the received
handle.

Two facts found while making this pass, both now recorded in the source:

- `sizeof(GraphicBuffer)` is **≥ 0x100** (`MGraphicBuffer::mOwner` at +0xb8,
  `mDeathCallbacks` at +0xe8..+0xf8 in the image's dtor). T0's "256 B is enough"
  was exactly on the boundary; a 256 B cell corrupts the caller's frame *inside
  the dtor*. The probe now reserves 512 B.
- `unflatten` must be called on an **already-constructed** `GraphicBuffer`
  (`GraphicBuffer::GraphicBuffer()` first). Unflattening into raw zeroed storage
  crashes in `~GraphicBuffer` because `RefBase`'s refcount state was never
  initialised. Real consumers hold an `sp<GraphicBuffer>` from `BufferItem`, so
  this is a probe bug, not a shim bug — but it is worth knowing before anyone
  writes the next probe.

## 3. Fences: why `-1` is correct here, not a shortcut

The shim answers `unlockAsync(handle, &fence)` with `*fence = -1`, and
`lockAsync(..., fenceFd, ...)` **closes** the incoming fence and maps the buffer
immediately.

- A software producer's writes are complete and coherent when `unlock()` returns:
  the buffer is a `MAP_SHARED` memfd, the writes are to the page cache, and there
  is no second engine that could still be reading. There is no outstanding work
  for a fence to represent.
- `BufferQueue` encodes exactly that state as `Fence::NO_FENCE`, whose fd is
  `-1`; `queueBuffer`'s `releaseFence->isValid()` test and `acquireBuffer`'s
  `Fence::NO_FENCE` short-circuit both treat `-1` as "already signalled", so the
  consumer proceeds without waiting.
- Emitting a real (e.g. `sync_file`) fence would be *less* faithful: it would
  claim deferred work that does not exist, and delay every consumer by a
  round-trip.
- Input fences are `close()`d, never leaked, because ownership of the fd
  transfers to the lock call (this matches `Fence`'s destructor contract).

Consequence to keep in mind (not silent): if a GPU ever appears behind this
allocator, `-1` becomes wrong, because then the pixel writes really can be
in flight. That is the one place where option A's "software only" boundary is
encoded in a return value.

## 4. Item (2) — BufferQueue probe: binder wall broken, cycle loop still hangs

### 4.1 The binder wall was the property table, not gralloc (cause #2 confirmed)

The probe already reached a full stock graph (`BufferQueue::createBufferQueue` +
`CpuConsumer` + `Surface`) and died in
`Surface::connect → BufferQueueProducer::connect → BufferQueueThreadState::getCallingPid
→ IPCThreadState::self → ProcessState::ProcessState("/dev/binder")`. That path
needs *some* binder stand-in even though no transaction is ever sent.

Candidate cause #2 from the first report was right: **run the probe with the
guest's full preload chain** — `libartshim.so` (which serves
`__system_property_*` from `/data/acos.properties`) `:` `libacosart.so`
(binder fake) `:` `libacoshw.so`, with `ACOSART_LOAD=:` and
`ACOSART_BINDER_FAKE=1`. `runner: G1_FULL_CHAIN=1 research/art-feasibility/g1-gralloc/run.sh blast`.
`ProcessState` then initialises over the fake and the connect succeeds:

```
[art] ProcessState: Binder driver /dev/binder is unavailable. Using /dev/binder instead.
[g1-blast] Surface::connect(CPU) rc = 0
```

(That "unavailable … using /dev/binder" line is libbinder's own wording for
"the fake answered BINDER_VERSION"; the ioctls come from `render_shim.c`, not
from the gralloc shim.) Two probe-side fixes were needed to get even this far,
both of which are findings: `Surface`/`CpuConsumer` are **heap-allocated** now
(16 KiB, not a 4 KiB stack cell), and `Surface::connect` segfaults
intermittently when the objects live on the stack — i.e. their layout is bigger
than a naïve cell, same class of bug as T0's 256 B `GraphicBuffer`.

### 4.2 Where it stops now: a **single-threaded futex wait** in stock BufferQueue

```
ACOSHWC[gralloc]: allocate: 1080x2400 fmt=1 layers=1 10368000 B (4320 B/row)
ACOSHWC[gralloc]: getTransportSize -> (1 fd, 9 ints)          <- last shim entry point
<no further output; the run is killed by --time>
```

Read from the host while it hung (`/proc/<pid>/…`; bwrap unshares the pid
namespace, so the probe is the child of the bwrap process):

```
State: S (sleeping)   Threads: 1   wchan: futex_do_wait
```

So it is **not** an infinite loop and **not** a crash: a single-threaded process
blocked on a futex inside stock libgui. The shim's participation is *complete* at
that point — `allocate` and `getTransportSize` both returned (the next shim entry
point would have been `lockAsync`, which logs). The wait is a
`Condition::wait(BufferQueueCore::mMutex)` in `BufferQueueProducer::dequeueBuffer`
inside the first `Surface::lock`.

**That is most likely my probe's design, not the queue's:** `BufferQueue`'s dequeue
waits for a free slot and `mDequeueCondition` is signalled by the *consumer*
(`onBufferReleased`), i.e. it assumes producer and consumer are **different
threads** — which is true for BLAST (app producer, SurfaceFlinger/BLAST consumer)
and false in this single-threaded probe. Two ways out, both cheap and both to be
tried in that order:

1. call `dequeueBuffer` with `async = true` (never blocks, drops instead), which
   is what a real BLAST producer does when it cannot wait;
2. pump `CpuConsumer::lockNextBuffer`/`unlockBuffer` from a second thread while
   the main thread dequeues/queues (one more `pthread`, no new library).

Two configuration facts were also established the hard way and are worth keeping:

- with 3 slots, `BufferQueueCore` requires `maxDequeued + maxAcquired + 1 ≤
  maxBufferCount`, so **maxDequeued 2 + maxAcquired 2 + 3 slots is rejected**
  (`setMaxDequeuedBufferCount: 2 dequeued buffers would exceed the maxBufferCount
  (3)`) — real BLAST runs 4 slots for exactly this reason; a 3-slot probe must
  use `maxAcquired 1, maxDequeued 1` (or 2/1 with 4 slots);
- `CpuConsumer::setMaxAcquiredBufferCount` above `maxBufferCount - 1` is
  *clamped with a warning* (`3 acquired buffers would exceed the maxBufferCount
  (3)`), so the "hold 3 buffers at once" rotation check is impossible with 3
  slots by construction; the 3-slot evidence has to come from the shim's
  allocation log (exactly three `allocate:` lines) plus the frame-number sequence.

**Still not demonstrated: the 60 acquire/release cycles, the 3-slot rotation and
the fence accounting.** I am not claiming them; what is proven here is that the
binder wall is gone, the shim's allocation/transport path is exercised end to end
against stock `BufferQueue` (a real 1080×2400 memfd buffer was allocated by
`BufferQueueCore` through our interposer), and the remaining blocker is a
producer/consumer threading assumption in the probe.

## 6. Item (4) — per-buffer memory, 1080×2400 RGBA, 3 slots: **measured**

`research/art-feasibility/g1-gralloc/probe_mem.c` (3 stock `GraphicBuffer`s held at
once, every page touched through the mapper's lock, `smaps_rollup` sampled):

```
ACOSHWC[gralloc]: allocate: 1080x2400 fmt=1 layers=1 10368000 B (4320 B/row)   ×3
[g1-mem] A: all 3 slots mapped+written, Rss kB = 39124
[g1-mem] A: Rss delta kB total = 30388
[g1-mem] A: Rss delta kB per slot = 10129
[g1-mem] A: payload kB per slot = 10125
[g1-mem] A: payload kB total = 30375
[g1-mem] B: unlocked, Rss kB = 8740
[g1-mem] B: Rss delta kB vs A = -30384
[g1-mem] B: mincore resident pages / total = 100 (×3)
```

Reading:

- **10,129 kB per slot** resident while mapped, i.e. **30,388 kB (~29.7 MiB) for a
  3-slot 1080×2400 RGBA set** — 5 kB over the 3 × 10,125 kB payload, so the
  per-buffer overhead is ~0.05 % (metadata is a 1-fd/9-int handle, plus one
  memfd and one VMA).
- After `unlock` the mapping goes away (Rss −30,384 kB) but `mincore` still
  reports **100 % of pages resident**: the pixels live as the memfd's shmem page
  cache. So the steady-state cost of an idle 3-slot queue is *page cache charged
  to the process* (reclaimable), not anonymous RSS. That is the honest accounting
  for option A and the number to compare against a real gralloc (ION/DMA-BUF,
  billed to the graphics allocator instead).
- `stride = width` px at 1080 (4320 B/row, 16-B aligned) — no padding waste here;
  the formula only pads non-multiples.

## 7. Honest gaps (what a reviewer should not assume)

1. **Item 2 is not demonstrated.** No 60-cycle evidence exists yet; §4 is the
   binder wall broken, a real stock-BufferQueue allocation through the shim, and
   a precise single-threaded futex diagnosis — not a pass.
2. **Item 3's md5 evidence is from `render-app`**, not from `session`, and the
   `launch` path was edited but not exercised (L1 is changing that path).
3. **HDR metadata is accepted and dropped** (`setSmpte2086`/`setCta861_3`/
   `setSmpte2094_40`). Nothing in this stack can display it; storing it would
   imply a fidelity that does not exist. Dataspace *is* stored in the handle.
4. **Metadata getters are still unimplemented** (`getPlaneLayouts`, `getWidth`,
   `getUsage`, `getBufferId`, `validateBufferSize`, `dumpBuffer…`). The image's
   lock/queue paths do not call them (verified by the `R_X86_64_JUMP_SLOT` set),
   `importBuffer` is answered by the shim itself, and `importBufferNoValidate`
   is implemented; anything else that calls them will crash rather than lie.
5. **`getUsage`-style bookkeeping differs by one field**: the handle carries
   `dataspace`, so `numInts = 9` (T0 shipped 8). Any other process importing a
   G1 handle must run the same shim — true for all ACOS processes, not for a
   stock gralloc consumer.
