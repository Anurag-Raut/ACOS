# Z3 — a real app (counter) in a child forked from a pre-initialised ART zygote

**Research prototype, Zygote track step Z3.** The only product-code change is one env-gated
seam in `crates/acos-art/src/launch.rs` (`ACOS_ZYGOTE_APP`, **unset by default**: with it unset
the argv, class path, guest dex and bind list are exactly what they were). Everything else is
under `research/zygote-proto/z3/`. No fixtures, no scenarios, no `tools/`, no `~/Projects/gaten`.

Every ART run went through
`tools/art-runtime/run-exclusive.sh --task Z3 -- tools/guarded.sh --mem 8G --time 300 -- …`;
scratch stayed in `.cache/z3-*`; `free -m` was checked before each run (host stayed well under
90 % — 46 GiB available).

## 1. The split: what is app-independent, what is per-child

`LaunchMain.run()` (`crates/acos-art/guest/java/dev/acos/art/LaunchMain.java:274-375`) is the
whole guest startup. Splitting it by *what the thing depends on*, not by line order:

### 1.1 Pre-fork, in the zygote (app-independent, thread-free)

| item | file:line | why it is app-independent | thread/fd/binder state |
|---|---|---|---|
| framework JNI registration (`RenderNat.register` × the `android::register_*_JNIEnv` table, incl. `register_android_app_ActivityThread`) | call `LaunchMain.java:275`, def `:1609-1720` | pure JNI entry-point table mutation; no class loader, no APK, no app object | none. `RenderNat.load()` (`:1610`) only `dlopen`s `libandroid_runtime.so`/`libhwui.so` **RTLD_GLOBAL**; measured: no thread created |
| binder-driver `.so` load | `LaunchMain.java:283` (`Nat.load()`) | loads `libacos_binder_driver.so`; the *connection* is per child | no thread, no socket yet — `startBinderLooper` (`:291`) is what creates both, and it stays below the split |
| system `Resources`: `framework-res` + immutable static RRO idmaps into the **system** `AssetManager` | `LaunchMain.java:290`, def `:222-271` | this is `AssetManager.createSystemAssetsInZygoteLocked` (a zygote job); every app `Resources` starts from `getSystem().getApkAssets()` | none |
| framework class resolution (34 classes `Class.forName(n, false, null)`, ZygoteInit `preloadClass` shape) | `ZygoteApp.java:preloadFrameworkClasses` | `initialize=false` = link only, no `<clinit>`, no app code | none |
| heap shrink + freeze | `ZygoteHooks.gcAndFinalize()`, `ZygoteHooks.preFork()` | ZygoteInit `:428` / `ZygoteConnection:290` | `preFork` **requires** 1 thread and produces 1 (`runtime.cc:835 CHECK_EQ(tl->Size(), 1u)`) |

### 1.2 Per child, after the fork (everything that names the app or owns a thread/fd)

| item | file:line | why it cannot be pre-fork |
|---|---|---|
| `new File(sOut).mkdirs()` | `:276` | per-session output dir |
| `Looper.prepareMainLooper()` | `:277` | creates the main `MessageQueue`: native epoll fd + wake pipe registered on a **thread-local**. AOSP also does it per child (`ActivityThread.main`), never in the zygote |
| `initAndroidRuntime(sPkg)` | `:286` | `argv0` is the app package (`Process.setArgV0`); also constructs libandroid_runtime's `AndroidRuntime` for this process |
| `Nat.startBinderLooper()` | `:291` | connects the driver to the peer socket (`E3G_SOCK`) and starts the **binder looper thread**. Inheriting this across a fork would share one socket + one object table between parent and child |
| `new ActivityThread()`, `mAppThread` | `:296-304` | the process's `IApplicationThread` |
| `buildBindApplicationRequest()` + `pushToPeer(1, bind)` | `:311` (builder `:1478-1560`) | the app's `ApplicationInfo`, manifest flags/theme/label, `dataDir`, `nativeLibraryDir` |
| `buildApplicationInfoReply` / `buildDisplayInfoReply` / `buildInstrumentationInfoReply` pushes | `:312-326` | per-app vtables for the peer's codecs |
| `ActivityThread.attach` (`IActivityManager.attachApplication`) | `:328` | per-process binder transaction to `ServiceHost` |
| `installLooperTrace` / `installStartActivityGuard` / `startWatcher` / `postFrameProbe` | `:341-374` | `startWatcher` and the probe **start threads**; they must be created after `postForkChild` |
| `Looper.loop()` | `:375` | the app's life |
| APK class loader, `LoadedApk`, `Application`, `Activity`, window, C1/gralloc buffers | framework, inside `handleBindApplication` / `TransactionQueue` | app-specific by definition; C1 buffers are the app's pixels |

`launch.rs` splits the same way: the **host** side (in-process `ServiceHost`, peer thread,
`InputHost`, C1 handles, `peer.sock`, `logd`, cgroups) is a separate *process* from the guest
(`launch.rs:326-455` peer thread, `:566-620` sandbox), so nothing there is inherited by a fork;
the child only inherits the guest's own fds.

### 1.3 What held threads/fds/binder state across the fork (the no-thread rule)

Measured in the zygote, from `/proc/self/status:Threads` (`guest.out`):

```text
Z3 zygote_pid=2 threads=6            <- ART's own threads under -Xzygote (JIT, GC, signals…)
Z3 no_thread_section=on threads=6
Z3 preapp_init ms=8 preloaded=34 threads=6      <- registerNatives + overlays + Nat.load + 34 Class.forName
Z3 post_preload_gc ms=3 threads=6
Z3 no_thread_section=off threads=6
Z3 after_preFork ms=6 threads=1      <- Heap::PreZygoteFork stopped the world: 1 thread
Z3 forked child=8 threads=6
Z3 child pid=8 fork_to_post_fork_ms=2 threads=6
Z3 child pid=8 daemons_started_ms=0 threads=10
```

* **Threads:** none of the four `LD_PRELOAD` shims (`libartshim`, `libacosart`, `libacoshw`,
  `libacos_binder_driver`) starts a thread at load, and `preFork` confirms it (`threads=1`).
  Everything that does start one — binder looper, `startWatcher`, `Choreographer` — is already
  per child in the production code. **This is why the split falls exactly on LaunchMain's
  pre/post lines and nothing had to be moved.**
* **fds:** one fd is inherited that the zygote should ideally not keep: the `logd` UNIX socket
  that `libartshim` opens at load. The parent does not write log lines after the fork (only its
  own `Z3 …` stdout), so nothing interleaves, but a product zygote should open logd per child
  or hand the child a duplicated fd. Not measured for cost.
* **binder state:** the driver has *no* connection before `startBinderLooper`; the raw
  `fork()` therefore cannot duplicate a live binder transaction. Z1 §5.1's caveat applies:
  raw `fork` skips bionic `pthread_atfork` handlers, which is safe *because* `preFork()` has
  already stopped the world.
* `preFork` cost is bimodal: **53 ms** on the first measured run (empty JIT/alloc state, full
  GC + `CreateZygoteSpace`), **6 ms** on the second (warm, `HasZygoteSpace()` early return,
  `heap.cc:2452`).

## 2. The prototype (opt-in, off by default)

`research/zygote-proto/z3/`:

* `build.sh` — javac+d8 of the **production** guest sources (`LaunchMain`, `RenderNat`,
  `Nat`) plus `ZygoteApp` and Z1's raw-syscall `dev.acos.z1.Nat`, and clang of Z1/Z2's
  `shim/z2fork.c` (91 LOC of raw `fork`/`wait4`); output `.cache/z3-build/`.
* `java/dev/acos/art/ZygoteApp.java` — `-Xzygote` entry: no-thread window → `registerNatives` +
  `applySystemOverlays` + `Nat.load` + 34-class preload → `gcAndFinalize` → `preFork` → `fork`
  → child: `postForkChild` + `Daemons.start()` (reflectively, `runtime.cc:1350`) + the
  **unmodified** `LaunchMain.main(args)`; parent: `postForkCommon` + blocking `wait4`.
* `drive.py` — the real product protocol: spawns `acos-art launch --interactive
  --until activity-resumed`, reads the ready line, then `tree` → `screenshot` →
  `tap(:id/inc centre)` → `tree` → `screenshot`, all on the launcher's **settled** frame
  (`wait_for_settled_observation`, not a sleep), optionally sampling `smaps_rollup` of the
  whole process tree.

The launch.rs seam (`launch.rs:550-557`, `:558-580`, `:620-631`):

```rust
let zygote_app: Option<PathBuf> = std::env::var_os("ACOS_ZYGOTE_APP").map(PathBuf::from);
// unset  -> production argv/class/dex/binds, unchanged
// set    -> -Xzygote -Xhidden-api-policy:disabled -cp /data/app/z3/classes.dex
//           dev.acos.art.ZygoteApp <the same 15 guest args>
```

The guest argv (`apk package out until activity appClass theme overlays …`) is passed through
verbatim (`argv.iter().skip(3)`), which is why the child needs no new code: it is the same entry
point with the same 15 arguments.

Two runs, one per path, same fixture (`fixtures/build/apps/counter.apk`), same driver, same
commands. Raw reports: `.cache/z3-runs/{normal,zygote}.json` (guest logs next to them).

| step | normal exec path | forked zygote child |
|---|---|---|
| ready line | `ok=true` in **168 ms** | `ok=true` in **200 ms** |
| `tree` count text | **"0"** | **"0"** |
| `:id/inc` bounds (from the tree) | `[42,240][273,366]`, tap at (157,303) | same |
| screenshot A md5 / sha256 / bytes / frame | `39d1e4e3633d98d76b992edb4b250a78` / `629611dfe28b7ce0` / 9 545 882 / **frame-7 g7** | **identical** (`629611dfe28b7ce0`, frame-7 g7) |
| `tap` (real InputChannel, acked) | `ok=true`, seq 3 | `ok=true`, seq 3 |

| screenshot B md5 / sha256 / frame | `9f3406c1627beef270f8cfddf9f61973` / `a5063bb8e115c39b` / **frame-59 g59** | **identical** (`a5063bb8e115c39b`, frame-59 g59) |
| guest `activity-resumed` marker | yes (`resume_ready=first-traversal`) | yes (`resume_ready=first-traversal`) |

**0 px diff** in the strongest available form: the two PNGs are the same bytes
(`sha256[:16]=629611dfe28b7ce0` before, `a5063bb8e115c39b` after), produced from the same C1
buffer generation and the same frame number. The tap is not credited by its ack: the count text

`guest.out` of the zygote run also shows the child is the real framework process:


and it re-runs `registerNatives`/`applySystemOverlays` itself (its own log lines):
`natives registered`, `overlays applied=1 base=2 total=3` — the pre-fork system `AssetManager`

### Versus the normal path at the same N

| N=1, guest side | normal | zygote + child | delta |
|---|---:|---:|---:|
| Σ Pss | 201 828 (197.1 MiB) | 221 203 (216.0 MiB) | **+18.9 MiB** |
| Σ Private_Dirty | 76 168 (74.4 MiB) | 50 068 (48.9 MiB) | **−25.5 MiB** |
| Σ Shared_Dirty (one physical copy) | 16 KiB | 68 948 KiB | the pre-fork heap, now shared |
| child's own Private_Dirty | 76 168 | 46 844 | **−38.5 %** |
| whole system incl. launcher | 219 265 Pss | 238 653 Pss | +19.4 MiB |

What this says, plainly: **at N=1 a zygote is a loss** — the parent's own Pss (87.5 MiB, of
which only 3.2 MiB private) has to be paid for and there is no second child to divide it over.
The app child is 29.3 MiB *cheaper* in private pages (46.8 vs 76.2 MiB) and shares 67.3 MiB
with its parent (the pre-fork heap + boot image), which is the number that compounds.

### N = 2 and 5: projection, not measurement (blocker §6.1)

Using the measured rows and the standard Pss apportioning over the shared set S ≈ 99 MiB
mapped by the parent and every child (zygote Shared_Clean+Shared_Dirty = 101 956 KiB, child
= 98 700 KiB), private per process 3 224 / 46 844:

| N | normal path Σ Pss (201 828 × N) | zygote Σ Pss (3 224 + 98 700 + 46 844·N) | crossover |
|---:|---:|---:|---|
| 1 | 197.1 MiB | 148.8 MiB model / 216.0 MiB **measured** | zygote loses (measured) |
| 2 | 394.2 MiB | 194.5 MiB | **zygote −50 %** |
| 5 | 985.5 MiB | 331.6 MiB | **zygote −66 %** |

The N=1 model row is off by 67 MiB against the measurement (the model ignores the parent's
own private growth and the child's non-shared clean pages), so treat N=2/5 as an estimate with
that error bar, **not** as a result. Z1/Z2 measured a 3.0–3.6 MiB marginal Pss per *idle* child
on the prototype workload; the app child here is much more expensive (real heap + gralloc +
C1 buffers) — that difference is the app, not the zygote.

## 5. Timing

| | normal exec | forked child |
|---|---:|---:|
| exec/start → `ready` (launcher, same driver) | **168 ms** | **200 ms** |
| `preFork` (one-off, first fork of the process) | — | 6–53 ms |
| pre-app init (JNI table + overlays + 34 classes) | — | **8 ms** |
| `gcAndFinalize` | — | 3 ms |
| `fork → postForkChild` | — | **2 ms** |
| `Daemons.start()` | — | **0 ms** |
| fork → first *correct* C1 frame (frame 1, `tree` settled) | 201 828-Pss process, 270 ms tree round trip | same 271 ms tree round trip on the child |

The child's `fork→postForkChild` of 2 ms is the figure the Zygote track cares about (Z1: 1 ms,
Z2: 5 ms); the rest is the app's own bind/attach/traversal, which the normal path pays too. At
N=1 the zygote **loses ~32 ms** on end-to-end ready: the one-off `preFork` (6–53 ms) is paid
and there is only one child to amortise it over. `Heap::PreZygoteFork` is idempotent
(`heap.cc:2452`), so forks #2..#N pay 1–2 ms (Z1 measured); this prototype forks only once
because the launcher is one session per process (§6.1).

## 6. Blockers for the next step

1. **N = 2/5 app children is not reachable through today's launcher.** `interactive_serve`'s
   peer accepts **one** guest connection (`launch.rs:383-397` `accept(listener)` once, then
   `serve(&mut peer, client, …)`), and `ServiceHost`/`InputHost`/C1 are built per launch
   (`launch.rs:352-455`). So one launcher process = one app child. A multi-session zygote needs
   a multi-peer host (one `ServiceHost` + C1 + input per child) and a child↔session routing
   key; that is the missing piece for the N=2/5 memory table above, and it is a launcher change,
   not a zygote change. This is why §4 has numbers for N=1 only.
2. **The zygote must outlive the session to be worth anything.** As wired here the zygote is
   spawned by the same `acos-art launch` that waits for one session, so it is torn down with it.
   A product shape needs a resident zygote process (started by the daemon, `acos serve`), with
   each session forked from it and the peer/ServiceHost created per session.
3. **`-Xzygote` + `Daemons.start()` is hidden API.** The child needs it (Z1 §6.2: without it the
   process dies silently inside finalization) and it is called reflectively under
   `-Xhidden-api-policy:disabled`, which is not a setting a product should ship. The honest
   replacement is to reuse `ZygoteInit.zygoteInit → RuntimeInit` wholesale, or to curate this
   as a documented hidden-API seam.
4. **`preFork` needs the world stopped and costs 6–53 ms the first time.** Nothing here is
   amortised at N=1; a resident zygote pays it once.
5. **Sandbox combination untested.** The zygote runs inside the existing bwrap + guest seccomp
   of the product path (so the child inherits both), but Z2's *in-process* `NEWUSER/NEWNS/NEWPID`
   sandbox was **not** combined with this app child. Inherited fd caveats (§1.3) and the
   untrusted-APK question stay open: the untrusted path remains the exec path.
6. **Not measured:** CPU per child, teardown of a hung child, per-child uid/seccomp (Z2 found
   `setresuid` to a distinct uid impossible unprivileged), and CoW behaviour of the *real* app
   child under repeated forks.

## 7. Reproducing

```bash
# 1. research guest dex + fork shim (no product build)
research/zygote-proto/z3/build.sh            # -> .cache/z3-build/{dex,lib}

# 2. the two paths (each holds the ART lock; never run them concurrently)
export ACOS_FONT_DIR=/home/Qui/Projects/acos/.cache/boot/android-34/fonts
tools/art-runtime/run-exclusive.sh --task Z3 -- tools/guarded.sh --mem 8G --time 300 -- \
  python3 research/zygote-proto/z3/drive.py --mode normal \
    --out .cache/z3-runs/normal --json .cache/z3-runs/normal.json \
    --sample .cache/z3-runs/normal-smaps.json
tools/art-runtime/run-exclusive.sh --task Z3 -- tools/guarded.sh --mem 8G --time 300 -- \
  python3 research/zygote-proto/z3/drive.py --mode zygote --zygote .cache/z3-build \
    --out .cache/z3-runs/zygote --json .cache/z3-runs/zygote.json \
    --sample .cache/z3-runs/zygote-smaps.json
```

`drive.py` exits 0 only when the count text goes `0 → 1` on settled frames; the pixel
equality is checked by comparing the `md5`/`sha256` of the two `live-frames/*.png` files. The
production path is the same command without `--zygote`.
