# P11 — event-driven strict settle (opt-in; quiet stays the default)

Worktree `perf-p11-event-settle`, branch of `1dd8bbb` (P9 merged). Owner approved
(2026-11-12): experiment behind a switch, adopt only after correctness is proven
equivalent. The switch is **`ACOS_STRICT_SETTLE=event`**; unset/`quiet` is the
default and keeps P10's 150 ms rule, the fast mode and `acos_assert`'s rejection
of fast byte-identical.

## 1. The rule

A strict reply in event mode is bound only when **all** of the following hold in
the guest, on the UI thread, at the sample that is returned:

| # | signal | AOSP source (android-14.0.0_r75) |
|---|---|---|
| 1 | no pending traversal on any attached `ViewRootImpl` (`mTraversalScheduled == false`, `mIsInTraversal == false`) | `base/core/java/android/view/ViewRootImpl.java:639` (`mTraversalScheduled`), `:644` (`mIsInTraversal`), `:2689-2698` (`scheduleTraversals`), `:2700-2713` (`unschedule`/`doTraversal`), `:3188` (set in `performTraversals`), `:4105` (cleared after draw) |
| 2 | no pending layout (`ViewRootImpl.mLayoutRequested == false`, root/`ViewRootImpl.isLayoutRequested() == false`) | `ViewRootImpl.java:646` (`mLayoutRequested`), `:2303-2306` (`requestLayout`), `:2311-2313` (`isLayoutRequested`); `base/core/java/android/view/View.java:25067-25069` (`View.isLayoutRequested`) |
| 3 | no invalidated-but-undrawn root (`mDirty` empty) | `ViewRootImpl.java:566` (`mDirty`), `:2326-2330` (`invalidate`), `:5274`/`:5399` (draw consumes and empties `mDirty`) |
| 4 | no pending Choreographer `INPUT`/`TRAVERSAL`/insets callback; `CALLBACK_ANIMATION` is left to the draw-stability rule (row 8) because the framework pumps Button press/elevation ValueAnimators there and quiet also answers before they end | `base/core/java/android/view/Choreographer.java:184` (`mCallbackQueues`), `:186` (`mFrameScheduled`), `:229-259` (callback types), `:938-945` (frame dispatch), `:1421-1425` (`CallbackQueue.mHead`, `hasDueCallbacksLocked`) |
| 5 | no running per-view `Animation` / `LayoutTransition` / `ViewPropertyAnimator`, and no pending transition list | `View.java:5274` (`mAnimator`), `ViewPropertyAnimator.java:221` (`mAnimatorMap`); `android/animation/LayoutTransition.java:1062` (`isRunning`); `ViewRootImpl.java:814` (`mPendingTransitions`), `:4087-4091` |
| 6 | no main-Looper message due inside horizon `H` (peek `mMessages.when`; `H = ACOS_STRICT_SETTLE_HORIZON_MS`, default **256 ms**) | `base/core/java/android/os/MessageQueue.java:59` (`mMessages`), `:118-121` (`isIdle`), `:333` (`next`) |
| 7 | window/focus/IME state stable for one frame (root set, labels, focus, IME focus, visible insets unchanged) | `ViewRootImpl.java:905` (`mImeFocusController`), `:814` (`mPendingTransitions`), `View.java` `AttachInfo.mHasWindowFocus`/`mVisibleInsets` |
| 8 | the sample is bound to a draw at/after the gesture publish and to the latest C1 store | host rule: `draw_ms >= publish_epoch_ms`, `sample.generation == latest C1 generation`, same `draw_seq` for `ACOS_STRICT_SETTLE_CONFIRM_MS` (default **24 ms**) |

`AnimationHandler` is not read globally: every `ValueAnimator` drives through
`AnimationHandler` → `Choreographer` (`ValueAnimator.java:1143`, `:1599-1603`;
`AnimationHandler.java:50-52`, `:94`), and its callback lists retain ended
animators for a frame, which would only add a false wait. The per-view
`Animation`/`LayoutTransition`/`ViewPropertyAnimator` checks cover the rest.

The global `CALLBACK_ANIMATION` queue is not a hard gate. On this image a
Button press/elevation ValueAnimator runs for ~0.9 s after every tap (animator
duration scale); gating it would pin every tap to ~1 s, and quiet also answers
before it ends. What *is* gated is the rendered state: a candidate must keep the
same `draw_seq` for the confirmation window, so any app animation that draws is
waited for frame by frame; an animation that changes no pixel until its end is
covered by the `onAnimationEnd` draw that then changes `draw_seq`. The guest
still reports `frame_callbacks` (the animation queue is visible), but only
INPUT/TRAVERSAL/insets callbacks add the `frame` pending reason.

The queue check ignores exactly one framework chrome timer: `View.ScrollabilityCache`
(the scrollbar fade). It is not app state, and quiet strict also answers before it
runs; without the exception every scrollable screen would wait ~1.2 s. The sample
still reports the queue message (`queue_what`/`queue_target`/`queue_callback`) so
the exception is visible, not silent.

The host requires the candidate draw to stay newest for the confirmation window;
a newer draw, a newer C1 store, or any newly pending signal restarts it. On
deadline the reply says `bound:"timeout"`, `settled:false`, `strict_rule:"event"`,
`reason:<guest reason>` (and `animating:true` for frame/animator reasons). It never
claims a settled state it did not observe. `acos wait`/`wait_for` remains the
contract for updates beyond `H` (for example the 1000 ms `postDelayed` case).

## 3. Method

All ART runs via
`tools/art-runtime/run-exclusive.sh --task P11 -- tools/guarded.sh --mem 8G --time …`.
Release binary built with `CARGO_TARGET_DIR=.cache/p11-target`,
`CARGO_BUILD_JOBS=4`, `ACOS_FONT_DIR=.cache/boot/android-34/fonts`, no
`ACOS_BOOT_DIR`, scratch under `.cache/p11-*`.

`p11_measure.py` holds one `acos serve` session per case, runs the action with
`settle:"strict"`, records client publish → reply (`wall_ms`) and the reply's
`settle` block, then takes an **immediate** fast tree and frame-only C1 capture.
It then waits for the case's known final state and takes the long-wait reference
frame **in the same rep**, so an early reply is visible without cross-launch
noise. `false_pass` = reply settled + immediate tree or PNG does not show the
final state. The `delay1000` case is reported separately (long-delay contract);
the infinite `ProgressBar` case is expected to time out.

## 4. Measurements

Clean cohorts, one fresh ART session per rep (the strict engine's
pixel-change guard compares against the previous capture; repeating an action
that lands on the same final pixels would otherwise be a `pixels-unchanged`
timeout). n=10 per case in both modes; event mode n=5 for rapid-taps because the
30 ms fast-tap setup is itself part of that case. Reference = one long explicit
wait per case/session, then the immediate tree + frame at the strict reply.

### 4.2 counter, strict tap (P10 `p10_m8.py`, n=20)

| mode | p50 | p95 | ok | bound |
|---|---:|---:|---:|---|
| quiet | **1073.57 ms** | 1087.09 ms | 20/20 | strict-quiet |
| event | **955.18 ms** | 968.45 ms | 20/20 | strict-event |

The 0.9 s is not the settle rule: it is a framework Button press/elevation
`ValueAnimator` that keeps redrawing after the tap. The event rule follows the
rendered draw sequence and therefore waits it out (quiet's last-store + 150 ms
also lands after it). Event is ~11 % faster, not the tens-of-ms target, on a
ripple/state-animated Button. The Activity transition (`303.85 ms` event vs
`417.51 ms` quiet) and the progress timeout are the cases where the event rule's
own signal path is visible without that animator.

## 6. Caveats

* **Latency target.** On this image every Button tap runs a framework
  press/elevation `ValueAnimator` for ~0.9 s. The event rule follows the actual
  rendered draw sequence, so it waits that animation out exactly as quiet waits
  the same stores + 150 ms; event is ~11 % faster (955 ms vs 1074 ms p50 on
  counter) but **not tens of ms**. The tens-of-ms behavior is visible on the
  Activity transition (304 ms vs 418 ms) and on actions without that animator;
  it is not claimed for ripple/state-animated Buttons.
* The global `CALLBACK_ANIMATION` Choreographer queue is not a hard pending
  reason. App animations that draw are waited for by the same-`draw_seq`
  confirmation; framework press/elevation animators would otherwise pin every
  tap to ~1 s. INPUT/TRAVERSAL/insets callbacks remain hard gates, and per-view
  `Animation`/`LayoutTransition`/`ViewPropertyAnimator` are checked directly.
* One framework MessageQueue item is exempt: `View.ScrollabilityCache` (the
  scrollbar fade, ~1.2 s). It is chrome, not app state; quiet also answers
  before it runs. The guest still counts all non-exempt queue items.
* Stopped/removed `ViewRootImpl`s are ignored during an Activity transition so
  the old root cannot hold `window-stopped` until the deadline; the live root is
  still fully checked (`no-focus` if none is live). This changed event activity
  from a 4.5 s timeout to 304 ms.
* The strict engine's pixel-change guard compares against the previous capture.
  Repeating the same final state in one session is therefore reported as
  `pixels-unchanged` (a timeout), not a false pass; the clean cohort uses one
  fresh session per rep so each measured settle is independent. The initial
  n=20 quiet run (before clean isolation) is kept only as raw evidence and is
  not used for the table.
* n=10 per case in the clean cohort (event rapid-taps n=5), not n=20: the
  shared ART lock was held by other agents (Z6) for >1 h; the first n=20 attempt
  was killed at its 30 min guard before writing its JSON. No missing number in
  the table is estimated.
* Real-app coverage is the required gate set plus counter M8; no per-case
  latency table for every real app (dialog/menus, fragments, todo, widget
  gallery, text input) beyond the green gates.
