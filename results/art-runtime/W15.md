## 1. What was measured

* **28 APKs** in `fixtures/build/apps/` (the complete set; build subdirectories
  such as `counter/`, `work-rn/` are not APKs).
* **40 scenario runs**: the 21 existing scenarios that target a fixture plus 17
  new minimal `scenarios/w15-*.yaml` scenarios for apps that had none. Existing
  scenarios were run unmodified.
* Command shape (exact):
  `tools/art-runtime/run-exclusive.sh --task W15 -- tools/guarded.sh --mem 8G --time 600 -- ./target/debug/acos verify --scenario <s> --apk <apk> --engine art --artifacts results/art-runtime/evidence/W15-artifacts/<id> --json`
* `first_frame_ms` is the launch step's measured duration (the W10 convention:
  engine spawn → first live C1 frame/tree; 0.52–0.54 s across every app that
  produced a frame). `-` means no live frame was ever produced.
* **First guest error** for every launch failure comes from a one-shot
  `./target/debug/acos-art launch --apk <apk> --until activity-resumed
  --log stderr --json` diagnostic run of the same APK (same guest path, same
  binary epoch) — the interactive engine does not expose a log stream
  (`logs: false`), so its `UNSUPPORTED_BACKEND` message only carries stderr.
  The LOOPER_THREW stack in `.stdout` names the first error. Raw JSON is under
  `results/art-runtime/evidence/W15-diag-*.json`.
* **ABI note (by design):** `rn-hello-arm64.apk` and `flutter-hello-arm64.apk`
  carry only `lib/arm64-v8a/`; host ART is x86_64. They are recorded as
  UNSUPPORTED_ABI, not fought.
* **Flutter is deferred by the owner** (`acos-counter.apk` = flutter-counter,
  `flutter-hello.apk`, `flutter-hello-arm64.apk`): recorded only, not run.
* **Compose:** no Compose fixture exists in the repo; nothing to run.
* Binary epoch of the matrix: `target/debug/acos` mtime
  `2026-11-12T02:27:37+05:30` = `2026-11-11T20:57:37Z`, before the 21:20:04Z
  rebuild (§6). The small fixes were tested on that same binary.

## 4. Small fixes applied (owned files only, verified by re-run)

1. `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java` — three
   registerNatives allowlist additions (the packet's permitted file/scope):
   `register_android_view_VelocityTracker`,
   `register_android_database_SQLiteConnection`,
   `register_android_database_CursorWindow`. All three symbols are exported by
   `.cache/art/sysroot/system/lib64/libandroid_runtime.so` (`nm -D`).
   *Verified effect, not a pass:* `widget-gallery` went from
   `InflateException: Error inflating class android.widget.Switch` (Caused by
   `UnsatisfiedLinkError: VelocityTracker.nativeInitialize`) to
   `activity_resumed=true`; `sqlite-crud` went from
   `SQLiteConnection.nativeOpen` → `CursorWindow.nativeCreate` → activity
   resumed. Both then hit blocker #4. Evidence:
   `W15-diag-widget-gallery.json`, `W15-diag-sqlite-crud.json`,
   `W15-diag-{widget,sqlite}-interactive.out`, and the post-fix countdowns in
   `runs.log` (21:14, 21:19).
2. `scenarios/w15-canvas-shapes.yaml` — expected status text corrected to
   `"canvas ready"` (the app's onCreate value; the sweep actually observed it).
3. `scenarios/w15-two-activity.yaml` — `main_state` expectation corrected to
   `"config changes=1"` (the app's own `onConfigurationChanged` at launch; the
   sweep observed it).
   Both corrections are **not yet re-verified as passes**: the shared binaries
   were rebuilt at 21:20:04Z and every launch after that fails with blocker #4
   (§6). The pre-rebuild sweep recorded the exact observed strings, so the
   corrected assertions are expected to pass once the input-service regression

## 9. Residuals / not done

1. Re-run the corrected `w15-canvas-shapes` / `w15-two-activity` scenarios and
   the two fixed apps once the W16 regression is resolved — they cannot be
   claimed as passes now.
2. `native-hello` / `native-hostile` are launch+capture passes only; their

   not asserted by the live tree and the engine exposes no log stream. Treat
   them as weak compatibility evidence.
3. Flutter deferred (3 APKs) and the two arm64-only APKs are UNSUPPORTED_ABI by
   design; no Compose fixture exists.
4. The interactive engine's `logs: false` means the guest logd batch is not
   surfaced on a failed ready line; the first errors here were recovered with a
   one-shot `--log stderr --json` run of the same APK. A future W-item should
   include the launcher's logd tail in the ready error (a diagnostics-only
   improvement; not made here).
5. Tooling note: `run-exclusive.sh --task <long-name>` puts `ACOS_ART_DATA`
   under `.cache/art-locks/data-<task>-<pid>`, and task names longer than about
   14 characters make the guest's Unix socket path exceed `sun_path`
   (`acos-art: io: socket path too long`). The first sweep attempt hit this for
   `W15-counter-type-unsupported`; the fix is to use the short `--task W15`
   (as the packet specifies) — the tool itself is outside this packet's OWN
   list.
6. One line in `docs/IMAGE_ABI_NOTEBOOK.md` would record the three newly
   verified registration facts; the notebook is outside this packet's OWN list,
   so it is requested, not edited.
