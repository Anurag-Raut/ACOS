# P3 — where one fresh M7 tree request spends its 186 ms

Time box: 60 min, started 2026-11-12T14:20Z. **Diagnosis only.** The only code
change is three `P3_TRACE`-gated trace hunks (unset = no work, no reply or
control-flow change). Nothing is implemented.

## 1. Result

One `acos_observe_tree` on a held `acos serve` ART session costs **186.42 ms p50
(187.45 p95, n=30, min 181.13, max 187.58)** on this host, HEAD `ecf7fa2` +
the trace hunks, release build. All 30 non-warmup samples were fresh and
complete: 12 nodes, 4 text nodes, 4,101 B JSON, `truncated=false`, and the guest
probe sequence advanced. A second rep (24 samples, 2 warm-ups) measured
**185.85 ms p50, 24/24 good**.

W57's M7 row was **251.93 ms p50**; the difference is almost entirely O1
(`8e81604`, table-driven crc32/adler32): capture fell from ~82 ms to **34.47 ms**
(encode alone 60.3 → **8.41 ms**), and this M5 control measured **29.85 ms p50**
vs W57's 80.08. The settle window is unchanged. The *split* is the deliverable,
not the absolute.

**Two phases are 99.5 % of the request:**

| rank | phase | p50 | share | file:line |
|---|---|---:|---:|---|
| 1 | **settle wait** — `wait_for_settled_observation`, hard-coded 150 ms quiet window, 15 ms poll | **151.112 ms** | **81.06 %** | `crates/acos-art/src/launch.rs:1968` (quiet `:1978`, sleep `:2050`), called from the `tree` handler `:2267`/`:2273` |
| 2 | **capture side effect** — C1 buffer clone + PNG encode + PNG write + md5 of the PNG file | **34.468 ms** | **18.49 %** | `capture_c1` `crates/acos-art/src/launch.rs:1706`, called at `:2314`; encode `encode_png_rgba` `:2725`; md5 `md5_hex_file` `:1890` |
| | everything else (dispatch, IPC, JSON, reply) | **~0.84 ms** | **0.45 %** | `crates/acos-cli/src/engine/serve.rs:1022`, `crates/acos-cli/src/engine/art.rs:1440`, `:1357` |

The tree reply uses **none** of that capture: `capture_c1` is called only to
obtain frame identity fields (`frame_seq`, `buffer_generation`, `frame_number`,
`md5`, `pixels_fnv1a`) and a PNG path. The PNG bytes are then **read back from
disk by the client** (`read_png`, `art.rs:2156`, via `absorb` `art.rs:1357`) and
never used by `observe_tree` (`serve.rs:1022` returns package/tree/windows/
counts only). The 9.5 MB PNG file is pure side effect on this verb.

### Settle detail

`launch.rs:2267` sends `{"cmd":"tree"}` with `min_generation=0`,
`min_probe_seq=0`, `previous_fnv=None`. `wait_for_settled_observation` therefore
always waits the full **150 ms** from entry (`last_change = Instant::now()`),
even on an idle screen, and then requires a probe sample stamped **after** the
last C1 store. It polls every **15 ms** and calls `cgroup.sample()` each loop.
Measured 151.112 ms p50 (p95 151.386) — the window plus one poll quantum. The
returned probe is 57.6 ms old at reply (p95 79.7 ms), i.e. up to one 50 ms poll
older than the settle decision; no new frame landed, so that is not stale, but
it is not "a tree taken at the request instant" either.

### Guest probe detail

* Lives in `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java`:
  `startLiveProbe` `:593`, a daemon thread that posts one `emitProbe` to the main
  `Looper` every **50 ms** (`Thread.sleep(50)` `:641`); `emitProbe` `:705` walks
  **every attached window root** (`windowViews()` → `WindowManagerGlobal`,
  Activity decor first) with `appendViewJson`, then prints one
  `ACOSPROBE {"seq","time","windows","tree":{…,"emit_us"}}` line.
* Host parser: `drain_tee_lines` `crates/acos-art/src/launch.rs:1540`, prefix
  `LIVE_PROBE_PREFIX` `:1124`; it keeps only the newest sample in `ProbeState`
  (`ProbeSample`, `:1136`) and re-parses each 3.8 KiB line.
* Cost measured over 14.78 s: **287 samples**, interval p50 **50.07 ms**
  (p95 50.20), guest `emit_us` **0 in every sample** (integer µs ⇒ <1 ms for
  12 nodes), host receive+parse lag p50 **0.58 ms** (p95 1.04), line 3,836–3,839 B.
  So the traversal itself is not the 252/186 ms; what costs is *waiting for the
  probe's 50 ms cadence inside a 150 ms quiet window*, and the capture done
  beside it.
* The probe is **polling**, not event-driven: ~19.4 full tree walks + JSON
  serialisations per second, all of them thrown away unless a request is open.
  That is cheap at 12 nodes, but it scales with node count (a 2,000-node forest
  is ~1 MiB per line) and competes with the app's own draws on the main thread.

## 4. Answers

### 4.1 Which phases are unnecessary for a tree-only request?

* **Capture (34.47 ms) and the PNG read-back (0.43 ms) are entirely
  unnecessary.** The reply's `tree` is the probe tree; only frame *identity*
  fields are used. A cheap C1 metadata accessor (generation/frame_number/fnv1a,
  no buffer clone) removes all 34.47 ms; the 12.58 ms clone is only because
  `capture_latest()` returns the pixels with the metadata.
* **The 150 ms quiet window is unnecessary for a *fast* tree** (navigation /
  "what is on screen now"), but necessary for a *strict* tree that is claimed
  to describe a settled, pixel-bound state. A tree-only request carries no
  pixels, so its binding only needs "this sample is newer than the last frame
  store and the last accepted input" — not "no store for 150 ms".
* Everything else (dispatch, IPC, JSON, reply) is 0.45 % and not worth touching
  before 3 and 4.

### 4.2 Can the guest probe push the tree on change?

Yes, and it is the right direction, with one constraint: **do not serialise a
full tree per draw.** Register `ViewTreeObserver.OnGlobalLayoutListener` (and
`OnDrawListener`, plus window add/remove) on each attached root; each callback
bumps a monotonic `view_generation` and sets `dirty`. The probe thread then
builds/serialises only on a host request or on a debounced dirty tick (e.g. min
16–50 ms), so an animating app cannot generate 60 full trees/s. Accessibility
events are a viable alternative but are asynchronous, need service flags and
lag the View state; the current in-process View walk is cheaper and already
ships text/bounds.

Freshness can then be proven by the **sequence**, not a wall clock guess: each
sample carries `view_generation`, `probe_seq`, `at_ms`; `acos-art` also knows
the C1 store generation/time and the last accepted input ack. A sample is
usable iff `probe.at_ms >= last_store_at_ms` (and `probe_seq` is past the last
invalidated seq) — exactly the rule the settle loop already implements. The
`emit_us` field is already there to police the cost.

### 4.3 Invalidation — never return an old tree as fresh

* Keep `last_store_at_ms` (C1), `last_store_generation`, and `last_input_ack`
  in `acos-art`/serve.
* A cached or pushed tree is **invalid** if `probe.at_ms < last_store_at_ms`,
  or if its `probe_seq` is not newer than the seq invalidated by the last
  input/frame, or if the guest is not the same live child (existing
  `liveness()`/`seq_offset`/`invalidate_frame` handles reset/relaunch).
* On invalidation, do not serve: either wait for the next dirty probe (event
  wakeup, not a 50 ms sleep) or trigger an immediate main-thread probe, with a
  bounded deadline that returns a structured `NO_FRESH_TREE` rather than the
  old tree.
* Always expose `probe_seq`, `probe_at_ms`, `settled`/`freshness` in the reply
  so a caller can tell a fast tree from a strict one, and never reuse a fast
  tree for a strict assertion.

### 4.4 Incremental / diff delivery

Possible: stable node path id + per-node content hash, send only changed nodes
and removals with `base_seq`, and force a full snapshot when the base does not
match. **At 12 nodes it buys nothing** — full-tree serialise + parse is 0.18 ms
and 3.8 KiB. It only matters for large trees (roughly >500–1,000 nodes), where
the probe line approaches hundreds of KiB–MiB and host parse/serialise becomes
milliseconds; then a diff plus a node budget is worth benchmarking.

### 4.5 What legacy did in 4.1 ms

Legacy's persistent reader was a **per-session long-lived instrumentation
process** (`ObserveServeInstrumentation`, legacy commit `44aec35`,
`research/observe/observe-apk`): `UiAutomation`/accessibility
(`getWindows()`, `getWindowsOnAllDisplays()`, `AccessibilityNodeInfo` with
text/desc/id/bounds), served over a Linux abstract socket (`acvm-observe`) with
one `{"op":"dump"}` → one JSON line. Startup ~0.61 s once per session, +12.6 MiB
PSS/session, **4.1 ms p50 / 4.6 p95, 25/25**. It had **no settle wait, no frame
capture, no PNG, no polling** — it walked the accessibility tree synchronously
at request time. Its freshness is "the a11y tree at request time", which is
*faster* but **weaker** than ACOS's frame/probe binding: it is not proven to
match a compositor frame. Legacy's other structure-only route was 2.2–2.8 ms
(on-device service) and 14–26 ms (WM dump).

## 5. Ranked options (savings, risk, fast/strict)

| # | option | expected p50 saving | correctness risk | fast/strict? |
|---|---|---:|---|---|
| 1 | **Tree-only reply without capture**: no buffer clone, no PNG encode/write, no md5 file; return C1 generation/frame_number/fnv1a from a metadata-only accessor; stop the client reading the PNG for `observe_tree` | **34.9 ms** (186.4 → ~151.5) | **Low–medium.** `observe_tree` never returned pixels; but `absorb()` currently binds tree to PNG and other verbs (`observe --tree`, tap-by-selector) share `tree()`. Needs a tree-only reply/cache path that never silently serves a tree bound to older pixels; `state_changed` compares tree signature *and* md5, so keep the signature authoritative. | Independent of fast/strict; strict tree stays 150 ms settle but pixel-free. |
| 2 | **Fast tree**: skip the quiet window; use the latest probe with `at_ms >= last_store_at_ms`, or trigger an immediate probe; label `settled:false`/`freshness:"fast"`; strict stays default | **~148–151 ms**; with #1 total **~2–5 ms** (one main-thread probe + JSON + IPC) | **Medium–high.** May return a mid-animation tree; must never be used for assertions/pixels and must say so. | **Is** the fast mode. **Coordinate with P1**, which is already adding the fast/strict settle option — P3 should consume it, not duplicate it. |
| 3 | **Event-driven probe**: `OnGlobalLayout`/`OnDraw` (and window add/remove) bump `view_generation` + dirty; serialise on request or debounced tick; keep 50 ms poll only as a canvas/background fallback | removes the 0–50 ms probe age and ~19.4 full walks/s; makes #2's ~2–5 ms reliable | **Low–medium.** Draw callbacks are frequent; must debounce and never serialise per draw. Canvases/background draws still need the fallback. | Enables fast; strict benefits only as a freshness signal. |
| 4 | Metadata-only C1 accessor (part of #1) | 12.6 ms of the capture | **Low.** Must read under the compositor lock and not clone. | Any. |
| 5 | Use `pixels_fnv1a`/tree signature as the content hash instead of md5-over-PNG (if capture is kept) | 11.5 ms | **Low–medium.** Changes a hash field tests/agents may read; md5 of a PNG and fnv1a of the buffer are different identities. | Any; better handled with the frame path (O2/P2). |
| 6 | **Diff delivery** | ~0 at 12 nodes; milliseconds only for large trees | **Medium–high.** Base/seq loss, identity bugs, per-node staleness. | Optional, after 1–3. |
| 7 | Serve-side cached tree (legacy-style) | the remaining ~0.3 ms | **Low only if** #3's invalidation is exact; otherwise a stale-tree machine. | Prefer as a consequence of #2/#3, not a standalone cache. |

Ordering note: P1 owns the settle-mode switch; **do not** add a second
fast/strict flag in P3. O2/P2 own the frame/PNG path; if they make capture
cheaper, #1 and #4 still remove it from this verb rather than compete.

## 6. Recommended implementation for the next task

1. **P3a — pixel-free tree reply (independent, lowest risk).** Add a
   `{"cmd":"tree","pixels":false}` variant (or a tree-only reply that omits
   `png`/`md5` and carries `frame_generation`, `frame_number`,
   `pixels_fnv1a`). In `capture_c1`, add a metadata-only path that does not
   clone the buffer or encode/write/md5 a PNG. In `absorb`, a tree-only reply
   must not require a PNG and must not overwrite the last pixel-bound cache with
   a pixel-less frame; `observe_tree` must keep returning the same tree shape.
   Expected **186.4 → ~151.5 ms p50**, zero change to bytes/text/freshness
   proof. Gate: 30/30 fresh trees, `truncated=false`, text nodes unchanged,
   strict pixel verbs unchanged.
2. **P3b — fast tree, wired to P1.** Use P1's fast observation mode: no quiet
   window; require only `probe.at_ms >= last_store_at_ms`; if no such sample,
   request an immediate main-thread probe; return `settled:false` +
   `tree_age_ms`/`probe_seq`. Expected **~2–5 ms p50** with P3a (legacy-class),
   strict path still 150 ms. Gate: fast replies labelled; assert/pixel paths
   refuse fast evidence; strict results unchanged.
3. **P3c — event-driven probe.** `ViewTreeObserver` dirty/generation + host
   wakeup + debounce; keep the 50 ms poll as fallback. This removes the 50 ms
   cadence from fast latency and the idle 19.4 walks/s. Measure with the same
   harness; only keep if fast p95 ≤ ~10 ms and strict correctness is identical.
4. Defer diff delivery until a large-tree (≥500 nodes) measurement shows
   serialise/parse >5 ms; do not build it for the 12-node counter.

## 7. What is verified vs not

Verified: one held serve session; 30 fresh tree requests (plus 2 warm-ups) at
n≥20 with p50/p95 per phase on one clock; fresh probe sequence, 12 nodes /
4 text / 4,101 B / no truncation; capture is a side effect not consumed by the
tree reply; client reads the unused PNG; probe cadence/cost; rep 1 replication
(24/24 good, 185.85 ms p50); host clean, no survivors; tests green.

Not verified: trees larger than the counter (the probe cost is measured only at
12 nodes); a fast-mode tree policy (not implemented); whether P1's flag shape is
exactly the one P3b should consume; guest-side `emit_us` resolution (integer
milliseconds would show the true sub-ms traversal); behaviour under animations
(the settle window's real cost when the ripple keeps frames landing).
