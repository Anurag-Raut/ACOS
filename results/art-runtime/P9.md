|---|---|---:|---:|---|---:|

| **M4** | `strict` + `pixels:true` (P7's reply) | 461.6 ms | 468.1 ms | 435 – 482 | — |
| **M4** | `strict` + default `pixels:false` | 440.1 ms | 448.8 ms | 415 – 449 | −21.5 ms |

| **M6** | `strict` + `pixels:true` | 481.8 ms | 496.8 ms | 453 – 497 | — |
| **M6** | `strict` + default `pixels:false` | 462.8 ms | 473.6 ms | 445 – 481 | −19.0 ms |
| **M6 end-to-end** (reset + strict re-read) | `fast` | 451.3 ms | 469.2 ms | — | vs 633.5 / 614.5 strict |

* **Fast is inside the predicted band.** P7 §7 estimated ≈135–220 ms for the
  no-architecture-change combination; the measured fast launch is **184.2 ms
  p50**, i.e. the 175 ms of real Android work (spawn → ART init → Activity
  resumed → first traversal → first C1 store) plus **≈9 ms** of evidence
  production (one immediate out-of-cadence guest probe + C1 metadata identity,
  `tree_age_ms` 0–1 ms). The 150 ms quiet window, a second probe period, the
  PNG capture and the 10 ms ready poll are gone from this path.
* **Strict is unchanged.** 461.6 ms p50 with `pixels:true` vs P7's published
  459.4 ms (p95 476.4 → 468.1): same rule, same reply, same md5
  (`39d1e4e3633d98d76b992edb4b250a78`), so nothing in the strict path moved.
  The remaining 19–21 ms between `pixels:true` and the new `pixels:false`
  default is exactly the PNG clone/encode/write/md5 the launch reply no longer
  does unless asked (§4).
* **Fast launch has a tail, and it is not the settle.** 18/24 reps are
  159–201 ms and 20/24 are under 250 ms; 4 reps hit 271, 280, 570 and 572 ms.
  Those four are guest-side relaunch variance (the same tail P7 saw: one 540 ms
  rep in 24), and the host was healthy throughout (load1 1.73–2.2, 37.9 GiB
  MemAvailable, host RAM 37 %, recorded per rep in the raw JSON). The settle
  block is `probe-fresh` with `tree_age_ms` 0–1 ms in **all** 24 reps, so the
  outliers are upstream of the reply's evidence step. p95 over 24 samples is
  the 23rd value, i.e. it *is* the outlier; the honest summary is
  "p50 184 ms, 20/24 < 250 ms".
* **M6 has no such tail** (177–213 ms, p95 212.6): a reset's relaunch is the
  same ~175 ms readiness the launch pays, plus stop 13 ms, and it never waits
  for a second probe period either.

## 2. Design

### 2.1 Fast readiness (what the reply proves)

A fast launch/reset reply is produced only when **all** of these hold:

1. the Activity is resumed (the guest's `activity-resumed.marker`),
2. the first traversal has been drawn (a guest probe sample exists, i.e.
   `window-views` was reached),
3. C1 has stored a buffer for it (`generation > 0` — this is the launcher's
   existing `ready` condition and is unchanged), **and**
4. the probe sample the reply binds is bound to a C1 generation **at least as
   new as the store current when the tree request began** (P3b's
   `probe_usable_for_fast_tree`, `launch.rs:2495`), i.e. the tree and the
   `buffer_generation` the reply names describe the same stored buffer.

Nothing is timed, and no quiet window is waited for. If the newest sample
predates the store that was current at request entry, the launcher asks the
guest for one immediate probe (`PROBE` on the session's stdin, P3b's channel)
and waits for that sample; in the measured cohort the sample was always already
fresh (`tree_age_ms` 0–1 ms, `bound:"probe-fresh"`, 24/24).

### 2.2 What strict still is

`strict` is byte-for-byte the old rule: generation advanced, a probe sample
after the last store, **no new store for 150 ms**, then (with `pixels:true`) the
C1 capture. The 150 ms window is untouched
(`launch.rs:2287` `wait_for_settled_observation`, `:2308` `quiet`), as are
`acos_assert` (still refuses `settle:"fast"`), `acos verify` assertions and
every `assert_screenshot`/`assert_region`. No scenario can ask for a fast
assertion.

### 2.3 Pixel-free launch reply (unless pixels are requested)

The launch reply used to pay a C1 clone + PNG encode + write + md5 (~25 ms) whose
pixels it never returned (it published the md5 only). It now defaults to P3b's
metadata identity and copies a PNG only for `pixels:true`:

| `pixels` | `frame` in the reply | cost |
|---|---|---|
| `false` (**default**) | `frame_seq`, `buffer_generation`, `frame_number`, `pixels:false`, `identity:"C1 buffer metadata (no pixel copy)"`, empty `md5` | ~0 |
| `true` | the same identity **plus** `md5` of the captured PNG (P7's reply) | ~25 ms |

`settle:"fast"` + `pixels:true` is refused (`INVALID_ARGUMENT`): a
mid-animation frame can never back a pixel claim, which is the launcher's own
existing refusal for `tree {pixels:true, settle:"fast"}`. A later
`acos_observe {png:true}` is still a real capture and is checkable against the
`buffer_generation`/`frame_number` the launch named — P7's reference check
(launch md5 == settled capture md5) still passes when `pixels:true` is passed
(24/24).

### 4.2 Freshness (the failure mode this must not have)

`evidence/P9/run/freshness-*.json`, 24 reps per row:

| proof | fast | strict |
|---|---|---|
| previous session driven to **count=3**, destroyed, then launch | **24/24 read count 0** | 24/24 read count 0 |
| session at **count=3** (read strictly), then reset | **24/24 read count 0** | 24/24 read count 0 |

Both directions are strict about the *previous* state: the pre-reset count is
read with `settle:"strict"` (a fast tap's own tree may be mid-animation, and a
freshness proof must not rest on that). A fast launch/reset never served a
previous session's tree: the tree in the reply comes from the new guest's own
probe sample, and that sample can only be bound to a C1 generation the new guest
stored.

## 5. What is left, and what was not touched

* The 150 ms strict quiet window is **untouched** (pending owner decision). Fast
  is the opt-in escape hatch; strict remains the default and the only
  assertion-evidence mode.
* Fast launch does not remove guest work: the 184 ms is ~175 ms of real Android
  work plus ~9 ms of evidence. The remaining big phase is the guest's own
  boot-image/ART/`Application` init (P7 §7 #3/#4/#5), which is the Zygote
  track's, not this one's.
* The 4/24 launch outliers are guest relaunch variance, not settle; they were
  present at p50-identical rates before this change (P7: 1 in 24 at 540 ms).
* Not measured: fast launch under concurrency (P5 owns M9), fast launch from a
  cold page cache, and a `fast` variant of `acos verify` (deliberately
  impossible: no scenario can request it).
