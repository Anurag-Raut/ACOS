# W16: the EditText-tap SIGABRT — first error, root cause, fix, and the 5-run repro
# generated 2026-11-11T21:42Z (W16). Supersedes the W13 open race in W13-tap-crash.txt.

## The first error (guest, logd; captured via the launch's structured `logs`)

After `E3G` frame-size fix (see below) the tap reached `InputMethodManager` and the
guest aborted ~0.9 s after READY. The retained logd tail of the failing run:

    ImeTracker | dev.acos.fixtures.textinput:48646c94: onRequestShow at ORIGIN_CLIENT_SHOW_SOFT_INPUT reason SHOW_SOFT_INPUT
    InputMethodManager | showSoftInput() view=android.widget.EditText{...} flags=0 reason=SHOW_SOFT_INPUT
    JavaBinder | assertion failed: env == nullptr Binder thread started or Java binder used, but env null. Attach JVM?
    logdw | pid: 2, tid: 21, name: binder:2_1  >>> dalvikvm64 <<<
    logdw | signal 0 (SIGABRT) ...
    logdw | #00 pc ... /data/shim/libartshim.so (__android_log_assert+452)

The aborting frame is `JavaBBinder::onTransact` (`android_util_Binder.cpp:395`,
`LOG_ALWAYS_FATAL_IF(env == nullptr, ...)`), i.e. a **Java binder received a
transaction on a libbinder pool thread that was not attached to the ART JVM**.

## Root cause chain

1. Tapping the `EditText` runs the stock focus + input path, which calls
   `IAutoFillManager.addClient` (and `IInputMethodManager.showSoftInput`).
   `acos-services::misc::AutofillService` answers the `IResultReceiver` argument
   (correct: a real autofill service does), so the host sends
   `IResultReceiver.send` **to the guest's Java `ResultReceiver` binder**.
2. The guest's E3G binder driver (`crates/acos-binder-peer/native/binder_driver.c`)
   delivers that transaction on libbinder's `binder:2_1` pool thread.
3. The guest never calls `AndroidRuntime::startReg`, which is what installs
   `androidSetCreateThreadFunc(AndroidRuntime::javaCreateThreadEtc)`. Without that
   hook, libutils' `createThreadEtc` creates `canCallJava` threads with the *raw*
   entry point (`androidCreateRawThreadEtc`), so they never `AttachCurrentThread`.
   `JavaBBinder::onTransact` then runs with `env == nullptr` and aborts.
   This is timing dependent: whether the transaction lands on the attached looper
   thread or a pool thread depends on which binder thread first picks it up.

Second, independent adjacent bug found first (it blocked every interactive launch
with the W16 KCM reply, not only taps):

4. `reader_main` in the same driver allocated a fixed **4096-byte** receive buffer
   on a `SOCK_SEQPACKET` socket. The synthetic `InputDevice` reply with the stock
   `KeyCharacterMap` is 6712 bytes, so the kernel truncated the frame
   (`E3G[warn]: truncated frame: need 6768 got 4096`) and the reader thread
   `return`ed, killing all later binder traffic. The app then sat forever after
   `IInputManager.getInputDevice` (`NO_LIVE_FRAME`, `c1_generation=0`). The tiny
   A-only KCM made the reply < 4096 B, which is why the failure tracked KCM size.

## Fixes (both AOSP-shaped, no sleeps, no Java shortcut)

* `binder_driver.c` `reader_main`: size the receive buffer like the host
  (`sizeof(fhdr) + E3G_MAX_FRAME + 64`, the host's `HEADER_SIZE + MAX_FRAME`
  contract) and fail loudly if allocation fails. A `SOCK_SEQPACKET` frame is
  then delivered whole.
* `binder_driver.c` `initAndroidRuntime`: after publishing
  `AndroidRuntime::mJavaVM` (the Q3 fix), resolve `androidSetCreateThreadFunc`
  (libutils) and `AndroidRuntime::javaCreateThreadEtc`
  (`_ZN7android14AndroidRuntime19javaCreateThreadEtcEPFiPvES1_PKcimPS1_`) and
  install the image's own thread shell, exactly as `AndroidRuntime::startReg`
  does. Every future `canCallJava` thread attaches before its entry runs.

No readiness signal was gated and no sleep was added; the tap is honest and
deterministic.
