# H2 — early post-first-frame ART collection as the exec-path product default

**Hypothesis (verbatim).** Requesting one ART concurrent GC right after the first live
frame on the normal exec path (no zygote) cuts memory per session by ~23–30 MiB
(Z7: (a′) vs (a): 491→375 MiB Pss at N=5; +50 % tasks/GiB-min at N=10) without
hurting correctness or agent latency. Make it the product default if the A/B
confirms it, else record the failure.

Worktree `h2` (branch `perf-h2-early-gc`), off `main` `1f21ea7` (includes the Z7
merge). One release binary (`CARGO_TARGET_DIR=.cache/h2-target`, `cargo build
--release --offline -p acos-cli -p acos-art`). Every ART run went through
`tools/art-runtime/run-exclusive.sh` + `tools/guarded.sh --mem 8G` (24G at N=10),
with the lock released between batches.

---

## 1. Mechanism change (the product default)

Z7 left the release behind `ACOS_ART_GC_AFTER_FIRST_FRAME` (off) and issued
`System.gc()` before `VMRuntime.getRuntime().requestConcurrentGC()`.
Z7 measured `System.gc()` inert (gc-count 3 → 3, 0 ms), so H2 removed it. The
guest now issues **one** `requestConcurrentGC()` after the first emitted probe
sample (the host's `ready`, the first live frame) on a daemon thread, and
nothing else. The `trimHeap` branch is removed: it was inert in Z7's reported
arms and no H2 cell used it.

| knob | default | meaning |
|---|---|---|
| `ACOS_ART_EARLY_GC` | **on** | `0` turns the request off (A/B off arm and escape hatch); any other value / unset = on |
| `ACOS_ART_GC_DELAY_MS` | 0 | opt-in research knob; delays the request by N ms (0 = at the first frame) |

`launch.rs` forwards only the host's value to the cleared guest environment, so
an unset variable really means “product default”. Unset is now on, unlike Z7.

Files: `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java` (`maybeEarlyRelease`),
`crates/acos-art/src/launch.rs` (two forwarded variables), `docs/SECURITY.md` row.

**Security.** This is guest-side ART heap work: it changes when the guest returns
its own free region space to the OS, not what the guest can map or write. No
Landlock/seccomp/namespace/rlimit line moved. The SECURITY row was updated to say
default ON and to name `ACOS_ART_EARLY_GC=0`.

**Mechanism check.** Every H2 “on” guest logged
`ACOSLAUNCH EARLY_RELEASE start delay_ms=0 gc_count_before=3` and
`... done ms=0` (20/20 first-action launches; all lifetime/loop cohorts likewise).
The count logged immediately after the request is still 3 because
`requestConcurrentGC` schedules the collection; the pages are returned after the
request returns. That is why the proof of the mechanism is the memory drop and
the Z7 1 Hz series, not the immediate counter reading.

## 2. First action right after launch (counter and form-validation, n=20/arm/app)

Protocol: one fresh `acos-art launch --interactive` per sample; read only `ready`;
then the **first** request is cycled over strict tree (`pixels:false`), fast tree
(`settle:fast`, `pixels:false`) and tap, so no tree precedes the measured action.
The tap point comes from a separate discovery launch and is not counted. ms =
request send → reply. Host x86_64, load recorded in `.cache/h2/runs/host.log`.

| app | arm | n | strict p50/p95 | fast p50/p95 | tap p50/p95 | ready p50 | failures | GC markers |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| counter | off | 20 | 142.0 / 142.3 | 0.2 / 0.3 | 945.1 / 945.6 | 175.7 | 0 | 0/20 |
| counter | on | 20 | 141.7 / 142.0 | 0.3 / 0.3 | 938.9 / 944.8 | 168.0 | 0 | 20/20 |
| form-validation | off | 20 | 141.9 / 142.5 | 0.3 / 0.3 | 170.8 / 172.2 | 174.2 | 0 | 0/20 |
| form-validation | on | 20 | 141.6 / 142.2 | 0.2 / 0.3 | 170.2 / 171.8 | 179.0 | 0 | 20/20 |

The early GC did not delay the first action: counter strict p50 −0.2 %, tap p50
−0.7 %, p95 tap −0.1 %. A delay knob was therefore not needed (kept only as an
opt-in research knob). No first-action request failed on either fixture.

`ready` (first frame); one whole-tree snapshot per child per age at
0.5/2/5/15 s; cell = median of the N child-anchored snapshots. Arms are the same
binary: off = `ACOS_ART_EARLY_GC=0`, on = `ACOS_ART_EARLY_GC=1` (product default
path). Order per rep alternates `off,on` / `on,off`; reps 1–3 were separate lock
acquisitions. Raw: `.cache/h2/runs/memory/rep*/{a,ap}-n*/result.json`.

| N | 0.5 s | 2 s | 5 s | 15 s |
|---:|---:|---:|---:|---:|
| 1 | 28.9 MiB / 12.8% | 29.8 MiB / 13.1% | 30.4 MiB / 13.3% | 29.6 MiB / 13.0% |
| 5 | 144.0 MiB / 27.2% | 149.2 MiB / 27.8% | 153.0 MiB / 28.2% | 145.6 MiB / 27.1% |

The hypothesis was **~23–30 MiB per session**. Measured as whole-tree ΣPss:

* **N=1: 28.9–30.4 MiB less (12.8–13.3 %).** The absolute per-session saving is in
  the predicted band; the smaller percentage is because the N=1 denominator
  (225–229 MiB) is mostly the launcher/bwrap/boot mappings that both arms share.
* **N=5: 144.0–153.0 MiB less = 28.8–30.6 MiB per session (27.1–28.2 %).**
* **N=10: 281.8–300.2 MiB less = 28.2–30.0 MiB per session (31.2–32.5 %).**

`ΣPrivate_Dirty` tells the same story (N=10, 0.5 s: 750.4 → 468.7 MiB; N=5:
383.3 → 238.9 MiB; N=1: 84.1 → 55.5 MiB), which is the collection returning the
guest's freed region space rather than a shared/file accounting artefact.
`SwapPss` is **0.000 MiB** in every cell of every rep. A single un-interleaved N=1 smoke run first appeared
inverted (off 156.3 MiB, on 197.8 MiB); the three interleaved reps do not
reproduce that, and only the interleaved cells above are reported as evidence.

## 4. Real agent loop (fresh launch per task, 1 min per arm/rep)

Protocol: Z7 `loop.py` — round = launch N fresh sessions → one verified task per
session (tree → tap → assert text → screenshot md5) → close the cohort → launch
the next. Every task runs on a freshly launched child. N=5 and N=10, 3
interleaved reps per arm, 1 minute per arm per rep. `tasks/GiB-min` is the
whole-tree **ΣPss** integral (Z7's denominator; the guarded job cgroup misses the
launcher scopes). p50/p95 are launch → verified result for that session.

| N | arm | reps | tasks/GiB-min (Pss) | net anon+shmem | tasks/min | PSS peak MiB | p50 ms | p95 ms | false passes |
|---:|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 5 | off | 3 | 98.8 | 119.1 | 48.52 | 562.3 | 3669.8 | 5979.6 | 0/0 |
| 5 | on | 3 | 135.6 | 171.0 | 48.43 | 522.0 | 3705.8 | 5991.3 | 0/0 |
| 10 | off | 3 | 55.7 | 56.2 | 49.15 | 972.4 | 7072.3 | 11695.6 | 0/0 |
| 10 | on | 3 | 85.9 | 84.8 | 50.59 | 845.6 | 7044.9 | 11623.8 | 0/0 |

Both loops are clean: **0 false passes** in all 12 runs (300/300 tasks at N=5 and
340/340 at N=10; every task is a real tree → tap → asserted value → screenshot
md5, never an acknowledgement). The central objective moves by **+37.2 % at
N=5** (98.8 → 135.6 tasks/GiB-min) and **+54.2 % at N=10** (55.7 → 85.9). The
secondary net anon+shmem integral agrees (119.1 → 171.0 and 56.2 → 84.8).
Throughput is unchanged (48.5 vs 48.4 tasks/min at N=5, 49.2 vs 50.6 at N=10),
and task latency is unchanged within the noise (N=5 p50 +1.0 %, p95 +0.2 %;
N=10 p50 −0.4 %, p95 −0.6 %). PSS peak is 40 MiB lower at N=5 and 127 MiB lower
at N=10. The N=10 off arm's third rep completed 50 tasks rather than 60 in its
1-minute box; the median is reported and every completed task verified.

## 5. Z7's 30 s form-validation tap timeout at N=5

**Reproduced with the GC off, so this is not an H2 regression.** Z7 §7 item 3
reported 30 s `:id/name` tap timeouts on form-validation at N=5. H2 ran the same
protocol (`loop.py --app form-validation --n 5 --cycles 1`) twice per arm:

| arm | run | verified | timed-out taps | tap ms |
|---|---:|---:|---:|---|
| off (`ACOS_ART_EARLY_GC=0`) | 1 | 2/5 | 3 | 30014, 30014, 30016 |
| off | 2 | 2/5 | 3 | 30021, 30011, 30019 |
| on (default) | 1 | 2/5 | 3 | 30011, 30008, 30017 |
| on | 2 | 2/5 | 3 | 30014, 30026, 30008 |

The failure is a 30 s tap bound on `:id/name` (the JSON records `tap_ms ≈ 30010`;
the task then fails because no text was typed). It happens in **both** arms, with
the same count, so it is a pre-existing load/input bug, not caused by the early
collection. It is recorded in `EXPERIMENTS.md` Backlog (H9) with this evidence and
is **not fixed here**, per the H2 brief.

## 8. Verdict

**PASS — the early post-first-frame collection becomes the product default.**

* It saves **28.2–30.6 MiB per session** at N=5/N=10 (27.1–32.5 % of whole-tree
  ΣPss) and **28.9–30.4 MiB** at N=1, at every age 0.5/2/5/15 s, with 0.000 MiB
  swap. This is the predicted ~23–30 MiB band.
* The central objective rises **+37.2 % at N=5** (98.8 → 135.6 tasks/GiB-min) and
  **+54.2 % at N=10** (55.7 → 85.9), with 0 false passes in 640 tasks.
* Agent latency does not regress: loop p50/p95 +1.0 %/+0.2 % at N=5 and
  −0.4 %/−0.6 % at N=10; first strict tree, fast tree and tap after launch are
  unchanged (counter strict 142.0 → 141.7 ms, tap 945.1 → 938.9 ms).
* No correctness, compatibility or security line moves: 7 gates + the 11 p11 gate
  scenarios + K1's five first-frame apps all keep their stages; the 30 s
  form-validation tap timeout at N=5 reproduces with the GC off (pre-existing,
  Backlog H9).

`ACOS_ART_EARLY_GC=0` remains the escape hatch and the A/B off arm.
