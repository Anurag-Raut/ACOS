## 1. The codec (image first)

`IntentFilter.writeToParcel` was dumped from the **image**, not remembered:
`cargo run -p acos-dex --example dexdump -- .cache/boot/android-34/dex/framework/classes.dex --json`
(`classes3.dex` for `PatternMatcher`). The image is **not** the r75 tag: it has
`mMimeGroups`, split `mStaticDataTypes`/`mDataTypes`, two partial-type booleans
and `mExtras`; it has **no** required-permission/title/group-id fields. The
16-group order, the `PatternMatcher` and `AuthorityEntry` payloads and the
`writeStringList`/`writeStringArray` equivalence are in
`docs/IMAGE_ABI_NOTEBOOK.md` §W28.

`parcelable.rs` additions: `FieldOp::StringList` (wire = `int count` + `String16`s,
decoded as `Value::StringList`), three specs (`android.content.IntentFilter`,
`android.os.PatternMatcher`, `android.content.IntentFilter$AuthorityEntry`),
and the scanner matcher for `PersistableBundle` now accepts the nested
`writeParcelable` form the image's `IntentFilter` produces (that is what makes
`codec_field_orders_match_the_framework_dex` report **25/25** instead of 24/25).

## 2. The AMS fake (`atms.rs`, `host.rs`)

`registerReceiver` (code 18) and `registerReceiverWithFeature` (code 19) are
answered in `atms.rs` (the arg indices come from the image's proxy):
`AtmsState::register_receiver` records a `ReceiverRegistration` (receiver binder,
`callerPackage`, `receiverId`, flags, actions, categories, schemes, static/data
types, mime groups, scheme-specific parts, authorities, paths, priority,
partial-type booleans, `autoVerify`, instant-app visibility, order), pushes a
`Debug` log line `ActivityManagerReceiver`, and mirrors the action/category set
into `ams::AmsState` for broadcast matching. The reply is the typed `null`
`Intent` (no sticky store). `unregisterReceiver` (code 20) drops both records.
`broadcastIntent` (code 21) stays in `ams::dispatch`; its match count is answered
and the queued matches are **discarded explicitly** with an
`ActivityManagerBroadcast` "not delivered" line — the ART host has no receiver
scheduler, so it neither fabricates a delivery nor leaks undelivered records.
The test proves the recorded filter drives that count: the registered action
matches exactly once, an unrelated action matches zero times.
`AtmsService::receiver_registrations` + `ServiceHost::receiver_registrations`
are the read-only hooks the tests use.

## 6. Residuals / next walls (ranked)

1. **`ApplicationInfo.flags` omits `FLAG_USES_CLEARTEXT_TRAFFIC` (1<<27)** although
   the APK's manifest has `android:usesCleartextTraffic="true"`. The launcher
   hard-codes `ai.flags = 0x4 | 0x800000` (`acos-art/guest/java/dev/acos/art/LaunchMain.java:1511`)
   and the manifest parser has no `usesCleartextTraffic` model, so
   `NetworkSecurityPolicy` denies RN's `http://localhost:8081` probe. Owner:
   `acos-art` + `acos-apk`. Even fixed, the debug APK needs a Metro server; the
   release APK is the renderable artifact (W25).
2. **`IPackageManager.getComponentEnabledSetting` (code 85, seen 4×) and
   `queryProperty` (code 203)** answer `UNSUPPORTED_ANDROID_API`; RN raises a
   soft `UnsupportedOperationException` and continues. Owner: `pms.rs` (W27);
   request: `getComponentEnabledSetting(componentName, userId)` → the enabled
   setting recorded by the manifest/PMS (default `0`), `queryProperty` → the
   `null` property list.
3. **`IActivityClientController.activityResumed`/`activityIdle` for a
   guest-launched activity** answer `SERVICE_ILLEGAL_STATE` because the host ATMS
   has no `ActivityRecord` for the token (`atms.rs::activity_resumed`). Not
   blocking (the launcher's guest-asserted markers carry the resume, and the ART
   launch path never calls `state.schedule`). The correct fix is a design
   decision — register/adopt the guest's token at `attach`/`activityResumed` —
   not a silent success in the fake; recorded here, not changed.
4. **Verify shorthand-language bug (not W28's)**: `acos verify`'s static manifest
   assertion rejects `package/.Class` even when `package.Class` is declared
   (`W28-gaten-debug-verify.json` is that failure; the APK itself is fine).
   Owner: `acos-verify`/`acos-cli`.
5. **`--json-out` wrote no file** for `acos-art launch` in this run; the JSON is
   the stdout copy at `W28-gaten-debug-launch.json`. Cosmetic, acos-art-side.
6. **Evidence-plumbing inconsistency (not a W28 change)**: the release row's
   `tree/N.json` artifacts each contain only the `DecorView`, while the same
   run's `wait_for {text: exact "Recently looked up"}` passes in 3 ms and the
   frames show the whole home screen (`text_available: true`). W25 recorded 160
   nodes from the same APK. Either the tree artifact is sampled from a different
   probe reply than the selector uses, or it is dumped after the app window is
   gone; the frames are the trustworthy evidence here. Owner: `acos-art`
   session/tree plumbing or `acos-cli` — flagged, not touched.
7. The live tree/frames of the **debug** row are blank (one `DecorView`, three
   identical frame hashes) for the reason in §6.1 — do not read that passing
   scenario as "Gaten's UI renders"; the release row (§3) is that evidence.
