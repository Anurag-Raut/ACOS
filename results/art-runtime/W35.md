## 1. Item 1 — the captured frame is a composite, bottom-to-top

Before: `capture_latest` returned the newest buffer of **one** layer
(`newest_frame_layer`), so the dialog — its own top-level `TYPE_APPLICATION` window
with its own compositor layer above the Activity (W32 §1) — was stored (C1
generation advanced) but never appeared in the frame.

Now (`crates/acos-services/src/surface_client.rs`):

* `capture_composite()` collects every layer with a stored buffer and a non-zero
  alpha, sorts **bottom-to-top by `(z, layer_id)`** (tie-break keeps a frame
  reproducible), and draws each one source-over into a canvas that is the **union
  of the visible layer frames** (crop-clamped). The canvas origin is that union's
  top-left, so a position is `layer frame − canvas origin`.
* Placement inputs, all already decoded: `layer_state_t.x/y/z` and
  `gui::WindowInfo.alpha` from the transaction, with the **window manager's**
  placement (`LayerPlacement`: frame origin, z, `LayoutParams.alpha`, `dimAmount`)
  pushed on every `relayout` by `WmsState::publish_layer_placement` →
  `SurfaceState::set_layer_placement`.
* **The placement is inherited down the parent chain** (`placement_of`, depth ≤ 8,
  cycle-guarded): a window's buffers arrive on the app's BLAST **child** layer
  (`bbq-wrapper`), not on the layer `relayout` created and the WMS placed. Measured
  before the fix: `origin=(0,0) … layer3(z=0 at 0,0) + layer6(z=0 at 0,0)`; after:
  `layer3(1080x2209 z=1 at 0,128 parent=Some(20)) + layer6(776x513 z=2 at 152,976
  dim=0.6 parent=Some(17))` — the dialog's window frame is exactly the
  `ACOS_WMS_TRACE` relayout frame.
* **Dim layer, per its flags.** The image never sends a dim *layer*: the dim is the
  window manager's `mDimLayer`, and its inputs (`FLAG_DIM_BEHIND` 0x2 +
  `dimAmount`) travel in `WindowManager.LayoutParams`. The WMS here is the host, so
  a window with `dimAmount > 0` darkens the canvas already drawn before it is
  drawn itself (stock bounds the dim to the display, so the whole canvas is
  dimmed). Live: `dim=0.6` on the fixture; background `(240,240,243) → (96,96,97)`,
  the dialog card untouched.
* **Caps (S7 style, fail closed, named codes)**: `MAX_COMPOSITE_LAYERS = 16`,
  canvas dims ≤ `MAX_BUFFER_DIMENSION` (8192), canvas bytes ≤ `MAX_BUFFER_BYTES`
  (64 MiB), total layer bytes read ≤ `MAX_COMPOSITE_INPUT_BYTES` (256 MiB), and
  format must be RGBA_8888. A refusal is a `CompositeError` with a
  `COMPOSITE_*` code; `capture_latest` returns `None` and logs the code once
  (`ACOSC1 composite refused: COMPOSITE_TOO_MANY_LAYERS (…)`) instead of handing
  out a partial frame.
* **The label is unchanged**: `capture_source: "acos-c1-buffer"`, and a frame is
  never called a device capture. A composite `FrameCapture` adds `layers` (how many
  were drawn) and `composite: true`; its `layer_name` is `composite(<n>)` and its
  rows are packed (`stride == width`).
* **One layer at the origin passes through unchanged**, including the buffer's own
  stride, so every W10–W32 single-layer frame stays byte-identical (pinned by a
  test row and by `sandbox_c1`'s 1080×2209/stride-1088 control).

Unit tests with teeth (`crates/acos-services/tests/w35_composite.rs`, 7 rows, real
`setTransactionState` wire): two 4×4 layers at `(0,0)`/z0 and `(2,2)`/z1 →
**exact** 6×6 pixels (`RED` under, `BLUE` over, transparent where nothing draws);
dim 0.5 → `(200,100,50) → (100,50,25)` behind the dialog and untouched inside it;
alpha 0.5 white-over-black → exactly `128`; pass-through keeps stride 12 for an
8×4/w=8 buffer; 17 layers → `TooManyLayers`; layers 8185 px apart →
`CanvasTooLarge`; empty registry → `NoFrame`. Against the pre-W35 capture every
composite row shows **one** layer (`layers == 1`), so they all fail.

Live (`results/art-runtime/evidence/W35-repro-dialog-composite.sh`, 02:05:32Z):
`screenshot` before the dialog → `composite(1)`; tap `Show dialog` → `composite(2)`
with the dialog at its window frame; the preview PNG

dimmed Activity and the "Confirm / Are you sure? / Cancel OK" dialog, and the 1:1

## 2. Item 2 — the `Intent` codec, and `startActivity` host-side

`crates/acos-services/src/parcelable.rs` gains a **dynamic** Intent codec (a flat
`FieldOp` spec cannot express recursion or a "presence-in-string" field):

* `write_intent` / `read_intent` in the image's `Intent.writeToParcel` order
  (W32 §3): action/type/identifier/package are **String8**; `data` is
  `Uri.writeToParcel` static (null = `0`); flags int; **`ComponentName` static
  writer — a null component is one null String16 with no presence word**, a
  present one is two String16s; sourceBounds = presence + 4 ints; categories =
  count + String8s; selector/originalIntent = presence + recursive Intent; clipData
  presence; contentUserHint; extras = the existing `read_bundle`/`write_bundle`.
* `read_payload`/`write_payload` dispatch on the class, so the generated
  `WireOp::TypedObject("android.content.Intent")` table entry, `FieldOp::Nested`
  and `FieldOp::Typed` all reach it (that is what makes `startActivity` decode).
* **Structured refusals, not guesses**: a non-null `data` `Uri` →
  `UNSUPPORTED_PARCELABLE(android.net.Uri)` (the image pins only the *static*
  writer); a present `clipData` → `UNSUPPORTED_PARCELABLE(android.content.ClipData)`;
  category count > 1024, nesting > 4, truncation → `SERVICE_BAD_REQUEST`.
* `IntentFacts`' indices are now the **wire's** (`parcelable::INTENT_*`:
  package=5, component=6, categories=8, extras=12) and `to_parcelable` emits the
  full 14-field shape. The old reduced six-slot order silently resolved **no
  component** (`START_NOT_FOUND`, reply `Int(4)`) even though the Intent decoded;
  after the fix the same wire records the launch and answers `START_SUCCESS`.

The request is recorded: `ams::dispatch` → `AmsState::start_activity` →
`PendingLaunch { package, class, intent.action, intent.extras, request_code }`
(`w35_start_activity.rs` asserts the whole chain off the real argument layout:
`binder, package, featureId, Intent, resolvedType, resultTo, resultWho,
requestCode, flags, profilerInfo, bOptions`).

**The second-Activity launch is still W27's structured marker**, and it now fires
from the right place: live `multi-activity`, the Send tap is
`unsupported UNSUPPORTED_ANDROID_API` — *"the app called
android.app.IActivityTaskManager.startActivity and the launcher has no
multi-Activity path; the guest stayed alive and no Activity was fabricated"* —
instead of a decode/assertion failure. The exact guest-side request (not mine to
implement, `crates/acos-art`):

> In `crates/acos-art/src/launch.rs`, when `AmsState` reports a `PendingLaunch`,
> build the stock `android.app.servertransaction.ClientTransaction` with
> `LaunchActivityItem` (`parcelable.rs` already carries the `LaunchActivityItem`
> spec, whose Intent field this codec now satisfies) and deliver it through the
> guest's `IApplicationThread.scheduleTransaction` on the existing `appThread`
> binder; the `LaunchActivityItem` also needs `ActivityInfo`,
> `Configuration` ×2, `ProfilerInfo`, and the token the ATMS will mint.

## 7. Residuals / next wall

1. **Tap in the dialog** (acos-cli, W34): `probe_input_offset` must be per window
   (`bounds_on_screen − bounds` of the node's own root); then `w27-dialog-window`
   can pass 7/7.
2. **Second-Activity launch** (acos-art, W31): the `LaunchActivityItem`
   `ClientTransaction` specified in §2 — the Intent half is now satisfied by this
   codec.
3. **Non-null `data` Uri** (this crate, next): disassemble the image's *static*
   `Uri.writeToParcel(Parcel,Uri)` and add it (a `content://` `startActivity` is
   common for `ACTION_VIEW`).
4. **Composite canvas** is the union of the visible layer frames, not the display
   rect: a frame's height is therefore 2209 (the app window), not 2400. If a
   screenshot should include the system bars, the compositor needs the display
   rect and the status/nav layers (which the host does not create yet).
