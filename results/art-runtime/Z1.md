# Z1 — standalone Zygote-style ART prototype: hook-driven fork, real GC and threads in the children

**Experiment Z1, prototype only.** Nothing under `crates/`, `scenarios/` or `tools/` was
changed. All code lives in `research/zygote-proto/` (4 Java files, 1 C shim, build/run/measure
scripts); the only committed measurement is this file plus
`research/zygote-proto/evidence/Z1-N{1,2,5}.json` (per-process `smaps_rollup` + grouped
`smaps` + timings; the raw `smaps` dumps were 14 MB and are reproducible with
`research/zygote-proto/measure.py`).

Every ART run went through
`tools/art-runtime/run-exclusive.sh --task Z1 -- tools/guarded.sh --mem 8G|10G --time … -- …`;
scratch stayed in `.cache/z1/`; every run ended with no surviving `bwrap`/`dalvikvm64`
(`pgrep -a -f 'dev.acos.z1'` empty).

> **Time box: overrun.** The box was 60 min; this took ~2 h 40 min, almost all of it on two
> environment problems (§5.1 and §5.2) that had to be solved before any of the questions in
> the brief could be answered. Scope was not expanded beyond the brief.

---

## 0. Verdict

| question | answer |
|---|---|
| Do the forked children survive **5 full GCs** + finalization? | **Yes.** 5 `Runtime.gc()` + `System.runFinalization()` per child, ~1 ms each, all 5 children of the N=5 run, plus the late 6th child. ART's own log: `Explicit concurrent copying GC freed … 20MB/26MB` per child. |
| Do they survive **4 contending Java threads**? | **Yes.** `contended=80000 expected=80000` in every child (4 threads × 20 000 monitor acquisitions), 5–10 ms. |
| Do they survive **re-allocation after GC**? | **Yes.** 20 MiB allocated before the GCs, heap 20 597 KiB used / 26 725 KiB total in every child; each child's own region-space live bitmap is private (`PrivDirty` 2 040 KiB). |
| Can the parent **fork again later**? | **Yes.** After N forks + N reaps the parent `preFork()`/`fork()`s a 6th child ("tag=99") and that child does the whole workload too (`fork→ready` 14–19 ms). |
| Do children **stay private** where they must? | **Yes.** `inherited=42` (parent's pre-fork static) is identical in every child; `private=1008/2020/3032/4044/5056` differ per child; `System.identityHashCode(String.class)` is the same object in all (`142058083`). |
| Does everything **get reaped / cleaned up**? | Children exit; **the parent cannot observe the exit status** — `wait4(2)` returns `ECHILD` inside ART (§5.2), a sandbox/ART property, not a zygote property. No leftovers. |
| Is the boot image private-dirty per child, as `D-M2-INVENTORY.md` §1.1 predicted for a re-exec'd image? | **No — 0 KiB private dirty per child.** §3. |

The one thing that is *not* pure Google code is the last line of §1: a pre-fork child needs
`java.lang.Daemons.start()` because `Runtime::StartDaemonThreads` (its only caller) runs in
`Runtime::Start`, which a zygote never executes.

## 1. Hooks used — all AOSP, with the line that matters

Parent, in the same order as `ZygoteInit.main`:

| step | what the prototype calls | AOSP source |
|---|---|---|
| runtime in zygote mode | `dalvikvm64 -Xzygote` | `art/runtime/runtime.cc:1616` (`is_zygote_ = Exists(Opt::Zygote)`) |
| no-thread window on | `ZygoteHooks.startZygoteNoThreadCreation()` | `base/core/java/com/android/internal/os/ZygoteInit.java:768`; native `art/runtime/native/dalvik_system_ZygoteHooks.cc:446` |
| preload | `Class.forName(name, false, null)` over `/system/etc/preloaded-classes` (ZygoteInit's `preloadClass`, capped at `--preload`, 800 in the recorded runs) | `ZygoteInit.java:258-345`, called at `:831` |
| shrink + finalize the pre-fork heap | `ZygoteHooks.gcAndFinalize()` | `ZygoteInit.java:427-428`, called at `:839` |
| no-thread window off | `ZygoteHooks.stopZygoteNoThreadCreation()` | `ZygoteInit.java:846`; native `dalvik_system_ZygoteHooks.cc:451` |
| freeze, per fork | `ZygoteHooks.preFork()` | call site `base/core/java/com/android/internal/os/ZygoteConnection.java:290`; native `dalvik_system_ZygoteHooks.cc:255-263` (CHECKs `IsZygote()`), → `Runtime::PreZygoteFork` `art/runtime/runtime.cc:810-855` → `Heap::PreZygoteFork` `art/runtime/gc/heap.cc:2438-2553` (full GC, `non_moving_space_->Trim()`, `SetupLinearAllocForPostZygoteFork`, `InternTable::AddNewTable`, `ClassLinker::MoveClassTableToPreZygote`, `CreateZygoteSpace` at `:2544`) |
| child side | `ZygoteHooks.postForkChild(0, false, false, null)` | `ZygoteConnection.java` child branch; native `dalvik_system_ZygoteHooks.cc:294-445` (`Heap::PostForkChildAction`, JIT `PostForkChildAction`, `Runtime::InitNonZygoteOrPostFork` `runtime.cc:1195`) |
| parent side | `ZygoteHooks.postForkCommon()` | `ZygoteConnection.java:297`; native `dalvik_system_ZygoteHooks.cc:265-267` → `Runtime::PostZygoteFork` `runtime.cc:857` |
| daemons in the child | `java.lang.Daemons.start()` (reflection, hidden API) | `Runtime::StartDaemonThreads` `runtime.cc:1350-1363` — **only** called from `Runtime::Start` at `runtime.cc:1127`, which a zygote never reaches |

`Heap::PreZygoteFork` is **idempotent** (`heap.cc:2452` early-returns once
`HasZygoteSpace()`), which is what makes fork #2…#N legal: measured `preFork_ms` is 6–7 ms on
the first fork and 1–2 ms afterwards. The parent re-checked and logged
`after_preFork threads=1` (`/proc/self/status:Threads`), which is the invariant
`Runtime::PreZygoteFork` enforces (`runtime.cc:835 CHECK_EQ(tl->Size(), 1u)` + `WaitUntilSingleThreaded`).

**Custom native code: 91 lines of C** (`research/zygote-proto/shim/z1fork.c`), a JNI shim over
`fork(2)`, `wait4(2)`, `getpid`, `getppid`, `rt_sigaction(SIGCHLD, SIG_DFL)` and
`CLOCK_MONOTONIC`, all as raw syscalls (bionic exports `fork`/`waitpid`/`clock_gettime` only
under symbol versions a `-nostdlib` shim cannot bind — measured, §5.1). It exists because no
Java-visible API offers fork: `android.system.Os` has none, and the `Zygote` natives all go
through `ForkAndSpecializeCommon`, which needs SELinux/uid/namespace privileges this
prototype does not have (`com_android_internal_os_Zygote.cpp:2468`). Raw `fork` skips bionic's
`pthread_atfork` handlers, which is safe here *because* `preFork()` has already stopped the
world: one thread, so no other thread holds a libc/allocator lock. That is an argument, not a
proof; a product shim should call bionic's `fork` through a linker-visible wrapper.

`research/zygote-proto/java/dalvik/system/ZygoteHooks.java` is a **signature shadow** (never
loaded — the boot class loader wins) whose signatures were extracted from the installed
`core-libart.jar` with `dexdump`:
`preFork()V`, `postForkChild(IZZLjava/lang/String;)V`, `postForkCommon()V`,
`start/stopZygoteNoThreadCreation()V`, `gcAndFinalize()V`.

## 2. What one child does (identical code runs as the cold control)

`research/zygote-proto/java/dev/acos/z1/Work.java`:

```text
work   prints pid, inherited static, its own private static, identityHashCode(String.class),
       identityHashCode(android.content.Context.class), thread count
alloc  20 × 1 MiB byte[]  (20 MiB live; the child then keeps them)
gc     5 × { Runtime.gc(); System.runFinalization(); }   (+ one line per step)
threads 4 threads × 20 000 × synchronized(LOCK){ }  started, then joined
ready  prints fork→ready (the parent's tFork is inherited through the fork), sleeps, exits 0
```

## 4. Fork-to-ready versus a cold `dalvikvm64` start of the same program

Same `Work.run()` in both; `CLOCK_MONOTONIC` in both; the cold control derives its own start
time from `/proc/self/stat` field 22 (`starttime` jiffies) via `Os.sysconf(_SC_CLK_TCK)`.

| | cold `dalvikvm64` (bwrap → exec) | forked zygote child |
|---|---:|---:|
| to first Java statement / `postForkChild` done | **63 ms** (`exec_to_main_ms`) | **1 ms** (`fork_to_post_fork_ms`) |
| to ready (20 MiB + 5 GCs + 4 threads joined) | **79 ms** (`exec_to_ready_ms`) | **14–19 ms** (`fork_to_ready_ms`) |
| of which the workload itself | 16 ms | 13–18 ms |

Cold numbers: `exec_to_main_ms=63 exec_to_ready_ms=79 work_ms=16` (separate `run.sh cold`
invocation, same argv, same root). The saving is ART boot (image relocation, class-table
setup, 8→7 threads, daemon start), not the workload — ~64 ms per launch, which matches the
`~145 ms` figure in E1C/E1A when the launch also pays framework init.

## 5. Two environment blockers that ate the box

### 5.1 A `-nostdlib` JNI shim cannot bind bionic's `clock_gettime`, `waitpid`, …

`dlopen failed: cannot locate symbol "waitpid"` / `"clock_gettime"` — bionic exports them only
under symbol versions a `-nostdlib` shim does not carry. Fixed by using raw syscalls in the
shim (the same choice `crates/acos-art/shim/artshim.c` makes) and `-fno-stack-protector`
(Ubuntu clang injects `__stack_chk_fail`).

### 5.2 `-Xzygote` forbids an oat file outside /system, /apex — the image had to move

`-Xzygote` sets `Runtime::only_use_system_oat_files_` (`runtime.cc:1626`), and
`OatFileManager::RegisterOatFile` then refuses anything outside the trusted locations
(`LocationIsTrusted`, `art/libartbase/base/file_utils.cc:899`). With the image bound at
`/data/img` (what `crates/acos-art/src/launcher.rs:214` does) the run aborts:

```text
Check failed: … Registering a non /system oat file: /data/img/boot.oat android-root=/system
```

Fix in `run.sh`: hardlink-copy the ART APEX dir (29 MB, links only) and put the image inside it
(`/apex/com.android.art/bootimg/…`), which *is* a trusted location. Nothing under
`.cache/art/sysroot` is written.

### 5.3 `wait4` returns `ECHILD` inside ART (unresolved)

The parent's `wait4(child)` **and** `wait4(-1)` both return `ECHILD` while the child is a real,
live child (`/proc/<pid>/stat` says `ppid` = the parent). It reproduces in a plain **cold**
`dalvikvm64` (no zygote, no hooks), and *not* in `python3` under the identical `bwrap` argv:

```text
waittest child pid=10 ppid=2 exiting 3
waittest parent pid=2 forked=10 wait4_ret=-10 status=0x0 wait4_any_ret=-10 any_status=0x0
```

`ECHILD` from `wait4(-1)` with a live child and `ppid` correct means the kernel considers the
child un-waitable — the signature of `SA_NOCLDWAIT` (children auto-reaped). A raw
`rt_sigaction(SIGCHLD, SIG_DFL)` before forking returns 0 and does not change the result; ART
itself never touches `SIGCHLD` (`grep SIGCHLD art/runtime` → nothing), and neither does the
preloaded `libartshim.so`. Not solved inside the box: **the parent cannot read a child's exit
status**. Consequence for the prototype: the children's own final `child_exit` line plus
`pgrep` are the exit evidence, and "the parent reaps it" holds only in the sense that the
parent calls `wait4` and then finds nothing left to reap.

## 6. What was shared, what was private

**Shared (one physical copy, CoW):** the whole boot image (`.art` anon mappings — 44 KiB
private dirty in total, mapped 6× at N=5), the APEX jars/`.so`s, the preloaded class table
(`MoveClassTableToPreZygote`), the intern table, the pre-fork heap after
`gcAndFinalize()` (`Shared_Dirty` ≈ 61 MiB in every process, one copy), the card table's
pre-fork part, and bionic/linker state.

**Private per child:** the region space and its live bitmap (2 040 KiB), its post-fork
class/intern table entries, its 20 MiB of new objects (LOS/alloc space), its thread stacks,
its `PRIVATE` static, its monitor state, and everything the child writes into the shared
pages (that is what `Private_Dirty` 3.1 MiB per child is).

### 6.1 Two honest observations about the shape

1. **The zygote space is nearly empty (32 KiB).** With a boot image most of what
   `preloaded-classes` names is already image-resident, so `gcAndFinalize()` shrank the
   pre-fork heap to 56 KiB used and `PreZygoteFork` had almost nothing to compact. The
   memory win here comes from **CoW of the image + pre-fork heap**, exactly as
   `D-M2-INVENTORY.md` §3.1 predicted, and *not* from a fat zygote space. A cooler preload
   (no image, thousands of classes resolved into the pre-fork heap) is the case where the
   zygote space would matter; it was not run (out of box).
2. **`-Xzygote` costs the app its `Daemons`.** A forked child has 3 threads at
   `postForkChild` and **dies silently inside `System.runFinalization()`** until
   `java.lang.Daemons.start()` is called (that call is what `StartDaemonThreads` does for a
   non-zygote process). With it, the child has 7 threads and every GC/finalization works.
   This is the one place where "the hooks" are not sufficient on their own, and it is worth
   knowing before anyone builds on `postForkChild`.

## 7. Blockers for the next step (in-process sandboxing after fork)

1. **`wait4`/exit status is unusable inside the sandbox** (§5.3) — a fork server must not
   rely on it, or the SIGCHLD cause must be found. This is the first thing to resolve.
2. **The sandbox is still an `exec`.** `run.sh` re-enters bwrap exactly as `launch.rs` does;
   a forked child that execs bwrap loses the warm image entirely. The next experiment has to
   replace "exec bwrap" with "`unshare(CLONE_NEWUSER|…)` + mounts + seccomp + `setresuid` in
   the child", in AOSP's order (`com_android_internal_os_Zygote.cpp:564-572` mount ns,
   `:2014-2022` seccomp while CAP_SYS_ADMIN is still held, `:2022` `setresuid` last). Nothing
   in Z1 measures that path.
3. **`-Xzygote` + a non-`/system` image is forbidden** (§5.2). A product needs the image (or
   zygote-space equivalent) in a trusted location — i.e. the image must be provisioned into
   the sysroot or an APEX-like bind, not under `/data`. This is a small but real launcher
   change, and it collides with S4's "inputs are read-only" rule only if the image is
   writable (it is not).
4. **`Daemons.start()` is hidden API** and had to be called reflectively with
   `-Xhidden-api-policy:disabled`, which is not a setting a product should ship. Either the
   zygote child's post-fork entry (`ZygoteInit.zygoteInit` → `RuntimeInit`) is reused
   wholesale, or this becomes a curated hidden-API seam.
5. **No hostile-child isolation was tested.** Everything here is one trusted parent forking
   children with identical privileges; the uid/gid/seccomp/cgroup/namespace split is untested,
   and the `32-bit-of-ASLR-variance` problem (`D-M2-INVENTORY.md` §4 option A risk 4) is
   inherited unchanged.
6. **Unmeasured:** CPU cost of N children, teardown behaviour if a child hangs, the USAP
   pre-fork pool, `-Xint` fallback, and a *cold* preload (no image) to see a real zygote space.

```bash
  python3 research/zygote-proto/measure.py --n 5 --hold 6000 --preload 800 \
  --out research/zygote-proto/evidence/Z1-N5.json

  research/zygote-proto/run.sh cold 7 cold        # the cold control
```
