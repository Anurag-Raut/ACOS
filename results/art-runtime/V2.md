`acos verify` now takes an explicit engine and never falls back:

```bash
acos verify --scenario scenarios/v2-art-counter.yaml --engine art     --json
acos verify --scenario scenarios/v2-counter.yaml      --engine rust-vm --json   # default
```

* `--engine` has exactly two values: `rust-vm` (default, existing
  `NativeBackend` path forwarded verbatim) and `art` (`acos-art session`).
  Anything else, and `--engine art` with `--reference` or `--native`, is a
  structured `INVALID_ARGUMENT` — never a silent substitution.
* If ART is unavailable (no binary, no sysroot, session will not start) the run
  fails with `UNSUPPORTED_BACKEND` naming the missing capability
  (`engine.art`, `engine.art.session`, ...). There is no preview fallback.
* The JSON verdict carries `engine`, `mode` (`live` | `preview`),
  `unsupported_steps` (each step index + kind + missing capability) and
  `evidence` (artifacts dir, annotated `verdict.json`, `engine.json`).
  `verdict.json` and `engine.json` are written into the artifacts dir.
* `mode: preview` (P3c-style offline output) can never pass: the CLI downgrades
  a preview `pass` to `unsupported`, adds a `mode.live` failure and a note.
  Only `mode: live` from a launched Activity counts.
* Unsupported steps stop the run and are reported as
  `status: unsupported` / `UNSUPPORTED_BACKEND` with the exact capability
  (`input.type_text`, `input.rotate`, `logs`, `environment`, ...). The README
  scenario (`scenarios/v2-art-type-unsupported.yaml`) pins that behaviour.

## 1. What the ART session must expose (the contract V2 is written against)

The engine talks to one `acos-art session` child over stdin/stdout: one JSON
request line, one JSON reply line. Every command re-traverses, draws and
publishes a **new** frame; `frame_seq` advances only when the pixels are
complete, and a reply that carries `frame_seq` also carries that frame's `png`
path and `md5`, so the tree and screenshot of one observation can never come
from different traversals.

| protocol command | request | reply (fields the engine relies on) | supported today | engine capability | gate |
|---|---|---|---|---|---|
| ready | — (first stdout line) | `ok`, `package`, `activity`, `width`, `height`, `frame_seq`, `png`, `md5` | **yes** | `launch` | `engine.art.session` |
| `tree` | `{"cmd":"tree"}` | `tree` (`class`, `id`, `text`, `bounds`, `clickable`, `visibility`, `children`), `frame_seq`, `png`, `md5` | **yes** | `tree` / `screenshot` | `ui.tree` |
| `screenshot` | `{"cmd":"screenshot"}` | `frame_seq`, `png`, `md5` (no tree) | **yes** | `screenshot` | `screenshot` |
| `tap` | `{"cmd":"tap","x":INT,"y":INT}` | `frame_seq`, `png`, `md5`, `tree`, `tap.handled` | **yes** | `tap` | `input.tap` |
| `tap_text` | *host-side*: `tree`, find node text, tap its centre | as `tap` | **yes (host-side)** | `tap_text` | `input.tap_text` |
| `key` | `{"cmd":"key","code":ANDROID_KEYCODE}` | `frame_seq`, `png`, `md5`, `key.handled` | **yes** | `key` | `input.key` |
| `reset` | `{"cmd":"reset"}` | `frame_seq`, `png`, `md5`, `tree` (fresh Activity) | **yes** | `reset` | `reset` |
| `close` | `{"cmd":"close"}` | `ok`, then the process exits | **yes** | `close` | `engine.art.close` |
| `type_text` | `{"cmd":"type","text":STR}` **missing** | — | **no** | `type_text` | `input.type_text` |
| `rotate` | `{"cmd":"rotate","orientation":STR}` **missing** | — | **no** | — | `input.rotate` |
| `back` | use `key` with code 4 (available), or a dedicated command | — | via `key` | `key` | `input.back` |
| `logs` | `{"cmd":"logs","since":N}` **missing** | — | **no** | `logs` | `logs` |
| crash report | `{"cmd":"crash"}` / crash fields on replies **missing** | — | **no** | `crash_reports` | `crash_reports` |
| environment | `set_network`/`set_permission`/`set_locale`/`set_density`/`set_theme`/`set_time` **missing** | — | **no** | `environment` | `environment` |

Protocol rules the engine depends on (already true in `session.rs`):

1. One reply line per command; `ok:false` carries `code` + `error`.
2. `png` is a **host** path (`host_reply` maps `/data/...` → data dir); the
   engine reads at most 64 MiB and never re-encodes it.
3. `frame_seq` is monotonic and advances only on a completed frame; an action
   that changes no pixels keeps the old seq (honest `NO_FRESH_FRAME`).
4. A reply carrying `tree` also carries the `png`/`md5` of that same frame.
5. `close` releases the process; the engine also kills the child's process
   group on drop (bounded startup/command timeouts, bounded line + stderr
   buffers, no orphans).

## 2. Engine abstraction (`crates/acos-cli/src/engine/`)

| file | contents |
|---|---|
| `engine/mod.rs` | `Engine {rust-vm,art}`, `Mode {live,preview}`, `SessionBackend` (`launch`, `tree`, `screenshot`, `frame`, `capture`, `tap`, `tap_text`, `type_text`, `key`, `reset`, `close`, `capabilities`), `SessionCapabilities` (supported/missing command names), `EngineBackend` (adapts to `acos_verify::Backend`), `ui_tree_from_json`, `preview_downgrade` |
| `engine/art.rs` | `ArtSession`: spawns `acos-art session --apk … --out …`, process group + timeouts + bounded buffers, line-JSON relay, host-side `tap_text`, `Mode::Live` |
| `engine/rust_vm.rs` | `RustVmSession`: the existing VM route behind the same trait (the default `rust-vm` path still forwards to `NativeBackend` verbatim) |
| `engine/fake.rs` | `#[cfg(test)]` deterministic counter session (live and preview) so the whole path is tested without an ART sysroot |

`EngineBackend` derives the executor's `Capabilities` from
`SessionCapabilities`, so a capability cannot be advertised without a command
behind it. `id()` is `acos-art-session` for ART; ART fidelity is
`art-reference`, preview is `simulated`.

## 3. Tests (`cargo test -p acos-cli`)

| test | asserts |
|---|---|
| `counter_scenario_passes_through_the_art_backend_path_live` | `scenarios/v2-art-counter.yaml` runs through `EngineBackend::session`: launch → tree → tap → `0`→`1` → fresh capture → reset → tap → `1`; verdict `pass`, `engine: art`, `mode: live`, 2 taps, real `tap(x,y)` reached the backend, no `type_text` |
| `preview_backend_never_yields_a_pass` | the same steps with `Mode::Preview` produce a `pass` run that is downgraded to `unsupported` with `mode: preview` and capability `mode.live`; the written `verdict.json` agrees |
| `unsupported_step_names_the_missing_capability_and_never_falls_back` | `scenarios/v2-art-type-unsupported.yaml` stops at `type` with `UNSUPPORTED_BACKEND` + `input.type_text`; a Rust-VM probe backend records **zero** calls |
| `art_session_capabilities_report_the_protocol_gaps` | supported = launch/tree/screenshot/tap/tap_text/key/reset/close; missing = type_text/logs/environment/crash_reports |
| `art_capabilities_name_the_protocol_gaps` / `keycodes_cover_the_art_protocol` | the capability table and keycode map match §1 |

Existing Rust VM behaviour is unchanged: the `rust-vm` branch still wraps
`NativeBackend` (or `ReferenceBackend` with `--reference`) with no adapter in
between; `tests/verify.rs` and `tests/negative_verify.rs` pass unchanged.
