# I2 — a host-injected tap travels the real InputChannel into `counter.apk` and increments it (0 → 1); key events are delivered and acked

**Status: DONE for the OUTCOME (tap accepted), PARTIAL for focus/key activation.**
The window session now hands the guest **one authoritative fd** from I1's producer
registry keyed by the `IWindow` token. A real launch with
`ACOSLAUNCH_HOLD_MS` + `ACOS_INPUT_TAP=176,303` publishes image-layout
`ACTION_DOWN`/`ACTION_UP` on that socket, the guest's real
`InputEventReceiver`/`ViewRootImpl`/`View` path receives them, the framework posts
`View$PerformClick`, `AcosCounter: increment value=1` is logged, the counter
TextView is `1` in the read-only live view-tree probe, and the host dispatcher
sees `FINISHED handled=true` for both sequences. Key events are delivered and
acked (`handled=false`) but dropped by the framework with
`Dropping event (no window focus)` because **window focus** is blocked by an
adjacent IME parcel-codec wall (below). No fake input, no direct `onClick`.

## 1. Wiring

- `WindowSessionService::with_input(InputHost::from_env())` is installed by
  `registry::install` next to the compositor.
- `addToDisplayAsUser`: `InputDispatch::register_window(token, name)` creates the
  I1 `SOCK_SEQPACKET` pair, publishes the real `TOUCH_MODE(true)` (and
  `FOCUS(true)` only under `ACOS_INPUT_FOCUS=1`), then `write_and_forget` writes
  `[1][1][token][name][fd]` and drops our client copy. `acos-wm`'s private
  channel is no longer the guest's input fd.
- `relayout`: the **first** relayout signals a worker thread; after
  `ACOS_INPUT_DELAY_MS` (default 200) it publishes `DOWN`+`UP`, then polls
  `FINISHED`/`TIMELINE` for `ACOS_INPUT_ACK_MS` and logs them. Repeated
  relayouts do not re-inject.
- `remove`: `InputDispatch::remove(window)` drops the server end; the guest's end
  sees EOF (test `remove_closes_the_guest_end`).
- Diagnostic gate: when an injection plan is active, the session **holds**
  `IWindow.dispatchAppVisibility(true)` and logs it. Reason measured in W6: the
  visibility callback makes the first traversal enter
  `drawSoftware` → `Surface.nativeLockCanvas`, which blocks the **main looper**
  (no buffer yet); input is dispatched on that same looper, so a tap would never
  run. The tap itself is still the real socketpair/InputChannel path. Remove
  this gate when the first buffer lands.

## 2. Wire fact corrected: FOCUS is 0x10

I1 recorded `FOCUS = 8` from a hand count. The image's `InputMessage::size()`
jump table returns `0x10`; `publishFocusEvent` writes `eventId` at `0x08` and
`hasFocus` at `0x0c`. Implemented and pinned with a golden test. `FOCUS` is also
the real focus path (`InputEventReceiver.onFocusEvent`), not an `IWindow`
transaction — consistent with W6's finding that API-34 `IWindow` has no
`windowFocusChanged`.

## 3. Why the tap carries its point in the message transform

First accepted tap run (`tap_final`): pointer coords `bits=0x3f, x=176,
y=303`, message length 312 (`0x138`), image-exact; yet a listener on the real
Button saw `x=0.0 y=0.0` and the event hit the Toolbar at `(0,0)`. Putting the same point in `MotionEvent.transform.tx/ty` with the
window/raw transform (message fields at `0x68`, first six floats) and neutral
pointer axes made the framework deliver raw `(176,303)` and view-local
`(134,63)`, posted `View$PerformClick`, and incremented the counter. This is
still an image-layout `InputMessage` (the transform is part of
`publishMotionEvent`'s body); it is not a Java shortcut. The exact native reason
pointer axes are dropped is left as the ledger's untested alternative.

## 5. Next walls (precise)

1. **IME `EditorInfo` parcel codec** (focus/key activation): image
   `IInputMethodManager.startInputOrWindowGainedFocus` arg 6 is
   `TypedObject(android.view.inputmethod.EditorInfo)`; the host's generic codec
   throws `no parcelable codec`, and the guest's main looper dies. Until then
   `FOCUS` stays opt-in and keys are delivered-but-dropped.
2. **First buffer** (removes the visibility gate): W6's
   `Surface.nativeLockCanvas` condvar wait must be fixed so the main looper is
   free with the window visible; then delete the injection-mode
   `dispatchAppVisibility` hold.
3. Native frame for #3 if coordinate fidelity through axes is required.
