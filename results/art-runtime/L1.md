## 3. The walls, in order, with the guest's own stack

### 3.1 `android.view.SurfaceControl.nativeGetNativeSurfaceControlFinalizer` missing
`ViewRootImpl.<init>` line 670 (`SurfaceControl$Transaction`) — the first thing the constructor
touches after W1 closed `openSession` (`:997`). Fix: register the class's natives in the guest
(§2). No chicken-and-egg: `RegisterNatives` uses `FindClass`, which does not run `<clinit>`.

### 3.2 `android.view.SurfaceSession.nativeCreate` missing
`ViewRootImpl.java:724` `new SurfaceSession()`. Fix: `register_android_view_SurfaceSession`.
`nativeCreate` then calls `SurfaceComposerClient::onFirstRef` → `createConnection`, which is
**still stubbed** (V1 code 3, structured `UNSUPPORTED_ANDROID_API`) — see §4. It is not fatal:
`SurfaceSession` keeps a client with `NO_INIT` and the constructor continues, which is exactly
the honest "no compositor" state.

### 3.3 `getService("SurfaceFlingerAIDL")` failed: `Status(-129, EX_TRANSACTION_FAILED): 'BAD_TYPE: '`
Two independent causes, both real:
* the image asks the **AIDL** name (V1 registered only `SurfaceFlinger`);
* more important, our transport wrote **stability = SYSTEM after a null binder**. libbinder's
  `Parcel::unflattenBinder` → `finishUnflattenBinder` → `Stability::setRepr(nullptr, level, log)`
  returns `BAD_TYPE` for any level other than `UNDECLARED`, so *every* null-binder reply (any
  `getService` miss) failed to parse. Fixed in `frame_from_parcel` + the name alias.

### 3.4 `stealReceiveChannel` failed: `'PERMISSION_DENIED: '` + "Attempt to read from protected data in Parcel"
The AIDL proxy reads the out `BitTube` with `Parcel::readParcelable` (image: `libgui.so`
0x161475 `call Parcel::readParcelable`), which reads an `int32 present` **before**
`BitTube::readFromParcel`. V1 wrote `status + fd + fd`, so the framework read the present flag
out of the first `flat_binder_object`, overlapping the object table → `validateReadData` →
`PERMISSION_DENIED`. Fixed by writing `1` (§2).

### 3.5 `stealReceiveChannel` failed: `'-9 (Bad file descriptor): '`
`BitTube::readFromParcel: can't dup file descriptor (Bad file descriptor)`. The descriptors the
peer sent (traced: `out ty=2 seq=80 … fds=[8, 14]`) were received by the guest driver and then
**dropped on the floor**: the F_RSP path copied data/offsets but not the SCM_RIGHTS fds, so the
FD objects kept the peer's fd numbers, and a later attempt closed them at build time. Fixed in
the driver (§2), matching the kernel's "the fd lives until the receiver frees the buffer" rule.
`E3G[warn]: BINDER_TYPE_FD in incoming parcel but no fd was received` is gone.

### 3.6 `ViewRootImpl.setView` → `addToDisplayAsUser` → `RuntimeException: Adding window failed`
```
java.lang.RuntimeException: Adding window failed
  at android.view.ViewRootImpl.setView(ViewRootImpl.java:1340)
  at android.view.WindowManagerGlobal.addView(WindowManagerGlobal.java:411)
```
`unsupported.jsonl` (last record):
```
{"code":2,"descriptor":"android.view.IWindowSession","error":"SERVICE_INTERNAL",
 "method":"addToDisplayAsUser",
 "message":"internal service error: android.view.IWindowSession: LayoutParams: parcel: object at 200 is not a binder (type 0x00000000)"}
```
Cause (code, not guess): `PhoneWindow`'s `LayoutParams.token` is **null** in this launch (the
activity token is null, P4b §3), and libbinder writes a null binder as **24 zero bytes + a 4-byte
stability int that is NOT in the object-offset table** (`Parcel::flattenBinder` →
`writeObject(obj, false)`, then `finishFlattenBinder`). `peer::import_parcel_raw` strips the
4-byte stability record only for objects that *are* in the table, so a request containing a null
binder desyncs by 4 bytes from that point on; W1's `LayoutParams` decoder then finds a zero type
where the `IWindow`/token binder should be. **This is the transport bug to fix next** (either
`import_parcel_raw` learns the null-binder rule from the argument table, or the codec reads the
wire form with the record inline). It is not a W1 wire-order bug: the bytes before the token
decode.

### 3.7 `dispatchVsync` → `SIGSEGV` in `AndroidRuntime::getJNIEnv`
Once §3.5 was fixed the vsync event reached the looper and the *dispatch* crashed:
```
signal 0 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr --------
Cause: null pointer dereference
#00 android::AndroidRuntime::getJNIEnv()+37              libandroid_runtime.so
#01 android::NativeDisplayEventReceiver::dispatchVsync(…) libandroid_runtime.so
#02 android::DisplayEventDispatcher::handleEvent(int,int,void*) libgui.so
#03 android::Looper::pollOnce(…)                          libutils.so
#04 android_os_MessageQueue_nativePollOnce               libandroid_runtime.so
```
The launcher *constructs* `AndroidRuntime` (so `gCurRuntime` is set) but never calls `start()`,
so the image's `getJNIEnv` — which dereferences the **static data member**
`AndroidRuntime::mJavaVM` (`mov GOT(mJavaVM),%rax; mov (%rax),%rdi; call *0x30(vtable)`) — sees
null. Fix: publish `GetJavaVM()` into the exported `_ZN7android14AndroidRuntime7mJavaVME`
symbol. Not at object offset 0: the constructor puts the **vtable pointer** there (verified in
the image's `AndroidRuntime::AndroidRuntime` disassembly), which is why the first attempt (writing
offset 0) did not help and would have corrupted the object.

### 3.8 The surviving vsync NPE (next, V1's side)
With §3.7 fixed, the callback runs and then throws:
```
ACOSLAUNCH TRACE >>>>> Dispatching to Handler (android.view.Choreographer$FrameHandler) … : 0
java.lang.NullPointerException: Attempt to read from field 'int android.view.DisplayEventReceiver$VsyncEventData.frameTimelinesLength'
    on a null object reference in method 'android.view.Choreographer$FrameTimeline android.view.Choreographer$FrameData.update(long)'
  at android.view.Choreographer$FrameData.update(Choreographer.java:1170)
  at android.view.Choreographer.doFrame(Choreographer.java:832)
  at android.view.Choreographer$FrameDisplayEventReceiver.run(Choreographer.java:1322)
```
The vsync **arrived** (that is the goal's proof) but the Java `VsyncEventData` the native
`dispatchVsync` hands to `Choreographer.FrameData` is null. The 216-byte event encodes
`frameTimelinesLength = 1`; the image's `dispatchVsync(long, PhysicalDisplayId, uint32,
gui::VsyncEventData)` builds the Java object from it, so the null means the payload/shape it
reads is not what we write (V1's `PackedVsyncEventData::readFromParcel` order or the
`Event` union offsets). One codec finding, not a launch finding.

## 6. Limits / not done

- `handleResumeActivity` does not complete: the launch stops at `addToDisplayAsUser` (§3.6). No
  `relayout`, no `performTraversals`, no window.
- No real surface: G1's gralloc interposer is not landed (`results/art-runtime/G1.md` absent,
  `crates/acos-art/shim/gralloc_shim.c` untracked). Even after §3.6 the relayout reply's
  `SurfaceControl` is W1's structural placeholder, so drawing would still not produce pixels —
  that is the honest next rung, not a workaround here.
- The vsync callback currently ends the run with an NPE in `FrameData.update` (§3.8). It is
  therefore behind `ACOSLAUNCH_FRAME_PROBE=1`; the default run keeps the activity path (and is
  timing-independent). `results/art-runtime/l1/vsync-callback.log` is the probe run that fired.
- `SurfaceFlingerAIDL` and `SurfaceFlinger` are the same node, one connection pool: two
  `DisplayEventReceiver`s in one process share the 4 pre-allocated slots (V1 §10).
- Reply buffers in the driver are not `mm_free`d (pre-existing: `BC_FREE_BUFFER` logs "ignored");
  the new fd table is bounded at 128 buffers and closes on free. Not a leak of fds, a leak of
  bump-allocator bytes in the guest.

## 8. Process note (the overrun)

The 60-minute checkpoint was passed with §3.4/§3.5 half-diagnosed; stopping there would have
left `stealReceiveChannel` failing with no explanation, which is worse for the next agent than
the overrun. Total ~95 min, no commit. The overrun bought: the null-binder stability bug (a
transport-wide defect — every `getService` miss was silently `BAD_TYPE`), the reply-fd lifetime
rule, the `mJavaVM` bootstrap, and the first end-to-end vsync dispatch.

**Smallest next action (one change, ~20 lines):** make the peer's `import_parcel_raw` handle the
null-binder stability record, i.e. strip 4 bytes after every *null* binder object as well
(the object-offset table does not list null binders; `read_args` knows the binder arguments, so
doing it in the codec reader with a "wire form" flag on `Parcel` is the precise version). That
turns `addToDisplayAsUser` from `SERVICE_INTERNAL` into a W1 reply and moves the wall to
`relayout` / the missing real `SurfaceControl`.
