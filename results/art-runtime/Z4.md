# Z4 — N sessions forked from ONE pre-initialised ART zygote: memory, isolation, security

**Research prototype, Zygote track step Z4.** The blocker from Z3 §6.1 ("the launcher accepts
exactly one guest") is solved with an env-gated seam that is **off by default**: with every
`ACOS_ZYGOTE_*` variable unset, the launcher's argv, class path, guest dex, bind list, seccomp
preload, run dir and socket dir are exactly what they were. Everything else lives in
`research/zygote-proto/{z3,z4,shim}`.

Every ART run went through
`tools/art-runtime/run-exclusive.sh --task Z4 -- tools/guarded.sh --mem 8G|16G --time 300|600 -- …`;
scratch stayed in `/home/Qui/Projects/acos/.cache/z4-*` (never `/tmp`); `free -m` was checked
before each run (host stayed under 90 % — 38 GiB available). **Time box: overrun** (see §9);
the six-run matrix and the N=2/5 security pass are complete, N=10 was not run.

---

## 0. Verdict

| objective | result |
|---|---|
| Blocker: one launcher = one guest | **Solved.** N independent `acos-art` launchers keep their own ServiceHost/InputHost/C1 and sockets; one zygote forks one child per session; each child enters its session's mount view and re-enters the **unmodified** `LaunchMain.main`. |
| N = 1, 2, 5 both paths | **All six configurations pass** (18 sessions total): count `0 → 1`, strict settled frames, cross-session isolation, identical pixels. |
| Isolation (the check that matters) | **Pass.** Tapping session K gives `1` only in K; every not-yet-tapped session re-reads `0` after each tap (15 ordered checks at N=5). |
| Pixel equality | **0 px diff.** Every one of the 18 sessions produced the *same* PNG bytes as the normal path: initial md5 `39d1e4e3633d98d76b992edb4b250a78`, after tap `9f3406c1627beef270f8cfddf9f61973` (the same two md5s as Z3). |
| Memory, marginal per session (guest tree) | **55.9 MiB/session zygote vs 79.2 MiB/session normal = 29.4 % saving**; as implemented with the research tombstone stubs 78.4 vs 92.6 = 15.3 %. |
| % saving at N = 5 | **14.6 %** guest tree / **6.6 %** as implemented whole system. N = 1 the zygote **loses 8.2 %**. |
| fork → first correct frame | **fork→postForkChild 1 ms, fork→sandboxed+guard+ready 5 ms**, then the app's own ~150 ms to first frame. |
| N = 10 | **Not run** (time box). Projection from the measured marginal: 21.0 % guest-tree / 10.4 % as-implemented saving. Clearly labelled as a projection. |

## 1. Design: one zygote, N sessions, N launchers

Mirrors Android (zygote + one connection per app) and keeps "one launcher = one session", so no
system-service state is shared between sessions:

```text
driver (research/zygote-proto/z4/drive.py)
├── session dirs  <root>/sessions/<k>/{run,sock,argv,binds,guest.fifo,pid}
├── launcher k (acos-art, k=1..N-1)   foreign-guest mode: own run root, own sockets,
│                                     own ServiceHost/InputHost/C1, own logd; spawns a
│                                     tombstone (`/system/bin/sleep`) and waits for a guest
└── launcher 0 (acos-art)             same, plus ACOS_ZYGOTE_APP: it spawns ONE
     └── bwrap sandbox 0             `dalvikvm64 -Xzygote dev.acos.art.ZygoteApp`
         └── zygote (pre-app init once: JNI table, overlays, driver load, 34 classes,
             │                        gcAndFinalize, preFork)
             ├── child 0  A(z4ns) → B(z4init, PID 1) → C(app, PID 2) → LaunchMain.main(argv0)
             ├── child 1  ... same, binds /sessions/1/... → LaunchMain.main(argv1)
             └── child k  ... each in its own user+mount+pid namespace
```

**Why this shape and not a multi-peer launcher:** `interactive_serve`'s peer, `ServiceHost`,
`InputHost`, C1 and `logd` are built per launch (`launch.rs:322-455`, `:560-700`); turning them
into a multi-session host would be a redesign of the product's session model (the decision doc
forbids "unnecessary redesign of system services or C1"). Keeping N launchers costs ~17 MiB Pss
each (measured, same as the normal path) and buys exact session isolation of every host object.

### 1.1 The seams (all env-gated, unset ⇒ production unchanged)

| seam | file:line | what it does when set |
|---|---|---|
| `ACOS_ZYGOTE_SESSION=<dir>` | `crates/acos-art/src/launch.rs:191-196` | foreign-guest session: run root `<dir>/run` (`lib.rs:254` `run_dir_at`), socket dir `<dir>/sock` (`launch.rs:1518` `ShortSocketDir::at`), no `ShortSocketDir`/`RunDir` deletion (`:1527`, `lib.rs:282`) |
| session contract | `launch.rs:621`, `:1539-1580` `write_zygote_session` | writes `<dir>/session.json` and `<dir>/argv` (one guest argument per line) atomically, **after** the listener exists |
| no guest spawn | `launch.rs:743-751` | spawns `/system/bin/sleep` (the sysroot's own toybox) in the session's bwrap/cgroup instead of ART; the launcher still serves its peer, so readiness/teardown semantics are unchanged |
| per-session guest output | `launch.rs:737-742`, `:825-845` | creates `<dir>/guest.fifo`; the child `dup2`s it onto stdout/stderr (`z2fork.c:654-667`) and the launcher parses **that** stream, so each launcher sees only its own child's `ACOSPROBE` lines |
| guard ordering | `launch.rs:642-655` | foreign mode does **not** preload the guest seccomp/Landlock stub into the zygote (it would block the child's `unshare`/`mount`); the child loads the *same* production `.so` after its mounts (AOSP order). The `/data/seccomp` blob + Landlock plan are the production artefacts; only the `.so` is recompiled with `-fno-stack-protector` because a `System.load` from a classloader namespace cannot resolve bionic's hidden `__stack_chk_fail` (Z4 §6) |
| plan dir | `launch.rs:661-668` | binds the host plan dir at `/sessions` (rw) and forwards `ACOS_ZYGOTE_SESSIONS=/sessions`, `ACOS_ZYGOTE_N` |
| security probe switch | `launch.rs:671-673` | forwards `ACOS_ZYGOTE_PROBE` for the ZS evidence (research only) |

Everything else is research code: `research/zygote-proto/z3/java/dev/acos/art/ZygoteApp.java`
(the N-session loop, `:119-200`), `research/zygote-proto/shim/z2fork.c`
(`spawnSession` at `:598-700`, bind list at `:237-300`), `research/zygote-proto/z4/drive.py`.

### 1.2 What each child does (in this order — AOSP's order)

`fork` → `unshare(CLONE_NEWUSER)` + map → `unshare(NEWNS)` → `unshare(NEWPID)` → fork B (PID 1)
→ B: `mount / MS_REC|MS_PRIVATE`, apply `<dir>/binds` (`src<TAB>dst`, `MS_BIND|MS_REC`), fresh
`/proc` → fork C → **C**: `System.load(libacos_seccomp_guest.so)` (Landlock + the production
seccomp blob) → `Daemons.start()` → `LaunchMain.main(argv_k)`.
`unshare(CLONE_NEWUSER)` **must** run before `ZygoteHooks.postForkChild` (it is `EINVAL` for a
multithreaded caller, and `postForkChild` restarts ART's threads — this was the first Z4 bug).

The per-session binds (written by the driver from the launcher's own contract):
`run/{dalvik-cache,misc,tmp,out,task,app-data,app-lib}` → the same `/data/*` paths,
`<dir>/sock` → `/dev/socket`, `<dir>/sock/peer.sock` → `/data/acos-launch.sock`. The guest's
`dataDir` in ACOS is `/data/app-data/<pkg>` (not `/data/data/<pkg>`), so that bind is the
"private app data" the brief asks for.

**No app is ever in one Java process:** every child is a fresh `fork()`, and every child gets
its own user/mount/pid namespaces and its own seccomp/Landlock guard.

## 2. Verification (strict settled frames, every N, both paths)

`--until activity-resumed`, `ACOSLAUNCH_FRAME_WAIT_SECS=30`, real InputChannel taps, and the
launcher's own `wait_for_settled_observation` (not a sleep). Reports:
`.cache/z4-run/{normal,zygote}-{1,2,5}.json`, raw guest logs next to them.

| N | path | sessions | tree 0 → tap → 1 | isolation (others stay 0) | md5 initial / after tap | verdict |
|---:|---|---|---|---|---|---|
| 1 | normal | 1 | 0 → 1 | — | `39d1e4e3…` / `9f3406c1…` | **pass** |
| 2 | normal | 2 | 0 → 1 (×2) | 1 check | identical | **pass** |
| 5 | normal | 5 | 0 → 1 (×5) | 10 checks | identical | **pass** |
| 1 | zygote | 1 | 0 → 1 | — | identical | **pass** |
| 2 | zygote | 2 | 0 → 1 (×2) | 1 check | identical | **pass** |
| 5 | zygote | 5 | 0 → 1 (×5) | **10 ordered checks** | identical | **pass** |

At N=5 the ordered sequence is: tap 0 → (1,0,0,0,0), tap 1 → (1,1,0,0,0), tap 2 → (1,1,1,0,0),
tap 3 → (1,1,1,1,0), tap 4 → (1,1,1,1,1); every cell is read from a *new* settled `tree` reply.
**0 px diff:** all 18 sessions produced byte-identical PNGs at both steps, and the same bytes as
Z3's normal path — the zygote path is not "similar", it is the same C1 buffer generation.

The tap is never credited by its ack: the count and the pixels are re-read on new settled
frames, and the isolation reads come from the *other* sessions' launchers.

## 3. Memory (KiB → MiB, `smaps_rollup`, held after the tap, same method both paths)

Roles from `/proc/<pid>/comm` + argv. `guest tree` = the ART side (zygote + app children +
`z4ns`/`z4init` helpers); `whole` = the driver's entire process tree (launchers, bwrap, stubs).
Raw: `.cache/z4-run/*.json` (`memory.processes`, `sum_by_role`, `total`).

### 3.1 Per-N totals (MiB)

| N | path | guest-tree ΣPss | guest-tree ΣPD | whole ΣPss | whole ΣPD | launchers | bwrap | stubs |
|---:|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | normal | 206.2 | 76.8 | 234.7 | 98.5 | 16.8 | 0.3 | — |
| 2 | normal | 281.2 | 148.5 | 322.6 | 182.8 | 29.0 | 0.5 | — |
| 5 | normal | 523.0 | 388.3 | 605.0 | 462.5 | 67.4 | 1.2 | — |
| 1 | zygote | 223.1 | 46.6 | 251.5 | 68.3 | 16.9 | 0.0 | 0.0 |
| 2 | zygote | 259.7 | 94.8 | 315.8 | 133.8 | 29.0 | 0.3 | 15.4 |
| 5 | zygote | 446.7 | 287.0 | 565.1 | 381.4 | 67.4 | 1.0 | 36.4 |

The zygote's own process and the children, N=5 (per-process Pss / PD, MiB): zygote parent
**39.8 / 0.6**, each app child **76.1–76.2 / 57.2–57.4**, each `z4ns` **2.7 / 0.0**, each
`z4init` **2.5 / 0.0**. At N=1 the zygote parent was 39.8 and the child 76.1 (whole guest tree
223.1): the pre-fork core is **~40 MiB Pss**, not the 87.5 MiB Z3 measured for a single child
(because here it is apportioned over 1 parent + 5 children).
`Shared_Dirty` grows 143.2 → 236.4 → 541.5 MiB across N = 1/2/5: that is the **one physical copy**
of the pre-fork heap + boot image, mapped by every process and divided by Pss.

### 3.2 Versus the normal path at the same N

| N | guest tree: normal → zygote | saving | whole system: normal → zygote | saving |
|---:|---|---:|---|---:|
| 1 | 206.2 → 223.1 | **−8.2 %** (loss) | 234.7 → 251.5 | −7.1 % (loss) |
| 2 | 281.2 → 259.7 | **+7.6 %** | 322.6 → 315.8 | +2.1 % |
| 5 | 523.0 → 446.7 | **+14.6 %** | 605.0 → 565.1 | +6.6 % |
| 10 | *projection* 919 → 726 | *+21.0 %* | *1068 → 957* | *+10.4 %* |

### 3.3 Marginal MiB per additional session (N=1→5 slope: `(X5 − X1)/4`)

| measure | normal | zygote | saving |
|---|---:|---:|---:|
| **guest tree ΣPss/session** | **79.2** | **55.9** | **29.4 %** |
| whole system ΣPss/session | 92.6 | 78.4 | 15.3 % |
| guest tree ΣPD/session | 77.9 | 60.1 | 22.8 % |
| whole ΣPD/session | 91.0 | 78.3 | 14.0 % |

Read this honestly:

* The **29.4 %** marginal saving is the zygote's real value: the ~40 MiB pre-fork core
  (boot-image pages, framework classes, JNI table, system `Resources`) is paid once and shared.
* The **as-implemented 15.3 %** is lower because the research seam keeps a per-session tombstone
  `sleep` (9.4 MiB Pss: toybox + bionic + its own heap) that a product would not need — a
  product launcher would simply wait without spawning a guest, or the zygote would own the
  session lifetime. Subtracting the stubs gives the 29.4 % row.
* At N=1 the zygote **loses** 8.2 % (guest tree) / 7.1 % (whole): the core is paid and there is
  no second child to divide it over; the crossover is between N=1 and N=2.
* The app child's own private memory dominates (57.2 MiB PD at N=5, 76 MiB of Pss per child
  net of the shared apportionment), which is why the saving is ~30 %, not Z3's optimistic 66 %
  projection: that projection assumed the child's non-shared clean pages were part of the
  shared set. They are not.
* This is **below the decision gate** (25 % *whole-system* over the optimised path) for the
  whole-system number; the guest-tree marginal is above it. N=10 is projected, not measured.

## 4. Timing

| | normal (N=5) | zygote (N=5) |
|---|---:|---:|
| first session ready (driver, from session thread start) | 224 ms | 158 ms |
| sessions 1–4 ready after session 0 (same driver clock) | 0 ms | 0 ms |
| per child `fork → postForkChild` | — | **1 ms** |
| per child `fork → sandbox + binds + guard active` | — | **5 ms** (`fork_to_ready_ms=5` for tags 0–4; `fork_to_sandbox_ms=3`) |
| pre-app init (once) | — | 7 ms + 3–6 ms GC |
| `preFork` #1 / #2..#5 | — | ~6 ms / ~1–2 ms (idempotent, `heap.cc:2452`) |
| fork → first **correct** frame | ~220 ms (app's own bind/attach/traverse) | ~160 ms (same work, no new runtime boot) |

The zygote wins the start-up too at N≥2: the children do not re-run `Runtime::Start` (dex
classpath setup, JNI table, system `Resources`), they start from the frozen image. At N=1 Z3
measured the one-off `preFork` as a 32 ms loss; here the fake-guest seam adds ~60 ms of
launcher/contract setup per foreign session (one-off, before `ready`), which the ready numbers
above include.

## 5. Security evidence at N > 1 (ZS review follow-up — recorded, not fixed)

ZS is right that every zygote-specific loss appears at N>1. Probe: `ZygoteApp.securityProbe`
(`ZygoteApp.java:257-330`), run inside every child *after* the production guard is installed;
raw `Z4SEC` lines in `.cache/z4-sec/zygote-{2,5}/s*/guest-*.out`. The zygote writes each child's
**zygote-namespace pid** to `/sessions/<k>/pid`, so the probes address real sibling pids.

| question | N=2 | N=5 | reading |
|---|---|---|---|
| (a) `/proc/<sibling>` / `/proc/<sibling>/fd` visible from a child? | `proc_sibling=false`, `proc_sibling_fd=false` (all children) | same, all 5 | **Stronger than Android's default.** A child is PID 2 in its own PID namespace; siblings and the zygote are not addressable, `/proc/<outer-pid>` does not resolve. `/proc/<zygote-pid-file>` "exists" only because that number (2) is the child itself. |
| (b) `kill(sibling, 0)` / `kill(zygote, 0)` from a child | `-13` (EPERM) both | `-13` both, every child | **Denied twice**: the pid is not in the child's namespace *and* the production seccomp filter denies `kill`/`tkill` (`seccomp.rs` deny list). The intermediate `z4ns` (A) stays in the zygote's PID namespace and can signal siblings — it is trusted launcher-side code, never app code. |
| (c) can child A reach child B's sockets? | `/sessions/1/sock/peer.sock` **exists, readable, writable** | same for every other session | **FAIL (real finding).** The plan dir is bound at `/sessions` in the zygote's mount namespace and every child inherits it; a malicious child could connect to (and impersonate a guest at) another session's peer socket. **Mitigation for a product:** bind only the child's own session dir over `/sessions` inside B, or `mount("tmpfs", "/sessions")` after applying the binds. Not fixed here per the review instruction. |
| (d) which cgroup? | all app children + zygote + launcher 0 in **launcher 0's session scope** `…/app.slice/run-p<pid>-<inode>.scope` (`1:net_cls:/`, v2 path identical); each tombstone stub has its own scope | identical | **Shared budget.** `memory.oom.group=0` on this host (`app.slice`), so the kernel OOM killer picks a task inside that one cgroup — it is not a group kill, but one child's growth counts against the same `MemoryMax` as the zygote and every sibling, so a child can starve or get a sibling killed. A product zygote should put each child in its own scope **and** set `oom.group=1` per child, or use per-child `memory.high`. |
| own user/mount/pid namespaces per child | `userns=0 mntns=0 pidns=0`, `NSpid=2` | same, all 5 | Pass |
| per-session writable root | `/data/{dalvik-cache,misc,tmp,out,task,app-data,app-lib}` resolve to that session's run dir; `app-data` is the guest's `dataDir` (`/data/app-data/<pkg>`) | same | Pass (root is private; the *contents* of another session's `run` are reachable through `/sessions` until (c) is mitigated) |
| production guard active per child | `seccomp=2`, `OK guard=active`, `OK landlock=active` in each session's `run/out/seccomp.log` | same | Pass (same blob/plan, applied in AOSP order) |

Additional ZS notes honoured: **`-Ximage` was not combined with `-Xzygote`** (Z1 §5.2 abort), and
**no per-session state is created in the zygote before `preFork`** — the zygote only reads the
contracts (`/sessions/<k>/argv`) and writes child pids; everything app-specific happens after
the fork. The zygote never touches a session's C1, ServiceHost, sockets or out dir.

## 6. Blockers and open items

1. **The tombstone stub** (`sleep` per non-zero session, 9.4 MiB Pss) exists only because
   `interactive_serve` needs a `Child` to poll for liveness (`launch.rs:2115`, `:2236`,
   `:2749`). A product needs a small "no guest spawned" state in the launcher (`Option<Child>` +
   a session-owned liveness source) so the zygote path does not pay ~9 MiB/session. This is the
   difference between the 29.4 % and 15.3 % rows in §3.3.
2. **The plan directory leaks the other sessions' sockets** (§5c). One-line fix in `z4init`
   (bind only `/sessions/<tag>` onto `/sessions`, or tmpfs over it after the binds); deliberately
   not applied so the finding stays visible in this measurement.
3. **One cgroup for all children** (§5d): per-child scopes + `oom.group=1` are a zygote-side
   change, not a launcher change.
4. **`-Xzygote` + reflective `Daemons.start()` is hidden API** (Z3 §6.3). Unchanged here.
5. **The guard `.so` is recompiled** for Z4: same source, same `seccomp.bpf`, same
   `landlock.plan`; only `-fno-stack-protector` differs, because `System.load` from a
   classloader namespace cannot resolve bionic's hidden `__stack_chk_fail` — `-fno-stack-protector`
   removes the reference mechanically (no source `#ifdef`). Alternatives were worse: preloading
   the guard into the zygote blocks the child's `unshare`/`mount`; adding a `DT_NEEDED libc.so`
   is not portable.
6. **Untrusted APKs stay on the exec path.** Nothing here changes the product default; the
   zygote seam only runs with `ACOS_ZYGOTE_*` set by the research driver.
7. **Not measured:** N=10 (time box), CPU per child, teardown of a hung child, per-child uid
   (Z2: impossible unprivileged), GC/allocator behaviour of the real app under repeated forks.
8. **`preFork` requires 1 thread**; the zygote is single-threaded because nothing it does before
   the fork starts one (measured `after_preFork threads=1` in Z3). The child's unshare now runs
   *before* `postForkChild` for exactly this reason.

## 7. Reproducing

```bash
# research dex + shim (+ the Z4 guard copy)
ZBUILD=z4-build research/zygote-proto/z3/build.sh

export ACOS_FONT_DIR=/home/Qui/Projects/acos/.cache/boot/android-34/fonts
CARGO_TARGET_DIR=/home/Qui/Projects/acos/.cache/z4-target cargo build --release -p acos-art

# all six configurations (normal and zygote × N = 1, 2, 5)
tools/art-runtime/run-exclusive.sh --task Z4 -- tools/guarded.sh --mem 16G --time 600 -- bash -c '
  for m in normal zygote; do for n in 1 2 5; do
    python3 research/zygote-proto/z4/drive.py --mode $m --n $n \
      --out .cache/z4-run/$m-$n --json .cache/z4-run/$m-$n.json
  done; done'
```

`drive.py` exits non-zero on any failure; it checks the count text on settled frames, the
ordered isolation matrix, cross-session and cross-path md5 equality, and samples
`/proc/<pid>/smaps_rollup` + cgroup/`NSpid` for the whole tree while the N sessions are held.
The normal path is the same driver with `--mode normal` and no `ACOS_ZYGOTE_*` variables.
Evidence: `.cache/z4-run/*.json` (matrix), `.cache/z4-sec/*.json` (N=2/5 with `Z4SEC` probes),
`.cache/z4-{matrix,sec,driver}.log`, guest launcher logs under each session's `s{0..4}/`.
