measurement names which one ran.

## 2. Method

### 2.1 Lifetime-matched memory

Z6 sampled 0.5/15/60 s after the **last tap**, and the tap phase grows with N (3–65 s), so its
"0.5 s" cell was not a child age. Z7 anchors on the guest's own first frame:

1. Spawn the cohort exactly as the Z4 driver does.
2. Read **only** each session's `ready` line (the first live-frame probe sample) before any
   tree/tap/screenshot request. Record `t_ready` per session.
3. For each child k and each age A ∈ {0.5, 2, 5, 15, 60} s, take a whole-tree snapshot at
   `t_ready[k] + A`. The named child is exactly A old; every other child's actual age is recorded in
   the sample. The cell is the **median of the N child-anchored snapshots**, with the age range.
4. After the 60 s snapshot, run one real verified task per session and the ordered isolation matrix
   (counter: `0` → tap → `1`; every untapped session still `0`).

ΣPss = Σ`Pss` of every process below the driver (`smaps_rollup`), same definition as Z5/Z6.
ΣPrivate_Dirty, per-role totals, `Swap`/`SwapPss` and the cgroup files are recorded per sample.
Repetitions are interleaved: rep 1 order `a ap c cp`, rep 2 `cp c ap a`, rep 3 `c a cp ap`.

### 2.2 The agent loop

P5's loop is launch → inspect → tap → assert → reset, with reset = relaunch. The prototype's Z4
zygote forks a fixed set of children once and has no per-session relaunch, so **every arm runs the
same round protocol**:

> round = launch N fresh sessions → one verified task on every session → reset = close the cohort
> → launch a fresh cohort.

Every task therefore runs on a freshly launched child (the young-child regime Z6 could not measure),
and every round pays its own launch cost. For (c)/(c') the round also pays a fresh zygote pre-fork
core; that is the prototype's reset, not a product zygote's (see §7 item 3). The same protocol for
all four arms keeps the comparison fair. N=10, 5.2 min time box per arm, tasks run sequentially
round-robin over the N sessions (as P5 ran its 5-session cohort).

**Metric.** The primary denominator is the integral of the whole-tree **ΣPss** sampled every 200 ms
(attributable resident memory, the policy's "total attributable PSS over wall time"). A second
denominator is `net anon+shmem` from the P5/W45 sampler. The guarded job cgroup's own
`memory.current` is **not** a valid denominator here: every `acos-art` launch creates its own
systemd transient scope as a *sibling* of the guarded scope, so the job cgroup alone misses the
guests (it reads 0.53–1.07 GiB-min where the process tree's PSS integral is 1.54–4.67 GiB-min).
Both the PSS integral and the anon+shmem integral are reported; the job-cgroup number is recorded
and marked unusable.

### 2.3 Teardown

The loop records, per round: every launcher's exit code, whether the zygote's pid still exists
after the close, the zygote's fds/threads/VmRSS before, after the tasks and after the close, and
the pids the driver had to SIGKILL to make the reset repeatable. The fixed-cycle test repeats this
for 20 rounds at N=5 (§6).

## 5. Does the early release happen within ~1 s? (mechanism)

**Yes.** The Z6 1 Hz probe on an idle cohort (N=2, 8 s, before any tap) shows it directly:

| t after last ready | (c) child Pss, MiB | (c') child Pss, MiB |
|---:|---:|---:|
| 0 s | 83.6 / 83.6 | 56.6 / 64.2 |
| 1 s | 83.8 / 83.6 | **56.6 / 56.8** |
| 2 s | 85.8 / 85.6 | 56.6 / 56.8 |
| 3 s | 85.8 / 85.6 | 58.7 / 56.8 |
| 5 s | 85.8 / 85.7 | 58.7 / 58.9 |
| 7 s | 85.8 / 85.7 | 58.3 / 58.9 |

(c') is already 19–27 MiB below (c) at t=0 and settles by t=1 s. (c) does not release in this
window; its release is the previously measured +9–10 s event.

The mechanism, measured rather than inferred:

* `System.gc()` in this guest is **inert**: `android.os.Debug.getRuntimeStat("art.gc.gc-count")`
  reads 3 before and 3 after, the call returns in 0 ms, and ΣPss does not move.
* The same thread then calls `VMRuntime.getRuntime().requestConcurrentGC()` (reflection; the guest
  runs platform code, so the hidden API is reachable in both arms). The count moves 3 → 4, the run
  takes ~4 ms to return, and the pages are returned within the next sample. This is a background
  CC collection; the child is not jank-perceptible, so
  `GarbageCollector::ShouldEagerlyReleaseMemoryToOS()` is true and
  `ConcurrentCopying::ClearFromSpace` / `RegionSpace::ReleaseFreeRegions` returns the region space
  (the same AOSP path Z6 §5.3 identified at +10 s).
* A control with `ACOS_ART_GC_DELAY_MS=2000` (same hook, 2 s later) produced the same end state at
  a 2 s later timestamp, so the effect is the request, not the hook's location.

The early release is **partial relative to waiting 10 s** in the exec arm by construction (the app
continues to allocate launch garbage after the first frame), and nearly complete in the zygote arm:
(c') at 60 s is +3.0 % above (c) at 60 s at N=10 (+12.3 MiB) and +2.9 % at N=5 (+8.3 MiB). It does
not make the steady state worse than (c) beyond that band; it removes the 10 s window.

## 6. Teardown, the 20-cycle test, and Z6's contradiction

**The fact.** In 32/32 zygote loop rounds (16 (c) + 16 (c')) and in the Z6 reruns on this host, a
`close` to a zygote session returns `{"ok":true,"cmd":"close"}` immediately and then the launcher
does **not** exit: the driver's bound expires and SIGKILLs it (`exit -9`). After the launcher is
gone the **zygote parent is still alive** (`/proc/<pid>` exists; 16/16 rounds). It is reparented and
keeps the pre-fork heap. The reset is only repeatable after the driver kills the zygote's tree
explicitly. **Z6 §8 ("every launcher still alive 20 s after close, killed by the bound") is the
true statement. Z6 §7.6 ("close on a (c) session takes the shared zygote down") is not what
happens here: the zygote survives; the launcher hangs.**

The 20-cycle N=5 fixed-cycle test and the per-cycle fd/thread/RSS series are reported in §6.1 (they
were still running at this commit; the loop already records the same per-round facts for every
round in `summary.json`).

## 7. Caveats and what was not measured

1. **The reported (a')/(c') arms use the guest early release, not the argv heap flags.** The
   `-Xms`/`-Xmx`/`-XX:HeapTargetUtilization` plumbing exists and validates, but it was not the
   measured arm: a target-footprint flag is a policy change that can fail an app under allocation
   pressure, while the early release is the same collection ART already schedules. The flag arm is
   therefore **not measured** (never estimated).
2. **The loop's reset for (c)/(c') is a cohort restart**, not a per-session relaunch; the Z4
   prototype forks a fixed set of children once. The zygote's pre-fork core is therefore paid per
   round and the zygote arms complete fewer tasks/min. A product zygote that forks a new child per
   reset would not pay it; that configuration is **not measured** and no number here estimates it.
3. **One fixture for the loop** (`counter.apk`). The form-validation fixture is being measured for
   the lifetime/correctness half; the loop is not repeated with it (time box).
4. **One host, x86_64, one release binary; two interleaved reps per lifetime cell at this commit**
   (third in progress). The host was shared with other agents' ART runs through the lock; queue
   waits are in `art-locks/runs.log`. All cells of a row come from one run, and arms are
   interleaved across reps, so host drift cannot skew one arm by itself.
5. **The task/GiB-min denominator is the whole-tree ΣPss integral**, not the guarded job cgroup's
   `memory.current`: the launchers live in their own systemd scopes, so the job cgroup misses the
   guests (measured: 0.53–1.07 GiB-min vs 1.54–4.67 GiB-min PSS). P5's exact job-cgroup number is
   reported next to it and marked unusable for that reason. The net anon+shmem integral agrees with
   the PSS ordering (44.3 / 65.2 / 67.5 / 98.0 tasks/GiB-min).
6. **Not measured:** `-Xms`/`-Xmx` arm; a persistent zygote with dynamic per-session forks; a
   second loop repetition; a heavier app (React Native/Gaten/allocation-heavy); per-session uid,
   SELinux, per-child cgroup; energy; steady-state CPU.

## 8. Security: unchanged from ZS

No sandbox line moved. The Z7 additions are environment seams that are **off by default**:
`ACOS_ART_XMS`/`ACOS_ART_XMX`/`ACOS_ART_HEAP_TARGET_UTILIZATION` (argv heap policy; validated) and
`ACOS_ART_GC_AFTER_FIRST_FRAME`/`ACOS_ART_TRIM_AFTER_FIRST_FRAME`/`ACOS_ART_GC_DELAY_MS` (guest
runs a real ART GC/trim earlier than the app would). They are listed in `docs/SECURITY.md`'s knob
table. The zygote secrets remain ZS's: untrusted APKs are still excluded on F1/F2/F3/F8/F9/F10, and
(b)+(c) still cannot be stacked (F11). The early release changes no protection; it changes when the
guest's own heap pages are returned to the OS.
