# W3 — the leash wall is `readStrongBinder`'s null rule, not a byte shift: `addToDisplayAsUser` now passes

**Status: DONE.** The guest decodes the whole `addToDisplayAsUser` reply, passes the
leash `SurfaceControl` and continues into `IWindowSession`'s window setup; the next wall is
`InputEventReceiver.nativeInit` (`UnsatisfiedLinkError`), i.e. the substrate's missing input
natives, *after* the add. W2's open question ("does the guest arrive early or late, and which
preceding read consumed a different number of bytes?") is answered with bytes, not guesses:
**the guest arrives exactly on time (leash `client` at frame offset 1352) and nothing before
it is mis-modelled; the 88-byte shift is the *cascade* of the first leash aborting, and it
aborts because we wrote a null binder into a slot the reader reads with `readStrongBinder`
(not `readNullableStrongBinder`), which turns a null into `UNEXPECTED_NULL`.** Fixed in the
`SurfaceControl` codec with the documented placeholder binder; pinned by a new regression
test that transcribes `readStrongBinder`'s semantics. No commit.

## 1. The measurement: the guest is on time; 1440 is the cascade

W2's §5.2 hypothesis was "the guest starts the leash parse one prefix late (+88)". That is
**wrong**, and the wrongness matters: it suggested a codec asymmetry that does not exist.

The reply frame the guest's driver hands to libbinder is dumped in
`research/art-feasibility/w3-leash/artifacts/w3-frame-add.hex` (2352 bytes = W2's 2324-byte
reply Parcel + 7 × 4-byte stability records). Replaying the image's readers over those exact
bytes (`scripts/cascade.py`, output `artifacts/w3-cascade.txt`) gives:

```text
controls: 3 (array walk starts at 1252)
ctl0 id=0x3 type=8 leash='Surface(name=InputMethod animation-leash of insets_animation)/@0x3'
binder reads, in order:
  InputChannel token @  16  binder 0x8 (object-table check)
    leash client     @1352  NULL binder -> UNEXPECTED_NULL (-2147483640)
    leash client     @1440  type 0x49003d is not a flat_binder_object
```

and the guest's own log for the same run (`artifacts/w3-launch-before.log`) is, in order:

```text
Parcel          Expecting binder but got null!
SurfaceControl  ERROR(Unknown error 2147483640, -2147483640). Failed to call parcel parcel.readStrongBinder(&client)
Parcel          Attempt to read object from Parcel bb225030 at offset 1440 that is not in the object list
SurfaceControl  ERROR(Unknown error 2147483647, -2147483647). Failed to call parcel parcel.readStrongBinder(&client)
```

Every number agrees: `-2147483640` is `UNEXPECTED_NULL` (`UNKNOWN_ERROR + 7`) from the
`readStrongBinder` at 1352, `1440` is the next leash's client read, and the two pairs are the
two aborted `readFromParcel` calls. Nothing between the reply start and 1352 consumed a
different number of bytes: `1352` *is* the offset of the first leash's `client` object
(`4` typed presence + `72` name8 block + `12` width/height/hasNative after the controls array
starts at 1252, all framework-order exact).

So the "88-byte shift" is arithmetic on the *cascade*, not a cause: after the first leash
aborts, the `InsetsSourceControl$Array` stub keeps reading its declared three elements from a
half-consumed control, which happens to land the next `SurfaceControl` client read exactly 88
bytes (one Java prefix: presence + name8 + w/h/present) later — 1352 + 88 = 1440.

## 2. Root cause (a wire **rule**, verified in the image's own source and binary)

```text
libgui  SurfaceControl::readFromParcel (0x13f7d0):
        SAFE_PARCEL(parcel.readStrongBinder, &client);
        SAFE_PARCEL(parcel.readStrongBinder, &handle);
        SAFE_PARCEL(parcel.readInt32, &layerId);
        SAFE_PARCEL(parcel.readUtf8FromUtf16, &layerName);
        SAFE_PARCEL(parcel.readUint32, &{transformHint,width,height,format});
libbinder Parcel::readStrongBinder(sp<IBinder>*) (0x7e7a0):
        status = readNullableStrongBinder(val);      // OK with a null value
        if (status == OK && !val->get()) {
            ALOGW("Expecting binder but got null!");
            status = UNEXPECTED_NULL;                // -2147483640
        }
libbinder Parcel::readObject(bool) (0x9f2c0, disassembled):
        read 24-byte flat object; if (!nullMetaData && cookie==0 && binder==0)
            return obj;                              // no object-table check
        else validate DPOS against the object table -> ALOGW "not in the object list"
libbinder Parcel::finishUnflattenBinder: reads the 4-byte stability record.
libandroid_runtime nativeReadFromParcel (android_view_SurfaceControl.cpp):
        SurfaceControl::readFromParcel(*parcel, &surface);   // status IGNORED
        return surface ? surface.get() : 0;                   // no Java exception
```

W2 §5.1 correctly established that `readObject`'s null fast path exists and that a null binder
is written without an object-table entry. What it missed is **which reader is used**:
`readObject`'s fast path makes `readNullableStrongBinder` *succeed with null*, and
`readStrongBinder` — the one `SurfaceControl::readFromParcel` uses, under `SAFE_PARCEL` — then
converts that success into an error. The chain is therefore:

1. leash 0 (`Surface(name=InputMethod …)`: `client` at 1352 is our **null** binder →
   `UNEXPECTED_NULL`, `SAFE_PARCEL` returns in the middle of the leash (position 1380);
2. `nativeReadFromParcel` swallows the status and returns 0, so the Java constructor assigns
   `mNativeObject = 0` and the enclosing `InsetsSourceControl` keeps reading from 1380
   (garbage: `initiallyVisible`, `Point`, `Insets`, `skip`, …);
3. the array's remaining elements drift; the next `SurfaceControl`'s `client` read lands at
   **1440** on UTF-16 characters (`type 0x0049003d`), fails the object-table check
   (`-2147483647`), and its `readFromParcel` aborts too;
4. the drifted walk reads the trailing `float[]` **count** from garbage (6357101 in the
   replay) while the caller allocated 1 → `Parcel.readFloatArray` throws
   `RuntimeException("bad array lengths")` at `IWindowSession$Stub$Proxy` line 1264, which
   surfaces as `Adding window failed` at `ViewRootImpl.setView:1362`.

Point 3 is why "the guest still fails at the leash" survived W2's fixes: the *first* error was
from a **null binder we wrote**, and every later message described the cascade.

## 3. Why W2's five ruled-out candidates were all correct — and irrelevant

The null-binder table rule, the stability records, the String16 padding, the controls-array
form and the `SurfaceControl` shape are all exactly as W2 verified (the replay above uses
them). None of them is the bug, because the bug is not a *shape* mismatch: it is the
**semantics of a null binder in a `readStrongBinder` slot**. W2 reasoned from the byte dump
(which is framework-perfect) and concluded the guest must be shifted; in fact the guest
parsed the dump perfectly and refused a null.

## 4. The fix — one rule in the codec, no session surgery

`crates/acos-wm/src/codec.rs` (`SurfaceControlInfo::write_to_parcel`, used by **both** the
`InsetsSourceControl.mLeash` bodies and `relayout`'s `outSurfaceControl`) now writes a live
**placeholder binder** for `client` and for the layer `handle`:

```rust
pub fn placeholder_binder(handle: u64) -> BinderId {
    BinderId(PLACEHOLDER_BINDER_BASE | (handle & 0xffff))  // 0x0100_0000 | layerId
}
```

Semantics, documented in the code and honest about what exists:

- the id is **live and routable** (the peer turns it into a node, the guest gets a real
  `BinderProxy`), so `readStrongBinder` succeeds and `readFromParcel` completes;
- it is **not registered** with the `ServiceHost`, so `INTERFACE_TRANSACTION` answers the empty
  descriptor; `interface_cast<ISurfaceComposerClient>` therefore yields **null**, which is the
  framework's own "we aren't the original owner of the surface" case
  (`SurfaceControl.cpp`, `SurfaceComposerClient(const sp<ISurfaceComposerClient>&)`); no
  `onFirstRef`/`createConnection` is triggered by it;
- any transaction sent to it is answered with the peer's structured `UNKNOWN_BINDER` — never a
  fake success. ACOS still has no SurfaceFlinger layer: the `SurfaceControl` is the same
  structural placeholder W2 shipped, only now byte-legal for the image's reader.

`window_session.rs` needed **no** change: `present(SurfaceControlInfo)` is the single write
path for the leash and the relayout surface, so the rule lands in one place. (Verified: the
guest's stderr has no driver warnings, and no `Parcel`/`SurfaceControl` log entry appears.)

## 6. Method note: the gdb route (prepared, measured, not needed)

The task asked for a host-gdb position trace; the byte replay settled the question first, but
the attach machinery is real and is kept in `research/art-feasibility/w3-leash/scripts/`:

- the guest is **not** a descendant of the host shell: `acos-art` spawns
  `systemd-run --user --scope` and the payload is exec'd by the user manager (`ps` shows the
  guest's parent as the manager, not the launcher), so yama `ptrace_scope=1` denies a plain
  `gdb -p` (measured: `ptrace: Operation not permitted`);
- the sanctioned workaround (the one Q3 used) is `prctl(PR_SET_PTRACER, -1)` from inside the
  guest: `scripts/ptracer.c` is a freestanding constructor appended to the scratch data root's
  `libartshim.so` (rebuild command in `scripts/repro.sh attach`; nothing in the repo changed).
  The guest's S5 seccomp filter does not deny `prctl`, so no guard had to be disabled — the
  filter was left active in every run (`seccomp: OK guard=active insns=82`);
- with that, `gdb -p <guest>` attaches (verified: 20+ LWPs, `info threads`); `scripts/attach.gdb`
  installs breakpoints on `android::SurfaceControl::readFromParcel` and the exported
  `Parcel::{readObject,readNullableStrongBinder,finishUnflattenBinder,readString16,readString8,readInt32}`
  and prints `dataPosition/dataSize/mObjectsSize` from the known `Parcel` field offsets
  (`mData 0x08, mDataSize 0x10, mDataCapacity 0x18, mDataPos 0x20, mObjects 0x28,
  mObjectsSize 0x30, mNextObjectHint 0x40`, read out of `Parcel::writeInt32`/`writeObject`);
- to have a window in which to attach, a **temporary** env-gated hold was added to
  `window_session.rs` (sleep before the reply leaves the peer) and a **temporary** reply-frame
  dump to `acos-binder-peer`; both are reverted (`git diff` clean for both crates).

**Open observation (not load-bearing, worth a follow-up).** With the *old* (null-binder) reply,
releasing the held reply a few hundred ms late made the run pass (5/5 held runs) while the
undelayed reply failed (4/4). The frame bytes are byte-identical in both cases (compared the
peer's reply frame dumps), so the difference is guest-side. The prime suspect is the binder
driver's transaction-buffer allocator: `mm_alloc` bump-allocates with an unsynchronised
`g_bump += n` while `build_reply` runs outside `g.mu`, so two concurrent reply builds can be
handed overlapping blocks. With the fix in place the slot bytes are non-null either way and
12/12 runs are stable, so this is not on the acceptance path — but it is a real race in
`crates/acos-binder-peer/native/binder_driver.c` and it deserves its own probe (dump `buf_off`
in `build_reply` under `E3G_DEBUG`; the attempted patch is described here so nobody repeats it:
inserting the dump into the first `uint32_t cmd = BR_REPLY;` block lands in `reader_main`, not
`build_reply`).
