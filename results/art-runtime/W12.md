## 1. Answer in one paragraph

Option A in its **small-pool shape** (2 gralloc buffers) costs **+48 MiB PSS / +47 MiB guest
cgroup per session** over the existing non-windowed ART path — the documented estimate in
`WR-window-surface-options.md` §3 was **+27 MiB**, so the estimate was **low by ~21 MiB**
(≈1.8×), and ~18 MiB of the measured delta is exactly the buffer bytes the estimate
predicted. The **product path as it stands today** (interactive `verify`, W10's
`DEFAULT_MAX_ACQUIRED_BUFFERS = 24` workaround) costs **352–363 MiB per session**
(cgroup peak 294–303 MiB + launcher 51–59 MiB + bwrap 0.2–0.4 MiB), **6.4×** the small-pool
window-stack cost and **13×** the +27 MiB estimate, because each session allocates 24 ×
1080×2209×4 B ≈ **218 MiB of memfd buffers** whose touched pages are charged to the guest
cgroup. Even so it remains **2.5–6× below** the *estimated* +120–300 MiB of a stock
SurfaceFlinger process (`WR` §3 option C) and roughly **2.0× the legacy ACVM per-session
N=1 figure** (130.3 MiB anon+shmem, different metric type) — with real `ViewRootImpl`,
`Choreographer`, `BLAST` and stock HWUI rather than a framework stand-in. Under load all
**1/1, 10/10 and 20/20** sessions passed `verify` (status `pass`, three taps each with a fresh
frame and the right tree), zero cgroup OOM kills, host peak **35.5 %**.

## 2. Method (what the numbers are, and are not)

`tools/art-runtime/bench-session.sh` runs N concurrent sessions **of one mode** in one
cohort, holds the host-wide ART lock (`run-exclusive.sh`) for the whole benchmark, and runs
the whole cohort inside one `guarded.sh --mem` scope. A `python3 -I` sampler walks each
session's process tree every `--sample-ms` (100 ms) and records:

* **per process** (`/proc/<pid>/smaps_rollup`): `Pss`, `Pss_Anon`, `Pss_File`, `Pss_Shmem`,
  `Private_Dirty`, `Private_Clean`, `Shared_Clean+Shared_Dirty`, `Rss`, threads, open fds,
  live `memfd:acos-gralloc` fds and mapped bytes, `utime+stime`; classified by role:
  **guest** (`dalvikvm64`), **launcher** (`acos-art`, which hosts the Rust peer/ServiceHost,
  C1, the window session and the input host), **bwrap**, **scope** (`systemd-run`/`sh`),
  **cli** (the `acos` process itself — harness, reported separately).
* **per session cgroup** (the guest's own systemd scope, found through
  `/proc/<guest>/cgroup`): `memory.current`, **`memory.peak`** (kernel high-water mark),
  `memory.max`, `memory.stat` (`anon`/`file`/`shmem`), `cpu.stat`, `memory.events`.
* **whole host**: `MemTotal`/`MemAvailable` at every sample (used delta vs an idle
  baseline) plus two full host PSS scans (sum of `Pss` over every `/proc/*/smaps_rollup`).

Modes (all real ART, same APK, same host, same sampler):

| mode | command | window stack | interaction |
|---|---|---|---|
| `full` | `acos verify --engine art --scenario scenarios/v2-art-counter.yaml` | **yes** (C1 + IWindowSession + BLAST + real `ViewRootImpl`) | launch → live tree → tap Increment → capture → tap Reset → tap Increment → teardown |
| `launch` | `acos-art launch --until activity-resumed` (+`ACOSLAUNCH_HOLD_MS=2500`) | **yes**, same | none (one-shot, held; cost = peak) |
| `render` | `acos-art render-app` | **no** (zeroed `ViewRootImpl` stand-in, software `Bitmap`, no BLAST/C1/window session) | none (one-shot; cost = peak) |

Decomposition: `full − launch` = interactive extras (live probe, `InputHost` taps, C1
captures); `launch − render` = **Option A's window/surface stack** plus the real traversal.
`acos-art session` (the older headless line-JSON path used by `bench.sh`) was tried as the
non-windowed comparator and **exits rc=1 right after `activity-resumed`, before answering one
command** at HEAD — recorded in §8, not worked around (`crates/` is read-only here).

Per-session "total" = guest `cgroup memory.peak` + launcher PSS + bwrap PSS. It is an
**upper bound** when sessions share sysroot file pages (each cgroup is charged its own copy),
while the PSS columns divide shared pages. Both are reported; they are never summed with
each other.

## 4. Per-component breakdown (N=1, peak sample)

| component | PSS MiB | Pss_Anon | Pss_File | Private_Dirty | what it is |
|---|---:|---:|---:|---:|---|
| guest ART + framework (`dalvikvm64`, comm `fixtures.counter`) | **210.8** | 77.0 | 125.5 | 87.8 | real ART 14 + `ActivityThread`/`Activity`/`ViewRootImpl`/`Choreographer`/BLAST/`libhwui`-Skia in the guest |
| Rust launcher (`acos-art`: peer + ServiceHost + C1 + window session + input + probe/PNG) | **59.4** | 50.6 | 8.8 | 50.6 | code ~6 MiB + heap for the service host, C1 buffer bookkeeping, window session and captures |
| bwrap | 0.4 | 0.2 | 0.2 | 0.1 | 2 processes |
| session total, peak sample (guest + launcher + bwrap) | **262.2** | 127.7 | 134.4 | 138.5 | the `full N=1` per-session PSS row |
| guest cgroup peak (kernel `memory.peak`) | **303.3** | anon 73.0 + file 218.6 (of which **shmem 218.5**) | – | – | the 24 gralloc memfds' touched pages + guest anon + charged file pages |
| `acos` CLI (harness, per invocation) | 84.4 | 62.0 | 22.4 | 62.0 | 232 MB debug binary + scenario/artifacts writer; **excluded** from the session rows |

The key accounting fact: **gralloc buffer pages are invisible to per-process PSS**. The
shim `mmap`s a memfd only for the duration of `lock`/`unlock` and unmaps afterwards, so
between frames the pages live in the page cache and are charged to the guest cgroup
(`memory.stat shmem = 218.5 MiB`) — not to any process RSS. That is why the cgroup peak
(303.3 MiB) exceeds the summed process PSS (262.2 MiB) by roughly the buffer bytes, and why
this harness reports the cgroup peak as a first-class number.

Buffer accounting at N=1 `full`: **24 allocations × 9 542 880 B = 218.4 MiB** of *virtual*
memfd (sparse `ftruncate`), of which the touched pages (~218.5 MiB per the cgroup) are
resident; 49 open `acos-gralloc` fds across guest+launcher (each buffer dup'd into C1).
`launch` allocates **2 buffers (18.2 MiB)**, `render` **0**.

## 9. Caveats (explicit)

1. **One repetition** per (mode, N). Memory is stable (ranges in `summary.json`), but there is
   no p95; latency medians are over 1–20 sessions per cohort, not 20 reps.
2. **Host-level deltas are noisy** (W11 active, PNG page cache). Prefer cgroup/PSS.
3. **cgroup peak over-counts sharing**: each session's cgroup is charged the sysroot file
   pages it maps, so Σ cgroup (2979.8 MiB at N=10) > host-attributable Σ PSS (1452.0 MiB).
   The cgroup number is the right *per-session* figure; the PSS sum is the right *share-aware*
   figure. Never add them.
4. **Unmapped buffer pages** are in the cgroup and in host used, not in PSS (see §4).
5. **Debug binaries** (dev profile). A release build would change code-page sizes
   (`Pss_File`/`Private_Clean`), not the anonymous heap; not measured here.
6. One-shot modes are **peak** estimates sampled at 100 ms over a 1.4–3.3 s run; the `full`
   rows are held ~7–8 s sessions.
7. `render-app` is the **non-windowed comparator**: real ART + real framework `Activity` +
   stock `libhwui`/Skia, but a zeroed `ViewRootImpl` stand-in and no BLAST/C1. It is *not*
   verification evidence; the window-stack delta it produces includes the difference between
   the stand-in and the real traversal.
8. The `acos` CLI (84 MiB PSS at N=1, ~65 at N≥10) is per-invocation harness cost and is
   excluded from per-session rows. In production one CLI process can drive many sessions.
9. The BLAST pool setting is recorded in `provenance.pool` of
   `results/bench/W12-session-memory.json` (`source_constant: 24`, no env override).
