# R1 — the `acos-art` OOM: a guest log loop retained by the host

**Status:** fixed, with defence in depth and tests. `acos-art` peak RSS under the
reproduced flood: **15.7 MB** (was unbounded: 4 GB in ~11 s).

## 0. Incident

The kernel OOM-killed `acos-art` three times on 2026-11-11:

| time | context | anon-rss |
|---|---|---|
| 13:23 | inside `tools/guarded.sh --mem 6G` | 6.2 GB |
| 16:00 | inside `tools/guarded.sh --mem 6G` | 6.2 GB |
| **16:05** | **unguarded**, whole-desktop OOM | **36 GB** (total-vm 39 GB) |

The 16:05 kill took down the desktop session and every running agent. The
trigger process is the Rust launcher (`acos-art`), **not** ART: the ART guest
reserves terabytes of *virtual* address space but only a few hundred MB of RSS,
so `VmRSS`/anon-rss can only have grown in the launcher.

## 1. Reproduction

`session` is the shortest path to the flood (a long-lived guest, one logd sink):

```bash
tools/guarded.sh --mem 4G --time 100 -- ./target/debug/acos-art session \
    --apk fixtures/build/apps/counter.apk --out /tmp/p3d/repro/out \
    --socket /tmp/p3d/repro.sock --session-id repro
```

Measured on the unfixed build, sampling `/proc/<pid>/status:VmRSS` every second
(`/tmp/repro3.sh`), no client on the socket:

```
t=2  art_rss_kb=    6832   cg=193MB
t=3  art_rss_kb=  347396   cg=571MB
t=4  art_rss_kb=  786268   cg=1001MB
t=5  art_rss_kb= 1227756   cg=1433MB
...
t=11 art_rss_kb= 3870920   cg=4021MB   → scope OOM (rc=137)
```

**~400 MB/s, linear, in a single thread.** Localisation:

* 4 threads: main in `futex_do_wait`, two blocked in `anon_pipe_read` (the
  guest's stdout/stderr), and **one thread `wchan=0` burning 44 ms utime +
  57 ms stime per second** — page-fault bound, i.e. writing fresh memory.
* `smaps` top mappings: one 538 MB anon region plus four 128 MB regions — a
  `Vec` doubling at large sizes, i.e. one vector of heap-allocated records.
* The guest's own RSS was 174 MB and its `guest-stderr.txt` stayed at 2.6 KB, so
  neither the guest nor the stderr pipe was the source.
* `/proc/<pid>/task/*/wchan` narrowed the writer to the logd reader thread, whose
  only allocation is `entries.push(entry)`.

### The trigger, named by the sink itself

`ACOS_ART_LOG_TRACE=1` prints every 10 000th entry with tag and message:

```
acos-art: logd trace: 44970000 entries, 44925000 dropped, cap 50000 —
  [E] ServiceManagerCppClient: Waited for servicemanager.ready for a second, waiting another...
```

The guest's libbinder `ServiceManagerCppClient` retries `servicemanager.ready` in
a **tight loop** (the ACOS sandbox runs with `ACOSART_BINDER_FAKE`, so no
servicemanager ever appears). That is **~1.5 M log entries/s**, each retained in
`logd::Logd::entries: Vec<LogEntry>` forever — an unbounded allocation owned by
the guest. At ~270 B/entry that is the observed ~400 MB/s; 15 s under a 6 GB
scope, or a few minutes unguarded, is 36 GB.

Every other candidate was checked and is *not* the cause here: `read_to_end` on
the guest pipes (both readers idle, stderr 2.6 KB), `session` reply/frame
buffers (no commands were sent), PNG retention (no frames), binder peer queues
(no guest transactions in this path). They are still unbounded, and are bounded
too — see §3 — because the next trigger will be one of them.

## 2. Fix

### 2.1 The cause: a bounded, drop-oldest logd sink

`crates/acos-art/src/logd.rs`

* `Logd` keeps at most `ACOS_ART_LOG_CAP` entries (**default 50 000**), dropping
  the oldest and **counting every drop** (`LogStats { total, kept, dropped, cap }`).
* Drops happen in batches of `len/8` so a spammer never turns each push into an
  O(n) memmove of the window.
* `Logd::finish_capped() -> LogBatch { entries, stats, first_dropped }` reports
  the accounting *and* samples the first evicted entry: a tail capture loses the
  beginning of a spam loop, and that first message is the diagnosis.
* `Logd::finish()` keeps its old signature (no caller breakage) and is `Capped`.
* `LogStats::summary()` is always in the run's diagnostics (`logd: N entries kept
  of M (K dropped, cap 50000 entries)`), so a truncated capture can never be
  read as a complete one.

### 2.2 Defence in depth (all new ceilings)

| structure | ceiling | behaviour on overflow |
|---|---|---|
| guest stdout / stderr (`launcher`, `launch`, `app`, `session`) | `ACOS_ART_STREAM_CAP`, **8 MiB** each | chunked ring keeps the tail, `[... N bytes truncated ...]` marker + first dropped bytes, drop counter (`capture::TailBuffer`) |
| session `guest-stderr.txt` (disk) | same 8 MiB | streamed then one cap marker; file stops growing |
| session non-protocol stdout lines | 8 MiB tail | ring + marker |
| session `replies` history | 10 000 (`MAX_REPLIES`) | drop-oldest, `replies: kept the newest …` diagnostic |
| logd entries | 50 000 | drop-oldest + `LogStats` |
| peer pending reverse deliveries | 4 096 (`MAX_PENDING_DELIVERIES`) | **`ART_RESOURCE_LIMIT`** remote exception to the guest, counted |
| peer unsupported records (memory + JSONL) | 4 096 | first-N kept, `ART_RESOURCE_LIMIT` record, drops counted |
| peer forwarded transactions | 8 192 (`MAX_SERVICE_CALLS`) | drop-oldest, counted |
| peer java binder table | 4 096 | `ART_RESOURCE_LIMIT` refusal |
| peer launch reply table | 256 | `ART_RESOURCE_LIMIT` refusal |
| `ProviderRegistry` lookup log | 10 000 (`MAX_PROVIDER_LOOKUPS`) | drop-oldest + `lookups_dropped()` |
| launcher RSS | `ACOS_ART_RSS_MAX`, **2 GiB** | watchdog kills the guest process group, run ends `HOST_MEMORY_LIMIT` |
| launcher `RLIMIT_DATA` (soft) | 1.25 × the RSS ceiling | allocation fails inside the launcher instead of the kernel OOM killer |

`crates/acos-art/src/capture.rs` — `TailBuffer`: a 64 KiB-chunked ring that keeps
the last `cap` bytes and evicts whole chunks from the front, so `push` is
O(bytes) with no memmove of the retained window; `total == len + dropped` is an
invariant, and the head sample is kept for the truncation marker. `0` as a cap
override means "use the default", never "unbounded".

`crates/acos-art/src/watchdog.rs` — `MemoryWatchdog`: one thread sampling
`/proc/self/status:VmRSS` every 50 ms (≈10 µs/sample); on breach it `SIGKILL`s
the armed process group (bwrap + dalvikvm64 + all ART threads) and records a
structured `Trip`. Every launch path checks `trip()` after `spawn` and reports
`Outcome::Unsupported` + code **`HOST_MEMORY_LIMIT`** with the RSS/ceiling in the
diagnostics. `install_process_guards()` (called once in `main`) also sets the
soft `RLIMIT_DATA` backstop; every guest `pre_exec` calls
`relax_child_limits()` to raise `RLIMIT_DATA`/`RLIMIT_AS` to unlimited, so ART
is never bounded by the launcher's limits (a *soft* limit is deliberate: a hard
one is inherited and could not be raised in the child).

`crates/acos-services` — `ServiceError::ResourceLimit { what, limit }` +
`codes::ART_RESOURCE_LIMIT` (maps to `EX_UNSUPPORTED_OPERATION`, so the guest
sees a real remote exception, not silence).

## 3. Evidence after the fix

### 3.1 Same flood, default caps

```bash
ACOS_ART_LOG_TRACE=1 tools/guarded.sh --mem 4G --time 40 -- ./target/debug/acos-art session \
    --apk fixtures/build/apps/counter.apk --out /tmp/p3d/r1f/out \
    --socket /tmp/p3d/r1f/d.sock --session-id r1f
# PEAK_ART_RSS_KB=15664
# logd trace: 44970000 entries, 44925000 dropped, cap 50000 — [E] ServiceManagerCppClient: ...
```

| metric | before | after |
|---|---|---|
| guest log entries produced | 44 970 000 | 44 970 000 (identical guest) |
| entries retained | 44 970 000 | **50 000** |
| launcher peak RSS | 1.6 GB at t=4 s → 4 GB at t=11 s (OOM) | **15.7 MB, flat** |
| outcome | kernel OOM (SIGKILL, rc=137) | run continues, `logd: … dropped` reported |

### 3.2 The watchdog, on purpose (cap disabled)

`ACOS_ART_LOG_CAP=100000000 ACOS_ART_RSS_MAX=600M` — the *old* behaviour, kept
reachable only by explicitly raising the cap:

```
acos-art: guards rss_max=600MiB rlimit_data=750MiB stream_cap=8MiB log_cap=100000000
acos-art: HOST_MEMORY_LIMIT: launcher RSS 606 MiB > 600 MiB (ACOS_ART_RSS_MAX); killed guest process group Some(2033438)
```

A structured `HOST_MEMORY_LIMIT` and a dead guest group — instead of a kernel OOM
kill that picks a random victim (in this desktop's case, everything).

### 3.3 No regression in the render path

```bash
tools/guarded.sh --mem 4G --time 300 -- ./target/debug/acos-art render-app \
    --apk fixtures/build/apps/counter.apk --out results/art-runtime/r1/counter
# frame=…/frame.png md5=9ec17f055843a2b9d18078ec595e9300 nodes=13 1080x2400@420
# outcome=ok wall=167ms draw_cold=825us peak_rss=191MB
python3 tools/art-render-app-compare.py --png … --tree … --out results/art-runtime/r1/compare.json
# ssim=0.99351 decor_band=… tree=12/12 structural=8/8  (P3c: 0.99351 / 12/12)
```

The frame md5 is byte-identical to P3c's (`9ec17f055843a2b9d18078ec595e9300`), so
the caps and the watchdog changed nothing about what the guest draws.

## 4. Tests (permanent)

`cargo test -p acos-art` (38 lib + 6 integration) and
`cargo test -p acos-binder-peer` (12) — green.

`crates/acos-art/tests/memory_caps.rs` — the spammer suite:

| test | assertion |
|---|---|
| `stdout_spammer_is_capped_and_the_host_rss_stays_flat` | a real `yes` process floods stdout; retained ≤ cap + one chunk, truncation marker present, `total == len + dropped`, **host RSS grows < 32 MiB** while capturing > 8× the cap |
| `stderr_spammer_is_capped_too` | same for stderr (the incident's `String` accumulator) |
| `logd_spammer_keeps_only_the_cap_and_counts_the_drops` | 60 000 datagrams through a 500-entry sink: kept ≤ cap, drops counted, first dropped sample kept, **RSS < +32 MiB** |
| `every_cap_is_smaller_than_the_watchdog_ceiling` | the caps sit below the watchdog, as layered defence requires |
| `stream_cap_is_configurable_but_never_absent` | `ACOS_ART_STREAM_CAP=0` falls back to the default, never to unbounded |
| `drain_to_tail_on_a_finite_reader_keeps_the_whole_stream` | no marker/truncation without overflow |
| lib `capture::tests::*` | ring invariants, single giant write, 512 MiB sustained flood bounded, `tail_text` keeps the truncation marker when a result field shortens a capture |
| lib `logd::tests::spammer_is_capped_and_drop_oldest` | 200 000 entries through a 1 000-entry sink |
| lib `watchdog::tests::*` | RSS read, 1-byte ceiling trips, `0` disables, `relax_child_limits` safe |

`crates/acos-binder-peer/tests/peer.rs` — the bounded-queue suite:
`the_unsupported_log_is_bounded_and_counts_the_drops`,
`the_java_binder_table_is_bounded_with_a_structured_refusal`,
`the_forwarded_transaction_log_is_bounded` (each drives the cap past its limit
and asserts the ceiling, the `ART_RESOURCE_LIMIT` code and the drop counters).

## 5. Notes / open items

* **The guest still spins.** The cap makes the spin harmless to the host, but
  `ServiceManagerCppClient` logging 1.5 M lines/s means the guest is burning CPU
  in a retry loop: the real servicemanager (`IServiceManager` host node) should
  answer `waitForService`/`isDeclared` for the launch/session path so the loop
  ends. That is guest work, not a host safety issue — tracked here so it is not
  forgotten.
* **`session` startup is currently broken upstream of R1** (not caused by, and
  not fixed by, this change): the guest aborts in
  `StateListAnimator → AnimatorSet.start → AnimationHandler.getProvider →
  Choreographer` (`guest-stderr.txt`), so a session never reaches its ready
  line. `render-app` and `launch` are unaffected. This is the unfinished state
  of the P3d workstream (the owning agents died mid-flight); the flood that
  killed the host happens *before* that abort.
* **Unblocking the build:** `crates/acos-services/src/host.rs` (other
  workstream's WIP) referenced `AtmsService::provider_lookups`, which exists; the
  `acos-services` tree was mid-edit and did not compile. R1 needed only the
  provider-lookup log bound (`MAX_PROVIDER_LOOKUPS`) and the new
  `ServiceError::ResourceLimit`; no behavioural change to the provider feature.
* **Env knobs** (documented in `acos-art --help`): `ACOS_ART_RSS_MAX` (default
  `2G`, `0` = off), `ACOS_ART_RLIMIT_DATA` (default `1.25 × RSS cap`, `0` = off),
  `ACOS_ART_STREAM_CAP` (default `8M`), `ACOS_ART_LOG_CAP` (default `50000`),
  `ACOS_ART_LOG_TRACE` (prints every 10 000th entry with tag/message — the tool
  that named this incident's trigger). `guarded.sh` already exports
  `ACOS_HOST_RSS_MAX=2G`, which is the *VM's* guard; `acos-art` now has its own
  and they no longer need to be the same knob.
* **Never run `acos-art` unguarded** (ADR-0018). Every command in this document
  ran under `tools/guarded.sh --mem 4G`.
