## 1. Item 1 — the dialog window attaches; W27's "addView blocks" is rejected

W27 concluded that the first non-Activity `WindowManager.addView` blocks the app main
thread and that the dialog root never reaches `WindowManagerGlobal.mViews`. W32 measured
the opposite: the host completes the whole attach, and the guest main thread returns to
its looper.

Instrumented the host with `ACOS_WMS_TRACE=1` (one line per `IWindowSession`
transaction + the add/relayout shapes; permanent, env-gated, in `window_session.rs`),
then tapped the `dialog-menu` fixture's Show-dialog button on the launch path
(`LaunchMain` live probe = the W27 window forest). 2026-11-12T01:24:26Z:

```
ACOSWMS add-request window=0x100000008 type=1 token=None title=Some("…/MainActivity") w=-1 h=-1
ACOSWMS add-done    window=0x100000008 result=0 frame=[0,128,1080,2337]        <- activity
ACOSWMS add-request window=0x100000011 type=2 token=None title=Some("…/MainActivity") w=-2 h=-2
ACOSWMS add-done    window=0x100000011 result=0 frame=[0,128,1080,2337]        <- DIALOG: ADD_OKAY
ACOSWMS relayout-request window=0x100000011 type=2 w=-2 h=-2 req=776x513
ACOSWMS relayout-done    window=0x100000011 result=0x7 frame=[152,976,928,1489]  (centred)
ACOSWMS enter code=9 (finishDrawing) …                                         <- dialog drew
ACOSWMS relayout-done    window=0x100000011 result=0x0 frame=[152,976,928,1489]
```

* `type=2` is `TYPE_APPLICATION`; the image's `PhoneWindow.adjustLayoutParamsForSubWindow`
  assigns a parent token only for `FIRST_SUB_WINDOW..LAST_SUB_WINDOW` (1000..1999), so a
  dialog is a **top-level** app window with `token = null` and its own `IWindow` token.
* the reply is `ADD_OKAY`, the dialog gets its **own compositor layer**
  (`bind_surface_layer`), `z = windows.len()+1` (above the Activity) and a
  `ClientWindowFrames` frame from the client-measured size (WRAP_CONTENT 776x513 centred
  in `[0,128][1080,2337]` → `[152,976,928,1489]`).
* the guest submitted the dialog's buffers: `c1_generation 7 → 66` across the tap.

**What still fails is guest-side.** During the stall:

* ART `kill -QUIT` of the guest: `"main" … state=S … held mutexes=` →
  `android.os.MessageQueue.nativePollOnce` ← `MessageQueue.next:335` ← `Looper.loop:294`
  ← `dev.acos.art.LaunchMain.run:346` — the main thread is **idle in its looper**, not
  blocked in a binder call.
* per-thread `wchan`: tid 1 `do_epoll_wait`, `acos-live-probe` `futex_do_wait`
  (`Thread.sleep(50)`); Signal Catcher `Dl`.
* the W27 probe publishes no sample after the dialog attaches (`probe_seq 83 → 83`), and
  the launcher's own `ACOSPROBE-STALL-DETECT` (fires when the probe's `pending` flag is
  set >2 s) never appears ⇒ the posted probe Runnable **did run** and `emitProbe` threw;
  the launcher swallows it (`catch (Throwable ignored)`).

So the wall is inside `acos-art`'s probe (walking a second root), not the WMS. The
session path used by `acos verify` is a second, independent gap: `SessionMain`'s tree is
`AppMain.dumpTree(sDecor)` — the Activity decor only, so no selector can ever see
`android:id/message` there even with the attach fixed.

### Request to W31 (`crates/acos-art/**`; not touched by W32)

1. **`AppMain.dumpTree(View)` → window forest.** Walk `WindowManagerGlobal.getWindowViews()`
   (fallback `mViews`), the Activity decor first labelled `"main"`, exactly like
   `LaunchMain.emitProbe` already does; add `windows:[{z,window}]` and per-node
   `window` + `bounds_on_screen` to the session `tree` JSON.
   Files: `crates/acos-art/guest/java/dev/acos/art/AppMain.java` (`dumpTree`, `appendViewJson`),
   `SessionMain.java:650` (`sLastTree = AppMain.dumpTree(sDecor)`).
2. **`LaunchMain.emitProbe`: report the swallowed throwable once**
   (`System.out.println("ACOSPROBE error=" + t)`) — one line turns the remaining stall
   into a named stack. The throw is reproducible with
   `results/art-runtime/evidence/W32-repro-dialog.sh .cache/w32/repro3 252`.
3. **C1 capture must be a composite of the visible window layers**, not one layer: the
   dialog's buffers are stored (`c1_generation` advances) but the captured pixels are
   unchanged (`tap … pixels did not change from the previous capture`). Check
   `capture.rs`'s use of `newest_frame_layer()` (compositor registry) against the window
   z-order the trace shows.
4. **Input offset is per window.** `crates/acos-cli/src/engine/art.rs::probe_input_offset`
   derives one `(dx,dy)` from the first node that has both `bounds` and
   `bounds_on_screen`; with two windows the dialog's origin differs from the Activity's
   (the dialog's `bounds` must be window-local to its own frame `[152,976]`). Request to

With (1)+(3) the scenario's steps 4–6 have a tree/frame; with (4) step 7's OK tap lands
in the dialog window. The host needs no further change for it (the dialog's

## 2. Item 3 — `IPackageManager` 83/85/203 (done)

* 83 `setComponentEnabledSetting(ComponentName, newState, flags, userId, callingPackage) → void`
* 203 `queryProperty(String, int userId) → ParceledListSlice`

`ComponentName` typed body = presence word + `writeString16(package)` + `writeString16(class)`.

it**, and answers `queryProperty` with the typed `null` slice (`acos-apk` parses no
`<property>` elements, so the empty list is the honest stock answer).

## 3. Item 2 — the `Intent` wire, read from the image (next piece, not implemented)

`Landroid/content/Intent;->writeToParcel(Landroid/os/Parcel;I)V` (`classes.dex`), verbatim
order (and `readFromParcel` mirrors every step):

```
action        writeString8   / readString8
data          Uri.writeToParcel(Parcel, Uri) [static]: null -> writeInt(0);
                                              else writeInt(1) + Uri.writeToParcel(Parcel,int)
type          writeString8
identifier    writeString8
flags         writeInt
package       writeString8
component     ComponentName.writeToParcel(ComponentName, Parcel) [static]:
                null -> writeString(null)  (a *single* String16 null, no presence word)
                else -> ComponentName.writeToParcel(Parcel,int) = writeString(package),
                                                                 writeString(class)  (String16!)
sourceBounds  presence int (0/1) + Rect.writeToParcel
categories    count int + count × writeString8     (0 = null)
selector      presence int (0/1) + recursive Intent.writeToParcel   (recursion!)
clipData      presence int (0/1) + ClipData.writeToParcel          (full ClipData body)
contentUserHint writeInt
extras        Parcel.writeBundle (the existing `write_bundle`)
originalIntent presence int (0/1) + recursive Intent.writeToParcel
```

Two traps for whoever implements it:

* the Intent-level strings are **String8** (`writeString8`/`readString8`), while
  `ComponentName`'s are **String16** (`writeString`); a uniform `Str16` mis-decodes the
  action of every `startActivity` request.
* `ComponentName` has **no** presence word here — a null component is one null String16.
  (`parcelable.rs`'s `android.content.ComponentName` spec `[Str16, Str16]` is the
  *typed-object* shape and cannot be reused for this field.)
* the image's `Landroid/net/Uri;` in `classes2.dex` declares only the **static**
  `writeToParcel(Parcel, Uri)` (its instance writer is absent from the dex), so an Intent
  with a non-null `data` Uri is not serialisable on this image until that is understood —
  prefer a structured error over a guessed body.

The clean home is a dedicated `FieldOp`/`parcelable` dynamic form (recursion +
presence-in-string cannot be expressed by the flat spec table), next to
`write_bundle`. `IActivityTaskManager.startActivity` then still needs the second
`scheduleTransaction`/`LaunchActivityItem` delivery, which W27's
`UNSUPPORTED_ANDROID_API` marker keeps honest until both halves exist.
