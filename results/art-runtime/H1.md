# H1 (launch-hang-fix) — `launch` returns when the guest dies before its milestone

Status: **accepted on `launch-hang-fix`** (commit on the branch, no push). Start stamp
`2026-11-11 04:15:26 UTC`; stop stamp `2026-11-11 04:45 UTC`. This section closes S6.md
§5 residual 1. The older H1 cleanup report follows unchanged below the separator.

## 0. Outcome (what is observable now)

`acos-art launch --until <milestone>` no longer blocks when the guest dies first. It reports the
guest's end as a structured result, cleans the run root and the guest scope, and leaves no process
naming the run's data tree:

| guest end | `outcome` | `code` | fields |
|---|---|---|---|
| normal `Application.onCreate` | `ok` | `null` | `guest_exit: 0`, `wall_ms: 159` |
| exits before milestone (missing Landlock plan) | `crash` | `GUEST_EXITED` | `guest_exit: 126`, `notes` has `ERR landlock=plan-missing` |
| killed by signal (whole-list KILL audit) | `crash` | `GUEST_KILLED_BY_SIGNAL` | `guest_signal: 31` (SIGSYS), stderr tail retained |
| milestone deadline | `timeout` | `TIMEOUT` | `guest_exit: null`, `guest_signal: null` |

`LaunchResult` now also carries `guest_exit`, `guest_signal`, `wall_ms` and `notes` (cgroup, guard
evidence, fail-closed reason). The existing `stderr` field remains the bounded guest stderr tail.

## 1. Baseline (before the fix, shown first)

Whole-list KILL seccomp audit (`ACOS_ART_SECCOMP_AUDIT=kill`), the S6 trigger:


Log: `.cache/h1/baseline-audit.log` (only the guard preamble, then no output for 25 s).
The normal path immediately before it was `rc=0` in 2 s, so the hang was the guest's death, not the
route itself.

## 2. Cause and hypothesis ledger

Chronological first block after the guest died was the peer thread's blocking `accept(listener)`:
the guest's preload constructor killed it before it connected, so no client ever arrived. `launch`
then waited 5 s for a peer summary and called `peer_thread.join()` without a deadline — forever.
Because `launch` never returned, `RunDir`'s `Drop` never removed the run root.

| Observation | Hypothesis | Prediction if true | Cheapest falsifying experiment | Result | Verdict | Remaining alternatives |
|---|---|---|---|---|---|---|
| rc 124; run root present; no JSON | guest died pre-connect, peer blocked in `accept` | a timeout/nonblocking accept lets launch return | kill guest before connect (audit/missing plan), measure return | 89 ms / 23 ms after fix; no run root | **confirmed** | none |
| `peer_thread.join()` unbounded | unbounded join is the second lock | bounded summary wait + stop flag returns even if peer wedges | instrument/observe unmodified run | baseline never returned; after fix returns | **confirmed** | a wedged service handler could still delay, now detached after 2 s |
| guest died before milestone, yet code was `NO_*`/exit | termination was not represented in result | status must be normalised and carried in JSON | check JSON before/after | baseline no JSON; after fix `guest_exit`/`guest_signal` exact | **confirmed** | none |
| run root survived | function never reached `RunDir::drop` | returning removes it | inspect `<data>/runs` | empty after every fixed run/test | **confirmed** | SIGKILL of launcher still needs the janitor (S4) |
| scope could outlive guest | root-process exit does not reap descendants | `cgroup.kill()` after guest end | process scan after signal test | none after 3 s | **supported** | detached host *thread* if a service handler wedges >2 s |
| missing Landlock plan returned `Err` once unblocked | guard refusal must stay fail-closed but structured | result carries exit 126 + guard note, not an opaque error | missing-plan run | `GUEST_EXITED`, `guest_exit:126`, note `plan-missing` | **confirmed** | other routes keep their existing `SECCOMP_UNAVAILABLE` error |

## 3. Fix (localised to `crates/acos-art/src/launch.rs`)

* Listener is `O_NONBLOCK`; the peer accept loop polls a shared stop flag.
* Accepted client gets `SO_RCVTIMEO=100 ms`; `serve` uses that only to observe the stop flag (a live
  idle guest continues; queued frames are still read).
* After the wait loop: set stop, `cgroup.sample()`, and `cgroup.kill()` when the root guest ended.
* Peer summary wait is 2 s; on timeout the thread is detached, never joined unbounded.
* `split_exit_status()` undoes bwrap's `128+signal` remap, so a SIGSYS kill is signal 31.
* Classification order: ok → timeout → signal → post-resume exit → no-resume → any early exit
  (`GUEST_EXITED`) → legacy `NO_APPLICATION`/`NO_BIND_*`.
* Guard refusal is folded into `notes`; it still cannot become `ok` (if it would, it becomes
  `unsupported`/`SECCOMP_UNAVAILABLE`).
* No Cargo files, STATUS.md, guest Java, window/session, services or WM files touched.

## 5. Residuals

1. A service handler that wedges for >2 s is detached rather than joined; the guest process tree is
   already killed, but a host thread could outlive the call. No such case was observed.
2. The guard-refusal path is now a structured result (`crash` + exit/signal + notes) on `launch`
   instead of `Err(SECCOMP_UNAVAILABLE)`. It still cannot be `ok`; other routes are unchanged.
3. `cleanup.rs` tests use `<repo>/.cache/h1-tests/...`; in this deep worktree their socket path
   exceeds `SUN_LEN`, so the full suite was verified in a short-path detached worktree of this
   branch. That is an environment limit of the old suite, not a launch regression; the new launch
   tests use short scratch paths.
4. `sandbox_s5::allocator_bomb…` is independently flaky on this shared host (observed once with no
   OOM event at the cap, then green). Not caused by this change.
5. The run-root janitor still covers a SIGKILLed launcher (S4); the new deadline covers guest death
   while the launcher is alive.

# H1 — cleanup and limits, proven from outside the launcher

Status: **implementer**, hard checkpoint 60 min, **nothing committed**. Owner files, all new:
`tools/art-runtime/leakcheck.sh`, `crates/acos-art/tests/cleanup.rs`, this file. No existing file
was edited (P4c owns `crates/acos-art/src` and `crates/acos-binder-peer`). Every ART/cargo command
went through `tools/guarded.sh`; scratch under `.cache/` (`.cache/h1/`, `.cache/h1-tests/`), never
`/tmp`; one ART process at a time (the suite serialises itself, §2.5).

Question this closes: R1's ceilings and S3's `--die-with-parent` were measured *once, by hand*.
Nothing stopped them regressing the next day. H1 turns both, plus "the run ends and the host goes
back to its earlier state", into repeatable checks that fail a build.

## 0. What was added

### 0.1 `tools/art-runtime/leakcheck.sh`

A three-mode snapshot/diff tool (no ART knowledge, no assumptions about *why* something survived):

```
leakcheck.sh snapshot STATE_FILE
leakcheck.sh check    STATE_FILE          # exits 1 and prints every leaked item
leakcheck.sh watch    STATE_FILE -- CMD   # snapshot, run CMD, check; rc=1 on any leak
```

Snapshot contents, all diffed by identity (not by name):

| class | identity | source |
|---|---|---|
| process | `pid:starttime` (pid reuse cannot fake or hide a leak) | `/proc/*/{comm,stat,cmdline}`, matched on `dalvikvm64`, `bwrap`, `acos-art`, `SessionMain` |
| cgroup | scope path | `/sys/fs/cgroup/**.scope` with `memory.max`, path matching `acos|guarded|systemd-run` |
| scratch | realpath | `target/tmp/guarded.*`, `.cache/tmp/*`, `.cache/acos-*`, `.cache/art/data/session/*` (+ `ACOS_LEAKCHECK_ROOTS`) |
| socket | `proto addr` | `/proc/net/{tcp,tcp6,unix}`, LISTEN/`SO_ACCEPTCON` only, and only sockets owned by a matched process |
| memfd | `pid` | `/proc/<pid>/fd -> memfd:` for matched processes |

Two noise filters, both earned while testing (they made the first runs report nonsense):

* a `bwrap` only counts when its cmdline names a path inside this repo — every desktop has
  flatpak/snap bwrap wrappers starting and stopping constantly;
* a process record is one line even when `bash -c '<script>'` puts newlines in the cmdline (that
  bug made the scanner "find" fake state lines), and a scan containing an unrecognised line is
  refused (`exit 3`) instead of interpreted.

Scratch entries are re-checked for existence when reported: a directory that a *concurrent* process
was using during the scan (another agent's `target/tmp/guarded.*`) is transient, not a leak. A real
leak still exists after the run.

### 0.2 `crates/acos-art/tests/cleanup.rs` (4 tests)

All four run the shipped binary (`env!("CARGO_BIN_EXE_acos-art")`) and assert from **outside** it:
a full `/proc` scan for processes, `/proc/<pid>/status:VmHWM` for peak RSS, and a datagram flood
into the real per-session logd sink. No internal counter can satisfy them.

| test | what it proves |
|---|---|
| `render_app_leaves_no_processes_or_scratch_behind` | normal `render-app` writes a real frame, then leaves **no** matching process and **no** new `<data>/session/*` dir within 3 s |
| `sigkill_of_the_launcher_takes_the_guest_and_bwrap_with_it` | launcher started in its own session (`setsid`) so the harness cannot mask anything; waits for a *new* `dalvikvm64`, `SIGKILL`s the launcher, then asserts guest **and** bwrap are gone within **3 s** (S3 `--die-with-parent`), and prints what the run had started and what survived |
| `r1_watchdog_reports_host_memory_limit_and_leaves_no_orphans` | with `ACOS_ART_RSS_MAX=1M` (and `ACOS_ART_RLIMIT_DATA=0` so the rlimit backstop cannot pre-empt the structured report), the run ends non-zero with `outcome=unsupported`, `code=HOST_MEMORY_LIMIT`, the trip naming `ACOS_ART_RSS_MAX`, and no orphan 3 s later |
| `log_spam_keeps_the_launcher_peak_rss_under_256_mib` | the R1 flood at product level: 300 MiB of shim-format log frames into `<data>/session/<id>/socket/logdw` while sampling the launcher's `VmHWM`; asserts peak **< 256 MiB**, `close` exits within 10 s, no survivors |

Host hygiene inside the suite: a private `cp -a` copy of the warm `/data` per test (so it cannot race
another agent's run), a `Reaper` guard that `SIGKILL`s the launcher if a test panics mid-run, a
`SIGKILL` for any survivor before asserting (so a failing assertion does not itself leak a guest),
and one `Mutex` so two guests are never alive at once. Missing sysroot or cached guest dex ⇒ the test
prints `SKIP …` with the command that produces the artefact and passes without asserting — a
`cargo test` cannot build a 1 GB sysroot.

## 2. Finding — a `session` run leaks its scratch directory (not a process/memory leak)

`leakcheck.sh` on a `session` that is opened and closed cleanly:

```
$ ACOS_LEAKCHECK_ROOTS=$PWD/.cache/h1/sess-leak2/data/session \
  tools/art-runtime/leakcheck.sh watch .cache/h1/lc/sess7.tsv -- bash .cache/h1/sess-leak2/run.sh
leakcheck: watched command exited rc=0
LEAK scratch dir /home/Qui/Projects/acos/.cache/h1/sess-leak2/data/session/h1leak2
leakcheck: FAIL — 1 leak(s)
```

`session` creates `<data>/session/<id>/{out,overlay,socket}` and never removes it; after `close` the
host keeps the directory, its `out/`, its copied overlay idmaps and the (now dead) `logdw` socket
inode path. `<data>/session/` in the productised tree currently holds 3.0 MB of such dirs from past
runs (`ab`, `acc0`, `n1a0`, `r1ev`, …, and `h1lc`/`h1leak` from this experiment — the ones this
checkpoint created were removed).

Classification: **scratch growth, not a leak of processes/memory/sockets.** It is bounded by the
number of sessions ever run, not by run length, and it is the same root cause S3 §5 named: there is
still no per-run data root, and `session` has no teardown step for its own dir. Suggested fix (not
done here — `session.rs` is P4c's this checkpoint): remove `sdir` at the end of `run_session` (keep
it on failure/`ACOS_ART_KEEP_SESSION=1` for debugging), or move it under the per-run dir from S3 §5.
The suite is unaffected because each test uses its own data copy inside its scratch dir.

No other leak was found: no surviving `dalvikvm64`/`bwrap`/`SessionMain` after normal runs, after
`SIGKILL` of the launcher, or after a watchdog kill; no listening socket, memfd or cgroup scope left
behind; no `render-app` scratch.

## 4. Residual / not covered

* The tests prove the *current* argv is enough; they do not prove that removing
  `--die-with-parent` fails, because that edit belongs to `lib.rs` (S3's `plain` trial already
  measured the negative: bwrap + guest both survive). Once P4c's changes land, a temporary revert is
  worth one run of test 2 as a mutation check.
* Nothing here bounds a guest that is *legitimately* long-running: the watchdog only acts on the
  launcher's RSS. A stuck supervisor is still a cgroup/timeout problem (S3 §3), which needs the
  mandatory per-run cgroup S1 §5 item 3 proposed.
* `leakcheck.sh` audits processes/sockets/memfds/scopes/dirs, not file *contents*: a guest that
  poisons `boot.art` or `classpath` (S3 §5) leaves no trace in this snapshot.
