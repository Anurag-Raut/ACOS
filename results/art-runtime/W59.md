# W59 — where the counter tap's 1.1 s goes, and the settle rule that pays it

UTC: **start 2026-11-12T06:27:00Z** (approx., first guarded run 06:32:27Z),
**end 2026-11-12T06:56:29Z**. No commit of the fix, no push, no `git add -A`;
scratch is under `.cache/w59/` (never `/tmp`).

**Result in one line.** The 1.1 s is not input delivery and not the settle
*estimate* W55 reported: it is the **framework Button ripple** keeping the C1
producer storing a frame every vsync for ~825 ms after the click, which resets
`wait_for_settled_observation`'s 150 ms quiet window until the animation ends.
The guest's actual `FINISHED` ack is ~20 ms after the tap; W55's 1,124 ms
`input_ack_ms` was a **stale-ack accounting bug** (the first `collect` consumed
the focus/touch-mode acks queued at attach, and the real tap acks were charged
to the next gesture). Stage table, file:line, and a tested fix proposal follow.

## 3. The named cause

`crates/acos-art/src/launch.rs:1819` `wait_for_settled_observation()`:

* `:1829` `let quiet = Duration::from_millis(150);`
* `:1848-1867` the loop resets `last_change = Instant::now()` on **every** new
  C1 `buffer_generation`, and only returns when `last_change.elapsed() >= quiet`
  (plus probe/frame binding and a pixel-change check).

A framework `Button` tap starts `RippleDrawable`'s ripple. The API-34
`RippleAnimationSession` is `ENTER_ANIM_DURATION = 450` and
`EXIT_ANIM_DURATION = 375` (`.cache/aosp/base/graphics/java/android/graphics/
drawable/RippleAnimationSession.java:42-43`); the exit is delayed by
`max(ENTER - timeSinceEnter, 0)` (`:96-139` invalidate), so the ripple keeps
invalidating until ~825 ms after DOWN. On this guest the click's `setText`
also changes the `TextView`, so the ripple's frames are *valid post-click
pixels*, but they are animation frames: the producer stores one C1 buffer per
vsync (52 stores, gen 7→59, `841,098 … 1,687,820 µs`). Because every store
resets `quiet`, the settle cannot complete until the ripple ends
(`1,851,011 µs`, quiet 163 ms) — hence `1,025 ms` to settle and `1,140 ms` for
the tap. The form's target is an `EditText`, whose pressed/focus feedback stops
after two stores (`865,039` and `880,147 µs`), so the same rule costs 194 ms.

The click itself is synchronous and cheap: `View$PerformClick` runs at +19.7 ms
(counter) / +4.8 ms (form) and the click-frame store lands at +30.2 ms in both.
The 1.1 s is **entirely after the app's state is committed**, in the animation
tail the settle rule insists on waiting out.

### 3.1 The ack was not 1,124 ms — it was a stale-ack accounting bug

The guest's `NativeInputEventReceiver` acknowledges focus and touch-mode events
with `finishInputEvent(seq, true)`
(`.cache/aosp/base/core/jni/android_view_InputEventReceiver.cpp:419-421,457-459`),
even though `crates/acos-services/src/input_channel.rs:1274`'s comment says they
are not acknowledged. The window attach publishes focus/touch-mode as seqs 1,2;
nothing drains their FINISHED replies until the first input.
`crates/acos-services/src/input_dispatch.rs:563-590` `InputHost::collect()`
pushes **every** `Finished` it reads and stops at `acks.len() == seqs.len()`, so
the first tap returned on the two stale acks (`seqs=[3,4]`, `acks=[(1,true),
(2,true)]`, `total_ms=0`) and the tap's real acks 3,4 were left in the socket
until the next input's `collect`, which charged them the 1.38 s publish→drain
latency. That is why W55 measured "guest input ack 1124 ms"; it is a measurement
artifact, not delivery. The real delivery is the `PerformClick` at +20 ms.
`fix-ack-drain.patch` (below) filters acks to the published sequences so the
phase evidence is honest. It is a small independent fix and does **not** by
itself move the gate; the gate is the settle rule.

## 4. Fix proposal

**File/function:** `crates/acos-art/src/launch.rs`, `wait_for_settled_observation()`
(`:1819`). **Patch:** `.cache/w59/fix.patch` (not applied, not committed).

Replace the unconditional "no new store for 150 ms" gate with a **state-commit**
gate:

1. Snapshot the newest probe tree at entry (`baseline_tree`).
2. Remember the first probe sample whose tree differs from it (`commit_probe`):
   that is the guest's own post-input state, read on the main thread by the
   framework's view walk.
3. As soon as a C1 store lands **after** `commit_probe.at_ms`, and
   `generation > min_generation`, return `Settled { probe: commit_probe, … }`.
   The returned tree is the sample that saw the change; the returned pixels are
   the store that came after it, so tree and frame still describe the same
   state (the W10 binding rule is preserved, not dropped).
4. If the tree did not change (no-op tap, focus-only, or a `tree` command), keep
   the old 150 ms quiet rule and the 3 s/1.5 s deadlines.

**Expected saving.** ~0.98 s per counter tap: settle 1,025 → 42–70 ms, tap
1,140 → 133–157 ms (counter) and 194 → 42–70 ms settle, 295 → 141–192 ms
(form) in the validation run. That is a p95 well inside the 300 ms target
instead of 1,142 ms. It also speeds the post-tap `tree` (248 → 116–139 ms) because
the tree no longer waits out the same animation tail.

**Why this is AOSP-faithful, not faked.** Android's input contract ends at
`ViewRootImpl.finishInputEvent` (`ViewRootImpl.java:9829-9856`): the input
receiver acks as soon as `dispatchTouchEvent` returns, *before* the traversal and
independently of any `Choreographer` animation. A real device's `tap` therefore
does not wait for a ripple to finish; the app's state (`count` 0→1) is committed
by the click runnable and the next traversal, both of which happen at +20/+30 ms
here. Waiting for `buffer_generation` to stop moving is a harness rule, not an
Android rule. The fix does not invent a frame, a tree, or a state: the reply's
tree is still the guest's own probe sample and the frame is still the C1 buffer
stored after that sample, and `state_changed` is still computed from the host's
own pixel/tree comparison. The old rule's actual purpose — never bind a
touch-feedback frame to a post-click tree — is enforced more directly by
"store after the probe that saw the change".

**Ownership note for the ack fix.** `crates/acos-services/src/input_dispatch.rs`
is B1b's right now, so `.cache/w59/fix-ack-drain.patch` is written but **not
applied**. It filters `Finished` replies to `seqs.contains(&ack.seq)` in
`InputHost::collect`. It is independent of the gate fix and should be reviewed
by B1b.
