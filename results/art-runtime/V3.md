# V3 — the vsync NPE is gone: `getLatestVsyncEventData`'s reply was missing `Parcel::writeParcelable`'s non-null flag

**Status: FIXED, with byte-level evidence.** With `ACOSLAUNCH_PROBE=1` the probe now gets
**8 consecutive `Choreographer.doFrame` callbacks with no exception**, 7 inter-frame deltas of
exactly `16666667 ns` (60 Hz), monotonic and contiguous (`results/art-runtime/w2/probe.json`).
The NPE that L1 §3.8 left behind was **not** in the 216-byte vsync event, not in our JNI
class/field IDs, and not in the Java `DisplayEventReceiver` allocation: it was one missing
`int32` in the **`IDisplayEventConnection.getLatestVsyncEventData` reply**.

## 1. Root cause (proved, not guessed)

The guest's own log, in order, in the L1 probe run:

```text
DisplayEventReceiver: Failed to get latest vsync event data:            <- libgui.so DisplayEventReceiver.cpp:102
DisplayEventReceiver: Failed to get latest vsync event data from surface flinger  <- android_view_DisplayEventReceiver.cpp:366 (returns NULL)
java.lang.NullPointerException: ... 'int android.view.DisplayEventReceiver$VsyncEventData.frameTimelinesLength'
  on a null object reference in method '... Choreographer$FrameData.update(long, DisplayEventReceiver$VsyncEventData)'
```

That ordering is the whole diagnosis: the native `getLatestVsyncEventData` call failed **first**
(so it returned `NULL`), and the Java path then fed that `null` into `FrameData.update`.

### 1.1 What the image's Java actually does (dexdump, `classes4.dex`)

```text
Landroid/view/Choreographer$FrameDisplayEventReceiver;
  .onVsync(JJILandroid/view/DisplayEventReceiver$VsyncEventData;)V
     invoke-virtual {mLastVsyncEventData, vsyncEventData}, VsyncEventData.copyFrom(...)
  .run()V
     mLastVsyncEventData -> Choreographer.doFrame(JIL...VsyncEventData;)V

Landroid/view/Choreographer$FrameData;
  .update(JLandroid/view/DisplayEventReceiver;)Landroid/view/Choreographer$FrameTimeline;   // Choreographer.java:1210
     invoke-virtual {receiver}, DisplayEventReceiver.getLatestVsyncEventData()...            // may be null
     invoke-virtual {this, frameTimeNanos, that}, FrameData.update(JL...VsyncEventData;)     // Choreographer.java:1170
        iget v0, vsyncEventData, DisplayEventReceiver$VsyncEventData.frameTimelinesLength:I  <- NPE here
```

So the image differs from the `android-14.0.0_r75` source snapshot in `.cache/aosp`: `doFrame`
re-reads the data through `DisplayEventReceiver.getLatestVsyncEventData()` (an AIDL round trip)
instead of using the object `dispatchVsync` filled through the weak reference. `nativeGetLatestVsyncEventData`
returns `NULL` on failure (`base/core/jni/android_view_DisplayEventReceiver.cpp:360-370`), which
is exactly the null the image's `FrameData.update` dereferences.

### 1.2 Why the AIDL call failed (`libgui.so` / `libbinder.so` disassembly)

The image's generated proxy reads its **parcelable return** with `Parcel::readParcelable`:

```text
libgui.so  BpDisplayEventConnection::getLatestVsyncEventData  0x1618c0
  0x1619f5  mov $0x4,%esi                    ; transaction code 4
  0x161a10  call Status::readFromParcel      ; exception header
  0x161ac5  call Parcel::readParcelable      ; <-- the return is a Parcelable, not raw bytes
```

`Parcel::readParcelable` **consumes an `int32` non-null flag first**:

```text
libbinder.so  Parcel::readParcelable  0xa2aa0
  0xa2b00  mov (%rdx,%rax,1),%eax           ; read int32 present
  0xa2b07  cmp $0x1,%eax
  0xa2b0a  jne  a2c2b                       ; != 1 -> BAD_TYPE, no body read
```

and the writing side is symmetric:

```text
libbinder.so  Parcel::writeParcelable 0xa0b30
  0xa0b51  movl $0x1,(%rcx,%rax,1)          ; writes int32 1 before Parcelable::writeToParcel
```

V1 answered code 4 as `status + body`. The framework therefore read **the low word of
`frameInterval` (`16666667` = `0x00fe4e6b`) as the present flag**, got `BAD_TYPE`, and
`getLatestVsyncEventData` failed. Nothing else about the body was wrong:

```text
libgui.so  ParcelableVsyncEventData::readFromParcel  0x14a550
  +0x08 readInt64  frameInterval
  +0x10 readUint32 preferredFrameTimelineIndex
  +0x14 readUint32 frameTimelinesLength
  loop: +0x18 readInt64 vsyncId, +0x20 readInt64 deadlineTimestamp, +0x28 readInt64 expectedPresentationTime
```

which is exactly `VsyncEventData::write_to_parcel`'s order (and `writeToParcel` 0x14a730 writes
`frameInterval`, `preferred`, `length`, then the three int64 per timeline).

### 1.3 The three candidates in the brief

| candidate | verdict |
|---|---|
| (a) JNI class/field/ctor IDs for `DisplayEventReceiver$VsyncEventData` uninitialised because natives are registered selectively | **rejected.** `register_android_view_DisplayEventReceiver` (`libandroid_runtime.so` 0x143040) ran: the vsync reached `NativeDisplayEventReceiver::dispatchVsync` (0x142b10), which only calls Java **after** reading `gDisplayEventReceiverClassInfo.vsyncEventDataClassInfo.*` field IDs and calling `GetReferent`; a missing ID would have thrown/crashed there. The failing call is the *later* `getLatestVsyncEventData` round trip, which logged through the same class info. Also note the guest never had to register `DisplayEventReceiver`'s natives — that is `libandroid_runtime`'s own `RegisterMethodsOrDie`. |
| (b) Java-side `mVsyncEventData` allocation | **rejected.** `Landroid/view/DisplayEventReceiver;` in the image has `mVsyncEventData` as `PRIVATE FINAL` and `<init>(Looper,IIJ)` allocates it (`new VsyncEventData()`); the `null` is not that field, it is the return value of `getLatestVsyncEventData()`. `FrameDisplayEventReceiver.mLastVsyncEventData` is likewise allocated in its `<init>`. |
| (c) our 216-byte event / payload layout | **rejected for this NPE.** The event decodes (`EVENT_SIZE` asserted, `pollOnce → handleEvent → dispatchVsync` reached) and `dispatchVsync` itself fills the preallocated Java object through the weak referents. The null comes one layer up: `Choreographer.FrameData.update(long, DisplayEventReceiver)` re-fetches the data via AIDL. The actual defect is the **parcelable framing** of that AIDL reply (missing present flag), not the inline `Event` layout. |

## 2. The fix (minimal, stock-first)

`crates/acos-services/src/display_events.rs`

```rust
pub const NON_NULL_PARCELABLE_FLAG: i32 = 1;

impl VsyncEventData {
    /// Parcel::writeParcelable: flag first, then ParcelableVsyncEventData::writeToParcel.
    pub fn write_parcelable_to(&self, parcel: &mut Parcel) {
        parcel.write_parcelable_marker(true);      // == libbinder's `int32 1`
        self.write_to_parcel(parcel);              // unchanged body
    }

    /// Parcel::readParcelable (strict: anything but 1 is BAD_TYPE).
    pub fn read_parcelable_from(parcel: &mut Parcel) -> SResult<Self> { ... }
}
```

Code 4 now writes `status + 1 + body` (48 bytes for one timeline) instead of `status + body`;
`write_to_parcel`/`read_from_parcel` stay the pure `ParcelableVsyncEventData` body, so nothing
else in the module changes behaviour. The `non_null` flag is written with the crate's existing
`Parcel::write_parcelable_marker`, the same primitive `stealReceiveChannel`'s `BitTube` reply
already needed (L1 §3.4) — the two failures had the same shape and the second was hidden behind
the first.

`crates/acos-art/guest/java/dev/acos/art/LaunchMain.java` (probe only, off by default)

* `postFrameProbe()` now collects `PROBE_TARGET_FRAMES = 8` frames and prints per-frame
  `deltaNanos`, plus one summary line with all deltas, `monotonic` and `contiguous`.
* `awaitFrameProbe()`: when the probe is enabled, the watcher waits (≤3 s) for the probe to
  finish **before** pushing the activity transaction. This is a timing guard for the diagnostic
  run only: the transaction's `addToDisplayAsUser` reply is the next wall (§4) and throws on the
  main thread, which used to cut the probe off after one frame. Probe disabled ⇒ no wait.
* Probe gate: `ACOSLAUNCH_FRAME_PROBE` **or** `ACOSLAUNCH_PROBE`. `launch.rs`'s sandbox
  (`crates/acos-art/src/launch.rs:284-291`, S5's file) clears the environment and re-seeds a
  fixed allowlist that forwards `ACOSLAUNCH_PROBE` but not `ACOSLAUNCH_FRAME_PROBE`, so the
  documented `ACOSLAUNCH_FRAME_PROBE=1` never reached the guest in this tree. Not edited here.

## 6. Limits / next

* The launch still stops at `addToDisplayAsUser`'s `InsetsState` reply (`DisplayCutout`
  `readTypedArray: bad array lengths`, L1 §E2) — W1/W2 codec work, one call before `relayout`.
  The probe run's log shows the same failure after the 8 frames, so the fix did not mask it.
* Two extra code-4 calls appear per run (`FrameData.update(long, DisplayEventReceiver)`
  re-fetches on every frame that goes through that overload); the reply is a pure read of the
  clock state, so this is cheap, but it is why the frame path needs the AIDL half to be correct,
  not just the `BitTube` half.
* The probe stays behind `ACOSLAUNCH_PROBE`/`ACOSLAUNCH_FRAME_PROBE`; default runs are unchanged
  in timing and outcome.
