# T0 — can an LD_PRELOAD interposer stand in for the gralloc HAL under stock `libui`/`libgui`?

**Verdict: (A) is feasible with a preload interposer of 8 entry points** for
`construct → allocate → lock → write → unlock → destroy`, **11 for the
`BufferQueue`/transport path** (add `importBuffer`, `freeBuffer`, and the four
`GraphicBufferMapper::set*` metadata setters that `libgui` calls — 15 total).
Not "needs stock gralloc HAL emulation", not "not feasible".

**The advisor's weakest assumption is confirmed, and it is worse than stated:**
interposing allocation is *not* enough — but the wall is not
`GraphicBufferAllocator` either. It is **`GraphicBufferMapper`'s constructor**,
which runs on the *first* `GraphicBuffer` construction (`GraphicBuffer()`'s init
list: `mBufferMapper(GraphicBufferMapper::get())`), and in the API-34 image it
does not fatal — it **hangs forever in HAL service discovery**. A shim that only
covers `allocate` never reaches `allocate`.

- Owner / date: T0 implementer agent, hard 45-minute checkpoint (used ~44), no commit.
- Scope written: `research/art-feasibility/t0-gralloc/**` (3 new files) and this file.
  **`crates/` untouched**, nothing committed.
- Every probe ran through `tools/guarded.sh --mem 4G --time 300`; one bwrap/ART
  process at a time; all scratch under `.cache/t0-gralloc/` (never `/tmp`).
- Image under test: `.cache/art/sysroot/system/lib64/{libui,libgui}.so`
  (API 34 x86_64 SDK image). AOSP reference: `.cache/aosp/native/libs/ui`
  (`android-14.0.0_r75`) — **which differs from the image in one important
  place**, §1.3.

## 1. Symbol evidence: what is interposable, and what is not

### 1.1 No `-Bsymbolic`, so `LD_PRELOAD` wins

```
readelf -d libui.so | grep -E 'SYMBOLIC|FLAGS'
  (FLAGS) BIND_NOW ;  (FLAGS_1) NOW      # no SYMBOLIC, no DF_1_SYMBOLIC, no PROTECTED
nm -D --defined-only libui.so | grep Gralloc   # every relevant symbol is `T`/`W`, default visibility
```
`BIND_NOW` is irrelevant to interposition: it only forces *when* the dynamic
linker resolves, not *which* definition it picks.

### 1.2 Every call in the `GraphicBuffer` path is a PLT call

`readelf -rW libui.so` has an `R_X86_64_JUMP_SLOT` for each of these (i.e. the
call site goes through `.plt`, so the preload's definition is used):

| called from libui.so / libgui.so | symbol |
|---|---|
| `GraphicBuffer::initWithSize` | `GraphicBufferAllocator::allocate(w,h,fmt,layers,usage,&handle,&stride,id,name)` |
| `GraphicBuffer::initWithSize` | `GraphicBufferAllocator::GraphicBufferAllocator()`, `GraphicBufferMapper::getTransportSize()` |
| `GraphicBuffer::free_handle` | `GraphicBufferAllocator::free()`, `GraphicBufferMapper::freeBuffer()` |
| `GraphicBuffer::lock` | `GraphicBufferMapper::lock(handle,usage,Rect&,void**,int*,int*)` |
| `GraphicBuffer::lockAsync` | `GraphicBufferMapper::lockAsync` (both the 32-bit and the 64/64-bit usage overloads) |
| `GraphicBuffer::unlock` / `unlockAsync` | `GraphicBufferMapper::unlock` / `::unlockAsync` (**tail `jmp @plt`**, 0x2fadb) |
| `GraphicBuffer::unflatten` | `GraphicBufferMapper::importBuffer()`, `::getTransportSize()` |
| `GraphicBufferMapper/Allocator` singleton init | their own constructors (`@plt`, 0x59200 / 0x59230) |
| libgui.so (`BufferQueueConsumer`) | `GraphicBufferMapper::setDataspace/setSmpte2086/setSmpte2094_40/setCta861_3`, `GraphicBufferMapper::GraphicBufferMapper` |

Disassembly spot checks (`objdump -d --start-address=...`):

```
GraphicBuffer::lock        0x2f0b0: call 592f0 <GraphicBufferMapper::lock(...)@plt>
GraphicBuffer::unlock      0x2fad0: mov 0x70(%rdi),%rsi ; mov 0xc0(%rdi),%rdi ; jmp 59310 <...unlock@plt>
GraphicBuffer::lockAsync64 0x....: call 59330 <GraphicBufferMapper::lockAsync(...mm...9_)@plt>
```

The same disassembly gives the object layout the probe relies on: the
`native_handle_t*` sits at `+0x70` and the `GraphicBufferMapper&` at `+0xc0`
of `GraphicBuffer`, so `sizeof(GraphicBuffer)` is ~0xc8 — the probe reserves 256 B.

### 1.3 The image is *older* than r75 in the lock path (r75 diverges)

`.cache/aosp` r75 `GraphicBuffer::lockAsync` calls
`getBufferMapper().lock(handle, usage, rect, base::unique_fd)` returning an
`optional<LockResult>` (and queries `getPlaneLayouts()` for bpp/stride). The
**image** instead calls the classic `GraphicBufferMapper::lock/ lockAsync`
overloads with `void** vaddr, int* bpp, int* stride` — confirmed both by the
`R_X86_64_JUMP_SLOT` set (only the classic signatures are present) and by the
disassembly above. **Practical consequence: the shim signatures must be taken
from the image's `nm -D`, not from the r75 tree** — the r75 shape would have
demanded `getPlaneLayouts()` (a metadata call the image never makes).

## 2. The probe and the interposer (both run, both green)

Files (all new, under `research/art-feasibility/t0-gralloc/`):

| file | what it is |
|---|---|
| `gralloc_memfd_shim.c` | the interposer: memfd-backed `native_handle_t` (1 fd + 8 ints: w,h,stride,format,usage_lo/hi,layers,bpp), `mmap` on lock, `munmap` on unlock, `dup` on import |
| `gbprobe.c` | 30-line-shaped probe that drives **stock `libui.so`** by mangled symbol name — no Android runtime, no binder, no C++ stdlib in the probe |
| `run.sh` | builds both with the NDK's bionic clang, then runs the probe **inside the same bwrap mini-Android root the ART launcher uses** (`--unshare-pid/net/ipc/uts/cgroup-try --die-with-parent --clearenv --cap-drop ALL --tmpfs /`, `/system` ro-bound from the sysroot, runtime APEX bound at `/apex/com.android.runtime`, `/data` = `.cache/t0-gralloc/data`) |

Reproduce:
```
tools/guarded.sh --mem 4G --time 300 -- research/art-feasibility/t0-gralloc/run.sh --control   # no interposer
tools/guarded.sh --mem 4G --time 300 -- research/art-feasibility/t0-gralloc/run.sh             # with interposer
```

### 2.1 Control run (no `LD_PRELOAD`): **hangs, does not fatal**

```
== bwrap (control, no interposer)
[gbprobe] step 1: GraphicBuffer(w=320,h=240,RGBA_8888,usage=0x300) -- stock libui ctor
<no further output; rc=124 = TIMEOUT after 300 s>
```

It never reaches `LOG_ALWAYS_FATAL("gralloc-mapper is missing")`
(`.cache/aosp/native/libs/ui/GraphicBufferMapper.cpp:82`) and never prints
anything else: with no logd the fatal would be silent anyway, but this is not a
fatal — the process is alive, one thread, and `/proc/PID/syscall` reads
`running` with `RIP` inside the **vDSO** (`[vdso]` +0xd4e, +0xd82 in two
samples), i.e. a timed retry loop in userspace, not a blocking syscall.

The loop is in the mapper's constructor, before any gralloc2/3/4 fallback:
`Gralloc5Mapper::Gralloc5Mapper()` → `waitForAllocator()` →
`AServiceManager_isDeclared()` then **`AServiceManager_waitForService(
"android.hardware.graphics.allocator.IAllocator/default")`**
(`libs/ui/Gralloc5.cpp:53–60`; the string `AServiceManager_waitForService` is in
the image's `libui.so`). If the AIDL service is absent (ours is), the wait never
returns; no `/dev/binder` peer means servicemanager never answers.

**Confidence note (honest):** the *layer* is pinned by source + the string +
the ctor order, but the last step (whether `isDeclared` returns false and the
hang is instead the gralloc**4** HIDL `IMapper::getService()` retry,
`Gralloc4.cpp:162`) was not separately instrumented — that costs 3 minutes
(interpose `AServiceManager_isDeclared`/`_waitForService` in the same shim and
log) and changes nothing about the verdict: both branches are **mapper-init HAL
discovery**, and both are skipped by replacing one constructor.

### 2.2 With the interposer: full sequence passes

```
== bwrap + LD_PRELOAD=/data/libacet0.so
[gbprobe] step 1: GraphicBuffer(w=320,h=240,RGBA_8888,usage=0x300) -- stock libui ctor
[acet0] mapper:ctor(no HAL probe)
[acet0] allocator:ctor(no HAL probe)
[acet0] allocate:memfd bytes= 307200
[gbprobe] step 1 ok (no LOG_ALWAYS_FATAL)
[gbprobe] step 2: initCheck = 0
[acet0] lock:mmap bytes= 307200
[gbprobe] step 3: lock rc = 0 / vaddr = 0x… / bytesPerPixel = 4 / bytesPerStride = 1280
[gbprobe] step 4 ok: 320x240 RGBA written
[acet0] unlock:munmap ok
[gbprobe] step 5: unlock rc = 0
[acet0] lock:mmap bytes= 307200
[gbprobe] step 6: relock rc = 0
[gbprobe] step 6 ok: pixels round-tripped through the memfd     <-- the memfd is the backing store
[acet0] lock:mmap bytes= 307200
[gbprobe] step 7: lock(Rect) rc = 0                             <-- Surface::lock's overload
[acet0] unlock:munmap ok
[acet0] allocator:free
[gbprobe] step 8 ok: destroy (free_handle -> allocator free)
[gbprobe] ALL STEPS PASSED
```

Step 6 is the one that matters beyond "it did not crash": pixels written before
`unlock` are read back after a fresh `lock`, i.e. `GraphicBuffer` really owns a
memfd, not a scratch page, and `stride`/`bpp` are self-consistent (`1280 B` for
320 px @ 4 B/px).

## 3. Exactly which entry points the shim must cover

### 3.1 `construct → allocate → lock → write → unlock → destroy` — **8**

1. `android::GraphicBufferMapper::GraphicBufferMapper()` (C1/C2) — no-op.
   *Without it: hang in HAL discovery (§2.1).*
2. `android::GraphicBufferAllocator::GraphicBufferAllocator()` (C1/C2) — no-op.
   *Without it: never reached, but would be `LOG_ALWAYS_FATAL` at
   `GraphicBufferAllocator.cpp:70`.*
3. `android::GraphicBufferAllocator::allocate(…, id, std::string)` — memfd.
   (The 8-arg overload without `id` is also interposed; both are exported.)
4. `android::GraphicBufferAllocator::free(native_handle const*)`.
5. `android::GraphicBufferMapper::getTransportSize(handle, uint32*, uint32*)`
   — called by `initWithSize` right after `allocate`; must agree with the handle
   (`1` fd / `8` ints here), because `flatten()` derives `getFlattenedSize()`
   and `getFdCount()` from it.
6. `android::GraphicBufferMapper::lock(handle, uint32 usage, Rect&, void**, int*, int*)`
7. `android::GraphicBufferMapper::lockAsync(handle, uint64, uint64, Rect&, void**, int, int*, int*)`
   (+ the 32-bit-usage overload — `Surface::lock` takes the async path)
8. `android::GraphicBufferMapper::unlock(handle)` and `::unlockAsync(handle, int*)`
   — counted as one item; `GraphicBuffer::unlock` tail-jumps to `unlock`.

### 3.2 `BufferQueue` / BLAST transport (`importBuffer`, `freeBuffer`, `unflatten`) — **+7**

9. `android::GraphicBufferMapper::importBuffer(handle, w, h, layers, fmt, usage, stride, &out)`
   — `GraphicBuffer::unflatten` calls it for every buffer crossing the queue
   (unflatten source: `free_handle()`, build handle, then `importBuffer`, then
   `getTransportSize`). For a memfd allocator "import" = `dup(fd)` + a new
   metadata block — no process-local registry needed, and it works across a
   `BINDER_TYPE_FD`/`SCM_RIGHTS` hop because the memfd is a real kernel object.
10. `android::GraphicBufferMapper::freeBuffer(handle)`.
11. `android::GraphicBufferMapper::isSupported(w,h,fmt,layers,usage,bool*)`
    (harmless but cheap: `GraphicBuffer::isSupported` is on the queue path).
12–15. `GraphicBufferMapper::setDataspace`, `setSmpte2086`, `setSmpte2094_40`,
    `setCta861_3` — **new finding from `libgui.so`'s relocations**: these are the
    only mapper methods `libgui` itself calls through the PLT
    (`BufferQueueConsumer` sets dataspace/HDR metadata per buffer). Not
    no-ops-by-choice: they must either store into our handle metadata ints or
    return `OK` without touching the uninitialised `mMapper`.

Everything else the shim defines (`isSupported`, `importBuffer`, …) is either
free or one of the above.

### 3.3 What the stock side keeps doing for us (unchanged, unmodified)

`GraphicBuffer::initWithSize/initWithHandle/unflatten/flatten/getFlattenedSize`,
the whole stride/format/usage bookkeeping, `FreezeLock`, `Rect` bounds checks,
`BufferQueue*`, `BLASTBufferQueue`, `Surface::lock/unlockAndPost`. The shim owns
only *memory* (memfd) and *address* (mmap) — which is exactly what a gralloc HAL
owns. That is the option-(A) claim in `WR-window-surface-options.md` §2 S4,
confirmed at the symbol level.

## 4. Residual risks this T0 does **not** retire

1. **Methods we deliberately do not implement** read the never-initialised
   `mMapper`/`mAllocator` fields and would crash: `getPlaneLayouts`,
   `getBufferId`, `getWidth/Height/Usage/…`, `dumpBuffer`, `validateBufferSize`.
   The image's lock path does not call them (§1.3), but `validateBufferSize` is
   on the gralloc5 `importBuffer` path in some versions — the shim's own
   `importBuffer` replaces that, so the risk is limited to *other* callers.
   Mitigation if it appears: one more no-op that returns `OK`.
2. **Fences are stubbed** (`lockAsync` closes the input fence, `unlockAsync`
   returns `-1`). `-1` means "no fence / already signalled", which is legal for
   a CPU-written buffer, but it means BLAST's acquire-fence bookkeeping never
   waits on anything. Correct for software drawing; wrong if a GPU ever appears.
3. **Handle metadata is ours**: stride = `width` px, bpp from format. A wrong
   stride shows up as a visibly skewed frame (cheap to diagnose, as WR §6 says).
4. **1 process, 1 thread, no binder** in this probe. The remaining unproven
   joint is memfd handles surviving the *real* `Transaction::setBuffer` →
   flatten/unflatten (`+9/+10` above make that path reachable, but it was not
   exercised here).
5. `GraphicBufferMapper::preloadHal()` (called by `libgui`'s `SurfaceComposerClient`
   path?) still runs the four `GrallocN::preload()` probes — those are
   `dlopen`-only, no service wait, but should be no-op'd for symmetry if it
   shows up in T1/T4 logs.

## 5. Verdict line (for the owner)

**A (software gralloc **interposer** over memfds) is feasible: 8 entry points
for `ctor→allocate→lock→write→unlock→destroy` (mapper+allocator ctors, allocate,
free, getTransportSize, lock, lockAsync×2, unlock/unlockAsync), +7 for the
`BufferQueue`/BLAST transport (importBuffer, freeBuffer, isSupported,
setDataspace, setSmpte2086, setSmpte2094_40, setCta861_3). It does not need a
stock gralloc HAL daemon, a servicemanager, hwbinder, or binder at all. The
binding wall is not `allocate` but the `GraphicBufferMapper` **constructor**,
whose HAL discovery hangs (not fatals) — so S4's "~250–400 C lines" estimate
stands, with one correction: it must replace the constructors, not just the
methods, and it must also cover libgui's four metadata setters.**

**Cheapest next step (≤45 min):** T1/T2 are unaffected; for T4, fold §3.1+§3.2
into `crates/acos-art/shim/` (`libacoshw.so`, preloaded after `libartshim.so`)
and re-run the *same* probe from inside an `acos-art` session instead of bwrap —
that is the only way to see whether the ART process's linker namespace accepts a
second preload and whether bionic's `AServiceManager_*` is called at all there.
