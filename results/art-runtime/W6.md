## 1. What changed

### 1.1 `WindowSessionService::drain_raw_deliveries` (the delivery)

`crates/acos-services/src/window_session.rs` now implements the `ServiceObject` hook that the
host already calls for dynamic nodes (`host.rs:690`):

- the `acos-wm` callback queue is popped once per transaction on this node;
- **only** `WmCallback::DispatchAppVisibility { visible: true }` becomes a
  `PendingDelivery { target: window, interface: "android.view.IWindow", code: 7,
  data: callback.to_parcel() }` — the same encoding the VM path already uses
  (`acos-runtime/src/wms_java.rs:68`);
- it is delivered **once per window** (`visibility_delivered: HashSet<u64>`), so the
  per-relayout re-queue cannot become a traversal storm;
- `windowFocusChanged` (code 17 — the replay model's extension, no such transaction in the
  API-34 `IWindow$Stub`) and `resized`/`insetsControlChanged` are **not** delivered
  (`callbacks_deferred` counts them; `ACOS_W6_CALLBACKS=1` prints each);
- a `null` window binder (rejected add) is never addressed; nothing is fabricated.

The peer sends the reply frame first and the delivery frame in the same turn
(`Peer::handle` → `take_delivery_frames`), so the callback arrives **after** the add reply —
the ordering W5 §5.1 asked for.

### 1.2 `ACOS_W6_DUMP` (capture plumbing for the next wall)

`surface_client.rs` gained `dump_latest_buffer`: when a transaction stores a new
`LatestBuffer` and `ACOS_W6_DUMP=<dir>` is set, it reads the pixels **through C1's own dup
of the guest's fd** (`pread` of `stride × height × 4`) and writes `<dir>/frame-<n>.rgba`
plus `<dir>/frame-<n>.meta` (`layer, frame, w, h, stride, format, bytes, fnv1a,
non_zero_pixels, distinct_pixels`), printing one `ACOSW6 dump …` line. That is the
"buffer retrievable from the latest-buffer store, dump to PNG" step; it is opt-in and
touches no product behaviour.

## 3. The next wall, measured: `Surface.nativeLockCanvas` waits on a condvar

SIGQUIT thread dump while blocked (`.cache/w6/run2.out` → `logs`, real ART dump):

```text
"main" prio=5 tid=1 Native
  native: #00 pc 0005db98  /apex/com.android.runtime/lib64/bionic/libc.so (syscall+24)
  at android.view.Surface.nativeLockCanvas(Native method)
  at android.view.Surface.lockCanvas(Surface.java:473)

  at android.view.ViewRootImpl.drawSoftware(ViewRootImpl.java:4991)
  at android.view.ViewRootImpl.draw(ViewRootImpl.java:4967)
  at android.view.ViewRootImpl.performDraw(ViewRootImpl.java:4643)
  at android.view.ViewRootImpl.performTraversals(ViewRootImpl.java:3822)
  at android.view.ViewRootImpl.doTraversal(ViewRootImpl.java:2465)
  ...
"acos-launch-watcher" daemon tid=13 Blocked
  at android.view.Surface.isValid(Surface.java:384)
```

Two facts from it:

1. **`drawSoftware` is reached** (W5 stopped at `cancelDraw`); the visibility callback is
   what moved the wall. No `Log.e("Could not lock surface")` and no `BQ_LOGE` is emitted, so
   the call is *waiting*, not failing.
2. The probe **could not** complete in run1/run2: the main thread holds the Java `Surface`
   monitor while blocked inside `nativeLockCanvas` (`Surface.lockCanvas` is
   `synchronized (mLock)`), and `probeViewRoot` called `Surface.isValid()` on the same
   monitor. So `held-after-resume` was the last line of stdout, `quit()`/`halt()` never ran,
   and the run was reported `outcome=timeout` — a *diagnostic* deadlock, not a framework
   path. Fixed in `LaunchMain.probeViewRoot` (field reads only + a live `getHostVisibility()`
   reflection call); run7 then finished `outcome=ok` and printed the visibility row above.

Kernel-level measurement of the same block (`/proc/<payload>/task/*/syscall`, run6):

```text
tid 2602964 comm=ixtures.counter  wchan=futex_do_wait  syscall=202 0x7fee81e38dd0 0x89 ...
tid 2602983 comm=SurfaceSyncGrou wchan=do_epoll_wait
tid 2602976 comm=Thread-1        wchan=__skb_wait_for_more_packets   (binder driver reader)
tid 2602979 comm=acos-launch-wat wchan=futex_do_wait  0x80            (the probe's Java monitor)
```

`0x89` is `FUTEX_WAIT_BITSET_PRIVATE` — a **pthread/std condition-variable wait**, not a
binder ioctl: no host transaction is in flight, and every other guest thread is idle. Inside
`nativeLockCanvas` (`ANativeWindow_lock` → `Surface::lock`) the reachable condition variables
are the `BufferQueueCore` `mDequeueCondition` / `mIsAllocatingCondition` (the
`Surface::mMutex` path is a libutils `Mutex`, futex `0x80`). No gralloc `allocate`/`lock`
line exists, so the wait is before `GraphicBuffer` allocation, i.e. **before** the shim.

## 8. The next wall, as a work item (measured boundary)

Everything up to and including `ViewRootImpl.drawSoftware` is now real and driven by the
host. The remaining blocker is **one libgui wait**:

```text
main: Surface.nativeLockCanvas -> futex (pthread condvar)  [no host transaction in flight]
```

What is *excluded* by measurement (do not re-test):

- not the delivery (the callback ran; `host_visibility=0`; `performDraw` entered);
- not a binder call to the host (no dequeue in the peer log; every other guest thread idle;
  the futex op is `FUTEX_WAIT_BITSET_PRIVATE`, not an ioctl/read);
- not gralloc (no `allocate`/`lock` line from the shim, so the wait is before
  `GraphicBuffer` allocation);
- not `getHostVisibility()`/`ADD_FLAG_APP_VISIBLE` (W5's wall; closed).

Two experiments, in order, both cheap once the tool is in place:

1. **Native frame.** yama `ptrace_scope=1` and the guest is exec'd by the user manager, so
   `gdb -p` is denied. W3's recipe works: a freestanding `prctl(PR_SET_PTRACER, -1)`
   constructor appended to the *scratch* `shim/libartshim.so` (see
   `research/art-feasibility/w3-leash/scripts/`), then break on
   `android::BufferQueueProducer::{dequeueBuffer,waitForFreeSlotThenRelock,requestBuffer}`,
   `android::BufferQueueCore::{waitWhileAllocatingLocked}` and print
   `mCore->{mFreeSlots,mFreeBuffers,mActiveBuffers,mIsAllocating,mMaxDequeuedBufferCount,
   mMaxAcquiredBufferCount,mConnectedApi,mAllowAllocation,mQueue.size()}`. The frame alone
   decides between `mDequeueCondition` and `mIsAllocatingCondition`.
2. **Queue dump without ptrace.** `BufferQueueProducer::dumpState` is reachable from
   `Surface`/`IGraphicBufferProducer::dump`; adding a Java-side `Surface`-level dump is not
   possible, but the guest could call `android_view_Surface`'s `nativeDump`? It has none in
   API 34. So (1) is the practical route, or a small C probe inside the ART namespace that
   drives the same `BLASTBufferQueue` with the same `getMaxAcquiredBufferCount` answer.

A fix that is *inside this slice's files* and worth trying once the frame is known: the
compositor's `getMaxAcquiredBufferCount` answer (`compositor_client` code 57, value 2) is
what sizes BLAST's queue (`mBufferItemConsumer->setMaxAcquiredBufferCount`). If the frame
shows a slot-accounting dead end (`mFreeSlots` empty / `mMaxBufferCount` too small), that
answer is the lever; if it shows `mIsAllocating`, the lever is whoever called
`allocateBuffers` (nothing in the ACOS launch path does today). Do **not** guess between them.
