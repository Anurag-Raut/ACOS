# W4 — `InputEventReceiver.nativeInit` is a missing stock registration; `relayout` now returns a `SurfaceControl`, and BLAST is the next wall

**Status: DONE (next wall named).** The `UnsatisfiedLinkError` at
`ViewRootImpl.setView:1455` was not an input-channel problem: `LaunchMain.registerNatives()`
is a hand-maintained allowlist of exported `libandroid_runtime` registration entry points,
and `register_android_view_InputEventReceiver` was simply absent. Adding it (plus the two
registrations the next two traversals need) moves the real `counter.apk` launch through
`InputEventReceiver.nativeInit`, through `performTraversals`, and into
`IWindowSession.relayout`, whose reply is read as a `SurfaceControl` and converted to a
`Surface`. The next wall is now the compositor placeholder: `ViewRootImpl` constructs a
`BLASTBufferQueue` over that `SurfaceControl`; `BLASTBufferQueue` asks the placeholder
`ISurfaceComposerClient` binder (`0x01001001`) for `createSurface`, the peer answers
`UNKNOWN_BINDER`, the queue's surface control is NULL, and libgui aborts
(`BLASTBufferQueue: mSurfaceControl must not be NULL`, SIGABRT). No fake success; no Rust
VM fallback; no compositor was invented.

  **15:44** (elapsed **~18 min**; the 60-minute limit was not approached). Every ART run
  through `tools/guarded.sh --mem 4G --time 300`, one guest at a time, scratch under
  `.cache/w4/`; no `/tmp`.
- Scope written: **only** `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java`

  (`window_session.rs`/`input_channel.rs`), `crates/acos-wm`, `crates/acos-art/src/**`,

## 1. Root cause (measured, not inferred)

`LaunchMain.registerNatives()` exists because this launch does **not** run
`AndroidRuntime::startReg` wholesale; it resolves a fixed list of exported
`android::register_*_JNIEnv` functions through `RenderNat.register(String)` and calls them
(`crates/acos-art/shim/render_shim.c`: `lookup_symbol` tries `_ZN7android<len><name>EP7_JNIEnv`,
then the global `_Z<len><name>P7_JNIEnv`). L1 had already added the classes the window path
needed then (`SurfaceControl`, `SurfaceSession`, `InputChannel`); W3 then reached
`ViewRootImpl$WindowInputEventReceiver.<init>` (`ViewRootImpl.setView:1455`), whose
`InputEventReceiver.<init>` calls `nativeInit` — but the class's registration function was
never in the list, so the class retained its default (unimplemented) native methods.

The image exports the missing entry point:

```text
$ nm -D --defined-only .cache/art/sysroot/system/lib64/libandroid_runtime.so | grep InputEventReceiver
0000000000147d90 T _ZN7android40register_android_view_InputEventReceiverEP7_JNIEnv
```

The `InputChannel` side needed **no** change. W2's `out InputChannel` body is
`[1][isInitialized][token][String16 name][fd]`; the fd is
`acos_wm::transport::Channel::duplicate_client_fd` of a real
`AF_UNIX`/`SOCK_SEQPACKET` pair (`wms.rs` creates it with `Channel::socketpair` per window,
and keeps the server end in `WmsState.channels`). I1's `InputChannelRegistry` /
`InputPublisher` is the still-unwired *producer* side (`results/art-runtime/I1.md` §6); it is
not needed to install the receiver, only to inject events later. This task therefore made no
`acos-services` edit.

## 2. The change (three registration strings)

`crates/acos-art/guest/java/dev/acos/art/LaunchMain.java`:

```java
"register_android_view_SurfaceControl",
"register_android_view_Surface",                    // W4: relayout's SurfaceControl -> Surface
...
"register_android_view_InputChannel",
"register_android_view_InputEventReceiver",         // W4: W3's nativeInit wall
"register_android_animation_PropertyValuesHolder",  // W4: performTraversals animator setup
```

Each name is the image's own exported stock entry point; no ACOS implementation of a
framework native was added, and no native is faked. The three are needed in this order:

1. **`InputEventReceiver`** clears `ViewRootImpl.setView:1455` and lets the window install
   its `WindowInputEventReceiver`.
2. **`PropertyValuesHolder`** is reached by the first traversal:
   `ViewRootImpl.performTraversals` → `dispatchAttachedToWindow` →
   `TextView.drawableStateChanged` → `StateListAnimator.setState` →
   `AnimatorSet.start` → `ObjectAnimator.initAnimation` → `PropertyValuesHolder.setupSetter`
   → `nGetFloatMethod`. The fixture's themed `TextView` has a state-list animator, so this
   is on the real path (not a diagnostic-only branch).
3. **`Surface`** is reached immediately after `relayout` returns:
   `ViewRootImpl.relayoutWindow` → `Surface.copyFrom(mSurfaceControl)` →
   `nativeGetFromSurfaceControl` (`Surface.java:638`). Registering `SurfaceControl` alone
   was not enough; the `Surface` class has its own registration function.

## 4. The next wall, precisely

With `Surface` registered (`fix3`/`fix4`/`fix5`, 3/3 identical):

```text
ACOSLAUNCH MARK activity-resumed ... recorded_after=looper-threw   (fix1/fix2)
...
service_calls:
  IWindowManager   code 5  useBLAST
  IWindowSession   code 2  addToDisplayAsUser
  IWindowSession   code 5  relayout
  ISurfaceComposerClient code 1  code 1

acos-binder-peer: UNSUPPORTED_ANDROID_API {"descriptor":"android.gui.ISurfaceComposerClient",
  "code":1,"error":"SERVICE_UNKNOWN_BINDER","message":"unknown binder handle 0x1001001"}

log:
  SurfaceComposerClient: SurfaceComposerClient::createSurface error Invalid argument
  BLASTBufferQueue: assertion failed: surface == nullptr BLASTBufferQueue:
                    mSurfaceControl must not be NULL

tombstone: signal 0 (SIGABRT), code -6 (SI_TKILL); frame #00 __android_log_assert
```

`0x01001001` is exactly W3's `placeholder_binder(layerId)` for the window layer
(`PLACEHOLDER_BINDER_BASE | (0x1001 & 0xffff)`; `wms.rs` allocates the window layer from
`next_layer = 0x1000`). The relayout reply's `SurfaceControl` is therefore read and used,
but its `client` binder is the unregistered placeholder. When
`updateBlastSurfaceIfNeeded()` asks that client for a BLAST surface
(`BLASTBufferQueue` → `SurfaceComposerClient::createSurface`, code 1), the peer correctly
answers `UNKNOWN_BINDER`; there is no layer, `mSurfaceControl` becomes NULL, and stock
libgui's assertion aborts the guest. This is **not** a missing native and **not** a parcel
misalignment: the next wall is the deliberate W3 placeholder meeting the first real
compositor client call.

Non-fatal observations from the same run (recorded so they are not mistaken for the wall):

- three `android.ui.ISurfaceComposer code 8` (`setTransactionState`) calls fail with
  `parcel: object at 108 is not a binder (type 0x00000013)`. They occur **before** the
  relayout call (service-call indices 59–61 vs relayout at 70, in the pre-relayout window
  setup) and the framework logs and continues. They are part of the same placeholder
  surface/transaction area and will need the same real-layer treatment once BLAST is
  unblocked; they are not the abort.
- `android.gui.ISurfaceComposer code 57` (`getMaxAcquiredBufferCount`) is answered after the
  failed `createSurface`; it is not the abort.

## 5. What is still not wired (input)

The receiver is installed on the real socketpair, so `nativeInit` is genuinely done.
Nothing publishes into that socket yet: `acos-services/src/input_channel.rs` (I1) has the
`InputPublisher`/`InputChannelRegistry`, but `window_session.rs` writes the
`acos-wm` channel's client fd and `acos-wm`'s dispatcher still uses its own framing. Wiring
I1 §6 (register the same pair by window token, publish `tap`/`key` through
`registry.publisher_mut(token)`, drop our client copy, consume `FINISHED`) is the next input
task. It does not block the launch, and no fake input is claimed here.

## 8. Smallest next action (needs a decision, not a silent shortcut)

`relayout`'s `SurfaceControlInfo` must carry the **real** `android.gui.ISurfaceComposerClient`
binder returned by C1's `ISurfaceComposer.createConnection` (and, consistently, a layer
handle/layer id issued by C1's `createSurface`), instead of W3's unregistered placeholder.
Then `BLASTBufferQueue`'s `createSurface` (code 1) reaches C1's implemented
`surface_client.rs` node and gets a layer; the three `setTransactionState` failures can be
retried against that layer, and the next wall (buffer allocation/dequeue or BLAST
transaction) can be measured. That is a compositor/binder change, so it is an owner-gated
step per `docs/OPERATING_DIRECTIVES.md` §10; it is **not** done in this slice.
