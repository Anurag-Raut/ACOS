## 1. The first deviation, and the chain that follows from it

The chronologically first failure was **not** in the framework, the window
system, Choreographer or the resource table. It was an uncaught Java exception on
RN's native-modules queue thread, printed by the JVM's default handler to
**stderr** (not logd, which is why W21 only saw its downstream effects):

```
Exception in thread "mqt_native_modules" java.lang.NoClassDefFoundError: Failed resolution of: Lokhttp3/JavaNetCookieJar;
	at com.facebook.react.modules.fresco.FrescoModule$Companion.getDefaultConfigBuilder(FrescoModule.kt:164)
	at com.facebook.react.modules.fresco.FrescoModule$Companion.getDefaultConfig(FrescoModule.kt:142)
	at com.facebook.react.modules.fresco.FrescoModule.initialize(FrescoModule.kt:79)
	at com.facebook.react.bridge.ModuleHolder.doInitialize(ModuleHolder.kt:213)
	at com.facebook.react.bridge.NativeModuleRegistry.notifyJSInstanceInitialized(NativeModuleRegistry.kt:94)
	at com.facebook.react.bridge.CatalystInstanceImpl.lambda$initialize$3(CatalystInstanceImpl.java:439)
	... Looper.loop(Looper.java:294)
	at com.facebook.react.bridge.queue.MessageQueueThreadImpl$Companion.startNewBackgroundThread$lambda$1(MessageQueueThreadImpl.kt:175)
Caused by: java.lang.ClassNotFoundException: okhttp3.JavaNetCookieJar
```

**Measured facts (all from the artifacts, not memory):**

* `okhttp3.JavaNetCookieJar` is **not** in `okhttp-4.12.0.jar` nor in
  `okhttp-4.9.2.jar`; it is in **`okhttp-urlconnection`**
  (`okhttp3/JavaNetCookieJar.class`). Verified with `unzip -l` over the Gradle
  cache and by scanning every cached jar for the class.
* `react-android-0.81.4.pom` declares `okhttp`, `okhttp-urlconnection` (4.9.2)
  and `okio` (2.9.0) all as `<optional>true</optional>`, so the optional-skipping
  POM walk in `tools/rn-hello-deps.py` never staged them as roots. The pre-fix
  APK's `classes*.dex` contained **one reference** to
  `Lokhttp3/JavaNetCookieJar;` and **zero definitions** — the classic
  compile-ok / runtime-fail shape.
* That exception is uncaught inside `MessageQueueThreadImpl`'s `Looper.loop()`, so
  the **`mqt_native_modules` thread dies**. Paper's `UIManagerModule` methods are
  plain `@ReactMethod`s: JS calls them and they are posted to that queue. A dead
  Looper means the whole view batch (`createView`/`setChildren`/`updateView`) is
  never executed, so nothing ever calls `requestLayout`:
  `dirty=Rect(0,0-0,0) layout_requested=false`, `ReactRootView` childless — exactly
  the W21 probe output. The bundle still runs (`ReactNativeJS: Running "rnhello"`)
  because the JS thread is independent.

So the answer to W21's two candidates is: **neither**. The UI batch was queued to
a dead thread (candidate 1, but not Choreographer's fault), and there was no
silent `createView` failure (candidate 2). Choreographer itself is fine and was
observed working: the launch stdout shows repeating
`>>>>> Dispatching to Handler (android.view.Choreographer$FrameHandler) … FrameDisplayEventReceiver`
/ `<<<<< Finished` pairs through the 20 s hold (vsync BitTube + FrameData path).

### And the `Invalid resource ID 0x0000000b.` ERRORs were our own probe

Pre-fix a 20 s hold logged exactly 2 of them; the interactive session logged
**4578 of its 4800 logcat lines**. They all came in seven distinct ids —
`0x5, 0x9, 0xb, 0x11, 0x19, …` — **654 times each**. 654 = 2 lookups × 327 live
probe samples. They are React Native's `View.generateViewId()` ids (a generated
id has package byte 0, i.e. it is not a resource id at all), resolved by the
launcher's own view-walk (`Resources.getResourceName` → `AssetManager2::FindEntry`
→ `LOG(ERROR) "Invalid resource ID 0x%08x."`, `base/libs/androidfw/AssetManager2.cpp:653`).
On a device the same call throws `NotFoundException` (which the probe already
swallowed), so the tree output is unchanged — but the probe was writing ERROR
lines it had not earned, and W21 read one of them as an app error. The probe now
resolves a name only when `(id >>> 24) != 0`: logcat drops from 4800 to 222 lines
and the invalid-resource lines go from 4578 to **0**, with an identical tree.

   (peak 124 MiB)`) and passes alone. Observed twice today. Pre-existing, packet

2. **`counter-v2` cold flake** (see §6): `c1_generation=0` within 60 s as the
   first row after the test suite. Worth a retry-once in the runner or a longer
   cold budget; engine-side (`acos-cli/src/engine`), W19/W22 ownership.
3. **`w21-rn-hello`'s former tap** is now only documented, not exercised; the
   button-tap teeth are `w23-rn-hello-tap.yaml`. Anyone still reading W21's report
   should read §1 here first.
4. **Log noise that is not a wall but is ERROR-level**: `netstats` service
   absence (`SystemServiceRegistry` + `AndroidRuntime: Error reporting WTF`,
   because `handleApplicationWtf` is unsupported), `SoLoader` recovery lines and
   the three `logdw` INFO lines are still `E`-level in logcat. None is produced by
   this fixture's own code; the first two are unsupported-service gaps.
5. **OKHttp version pin**: §2 last-but-one row — `okhttp 4.9.2` is a parity choice,
   not an independently falsified necessity.
6. **The RN fixture's `libappmodules.so` recovery lines** (`Failed to recover`)
   are still logged; RN tolerates them (no `SoLoader.init` fatal). If a later app
   needs those modules, the fixture build (not ACOS) is the place to look.
7. `fixtures/build/apps/rn-hello.apk` is now built from the 4.9.2 family; the
   arm64 reference variant was rebuilt too, but not run (no phone run this wave).
