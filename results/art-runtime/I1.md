The descriptors stay **blocking** (as AOSP leaves them) because both sides pass
`MSG_DONTWAIT` per call: the guest's `Looper` can block on its channel, and this
side never does. `InputChannel::sendMessage`/`receiveMessage` in the image and
in r75 both use exactly those flags.

## 2. Exact `InputMessage` layouts used (image-verified)

Source of truth: the image's **`libinput.so`** plus r75
`include/input/InputTransport.h`/`InputTransport.cpp`. Unlike `IWindowSession`
(W2: the image's tail codes are one behind the tag) **the image agrees with
r75 on every `InputMessage` field and size used here** — checked, not assumed:

- `InputMessage::size()` (`libinput.so` **0x77410**) is a jump table over
  `Type`. The immediate results are `MOTION` = `0xa8 + 0x90·pointerCount`
  (`lea rax,[rax+rax*8]; shl rax,4; add rax,0xa8`), `KEY` = `0x68`,
  `FINISHED` = `0x18`, `FOCUS`/`CAPTURE`/`TOUCH_MODE` = `8`, `DRAG` = `0x18`,
  `TIMELINE` = `0x20`.
- `InputMessage::getSanitizedCopy` (**0x775d0**) zeroes **0x9a8** bytes —
  `sizeof(InputMessage)` = 8 header + 0xa0 fixed motion body + 16 × 0x90
  pointers, so `Pointer` = 144 = 8-byte `PointerProperties` + 136-byte
  `PointerCoords` (`uint64 bits` + 30 floats + resample flag = r75's
  `MAX_AXES = 30`).
- `InputPublisher::publishMotionEvent` (**0x79280**) stores `eventTime` at
  `0x10`, the 32-byte hmac at `0x24`, `action`/`actionButton`/`flags`/
  `metaState`/`buttonState` at `0x44`/`0x48`/`0x4c`/`0x50`/`0x54`,
  `classification` at `0x58`, `edgeFlags` at `0x5c`, `downTime` at `0x60`, the
  window transform at `0x68`, precision/cursor at `0x80`, the raw transform at
  `0x90`, and the pointer array at `0xa8` — the field order below.

`Type` values: `KEY=0, MOTION=1, FINISHED=2, FOCUS=3, CAPTURE=4, DRAG=5,
TIMELINE=6, TOUCH_MODE=7`.

### 2.1 Header (8 bytes, both directions)

```text
0x00 u32 type
0x04 u32 seq            (never 0 for a published event; publisher rejects 0)
```

### 2.2 `MOTION` (size `0xa8 + 0x90·pointerCount`)

```text
0x00 u32 type = 1              0x48 i32 actionButton
0x04 u32 seq                   0x4c i32 flags
0x08 i32 eventId               0x50 i32 metaState
0x0c u32 pointerCount          0x54 i32 buttonState
0x10 i64 eventTime             0x58 u8  classification, 0x59..0x5c pad
0x18 i32 deviceId              0x5c i32 edgeFlags
0x1c i32 source                0x60 i64 downTime
0x20 i32 displayId             0x68 6×f32 window transform
0x24 [u8;32] hmac              0x80 4×f32 xPrecision,yPrecision,
0x44 i32 action                       xCursorPosition,yCursorPosition
                               0x90 6×f32 raw transform
                               0xa8 pointers[pointerCount]
```

Per pointer (0x90 bytes):

```text
+0x00 i32 id
+0x04 i32 toolType (1 = FINGER)
+0x08 u64 bits                     (axes present, `1 << axis`, 30 bits used)
+0x10 f32 values[30]               (only the set axes, packed ascending)
+0x88 u8  isResampled              (+7 pad)
```

`PointerCoords::touch(x,y)` sets `X,Y,PRESSURE,SIZE,TOUCH_MAJOR,TOUCH_MINOR`
(`bits = 0b111111`) with `(x, y, 1.0, 0.05, 0.1, 0.1)`; values are packed in
ascending axis order exactly as `PointerCoords::getAxisValue` reads them.
The two transforms are the identity (`1,0,0,1,0,0`).

### 2.3 `KEY` (size 0x68)

```text
0x00 u32 type = 0              0x48 i32 flags
0x04 u32 seq                   0x4c i32 keyCode
0x08 i32 eventId               0x50 i32 scanCode
0x0c u32 empty1 = 0            0x54 i32 metaState
0x10 i64 eventTime             0x58 i32 repeatCount
0x18 i32 deviceId              0x5c u32 empty2 = 0
0x1c i32 source                0x60 i64 downTime
0x20 i32 displayId
0x24 [u8;32] hmac
0x44 i32 action
```

### 2.4 `FINISHED` (client → server, size 0x18)

```text
0x00 u32 type = 2
0x04 u32 seq            (the sequence being acknowledged; 0 is illegal)
0x08 u8  handled        (0x09..0x10 = 7 pad bytes)
0x10 i64 consumeTime    (same CLOCK_MONOTONIC base as event times)
```

`handled` is returned verbatim (a `false` ack stays `false` in `Ack`), and the
publisher records `Injected→ack` latency from a host `Instant` per sequence.
Out-of-order acks only remove their own sequence; a `TIMELINE` never clears a
pending sequence.

### 2.5 `TIMELINE` (client → server, size 0x20)

```text
0x00 u32 type = 6
0x04 u32 seq            (the sequence the timeline belongs to)
0x08 i32 eventId
0x0c u32 empty = 0
0x10 i64 graphicsTimeline[0]   (GPU_COMPLETED_TIME, GraphicsTimeline::SIZE = 2)
0x18 i64 graphicsTimeline[1]   (PRESENT_TIME)
```

## 3. Time and sequencing

- `eventTime`/`downTime`/`consumeTime` use `CLOCK_MONOTONIC` ns
  (`monotonic_nanos()`), the base `MotionEvent.getEventTime()` and
  `System.nanoTime()` need.
- A tap/key press allocates **two consecutive sequences** and one shared
  `downTime`; `UP.eventTime = DOWN.eventTime + hold` (default 50 ms, matching
  `acos-wm`'s injector), so `ViewConfiguration.getTapTimeout()`/long-press
  classification sees a normal click.
- `eventId` is a separate counter (the framework requires uniqueness per input
  stream; one counter per channel keeps traces readable).
- `seq` wrapping is guarded: a would-be 0 is an error, not a wrap.

## 5. Deliberately not real

- **Text injection.** `type("abc")` is not implemented. `InputMessage::Body::Key`
  has no `unicodeChar` field; the app derives characters through
  `KeyCharacterMap` from `keyCode`+`metaState`, which is per-device data ACOS
  does not have yet. A text API needs either a key-character-map resource or an
  IME/`InputConnection` path — a separate task. `key(code)`/`key_sequence` are
  the honest surface today.
- **Dispatcher policy.** Which window receives an event, focus, ANR deadlines
  and batching are not in this module. `acos-wm` already models them for the
  in-memory channel; §6 is how this fd path connects to it.
- **Only the message types needed.** `FOCUS`/`CAPTURE`/`DRAG`/`TOUCH_MODE` decode
  as `UnsupportedType` rather than being silently accepted.

## 6. What remains to wire (the smallest path to real input)

1. **One channel per window, and the same one in both places.**
   `acos-wm`'s `WmsState::add_to_display_as_user` (`crates/acos-wm/src/wms.rs`)
   already creates a `Channel::socketpair` and stores it in
   `WmsState.channels`; `window_session.rs::write_input_channel` duplicates
   **its** client fd into the reply. To publish on that same socket, either
   - the session layer registers the channel in `InputChannelRegistry` and
     writes **the registry's** client fd instead (`write_to_parcel` already
     emits the exact W2 body), or
   - the session layer wraps the existing server end:
     `InputPublisher::new(dup(channel.dispatcher.fd()), name)` (the
     `acos-wm::transport::Channel::dispatcher` field is public) and keeps using
     the fd already written.
   The first is cleaner: the token key then exists in exactly one registry.
2. **After the reply is written, drop our client-end copy**
   (`InputChannelRegistry::forget_client_end(token)`), exactly as WMS releases
   its `outClientChannel` after `addToDisplay`. Keeping it open would hide the
   guest's death from `publish` (no `EPIPE`/EOF).
3. **Key the registry by the window token W2 writes** (`BinderId` from
   `AddWindowResult::input_channel.token`) and remove it on
   `IWindowSession.remove`.
4. **Publisher selection for `svc.input`.** `acos-wm`'s dispatcher currently
   writes its own framing (`acos-wm::input::InputMessage { kind, seq, cause_id
   }`) to `Channel`; a tap must instead call
   `registry.publisher_mut(token).tap(x, y)`. The frame writer in
   `acos-runtime::input_java` is then no longer on the path for real input:
   the guest's `InputEventReceiver` on the window's real `InputChannel` reads
   the bytes directly.
5. **Read acks back.** The guest's `FINISHED` (from
   `InputEventReceiver.finishInputEvent` → `InputConsumer::sendFinishedSignal`)
   arrives on the server fd; `receive_consumer_response` returns `handled` +
   latency. Feeding that into `InputDispatcher::finish_event` is the wiring on
   the `acos-wm` side.
6. Once 1–5 land, the real `ViewRootImpl`'s
   `WindowInputEventReceiver.onInputEvent` receives the `MotionEvent`/`KeyEvent`
   that this module encoded — no `View.dispatchTouchEvent` injection anywhere.

I did not make those edits: this task owns only the new files + the additive
`lib.rs` line, and W3 is editing `window_session.rs`/its peer concurrently.

## 7. Why no stock-libinput probe yet

The image's `libinput.so` is an x86-64 ELF but bionic-linked; `dlopen`-ing it in
a glibc host process fails on `libc.so`/`libc++.so` symbols, and bringing up
the sysroot runner plus the `InputTransport.h`/libui/libbinder compile in under
20 minutes was not realistic inside this checkpoint. The wire proof used
instead is the image's own immediates (`size()`, `getSanitizedCopy`,
`publishMotionEvent`, all cited above with addresses) plus byte-for-byte
hand-built layouts. **Next step (optional hardening):** a tiny native consumer
built against the image sysroot that calls
`InputChannel::openInputChannelPair` + `InputConsumer::consume` on these bytes,
run under the existing sysroot runner; expected command shape:
`tools/guarded.sh --mem 4G --time 300 -- .cache/i1-probe/consume <bytes>`.
