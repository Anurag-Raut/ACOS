# Q3 — `RippleDrawable.draw()` on a software Canvas: root cause, native backtraces, supported fix

**Answer: it is not a graphics bug.** `RippleDrawable.draw()` starts `android.animation.ValueAnimator`s
(background-opacity and ripple-enter). `ValueAnimator.start()` builds a `Choreographer`, whose
constructor creates a native `DisplayEventReceiver`, which asks **libbinder for `SurfaceFlinger`**
(`ISurfaceComposer`). In a process that has no `servicemanager` and no `SurfaceFlinger` — i.e. our
`dalvikvm64` guest — that one call has exactly two outcomes, both measured here:

| guest transport state | outcome | evidence |
|---|---|---|
| no `servicemanager.ready` property (E4H's environment) | **infinite wait** in `android::base::WaitForProperty`, 1 s poll loop, forever | `artifacts/q3-hang-gdb.txt`, `artifacts/q3-hang-javastack.txt` |
| property served, but `SurfaceFlinger` absent | **SIGSEGV, `si_addr = 0x0`**, in `AndroidRuntime::getJNIEnv()+37` (`mov (%rdi),%rax`, `rdi = 0`), reached from `~NativeDisplayEventReceiver()` | `artifacts/q3-segv-gdb.txt`, `artifacts/q3-segv-crashtrace.log` |

E4H's "silent SIGSEGV with no tombstone" was the second one. The `Canvas` is irrelevant: the same
crash happens with `Canvas(Bitmap)`, and would happen with a `RecordingCanvas`, because the failing
call is the *animation clock*, not the rasteriser.

**Chosen route: (b) framework software-draw path + (c1) guest "settle" policy. Rejected: (a).**
The stock software branch of `RippleDrawable` is fine and needs no new dependency; what is missing is
a **vsync source**, which is a runtime capability (`Choreographer`), not a draw-path choice. Until the
peer provides one, a frame must not start animations. That is a 2-file, ~25-line change in
`crates/acos-art/guest` (§8), which I did **not** make.

- Owner / date: Q3 agent, 2026-11-11. Hard checkpoint 60 min; **used ~130 min** (the overrun is
  the reproduction: the crash needs a *servicemanager stub* to get past `WaitForProperty`, and the
  gdb attach needs a launch window — two 20 s instrumented runs).
- Depends on: **E1A** (sysroot), **E2D/E2E** (substrate shim, `register_android_graphics_classes`),
  **E4H** (the ladder that hit this on `counter.apk`).
- Constraints honoured: no ACOS crate touched (`crates/` unmodified), nothing committed, no sudo,
  every ART run through `tools/guarded.sh --mem 4G --time 300`, all scratch under `.cache/`,
  ownership limited to `research/art-feasibility/q3-ripple/` + this file.

### 1.1 Why it is the destructor of a *failed* `DisplayEventReceiver`

`base/core/jni/android_view_DisplayEventReceiver.cpp:122`:

```cpp
NativeDisplayEventReceiver::~NativeDisplayEventReceiver() {
    JNIEnv* env = AndroidRuntime::getJNIEnv();     // <-- this is the crash site
    env->DeleteGlobalRef(mReceiverWeakGlobal);
    ALOGV("receiver %p ~ dtor display event receiver.", this);
}
```

`initialize()` fails (`status = -19 = -ENODEV`, because `DisplayEventDispatcher` could not get a
`SurfaceFlinger` connection), the constructor body never returns normally, the object is destroyed,
and the *error path* is what dereferences a null `JavaVM*`. `getJNIEnv()`
(`base/core/jni/AndroidRuntime.cpp:1340`) is:

```cpp
/*static*/ JavaVM* AndroidRuntime::getJavaVM() { return AndroidRuntime::mJavaVM; }  // line 1340

/*static*/ JNIEnv* AndroidRuntime::getJNIEnv() {
    JNIEnv* env;
    JavaVM* vm = AndroidRuntime::getJavaVM();
    assert(vm != NULL);                      // compiled out (NDEBUG) in the shipped lib
    if (vm->GetEnv((void**) &env, JNI_VERSION_1_4) != JNI_OK)   // vm == NULL -> *(0)
        return NULL;
    return env;
}
```

Disassembly of the image library agrees byte for byte (`objdump -d libandroid_runtime.so`,
`0xe6cf0`):

```
e6d0b: mov 0x15ff3e(%rip),%rax     # rax = &AndroidRuntime::mJavaVM  (PIC/GOT)
e6d12: mov (%rax),%rdi             # rdi = mJavaVM            -> 0
e6d15: mov (%rdi),%rax             # <-- FAULT: null vtable load
e6d22: call *0x30(%rax)            # vm->GetEnv(...)
```

`AndroidRuntime::mJavaVM` (`:300`) is set in exactly one place, `AndroidRuntime::start()`
(`:1246`). **A `dalvikvm64` process never calls `AndroidRuntime::start()`** (its `main()` calls
`JNI_CreateJavaVM` itself), so `mJavaVM`/`gCurRuntime` stay null and *every* JNI-upcall that
libandroid_runtime makes from a native callback — including a destructor on a failure path — dies at
`0x0`. The `assert` that would have turned this into a readable abort is compiled out.

> This is a **second, independent defect** and it is in our launcher, not in the framework:
> the same `RippleDrawable` code on a real device only ever sees the *first* defect (missing
> `SurfaceFlinger`), and there it degrades to a logged failure instead of a SIGSEGV.

Row 1 is the important correction to E4H: **no press is needed**. The first *unpressed* draw of a
`Button` already starts the background-opacity animator. `setBackground(null)` "fixing" it (E4H's
isolation) is consistent: no ripple ⇒ no animator ⇒ no `Choreographer`.

Row 6 kills route (a) empirically as well as by source: a `RenderNode` can only be rasterised by the
HWUI GPU pipeline, and `RecordingCanvas` needs a node that `isAttached()` to a live window
(`useRTAnimations`), i.e. a `ViewRootImpl` + `SurfaceFlinger` + GPU. Route (a) *adds* three
dependencies to remove none.

## 5. Route decision

| route | does it fix the SIGSEGV? | what it needs | cost | verdict |
|---|---|---|---|---|
| **(a)** `RecordingCanvas`/`RenderNode` | **no** — the animator is started *before* the `isHardwareAccelerated()` branch; `drawRenderNode` throws on a software canvas (measured, row 6); an unattached node falls back to `enterSoftware()` | GPU + EGL + HWUI `RenderThread` + an attached window + `SurfaceFlinger` (+ still vsync) | E2E's (b): 8–15 d, new GPU dependency | **rejected** |
| **(b)** framework software-draw path (`ViewRootImpl.drawSoftware` semantics: a `Canvas` over a `Bitmap`) | **not by itself** — this *is* what we already do; the pixels are right, the animator is the problem | a `Choreographer` with a vsync source (route c2) to animate; a **Looper-less draw thread** to make draw-time starts degrade instead of crash | 0 (already shipped) | **chosen, as the base** |
| **(c1)** guest "settle" policy (replace ripple with its content layer / `jumpToCurrentState()` before drawing) | **yes**, for the ripple class; zero native work, deterministic, no new dependency | per-frame application (an app can install a new background at any time) | ~25 lines, already 80 % present | **chosen, immediate** |
| **(c2)** peer-side vsync: an `ISurfaceComposer` stand-in in the ACOS binder peer returning a valid `IDisplayEventConnection` (BitTube, no vsync) + fixing the launcher's `AndroidRuntime::start()` contract | **yes**, and it makes the *stock* animation code run unmodified (ripples, focus halos, `ViewPropertyAnimator`) | `servicemanager` + `SurfaceFlinger` AIDL subset in the peer; launcher must set the JavaVM the way `AndroidRuntime::start()` does | 3–5 d | **chosen for M-C** (animations), not needed for a static frame |

Preferring stock is what selects (b)+(c1) *now* and (c2) *later*: both keep the framework's own code
in charge and add capability instead of rewriting `Drawable`s. (a) is not "more stock" — it is a
different, much larger runtime.

all we can honestly produce, and its pixels are correct.

## 7. Why "no tombstone, no log line" (E4H §3.4)

Four things stack up, which is why the original finding looked like a silent libhwui fault:

1. `tombstoned` does not exist in the sandbox — the bionic crash detailer's write path fails
   (`LOGM(6): Failed to write stack traces to tombstoned`) and only ART-internal metrics get dumped
   (`artifacts/q3-raw-hang.log`);
2. the fault is in `libandroid_runtime`, not `libhwui`, so a "graphics" hypothesis sends you to the
   wrong library;
3. with the property absent you do not crash at all — you *hang*, and the guard's SIGKILL looks like
   "the process died silently";
4. every ALOG after the fault is unflushed, so the last thing you see is the *previous* frame's line.

The instrumentation that turned it into a 10-minute answer: `native/crashtrace.c` (extended here —
all executable maps dumped verbatim, `dladdr` symbol names, 1 MB maps buffer) plus host gdb through
`PR_SET_PTRACER_ANY`, plus `kill -QUIT` for the ART Java+native stack.

## 8. Exact change needed in `crates/acos-art/guest` (not made)

Three edits, ~25 lines, no new dependency. Files: `AppMain.java`, `SessionMain.java`.

**(1) `AppMain.java` — make the policy a function that survives tree mutation.** Today
`downgradeRipples(View)` exists (line ~1035) and is called once at attach and once inside `AppMain`'s
own draw. Add the general form next to it:

```java
/** Freeze every drawable that would start an animation from inside draw().
 *  A frame renderer has no vsync source; Choreographer -> DisplayEventReceiver ->
 *  SurfaceFlinger is a hang or a SIGSEGV in this process (Q3). */
static int settleDrawables(View v) {
    int n = 0;
    Drawable bg = v.getBackground();
    if (bg != null) { bg.jumpToCurrentState(); n++; }
    if (v instanceof ViewGroup) {
        ViewGroup g = (ViewGroup) v;
        for (int i = 0; i < g.getChildCount(); i++) n += settleDrawables(g.getChildAt(i));
    }
    return n;   // jumpToCurrentState() does NOT clear RippleDrawable.mAddRipple, hence (2)
}
```

**(2) `SessionMain.java` — apply it per frame, not once at attach.** `publishFrame()`
(`sDecor.draw(canvas)`, ~line 657) becomes:

```java
        traversal();
        sLastTree = AppMain.dumpTree(sDecor);
        ...
        AppMain.downgradeRipples(sDecor);      // idempotent; an app may have set a new background
        AppMain.settleDrawables(sDecor);       // clears pending container/AVD animations
        sDecor.draw(canvas);
```

Keep the attach-time calls (they must run *before* any input, see (3)) — the per-frame call is the
safety net for `setBackgroundResource()`/theme changes after attach.

**(3) `SessionMain.java` — draw on a thread with no `Looper`.** This is the part that turns *this
whole class* of failure from "process killed" into "logged, catchable", using the framework's own
guard (`RippleDrawable.java:872`) and `ValueAnimator`'s own precondition check. Input dispatch must
stay on the main `Looper` (it needs it), so `publishFrame()` splits:

```java
    static void publishFrame() throws Throwable {
        // Input dispatch (and therefore every animator the framework starts from a
        // state change) stays on the main Looper. The *draw* goes to a thread with no
        // Looper: RippleDrawable skips its background animation there, and any other
        // drawable that starts a ValueAnimator gets a catchable
        // AndroidRuntimeException instead of entering
        // Choreographer -> DisplayEventReceiver -> SurfaceFlinger (Q3).
        Throwable[] err = new Throwable[1];
        Thread t = new Thread(() -> {
            try { drawAndPublish(); }
            catch (Throwable e) { err[0] = e; }
        }, "acos-draw");                 // no Looper.prepare() on this thread, ever
        t.start(); t.join();
        if (err[0] != null) throw err[0];
    }
```

with `drawAndPublish()` = the current body from `traversal()` through the PNG/hash/`sSeq++`.
Note the boundary: the thread must be created **without** `Looper.prepare()`, and it must not call
`View` methods that require `AttachInfo` (measure/layout/draw do not — measured 1.5 ms + 0.5 ms).

**Do not** take route (a). **Do not** rely on `canvas.isHardwareAccelerated()` — the software branch
of `RippleDrawable` is not a guard for the animator (`RippleDrawable.java:886-950`).

**(4) Separate defect, outside `guest/` (for the launcher/ART-integration owner).**
`AndroidRuntime::mJavaVM`/`gCurRuntime` are null because the guest is started as `dalvikvm64`, not via
`AndroidRuntime::start()`; `assert(vm != NULL)` is compiled out, so **every** JNI-upcall from a
libandroid_runtime native callback/error path is a potential SIGSEGV at `0x0`. Concrete options, in
order of preference: start the guest through `app_process` semantics (`AndroidRuntime::start`, which
sets `mJavaVM` at `AndroidRuntime.cpp:1246`), or set `gCurRuntime`/`mJavaVM` after
`JNI_CreateJavaVM` through the exported `AndroidRuntime` API, or (cheapest, but a shim) interpose
`AndroidRuntime::getJNIEnv()` in the substrate to return the JNI env of the current thread. Until
then, no Java code in the guest may let an animation *fail* — failures are fatal.

## 9. What this changes in the plan

1. **E4H §3.4 / §6.5 is corrected**: it is not "`Drawable`s that assume hardware", it is
   **`Drawable`s that assume an animation clock**. The audit must be over `ValueAnimator`/
   `Choreographer` reachability from `draw()`/state changes, not over `RenderNode` use. `RippleDrawable`
   is simply the first such drawable in a Material theme; `AnimatedVectorDrawable`,
   `TransitionDrawable`, `StateListAnimator`, `ViewPropertyAnimator`, `RecyclerView`'s `ItemAnimator`
   and `TextView.setEllipsize` marquee are the same shape.
2. **M-B/M-C boundary**: the static first frame never needed animations; a *press* now works too
   (§6). Ripple/halo/shadow *animation* is the first genuinely vsync-dependent feature ⇒ route (c2),
   ~3–5 d, and it should be scheduled with the binder peer work (`ISurfaceComposer` is the smallest
   AIDL slice that unlocks `Choreographer` for every app).
3. **`View.jumpDrawablesToCurrentState()` is not sufficient** for a patterned ripple (it calls
   `endPatternedAnimations()` but leaves `mAddRipple = true`); the content-layer substitution stays
   necessary until vsync exists.
4. The existing product workarounds (`AppMain.downgradeRipples`,
   `SessionMain.downgradeStateListAnimators`) are **load-bearing**, not cosmetic: removing either puts
   the process back into the hang/SIGSEGV paths measured here. `SessionMain`'s comment ("DOWN at a
   Button wedged for >4 s") is the same bug seen from the input side.
