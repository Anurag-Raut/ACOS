## 1. Per-window input (W36 §4.2)

`UiNode` now carries `window` (serde-default `""`; schemars regenerated), the engine
copies it from the probe (`bounded_on_screen` stays the screen-space `bounds`), and:

* `ArtSession` keeps `window_offsets: HashMap<window, (dx,dy)>` measured from the
  same probe sample (`screen.left - bounds.left`, `screen.top - bounds.top`), plus
  the first window's offset as the fallback for an input with no window label
  (an explicit `x/y` screen point). The old single `input_offset` is that fallback.
* `SessionBackend::tap_in_window(window, x, y)` defaults to `tap(x, y)` for
  single-space backends; `ArtSession` subtracts that window's origin.
* Selector taps resolve `(window, screen centre)` from the freshly bound tree
  (`point_for`) and dispatch through `tap_in_window`; `tap_text` resolves the
  node's own window. An explicit screen point still uses the first-window offset.
* A selector that matches nothing in a truncated tree is `TREE_TRUNCATED` here
  too (not `ASSERTION_FAILED`).

Measured: `w27-dialog-window`, shared binary, **2026-11-12T03:07:49Z**: **pass,
9/9 steps, verdict wall 4097 ms**. The OK tap is sent to the dialog window's
channel (dialog origin `[152,976]`; OK screen centre `(770,1365)` → dialog-local
`(618,389)`), and the Activity status becomes `"Dialog confirmed"`.
Evidence `results/art-runtime/evidence/W40-w27-dialog-window.json`.

Unit test with teeth: `engine::art::tests::per_window_offsets_map_a_dialog_tap_into_the_dialog_window`
builds the W36 two-window tree (`main [0,128]`, dialog `[152,976]`) and asserts
`(770,1365)` maps to `(618,389)` for the dialog while `(540,1290)` maps to
`(540,1162)` for main, and that an empty/unknown label falls back to the first
window. It fails on the pre-W40 single-offset code.

**What still fails (`form-validation`)** — deterministic twice (03:14Z, 03:15Z):
steps 0–22 pass (type/validate/log/tap); step 23 `assert_text` fails bounds. The
message node is at y `1157..1214` in both live and stock reference, i.e. the
vertical dialog layout is identical; the live dialog window is 776 px wide
(`[152,976][928,1489]`) while the stock API-34 reference is 940 px
(`[70,…][1010,…]`). This is the guest/WM horizontal dialog-width policy
(`acos-art` / `acos-wm`), not the caller's offset: the submit tap targets the
Activity window whose offset `[0,128]` is the same in the old global and the new
per-window mapping. Evidence `evidence/W40-form-dialog-bounds.txt`.
The other dialog scenarios pass: `w15-dialog-menu` 3/3, `w15-dialogs-menus` 5/5
(incl. the OK-press/status), T12 good+wrong at the suite level.

## 2. `TREE_TRUNCATED`

* `acos-protocol/src/error.rs`: `ErrorCode::TreeTruncated` → `"TREE_TRUNCATED"`,
  hint names the **2000-node-per-window** budget and says it is not proof of
  absence; `default_status = Fail`; **not** in `retryable()` (no stale-ref retry);
  added to `ALL_ERROR_CODES`.
* `acos-verify/src/assertions.rs`: `missing_error(observation, selector)` returns
  `TREE_TRUNCATED` iff `observation.tree.truncated` (the probe sets it when **any**
  window hit the cap), else `ELEMENT_NOT_FOUND`; used by `text`, `visible` and
  `state` selectors and `element_missing` (executor `wait_for` passes the last
  observation it holds). `element_missing`'s diff detail says "in a truncated
  tree" so the verdict evidence cannot be confused with a true miss.
* `acos-verify/src/native.rs::input_error`: `TREE_TRUNCATED` rides the `Failed`
  path like `ELEMENT_NOT_FOUND`, never the retryable/stale path.
* `acos-cli` selector taps return it from `point_for`.
* Schemas regenerated with `UPDATE_SCHEMA=1 cargo test -p acos-protocol`
  (`ui-tree.json` gains the `window` property; the error-enum schemas gain the
  code). `docs/ERROR_CODES.md` row added.

Teeth test: `truncated_tree_reports_tree_truncated_not_element_not_found` — the
identical missing selector/tree returns `ELEMENT_NOT_FOUND` with
`truncated:false` and `TREE_TRUNCATED` with `truncated:true`; it also asserts
non-retryability and that the hint names the budget. No end-to-end truncation
repro was manufactured (that needs a >2000-node real app); W36's measured 244-node
Gaten tree is the honest non-truncated counterexample.
