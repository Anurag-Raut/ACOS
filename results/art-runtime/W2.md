## 1. What was wrong (the two codec bugs, both in the *reply*)

### 1.1 `out InputChannel` — wrong field order and a missing int

`InputChannel` is **not** a Java-parcelable shape: `InputChannel.writeToParcel` is
`nativeWriteToParcel`, and the image's native implementation is
`android::InputChannel::writeToParcel` (libinput.so `0x78d40`):

```text
strong binder  token   (mToken)
String16       name    (writeUtf8AsUtf16)
fd             fd      (writeUniqueFileDescriptor)
```

and `readFromParcel` (`libinput.so:0x78dc0`, reached from
`android_view_InputChannel_nativeReadFromParcel`, libandroid_runtime.so `0x144f40`)
mirrors it **after** reading an `int32 isInitialized`. So the AIDL out parameter is:

```text
int32  1     // AIDL `writeTypedObject(InputChannel)` presence (the stub creates the object)
int32  1     // nativeReadFromParcel's `isInitialized`
binder token
String16 name
fd
```

W1 wrote `[1][name][fd][token]`. The first native read therefore consumed the name's
length word as a `flat_binder_object` (`ALOGW "Attempt to read object from Parcel … at
offset … that is not in the object list"`, which is the log line P4c/L1 saw), then read a
garbage `String16`, and every subsequent byte of the reply was shifted — which is what
made the `InsetsState` look like it had a bad cutout array (L1 E2).

### 1.2 `out SurfaceControl` (relayout's `outSurfaceControl` and every
`InsetsSourceControl.mLeash`) — 8-byte handle vs the real native body

`SurfaceControl.java` writes its Java fields (`String8 mName`, `int mWidth`,
`int mHeight`, an `int` "has a native object" marker) and then calls
`nativeWriteToParcel` → `SurfaceControl::writeToParcel` (libgui.so `0xca270`, source
`.cache/aosp/native/libs/gui/SurfaceControl.cpp:237`):

```text
strong binder client   (ISurfaceComposerClient)
strong binder handle   (the layer handle)
int32         layerId
String16      layerName
uint32        transformHint
uint32        width
uint32        height
uint32        format
```

The reader (`SurfaceControl::readFromParcel`, libgui.so `0x13f7d0`, verified instruction
by instruction) mirrors it and **tolerates a null client and a null handle** ("we aren't
the original owner of the surface"), which is exactly what ACOS has. W1 wrote a bare
8-byte handle, so the guest's first `readStrongBinder(&client)` consumed 24 bytes of the
following `layerName` and the reply desynchronised (the `SurfaceControl: … Failed to call
parcel parcel.readStrongBinder(&client)` log lines).

ACOS now writes the full shape with **null** client/handle binders, the synthetic ACOS
layer id in `layerId`, the name as `String16`, `transformHint = 0` and
`format = 1 (RGBA_8888)`. Nothing is claimed to be a SurfaceFlinger layer: the
`SurfaceControl` the app receives is a real Java object with no compositor behind it —
the same honest placeholder W1 documented, now byte-exact.

### 1.3 `out float[] sizeCompatScale` — the count is the caller's

An AIDL `out float[]` is caller-allocated: `IWindowSession$Stub$Proxy` writes
`data.writeInt(array-length)`, the stub allocates `new float[thatLength]`, and
`Parcel.readFloatArray(val)` throws `RuntimeException("bad array lengths")` unless the
reply count equals `val.length` (`Parcel.java:1719`). The reader now consumes the
client's length from the request and pads/truncates `acos-wm`'s values to it
(`write_size_compat_scale`). The previous "all out parameters absent on failure" branch
also disagreed with the image: the stub creates all four out objects in `onTransact` and
writes them **unconditionally** (`writeTypedObject` + `writeFloatArray`), so a rejected
add still carries a full `InsetsState`/controls body and an *uninitialised* channel
(`presence 1`, `isInitialized 0`).

## 2. `InsetsState` / `DisplayCutout`: what the image actually reads (L1 E2's cause)

`InsetsState.readFromParcel` (classes4.dex, `0x1ba7dc`) and `writeToParcel`
(`0x1bbd8c`) are field-for-field the ones `acos-wm` already encoded:

```text
Rect.readFromParcel               mDisplayFrame        (bare, 4 ints)
ParcelableWrapper.readFromParcel  mDisplayCutout
readTypedObject(RoundedCorners)   mRoundedCorners
Rect.readFromParcel               mRoundedCornerFrame  (bare)
readTypedObject(PrivacyIndicatorBounds)
readTypedObject(DisplayShape)
int size; size x readTypedObject(InsetsSource)
```

`DisplayCutout$ParcelableWrapper.readCutoutFromParcel` (`0x192ac4`) is the important one:

```text
int variant              -1 null, 0 NO_CUTOUT, anything else = present
readTypedObject(Rect)    mSafeInsets
new Rect[4] + Parcel.readTypedArray(Rect.CREATOR)   <-- FIXED LENGTH 4
readTypedObject(Insets)  mWaterfallInsets
int displayWidth, displayHeight, physicalDisplayWidth, physicalDisplayHeight
float density
String16 cutoutSpec
int rotation
float scale
float physicalPixelDisplaySizeRatio
```

Two image-vs-tag facts, both now encoded and documented in
`crates/acos-services/src/parcelable.rs`:

1. **The bounds array is a fixed `Rect[4]`.** `Parcel.readTypedArray(T[] val, Creator)`
   compares the wire count with `val.length` and throws `"bad array lengths"` otherwise
   (`Parcel.java:3998`). `acos-wm` already serves exactly four rects, which is why the
   crash moved on after §1.1 — the cutout itself was never the bug, the alignment was.
2. **The image writes no `mSideOverrides` int array** (`android-14.0.0_r75` does).
   `crates/acos-services/src/display.rs` / `parcelable.rs` dropped it (14 → 13 fields) and
   `read_cutout` now rejects a bounds count that is not 4 with the framework's own
   reasoning, so an ACOS `DisplayInfo` cutout stays readable if a phone override ever
   serves one.

## 5. Proof that the reply bytes are right (and where the guest diverges)

The launch's **actual** `addToDisplayAsUser` reply was dumped from the host
(`ACOSDBG_DUMP_REPLY`, removed before hand-off) and decoded offline with a hand-written
transcription of the image's readers (`.cache/s6/reply.hex`, `.cache/s6/decode.py`):

* 2324 bytes; the walk ends at **2324/2324** — every field decodes and the tail is
  `[attachedFrame (0,128,1080,2337)] [float[1] = 1.0]`;
* cutout: variant 1, safe insets `(0,128,0,0)`, **4** bounds with the hole punch at
  `(492,0,610,128)`, the real `cutoutSpec`, density 2.625;
* 10 `InsetsSource` rows (status 128, nav 63, IME/gesture/tappable rows as `display.txt`);
* 3 `InsetsSourceControl` rows, each with a leash `SurfaceControl` whose native body is
  `client(null) handle(null) layerId=0x1002/0x1003/0x1004 name16 width 1080 height 2400
  transformHint 0 format 1`, then `initiallyVisible/Point/Insets/skip`
  (`(0,128)`, `(0,0,0,883)` for the IME leash — the values `acos-wm` sets).

The guest, however, reads the first leash's `client` binder at **guest offset 1440**.
With the peer's stability inserts (`+4` per binder object; the channel token is the only
one before that point) that is **host offset 1436** — 88 bytes *past* the leash's real
client object (host 1348), i.e. inside the leash's `layerName` `String16`. So the guest
has consumed 88 bytes more than the framework order in §2 consumes at that point. Where
exactly is **not yet identified**; the candidates, in the order I would test them:

1. **transport, not codec**: whether the peer's `frame_from_parcel` inserts the 4-byte
   stability record for these *null* binders and keeps the object-offset table in step
   (the guest's object list must then contain 20/288/1352/1376/…). A dump of the
   guest-visible frame bytes for this one transaction settles it in one run.
2. **a guest-side position trace**: log `Parcel::dataPosition()` at each step of
   `InsetsState.readFromParcel`/`InsetsSourceControl(Parcel)` in the guest (a two-line
   patch to the image-side reader is not available, so the practical variant is a
   `ACOSLAUNCH` Java-level probe or `gdb` on the guest's `libgui` `readFromParcel`,
   both of which the next agent can do without touching these crates).
3. only if 1 and 2 come back clean: a still-unmodelled nested shape in the controls
   region. Every leaf I could read out of the image DEX/libgui now matches, so I would
   not expect this.
