# F2 — the suppressed fatal CHECK is gone: ART starts on its real device classpath

**Status: fixed and enforced. ART's `Check failed: !location.empty() No mainline
framework library found` no longer fires — not because it is silenced, but
because the input it reads is now the device-accurate
`BOOTCLASSPATH` / `DEX2OATBOOTCLASSPATH` pair. The abort suppression is removed:
a fatal CHECK now dies of SIGABRT with a tombstone, exactly as on device. The
corpus is 27/27 with 0 recorded fatal ART log entries.** Owner: implementer,
continuation of `results/art-runtime/F.md` §1 task 5 / §4 item 1. Owned files:
`crates/acos-art/**`, this report. No commit made.

## 0. Answer first: what the check wants

Disassembly of `libartbase.so` (`objdump -d`, string xref at `.rodata+0x15dbe`)
gives the whole condition; the symbol is exported:

```
art::GetFirstMainlineFrameworkLibraryFilename(std::string* error_msg)
```

```
r15 = getenv("BOOTCLASSPATH")            # .rodata 0x18816
r12 = getenv("DEX2OATBOOTCLASSPATH")     # .rodata 0x17cd0
if (!r15 || !r12)  error = "BOOTCLASSPATH and DEX2OATBOOTCLASSPATH must not be empty"
else if (!StartsWith(r15, r12))
                   error = "DEX2OATBOOTCLASSPATH must be a prefix of BOOTCLASSPATH"
else { Split(r15 + strlen(r12), ':');  if (empty) error = "No mainline framework library found";
                                      else return first element }
```

Caller chain (all confirmed by xref, not guessed):

```
libart.so  Runtime/ImageSpace
  └─ art::GetDefaultBootImageLocation(boot_classpath, debuggable)   [libartbase 0x2a7e2, line 522]
       ├─ art::GetDefaultBootImageLocationSafe(...)                 [0x29560]
       │    └─ art::MaybeAppendBootImageMainlineExtension(...)      [0x2a2e0]
       │         └─ art::GetFirstMainlineFrameworkLibraryFilename   [0x29370]   ← "No mainline framework library found"
       └─ CHECK(!location.empty()) << error_msg                     [0x2a88c → 0x168e5 "Check failed: !location.empty()"]
```

So the check is not about `apex-info-list.xml`, `ro.vndk.version` or
`apex.libraries.config.txt` (the three candidates F.md listed). It is a
**boot-image mainline-extension** computation: `DEX2OATBOOTCLASSPATH` must be a
strict prefix of `BOOTCLASSPATH`; the remainder is the mainline framework jar
list, whose first jar names the mainline boot image (`boot-<jar>.art`) that
`odrefresh` builds next to `boot.art`.

Our launcher was setting **both variables to the same string**
(`lib.rs`: `DEX2OATBOOTCLASSPATH` = `bc.join(":")`, i.e. the full list), so the
remainder was empty → `error_msg = "No mainline framework library found"` →
`location` empty → FATAL CHECK → and the shim's no-op `__android_log_aborter`
turned that into a log line and carried on. That is the exact bug F.md recorded
as "documented, not fixed".

## 1. The missing input: the device classpath pair

On device neither variable is hand-written: `init` runs the image's own
`/apex/com.android.sdkext/bin/derive_classpath`, which reads every
`/etc/classpaths/bootclasspath.pb` fragment (platform + each APEX) plus the APEX
manifests and writes `/data/system/environ/classpath`:

```
export BOOTCLASSPATH          <35 jars: ART core, /system/framework, i18n, mainline APEX jars>
export DEX2OATBOOTCLASSPATH   <first 12 of them: ART core + /system/framework/* + core-icu4j.jar>
export SYSTEMSERVERCLASSPATH  …
export STANDALONE_SYSTEMSERVER_JARS …
```

`acos-art` now **runs that binary** (reuse, no reimplementation of the merge
rules) in the same sandbox during `ensure_classpath_env()`, caches the file in
`<data>/system/environ/classpath`, and uses the pair verbatim:

| variable | value | source |
|---|---|---|
| `BOOTCLASSPATH` | 35 jars | `derive_classpath` |
| `DEX2OATBOOTCLASSPATH` | **12** jars (prefix) | `derive_classpath` |
| mainline remainder | from `framework-adservices.jar` (23 jars) | implied by the pair |

Both were previously 35 jars, i.e. the bug above.

Two device-fidelity bugs had to be fixed for `derive_classpath` to run cleanly
(and they are real, not workarounds):

1. **APEX mount name is the manifest name, not the host directory.** The two
   Google-signed modules are extracted into `com.google.android.configinfrastructure`
   / `…ondevicepersonalization` (named after the `.apex` payload), but their
   `apex_manifest.pb` names are `com.android.configinfrastructure` /
   `com.android.ondevicepersonalization`, which is what apexd mounts under
   `/apex/<name>` and what every classpath fragment references. Mounting the
   host directory name made `derive_classpath` CHECK-abort twice
   (`… must not export a jar from outside of the apex`), i.e. a second, hidden
   fatal CHECK. `ApexModule` now carries both (`name` = host dir, `mount` =
   manifest name); `host_path()` resolves either spelling and the sandbox mounts
   by `mount`.
2. **`ld.config.txt` is invalidated when the mount table changes.** It was
   only regenerated when absent, so a changed mount list left a stale config and
   `dalvikvm64` failed with `CANNOT LINK EXECUTABLE … libnativehelper.so`.
   `ensure_linkerconfig` writes a `.mounts` fingerprint and regenerates on
   mismatch.

Old sysroots (the E1A scratch dir) have no `/system/etc/classpaths/`, so their
derivation is incomplete (no `framework.jar`). `Classpaths::is_complete()`
rejects that output, prints a warning, and the launcher falls back to the
sysroot's own `BOOTCLASSPATH` list with a fragment-derived
`DEX2OATBOOTCLASSPATH` prefix (`fallback_dex2oat_classpath()`), so those sysroots
keep working instead of silently booting a classpath without framework classes.

## 2. Abort suppression removed (`shim/artshim.c`)

Before: `__android_log_call_aborter` logged `art_aborter` and **returned**, so a
fatal CHECK continued execution. Now the shim does what liblog's default aborter
does — write the message to the logd sink, then `tgkill(getpid(), gettid(),
SIGABRT)` — and `__android_log_assert` (bionic's other fatal funnel) does the
same instead of returning. Restored behaviour, demonstrated by re-creating the
old classpath bug in a throwaway data dir:

```
$ # data dir with DEX2OATBOOTCLASSPATH == BOOTCLASSPATH (the old launcher behaviour)
$ acos-art run --dex 01_hello/classes.dex --class Main --json
outcome crash  code ART_FATAL_CHECK  exit null  signal 6
diagnostics: terminated by signal 6 (SIGABRT)
             ART [F] : Check failed: !location.empty() No mainline framework library found
logs: 23 entries incl. a debuggerd-shaped tombstone
      Abort message: 'Check failed: !location.empty() No mainline framework library found'
      #00 pc … /data/shim/libartshim.so (__android_log_call_aborter+92)
```

`classify()` now maps that pair (SIGABRT + a fatal `Check failed` entry) to
`ART_FATAL_CHECK`; before, a signal with no stderr text fell through to
`ART_CRASH`. Two unit tests cover it (`sigabrt_from_fatal_check_is_art_fatal_check`,
`aborter_log_entry_is_fatal`).

### 3.1 AOT boot image needed one more fix

With the correct pair ART now demands the **split** image layout it derives from
the mainline remainder: it looks for the per-mainline-jar components
(`boot-framework-configinfrastructure.art/.oat/.vdex`, …) next to `boot.art` and
rejected the first rebuilt image with

```
Error reading named image component header for /data/img/boot.art …
Could not create image space with image file '/data/img/boot.art'. Attempting to
fall back to imageless running.
```

Cause: `build-image` passed the sysroot's hand-derived jar list, whose device
paths use the *host* directory spelling (`/apex/com.google.android.configinfrastructure/…`),
so `dex2oat` named those components differently from what the runtime looks up.
`build-image` now takes the jars from the same `derive_classpath` output as the
run environment; the image then loads with no fallback. (With the fix the image
is 65 ms vs 60 ms imageless on this host — the AOT advantage F.md measured
(187 → 76 ms) came with the broken classpath, so image-vs-imageless needs a
fresh measurement; it is not a claim of this task.)

## 5. Open items (carried forward)

1. **Image vs imageless** must be re-measured now that the classpath is correct;
   the old 187 → 76 ms numbers were taken with the failing lookup.
2. **`linkerconfig` warning for `com.android.sdkext`**: regenerating
   `ld.config.txt` yields `… ld.config.txt:284: error: list of shared_libs for
   sphal->vndk link is not specified or is empty`, so `derive_classpath` runs on
   the default namespace config. Harmless today (it still links and produces the
   file), but it is link-time config fidelity worth a look.
3. The shim still formats liblog messages itself; letting real liblog write to
   the Rust logd sink (F.md §4 item 3) would remove the last "we reimplemented a
   writer" corner. The fatal path is now behaviourally faithful either way.
4. `derive_classpath` runs once per data dir, not once per boot; a concurrent
   pair of `acos-art` runs sharing one `--data` can race on
   `<data>/system/environ/classpath` (same class of race F.md §4 item 5 noted for
   `linkerconfig`). Serialise or per-run `--data`.
