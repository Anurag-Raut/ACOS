## Where the JVM oracle is wrong for Android

The only measured divergence in this corpus is `20_uncaught`, and it is
**not** a runtime-semantic difference: build-fixtures.sh records only the
first stderr line of a failed program, while ART (like any JVM) emits the
full stack trace. The complete ART trace is:

```
Exception in thread "main" Main$Fatal: fatal without args
	at Main.main(Main.java:14)
```

Everything else is byte-identical on both VMs, which is a real (if narrow)
result: for this portable subset there is **no** JVM-ART divergence in
Float/Double printing (04), String.hashCode (09), Object.toString
class-prefix behaviour (10), collection iteration order (17), Integer
cache/boxing identity (17), thread-scheduling output (19), or the VM-thrown
exception class names the fixtures print (13).

Caveat: the fixtures were deliberately written to avoid JVM-specific message
text and identity hashes (see fixtures/README.md); "identical" therefore
means "identical on this portable subset", **not** "ART == JVM for all
Android semantics". A jvm-reference pass still can never satisfy an
art-reference requirement (ADR-0005); the real Android app/framework/JNI
evidence is in fixtures/reference/.
