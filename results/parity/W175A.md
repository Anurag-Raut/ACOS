# W175-A phone-vs-ACOS *element* parity (counter) and display reference mode

Device `ZA222WGJPP` (moto g35 5G, Android 15 / API 35, 1080x2400 @ 400 dpi,
gesture navigation), fixture `dev.acos.fixtures.counter` (`fixtures/build/apps/counter.apk`,
`targetSdk 34`, no `android:theme`). Goal: make the W167-A frame comparison
meaningful and shrink the *real* layout differences.

## What changed in this task

1. **Phone capture via the agent-device skill** — installed only our fixture,
   launched `dev.acos.fixtures.counter/.MainActivity`, captured the full
   accessibility tree (`snapshot --json --force-full`, 16 nodes, resource ids +
   rects) and a full-display screenshot, then closed and uninstalled the
   fixture. No device setting/account/security command was issued.
   * The device was claimed by a **stale** agent-device session
     (`cwd:0fe32c84c8b0f19b`, last event 2026-11-10T16:00Z, app `com.fitmedik`,
     ~9.5 h old; only the long-lived daemon PID survived). agent-device therefore
     could not cover the device, so the claim was released with `agent-device close`
     from the owner's workspace (no live agent was disturbed) and the run then used
     agent-device for install/open/snapshot/screenshot/close/uninstall.
2. **Per-element diff tool** (`crates/acos-cli/src/parity.rs`): a new ranked
   `element_diff` that matches ACOS vs phone/reference **by resource id** and
   reports per-edge `delta = acos - phone`, per-axis `size_delta`, text mismatch
   and a magnitude `score`, sorted largest-first.
   CLI: `acos parity --acos-tree <acos.json> --device-snapshot <phone.json> --element-diff [--json]`.
3. **ACOS display options** (`crates/acos-cli/src/launch.rs`):
   * `acos launch --density <dpi>` — override `DisplayMetrics` density
     (default display stays 1080x2400).
   * `acos launch --display <WxH>` — override the logical size.
   * `acos launch --reference` — run with the **phone's exact parameters**
     (`1080x2400 @ 400 dpi`, 108 px status bar, 0 px navigation bar).
   The override is applied to `DisplayInfo`/`DisplayMetrics`, the WMS
   `DisplaySpec`/`DisplayFacts`, the boot `Configuration` (density + dp bounds)
   and is carried through the `acos serve` daemon via the launch request.

Same phone tree, same comparator, only ACOS's display config changed:

| element | default ACOS (1080x2400 @ 420, status 128, nav 63) | `--reference` (400, status 108, nav 0) |
|---|---|---|
| `id/inc` score | 741 | **550** |
| `id/count` score | 542 | **435** |
| `id/reset` score | 969 | **756** |
| action bar bounds | `[0,128,1080,275]` | `[0,108,1080,248]` (phone-exact) |
| `id/inc` height | 126 | **120** (phone 120) |

So the top inset (108 vs 128), the navigation inset (0 vs 63), the density
(400 vs 420) and the derived dp bounds (`432x960dp` vs `411x842dp`) were real,
principled differences and are now configurable and matched. The element scores
drop ~23% with the phone's parameters.

## Theme / system-bar colour (open, not a geometry config)

Sampled mean RGB of the app-window bands at 1080x2400:

| band | ACOS `--reference` | phone | note |
|---|---|---|---|
| status bar `y 0..108` | `[124,124,125]` | `[31,35,38]` | ACOS status-bar background is light grey |
| action bar `y 108..248` | `[213,213,215]` | `[26,30,33]` | **ACOS renders a LIGHT action bar; phone a DARK one** |
| content | `[239,239,241]` | `[236,239,244]` | close (Δ ≤ 5) |

The phone's app uses the framework `android.widget.Toolbar` (from
`dumpsys window`: `android:id/action_bar` → `android.widget.Toolbar`,
`android:id/action_bar_container` at `[0,108,1080,248]`), i.e. the platform
`DeviceDefault` family — **not** a Material3 toolbar. The fixture declares no
theme, so the phone's resolved theme is the platform default with a dark action
bar (`Theme.DeviceDefault.Light.DarkActionBar`). ACOS's tree has the same widget
classes and the correct 140 px (`56dp @ 400 dpi`) action-bar height, but renders
the light action bar: its theme parent resolution drops the `DarkActionBar`
action-bar style / background. This lives in the framework-res theme engine
(`crates/acos-framework-natives/src/res/`), not in the display config, and is
left to the in-flight theme work (W173-A).

## Open layout bugs (largest remaining real differences)

* **A — 2x horizontal layout.** Every horizontal position is doubled
  (`count/inc/reset/title x=80` vs phone `40 = 16dp @ 400 dpi`), and
  `ActionMenuView` sits at `x=2160 = 2x1080`. The same doubling is present in
  the ART oracle comparison: at 420 dpi the ART tree is `x=42` while live ACOS is
  `x=84`. The action bar height is *not* doubled (147 = 56dp @ 420dpi), so this
  is a dimension/position resolution problem, not density itself.
* **B — content frame offset.** `android:id/content` is shifted down (and its
  bottom extended) by exactly one action-bar height: ACOS `top=388 = 108 + 2*140`
  vs phone `248 = 108 + 140`. The action bar is applied to the content offset
  twice.
* **C — vertical child spacing.** In the fixture `LinearLayout` (tight children,
  phone: `count` bottom 334 = `inc` top 334 = `inc` bottom 454 = `reset` top 454)
  ACOS inserts a gap of one child height between siblings (`inc` bottom 672 →
  `reset` top 792).

A/B/C are in the framework view-layout path, not in display/inset configuration,
so they are out of scope for the "config with tests" fix here and are recorded
for the layout workstream.
