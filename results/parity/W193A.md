## 0. Summary

| # | Finding | Result |
|---|---|---|
| 1 | `inc` Button 269 px vs ART 231 px | **Root-caused**: ACOS renders `textAllCaps` ("INCREMENT"), the ART reference renders mixed case ("Increment"). Mixed case fits `text + 12dp/side` exactly into `minWidth` 88dp = 231; all-caps is 38 px wider. The `textAllCaps` value comes from `@bool/config_buttonTextAllCaps` in the extracted `framework-res.apk` (true); the reference emulator's runtime RRO sets it false. ACOS does not apply RROs. **Left to W150-A (theme/res).** |
| 2 | Parity was accidentally measured on the **host** Noto fonts | `FontCollection::load` searches `$ACOS_FONT_DIR`, then the boot image, then `/usr/share/fonts`. With no `ACOS_FONT_DIR` and a worktree built under `.cache`, the boot path misses and the host Noto Naskh Arabic is used (text 23 px tall). Setting `ACOS_FONT_DIR` fixes it — the parity harness now does. |
| 3 | After the font fix, every 14sp `TextView` was ~4 % **narrow** (title 182 vs 189 px) | **Root-caused and fixed**: `typeface_create_from_array` took the **first** resolvable face in the family and ignored the requested weight. `sans-serif` lists Roboto's variable axes in weight order (`wght=100` first), so every `Typeface.DEFAULT` shaped at `wght=100`. | 4 | Frame SSIM is low across the matrix (~0.20 global / ~0.87 mean) | **Not text/layout**: the W182-A action-bar/shadow gap dominates it (the action-bar `ColorDrawable` is not recorded, the node's elevation shadow is painted instead; the status band is absent). That is W186-A's display-list workstream. Tree parity is the meaningful number here. |

## 1. `Button` width: `textAllCaps`, not padding/minWidth

Ground truth (probe of the live `View`, `ACOS_PROBE_VIEW`):

```
inc    padL=31 padR=31 minWas=231 measW=269 textSize=37 text="Increment"
reset  padL=31 padR=31 minWas=231 measW=231 textSize=37 text="Reset"
```

`padL/R` = 31 px = 12 dp/side (`button_inset_horizontal_material` 4 dp + the
`btn_default_mtrl_shape` `<padding>` 8 dp), `minWidth` = 88 dp = 231 px. The
`Reset` text + padding is below `minWidth`, so it clamps to 231; `Increment`
does not clamp **only because ACOS measures the all-caps transform**
(`INCREMENT` = 204.8 px at 14sp Roboto + 63 px padding = 269). ART's `inc` is
231, i.e. its `Increment` (165.5 px mixed case + 63 px padding = 228.5) fits
inside `minWidth`.

The proof that ART is mixed case comes from `dialog-menu`, whose buttons are
wider than `minWidth` and therefore expose the padding directly:

| text | ART width | mixed-case + 12dp/side | all-caps + 12dp/side |
|---|---:|---:|---:|
| `Show dialog` | 263 | 199.94 + 63 = **262.9** | 243.2 + 63 = 306 |
| `Show toast` | 246 | 183.71 + 63 = **246.7** | 230.0 + 63 = 293 |

The mixed-case prediction is consistent (and matches the screenshot glyphs:
"Increment", "Show dialog", "Greet" are lower-case); the all-caps prediction
misses by 43–48 px. `Widget.Material.Button`'s `textAppearanceButton` →
`TextAppearance.Material.Button` is 14sp `sans-serif-condensed`, `textAllCaps`
= `@bool/config_buttonTextAllCaps`; the extracted
`.cache/boot/android-34/framework-res.apk` resolves it to **true**, the Google
emulator image applies a runtime overlay that resolves it to **false**, and
`.cache/boot/android-34` carries no overlay APKs. ACOS is therefore consistent
with its own resource table; matching ART needs the resource-overlay layer,
which is W150-A's. **No theme/res code was changed.**

Consequence for the matrix: `counter:inc +38`, `dialog-menu:toast +48`,
`dialog-menu:dialog +44`, `todo-list:clear +18` px width. Every other Button
clamps to the 231 px `minWidth` and matches.

## 2. The higher-yield fix: `Typeface.DEFAULT` weight selection

`crates/acos-vm/src/natives/fwk_fonts.rs::typeface_create_from_array` iterated
the family's `Font` handles and `break 'outer` on the first one that resolved:

```rust
for fh in &fam.fonts {
    if let Some(fr) = font.resolved_font() {
        chosen = Some((family, w, it, fr));
        break 'outer;             // <-- ignores font.weight
    }
}
```

`fonts.xml`'s `sans-serif` family lists `Roboto-Regular.ttf` once per variable
axis set, in weight order (`wght=100` first). The framework's
`Typeface.createFromFamilies` calls the native with the requested weight (400
for `Typeface.NORMAL`); ACOS always took the `wght=100` face. Live effect at
14sp: `Hello ACOS` 182 px (ART 189), `clicks: 0` 125 px (ART 133) — a ~4 %
narrow every default-weight `TextView`, while 20sp action-bar titles (weight
500) happened to be right.

Fix: score every reachable face with `face_score` (weight distance ×2 + a
100-point style penalty) and keep the minimum, matching `FontFamily.getFont`.

| metric (hello-views, 420 dpi) | before | after | ART |
|---|---:|---:|---:|
| `title` ("Hello ACOS") width | 182 | **190** | 189 |
| `result` ("clicks: 0") width | 125 | **134** | 133 |
| `title`/`result` height | 51 | 51 | 51 |
| action-bar "Hello Views" width | 279 | 279 | 279 |

Regression tests (`cargo test -p acos-vm --lib natives::fwk_fonts`):
`face_score_selects_the_requested_weight`, `face_score_prefers_style_on_a_weight_tie`.

## 5. The single remaining cross-app layout gap: EditText height

Six of ten apps differ by exactly **11 px** on an `EditText` (`name`/`email`/
`input`/`message`), and the difference cascades to every sibling below it. The
text line height is identical (51 px); the 11 px is the background
`edit_text_material` `InsetDrawable` + nine-patch content padding. ACOS applies
56 px while ART applies 67 px of vertical background padding. That is the
drawable/theme padding layer (`crates/acos-framework-natives/src/res` and the
drawable inflation path), owned by W150-A, so it was **not** changed here. It is
the highest-yield follow-up: fixing it removes the vertical drift in
hello-views, form-validation, todo-list, multi-activity, text-input and
two-activity at once.
