# W182-A — why the counter action bar is not the reference's dark `#191c1e`

Follow-up to W175-A (§ "Theme / system-bar colour") and the W144-A theme note.
W175-A concluded that ACOS *renders a light action bar* and attributed it to the
framework-res theme engine dropping `Theme.DeviceDefault.Light.DarkActionBar`'s
`DarkActionBar` action-bar style. **That attribution is wrong.**

## Bottom line

The theme/style chain is resolved **correctly**. The action bar's
`android:background` is resolved by `nativeApplyStyle` to `0xff191c1e` — the
exact colour the real device/emulator draws. The light band W175-A measured is
**not the action bar background at all**: it is the action-bar `RenderNode`'s
own **elevation shadow** composited over the light window background, because
the action-bar view's background drawable never reaches the render node's
display list.

The remaining bug is therefore in the view → `RenderNode` display-list path
(`View.draw`/`setWillNotDraw`/`Drawable.draw` recording), not in
`crates/acos-framework-natives/src/res/` (theme.rs, style-bag merge, `?attr`
chasing, theme overlays). No production code was changed in this task; the
deliverable is the root-cause evidence plus two regression tests that pin the
resolved values.

## 1. Theme-attribute resolution is correct (proved two ways)

### (a) Static: new tests in `crates/acos-framework-natives/tests/theme_resolution.rs`

`device_default_dark_action_bar_resolves_to_neutral_900` walks the whole chain
that the phone uses:

```
Theme.DeviceDefault.Light.DarkActionBar        0x0103013f  (applied, force=true)
  colorPrimary      (0x01010433) -> @color/primary_device_default_dark      0x010602a9
  colorPrimaryDark  (0x01010434) -> @color/primary_dark_device_default_dark 0x010602a0
                                   -> @color/primary_device_default_dark    0x010602a9
                                   -> @color/system_neutral1_900            #ff191c1e
  actionBarStyle    (0x010102ce) -> Widget.Material.Light.ActionBar.Solid    0x01030290
                                   -> background = ?attr/colorPrimary  (0x010100d4, TYPE_ATTRIBUTE)
  nativeApplyStyle(defStyleAttr=actionBarStyle).background -> type 0x1d data 0xff191c1e
```

and `dark_action_bar_overlay_keeps_device_default_primaries` applies
`actionBarTheme` = `ThemeOverlay.Material.Dark.ActionBar` (0x0103024c) with
`force = true` — the `ContextThemeWrapper` path the action bar uses — and
asserts it does **not** retarget `colorPrimary`/`colorPrimaryDark` (it only sets
`colorControlNormal` + the dark `windowBackground` 0x01060313).

Note the trap the tests pin: `Theme.DeviceDefault.Light.DarkActionBar`'s parent
is `Theme.Material.Light.DarkActionBar` whose parent is `Theme.Material.Light`,
whose `colorPrimaryDark` is `@color/primary_dark_material_light` =
`@color/material_grey_600` = **#ff757575** — i.e. exactly the light grey the
W175-A screenshot showed. Had the style-bag merge order or the `?attr` chase
stopped one or two levels early, the action bar would be `#757575`. It is not:
the engine keeps the DeviceDefault overrides.

### (b) Runtime: traced on the real framework launch

An env-gated trace of `AssetManager::apply_style` / `Theme::apply_style_id`
(temporary instrumentation, removed again) on `acos launch counter.apk`:

```
TRACE_THEME apply res=0x01030005 force=true n=335 colorPrimary=(1,0x010602a9) colorPrimaryDark=(1,0x010602a0)
TRACE_THEME apply res=0x0103013f force=true n=407 colorPrimary=(1,0x010602a9) colorPrimaryDark=(1,0x010602a0)
TRACE_THEME apply res=0x0103024c force=true  ... colorPrimary=(1,0x010602a9) colorPrimaryDark=(1,0x010602a0)
TRACE_THEME apply_style defAttr=0x010102ce (actionBarStyle) attrs=[...,0x010100d4,...]
  TRACE_THEME  attr 0x010100d4 -> type=0x1d data=0xff191c1e cookie=1 resid=0x01060028
```

So the `TypedArray` that becomes the action bar's `ColorDrawable` already holds
`#191c1e`.

ACOS: `acos launch fixtures/build/apps/counter.apk` (default display config,
420 dpi, status bar 128) → `observe --screenshot`; colours below are the modal
pixel of the element's bounds plus the trace's paint values.

| element | ART reference | ACOS | verdict |

Row-level check of the ACOS frame (default config) shows the shadow ramp
`#aeaeae` → `#757576` over y 0..29, a flat `#757576` y 29..134 and the inverse
ramp back to `#f0f0f3` at y 147 — the signature of a *blurred shadow*, not of a
`ColorDrawable` fill, whose edges would be hard.

## 3. Why the band is a shadow: the display list has no background op

An env-gated trace inside `RenderContext::render_node_recursive` /
`execute_display_op` (temporary, removed) on the same launch:

```
TRACE_RENDER node RectF { 0,0,1080,140 } opcount=1
TRACE_RENDER nodeop DrawRenderNode(Handle(4294967300))          <- the title TextView only
TRACE_RENDER shadow bounds={0,0,1080,140} elevation=10 ambient=0x40000000 spot=0x59000000 alpha=1 ops=1
TRACE_RENDER DrawText "Counter" at (0,47) color=0xdeffffff      <- child node
TRACE_RENDER DrawRect { 0,0,1080,2292 } color=0xfff0f0f3        <- window background only
TRACE_RENDER DrawRoundRect { 10,15,246,105 } rx=10 ry=10 color=0xffffffff
```

* The action-bar node (1080x140 = 56dp @ 400/420 dpi) has **one** op, a
  `DrawRenderNode` for its child; there is no `DrawRect`/`DrawPath`/
  `DrawRoundRect` carrying `0xff191c1e` anywhere in the frame.
* Its `elevation = 10` (4dp) shadow is drawn with two black lobes,
  `ambient=0x40000000` (α 0.251) and `spot=0x59000000` (α 0.349), filled over the
  node outline with `BlurStyle::Normal` — reproducing the measured `#757576`
  **exactly** over `#f0f0f3` (`240 × 0.749 × 0.651 = 117.0`; the +1 blue is the
  `#f0f0f3` blue channel: `243 × 0.749 × 0.651 = 118.5` → 118).
* The button's fill *is* recorded and painted (`0xffffffff`), so `Drawable.draw`
  → display-list recording works in general; only the action-bar view's
  background is missing.

Two follow-ups for the view/compositing owner (both are outside
`crates/acos-framework-natives/src/res/`):

1. The action-bar view's background drawable (a `ColorDrawable(#191c1e)`, value
   already confirmed above) is not recorded into its `RenderNode` display list
   — likely `setWillNotDraw(true)` (`ActionBarContainer` sets it when all three
   backgrounds are null) combined with the framework drawing the background
   from `mBackground`/`mPrimaryBackground` in `onDraw`, which the ACOS view host
   skips.
2. Text/shape paint alpha is not composited against the destination: a paint of
   `0xdeffffff` renders as `(222,222,222)` regardless of what is under it, and
   the Material button's `ColorStateList` (`?attr/colorButtonNormal` →
   `@color/btn_default_material_light` → `#d6d7d7`) ends up as opaque white.

is bit-identical before and after (`content_hash b6759db639b5701719be165f2ff819a1`,

as the W182-A baseline for the render-side fix. The `--reference` frame is the
better score only because its 400 dpi layout is closer to the reference's
metrics; it does not change any colour.

## 5. Environment caveat (blocks a clean-HEAD frame capture)

```

        -> AssetManager.createSystemAssetsInZygoteLocked
```

i.e. the frame comparison currently depends on the in-flight **W181-A io
natives** change that is present (uncommitted) in the shared tree. The frames
and traces above were therefore captured with a build of the shared working
tree (HEAD `4f5b3fd` + W181-A's `io_linux.rs`, W178-A RN, W176-A bench); the
theme/render code involved is unchanged by those. Once W181-A lands, the
capture reproduces from a clean worktree.
