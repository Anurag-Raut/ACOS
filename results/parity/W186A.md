# W186-A — action-bar background, shadow semantics, and button tint reach the display list

Follow-up to W175-A and W182-A. W182-A proved the theme chain resolves
`android:background` to `0xff191c1e` and localised the light band to the
action-bar `RenderNode`'s display list. W186-A fixes the four render-side
causes and measures the parity change on the counter and hello-views fixtures.

## Bottom line

* The action bar's `ColorDrawable` now reaches the display list
  (`DrawRectRectF {0,0,1080,147} paint=0xff191c1e`) and paints `#191c1e`.
* Elevation shadows are drawn only when the node's outline is non-empty
  (HWUI `SkShadowUtils` semantics).
* The Material button's `?attr/colorButtonNormal` `SRC_IN` tint is carried into
  the frozen paint; the reset button fill is `#d6d7d7`.
* The colour-filter ARGB channel order was wrong (`0xAARRGGBB` decoded as a
  packed premultiplied RGBA word); fixed at both `PorterDuff` and `BlendMode`
  branches.

Counter masked SSIM vs the ART reference rises from **mean 0.9146 / global
0.3283** to **mean 0.9263 / global 0.4629** on the 400 dpi `--reference`
frame, and from mean 0.8772 / global 0.1985 to **mean 0.8897 / global 0.3185**
on the default 420 dpi frame. Hello-views rises from mean 0.9069 / global
0.3335 to **mean 0.9226 / global 0.4779** (400 dpi).

## 1. XML-tag `style` attribute source (`crates/acos-framework-natives/src/res/theme.rs`)

`apply_style` merged the explicit XML attributes, the theme's `defStyleAttr`
and `defStyleRes`, but never resolved the tag's own `style="..."` attribute
(`AttributeResolution.cpp::GetXmlStyleBag`). Added `xml_style_value()`, which
reads the current `XmlEvent::StartTag`'s `style` attribute and resolves it
through the theme (`?attr` → theme lookup, `@resid` → direct) as a source
between the explicit attributes and `defStyleAttr`.

Result: `ActionBarContainer` resolves `android:background` to
`android.graphics.drawable.ColorDrawable`, and the action-bar node now emits
`DrawRectRectF {0,0,1080,147} paint=0xff191c1e` (was `opcount=1`, title only).
Frame pixels `(540,60)` / `(540,140)` = `(25,28,30)` = `#191c1e`.

## 2. Shadow only from a non-empty outline (`crates/acos-render/src/context.rs`)

The shadow gate was `elevation > 0.0` and fell back to `local_bounds`, painting
a blurred rectangle shadow under every elevated container. HWUI draws a shadow
from the node's **outline** only. Gate is now
`elevation > 0.0 && !props.outline.is_empty()` (`Outline::is_empty()` in
`geom.rs`).

## 3. Colour filter carried into the frozen paint (`crates/acos-vm/src/natives/gfx_state.rs`)

`render_paint_from` copied colour/alpha/style but dropped the
`PaintRec.color_filter`, so a `GradientDrawable`'s `android:tint` was lost.
It now resolves `rec.color_filter` through `gfx_paint::filter_spec()` into
`p.color_filter`. Button ops show
`DrawRoundRectRectF {10,15,246,105} paint=0xffffffff alpha=255 style=Fill
cf=Some(BlendMode { color: 4292270039, mode: SrcIn })`
(`4292270039 = 0xFFD6D7D7`).

## 4. ARGB channel order for colour filters (`crates/acos-render/src/canvas.rs`)

Both `ColorFilterSpec::PorterDuff` and `ColorFilterSpec::BlendMode` decoded the
filter colour with `unpack_unpremul(pack_word(*color))`, treating an Android
`0xAARRGGBB` int as a packed premultiplied RGBA word. They now use
`crate::color::argb_to_rgba(*color)`; the unused `pack_word` helper was
deleted. The reset button interior renders `(214,215,215)` = `#d6d7d7`.

## Known remaining discrepancies (not fixed here)

1. **Increment button renders black in the published frame.** The button's
   `View` has `focused=True` (the reset button does not). The focus state makes
   `RippleDrawable` add a focus-hotspot `DrawCircle(134,63,r=148)` with a
   `Bitmap` shader and `cf=SrcIn 0xff000000`; the opaque shader is re-coloured
   opaque black. Skipping that circle restores the fill to `#d6d7d7`
   (`ACOS_W186A_SKIP_CIRCLE=1` experiment). The isolated colour-filter and
   `fill_path_filtered` path is verified correct for the same paint values
   (`#d6d7d7`), so the remaining cause is the focus state / bitmap-shader
   interaction, not the ARGB fix. The ART reference's Increment button is not
   focused.
2. **Action-bar dark band is vertically truncated.** At x=540 the dark span is
   `0..139` vs the reference `0..274`. The action-bar `RenderNode`'s
   `DrawRect {0,0,1080,147}` is drawn at window-local y=0 while
   `ActionBarContainer` is `[0,108,1080,248]`; the window/inset offset
   (`attached_frame [0,128,1080,2337]`) is not applied to the node's matrix.
   Light pixels fill y≈140-255.
3. **Status bar band.** The ART reference screenshots include the system UI
   (status/navigation bars). The framework preset masks `[0,0,1080,64]` and
   `[0,2304,1080,2400]`; these bands are not part of the compared region.
