## 1. Gap 1 — the static RRO the reference emulator applies

### 1.1 Where the value comes from

`Widget.Material.Button` → `textAppearanceButton` →
`TextAppearance.Material.Button` carries `textAllCaps = @bool/config_buttonTextAllCaps`.
In the extracted `.cache/boot/android-34/framework-res.apk` that bool is
`true` (id `0x0111004a`). The emulator, however, renders mixed case, which is
what W193-A proved from the `dialog-menu` widths and the screenshot glyphs.

### 1.2 The overlay, located on the system image

The SDK system image is a GPT disk with one `super` partition holding the
dynamic partitions. W193-A only extracted `system`; the overlays live on
**`product`** and **`system_ext`**. Unpacking them (`lpunpack -p product -p
system_ext`) and listing `/overlay` gives 25 RRO APKs, of which **five** are
`isStatic=true` with `targetPackage="android"`:

| APK (from `product/overlay/`) | package | touches `config_buttonTextAllCaps` |
|---|---|---|
| `GoogleConfigOverlay.apk` | `com.google.android.overlay.googleconfig` | no |
| `GoogleWebViewOverlay.apk` | `com.google.android.overlay.googlewebview` | no |
| `LargeScreenConfigOverlay.apk` | `com.google.android.overlay.largescreenconfig` | no |
| **`PixelConfigOverlayCommon.apk`** | `com.google.android.overlay.pixelconfigcommon` | **yes → `false`** |
| `framework-res__auto_generated_rro_product.apk` | `android.auto_generated_rro_product__` | no |

`aapt2 dump xmltree --file AndroidManifest.xml` on the winner:

```
E: overlay
  A: android:priority=1
  A: android:targetPackage="android"
  A: android:isStatic=true
```

and `aapt2 dump resources`:

```
resource 0x7f020001 bool/config_buttonTextAllCaps
  () false
```

A **static** overlay cannot be enabled or disabled at runtime — the framework
applies it unconditionally — which is why ART diverges from the raw
`framework-res.apk` value and why the fix belongs in the resource layer, not in
`TextView`.

### 1.3 The overlay layer

`crates/acos-framework-natives/src/res/manager.rs`:

* `ResTableIndex::entries()` (`arsc.rs`) enumerates `(id, type, key)` over every
  type chunk, so the overlay's own package-local ids can be named.
* `AssetManager::apply_overlay(apk)` reads `android:targetPackage` from the
  overlay's binary manifest (`overlay_target_package`), resolves each overlay
  entry to the base id by `type/key` (`find_target_id`), and records
  `Overlay { apk, map: target_id → overlay_local_id }`.
* `lookup_with()` consults `overlays` **before** the base sources, highest
  priority last, and hands back the overlay's `ResolvedEntry` carrying the
  **target's** `package_name`/`type_name`/`key`/`type_id`/`entry_id` so
  `get_resource_name` and the `get_resource_{package,type,entry}_name` natives
  stay consistent for an overridden id.

Two deliberate constraints, both documented in code:

1. **The overlay APK is not pushed into `sources`.** The Java `AssetManager`
   caches one `StringBlock` per `ApkAssets` it passed to
   `nativeSetApkAssets`; adding a native-only source desynchronised that array
   and threw `ArrayIndexOutOfBoundsException: Index 2 out of bounds for length 2`
   in `getPooledStringForCookie` during `AdaptiveIconDrawable.<init>`. Found by
   running the launch, not by inspection.
2. **Only simple scalar values are substituted** (`bool`/`int`/`color`/
   `dimension`/`fraction`). A `TYPE_STRING` would need the overlay's own global
   string pool and an `@resid` would need its package id — neither of which the
   Java side can address for a source it never saw. Those entries fall through
   to the base value rather than producing a wrong one.

`crates/acos-vm/src/natives/fwk_res.rs::am_set_apk_assets` loads
`<boot>/overlays/*.apk` (sorted, deterministic) and applies them after
`set_apk_assets`, so every manager — framework, app, and the ones created
later — sees the same overlay set.

### 1.4 Reproducible extraction

`tools/extract-bootclasspath.sh` gains a `2b. static resource overlays` stage:
after the `system` partition it also `lpunpack`s `product` and `system_ext`,
scans each `/overlay/*.apk`'s binary manifest with an inline AXML reader (no
`aapt2` dependency, matching the script's "unprivileged, already-installed
tools only" rule) and copies only `isStatic && targetPackage == "android"` into
`.cache/boot/android-34/overlays/`. Verified against the real image: it selects
exactly the five APKs above and rejects the 20 dynamic or app-targeted ones
(e.g. `SystemUIGXOverlay.apk` is `isStatic=false`; the `*__auto_generated_rro_*`
overlays for `com.android.settings`, `com.android.systemui`, … target other
packages).

## 2. Gap 2 — nine-patch content padding

### 2.1 The padding is in the PNG, ACOS just never read it

`edit_text_material` is `<inset>` (4 dp / 10 dp / 7 dp) over a `<selector>` of
`<nine-patch src="@drawable/textfield_default_mtrl_alpha">`. The nine-patch's
`npTc` chunk for the 480 dpi bucket is:

```
00 02 02 02 | xDivsOffset=32 | yDivsOffset=40 | padL=0 padR=0 padT=0 padB=12 | colorsOffset=48 | ...
```

`Res_png_9patch` (AOSP `ResourceTypes.h`) declares the fields as
`paddingLeft, paddingRight, paddingTop, paddingBottom` — **L, R, T, B**, not
L, T, R, B — and `deviceToFile()` byte-swaps them to network order.
`NinePatchChunk::parse` kept only `x_divs`/`y_divs`/`colors`, and
`ImageDecoder.nGetPadding` was a stub that wrote four zeros, so
`NinePatchDrawable.getPadding` reported nothing and `View.setBackground`
(`background.getPadding(padding)` → `internalSetPadding`) saw no content inset.

### 2.2 The fix

* `NinePatchChunk` gains `padding: [i32; 4]` (`[left, top, right, bottom]`),
  parsed from the header and round-tripped by `to_bytes`.
* `NinePatchChunk::padding_scaled(scale)` applies
  `(int)(v * scale + 0.5f)` — AOSP `NinePatchPeeker::scale`.
* `BitmapFactory.nativeDecodeStream` now fills its `Rect outPadding` argument
  (`bf_decode_stream` → `pad`) using
  `inTargetDensity / inDensity` from `BitmapFactory.Options`, which is exactly
  what `BitmapFactory.decodeResourceStream` sets before calling it.
* `ImageDecoder.nGetPadding` is no longer a stub: it reads the padding from the
  registered decoder and scales by `Source.getDensity()` →
  `computeDstDensity()` = `getResources().getDisplayMetrics().densityDpi`, i.e.
  `420 / 480 = 0.875` here. (AOSP leaves a nine-patch bitmap itself unscaled —
  `if (mIsNinePatch && mPostProcessor == nullptr) return srcDensity;` — so only
  the padding is scaled, which is what `NinePatchDrawable` expects.)

`12 * 0.875 + 0.5 = 11` px, which is precisely the missing 11 px.

## 6. Follow-ups (not in this wave)

1. **Dynamic RROs / `OverlayManager`.** Only static overlays are applied. A
   dynamic overlay needs the overlay service (`IOverlayManager`), which ACOS
   does not model; `acos-services` already has the `OverlayProperties` parcelable
   for `DisplayManager.getOverlaySupport`, so the service surface is the gap.
2. **Overlay strings and `@resid` values.** Currently skipped (see §1.3). Doing
   it properly needs the overlay registered as a real `ApkAssets` source with
   its own `StringBlock` and package id — i.e. a `nativeSetApkAssets` that
   reports the same array to Java.
3. **Equal-priority ordering.** AOSP orders equal-priority static overlays by
   its own scan order; ACOS uses sorted file name. No current conflict exists
   (`config_buttonTextAllCaps` is declared by exactly one overlay), but a future
   image could expose it.
