## 1. What was wrong with the existing `UnixFileSystem` registration

`crates/acos-vm/src/natives/io_linux.rs` registered the **legacy libcore
spellings** (`getLastModifiedTime0`, `createDirectory0`, `list0`, …) plus a
`getBooleanAttributes0(String)` variant. Android 14's real
`java.io.UnixFileSystem` (verified with
`javap -classpath .cache/boot/android-34/jars/core-oj.jar`) declares:

| declared native (API 34) | was | now |
|---|---|---|
| `getBooleanAttributes0(File)I` | only `(String)I` | `(File)I` **added** |
| `checkAccess(File,I)Z` | **absent** | **implemented** |
| `getLength(File)J` | **absent** | **implemented** |
| `setPermission(File,IZZ)Z` | **absent** | **implemented** |
| `setReadOnly(File)Z` | **absent** | **implemented** |
| `delete0(File)Z` | **absent** | **implemented** |
| `rename0(File,File)Z` | **absent** | **implemented** |
| `getLastModifiedTime(File)J` | only `…Time0` | both |
| `setLastModifiedTime(File,J)Z` | only `…Time0` | both |
| `list(File)[String` | only `list0` | both |
| `createDirectory(File)Z` | only `…0` | both |
| `createFileExclusively(String)Z` | only `…0` | both |
| `getSpace(File,I)J` | only `getSpace0` | both |
| `canonicalize0`, `getNameMax0`, `initIDs` | present | unchanged |

Because natives are keyed by exact `(class, name, signature)`, the
`0`-suffixed entries were dead for the real boot classpath: the first
`File.exists()`/`canRead()`/`length()` that reached one of the unsuffixed
declarations raised `UNSUPPORTED_JAVA_API` — i.e. `checkAccess` was a
platform-wide blocker, not a Gaten property.

### 1.1 Semantics (VFS-confined, real Java compared)

* `checkAccess(File, access)` evaluates the mode bits against the **host
  `euid`/`egid`** (the identity the kernel uses for `open` inside the sandbox
  root), owner/group/other classes, root short-circuit, `X_OK` requires an
  execute bit. `libcore.io.Linux.access` deliberately keeps reads open on the
  sandbox; `File.canRead()` must not, and real Java says so.
* `setPermission` / `setReadOnly` rewrite the mode of an **existing** guest path
  through `vfs.chmod` (AOSP's `UnixFileSystem_setPermission0` mapping:
  `ACCESS_READ/WRITE/EXECUTE` × owner-only), returning `false` on stat/chmod
  failure — including read-only boot files (`EROFS`) and synthetic paths.
* `getLength`, `delete0`, `rename0`, `list`, `createDirectory`,
  `createFileExclusively`, `get(Set)LastModifiedTime`, `getSpace`,
  `getBooleanAttributes0(File)` all go through the existing VFS calls
  (`stat`/`remove`/`rename`/`list`/`mkdir`/`open`/`utimens`/`statvfs`), so
  confinement, denial accounting and `EROFS` behaviour are unchanged.
* `crates/acos-vm/Cargo.toml`: `rustix` gets the `process` feature (for
  `geteuid`/`getegid`); the crate stays `#![forbid(unsafe_code)]`.

## 2. Acceptance — Java vs real Java

New `crates/acos-vm/tests/io_file.rs` + `tests/java/JavaFileMain.java`: the
**same `.class`** is run twice and the outputs must match **verbatim** —
once on the host JVM (real OpenJDK `java.io.UnixFileSystem` = the oracle),
once on ACOS with `--corelib real` over the VFS. The case covers
`createDirectory`, `getBooleanAttributes0`, `createFileExclusively`,
`getLength`, `checkAccess`, `setPermission` (`setReadable/Writable/Executable`),
`setReadOnly`, `get(Set)LastModifiedTime`, `rename0`, `delete0`, `list`,
`getSpace`, plus missing-path behaviour (no exceptions, `false`/`0`).

First run found one real divergence (`canRead()` stayed `true` after
`setReadable(false,false)`), which is exactly the `File.canRead`/`access`
semantics described above — fixed by evaluating mode bits in `checkAccess`.

## 3. bionic non-local jumps (`acos-native-loader`)

`libhermesvm.so` imports `_setjmp@LIBC` + `_longjmp@LIBC`.
`bionic/engine_gaps.rs` now carries a full x86_64 bionic-ABI implementation:

| symbol | behaviour |
|---|---|
| `_setjmp` / `_longjmp` | callee-saved GPRs + `rsp`/`rip`, no signal mask (bionic `<setjmp.h>`) |
| `setjmp` | **saves the mask** (`sigsetjmp(env,1)` — bionic's documented contract) |
| `sigsetjmp(env, savemask)` | tail-jump to the register-only or mask-saving save |
| `longjmp` / `_longjmp` / `siglongjmp` | restore registers, restore the 8-byte mask when the buffer says one was saved, `val==0 → 1` |

Design points (documented in the file):

* The host glibc `setjmp` is **never** called: its `jmp_buf` is larger and
  pointer-mangled, so forwarding would smash the guest stack. Save/restore is
  inline asm.
* The save runs at the **shim entry** — no Rust wrapper frame sits between the
  guest call and the saved `rsp`/`rip`; `sigsetjmp` is a tail-jump for the same
  reason. `longjmp` therefore genuinely returns twice at the guest call site
  (the shim frame is dead either way).
* Buffer use: words 0–7 registers, word 8 flags (`0x534f4341`|1 = mask valid),
  word 9 the bionic 8-byte `sigset_t` (saved/restored with
  `rt_sigprocmask` syscall 14 and an 8-byte sigset). That is inside bionic's
  11-word `jmp_buf` / 12-word `sigjmp_buf`; nothing in the corpus inspects the
  layout. `_setjmp` leaves the flag word 0, so `longjmp` will not restore a mask
  that was never saved.
* Non-x86_64 keeps the fail-closed structured trap (no faking).

Test: `crates/acos-native-loader/tests/native/testjmp.c`, built with NDK clang
at test time and executed through the loader — 7 checks: double return from a
deeper frame, `_setjmp`/`_longjmp`, `longjmp(env,0)→1`, `sigsetjmp(env,0)`,
`setjmp` restores the mask, `_setjmp` does not, `sigsetjmp(env,1)` does.

## 5. Gaten ladder after the fixes

(1374 provided, 56 partial), i.e. `_setjmp`/`_longjmp` now resolve:


`acos launch .cache/w181a/gaten.apk --json` through the parent/child harness now
fails at the harness boundary, not with the old `setPermission0`:

```
status: error  code: INTERNAL  message: "confined child closed stdout"
```

The child's own stderr is empty (`ACOS_MCP_QUIET=1`, stderr inherited) so the
real cause was obtained by running the *same* confined child directly
(`acos --confined-child --rw … --ro … --rn-dex …`) and feeding it the MCP
`initialize` + `acos_launch` frames. That reproduces deterministically in ~10 s
with the release binary:

```
[android-log 3] jni_lib_merge: Entering merged library JNI_OnLoad.
[android-log 3] jni_lib_merge: Preparing 4 pre-merged libs (including stub)
[android-log 3] jni_lib_merge: Preparing to register libhermes_executor_so.  onload_func: 0x7f…

[android-log 3] jni_lib_merge: About to register 3 actual methods.

ACOS guest assertion failed: LocalReferenceAllocator{}.verifyReference(ref) || GlobalReferenceAllocator{}.verifyReference(ref)
  at .../fbjni-0.7.0/prefab/modules/fbjni/include/fbjni/detail/References-inl.h:424
  (facebook::jni::alias_ref<_jclass *>::alias_ref(javaobject) [T = _jclass *])
```

Interpretation (evidence, not guess): the `setPermission0` blocker is gone and
the mount proceeds **into the Hermes executor's `JNI_OnLoad`**. RN 0.86's
merged-JNI registration path then fails fbjni's reference verification: fbjni
constructs `alias_ref<jclass>` from a `jobject` that its
`LocalReferenceAllocator`/`GlobalReferenceAllocator` do not recognise. ACOS's
JNI bridge hands guest native code VM handles (indices), not real ART
reference pointers with fbjni's per-thread tracking, so fbjni's debug-time
`verifyReference` fires. This is a **JNI-bridge contract gap** (fbjni reference
identity), not a file-permission or Hermes-bytecode problem.
