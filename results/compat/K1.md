This report answers one question with measurements, not opinions: **how many
real, popular, open-source apps get through the ACOS ladder (inspect → process →
`Application.onCreate` → first frame → tree → screenshot → tap) on real ART, and
what blocks the rest?** It contains no engine changes: every wall below is a
finding, with the first failing call and the ACOS component that owns it.

## 2. Harness and exact commands

Two committed tools, no engine changes:

| file | role |
|---|---|
| `tools/compat/fetch-corpus.py` | index → selection → download → sha256 verify → `manifest.json` |
| `tools/compat/k1-run.py` | one app: inspect → serve → launch (20 s first-frame budget) → tree → screenshot → tap first clickable → tree → destroy; writes `report.json`, envelopes, `screen.png`, serve log |
| `tools/compat/run-k1.sh` | corpus loop: one `acos serve` per app, inside `run-exclusive.sh` + `guarded.sh` |
| `tools/compat/k1-analyze.py` | stage funnel, per-app table, ranked walls → `results/compat/k1-results.json` |

The driver holds **one serve connection for the whole app** (the guest dies when
the launch connection closes today — GL1's bug), and it reads the ART guest's
own `session-exit.json` (`application_created`, `activity_resumed`,
`guest_crash`) rather than trusting the transport code `GUEST_EXITED`.

```bash
# 1. corpus (data only; never committed)
tools/compat/fetch-corpus.py --jobs 5          # -> .cache/corpus/k1/{apks,manifest.json}

# 2. engine (this worktree)
CARGO_TARGET_DIR=/home/Qui/Projects/acos/.cache/k1-target CARGO_BUILD_JOBS=8 \
  cargo build --release -p acos-cli -p acos-art
mkdir -p /home/Qui/Projects/acos/.cache/k1/bin
ln -sf .../k1-target/release/acos /home/Qui/Projects/acos/.cache/k1/bin/acos
ln -sf .../k1-target/release/acos-art /home/Qui/Projects/acos/.cache/k1/bin/acos-art

# 3. one corpus run (lock + guard per app/batch; never the zygote, no network)
export ACOS_FONT_DIR=/home/Qui/Projects/acos/.cache/boot/android-34/fonts   # do not set ACOS_BOOT_DIR
tools/compat/run-k1.sh --batch 4                 # normal: release the ART lock every 4 apps
tools/compat/run-k1.sh --batch 1 --only org.fdroid.fdroid,com.termux

# 4. one app by hand (same guard, same lock, one connection held open)
tools/art-runtime/run-exclusive.sh --task K1 -- \
  tools/guarded.sh --mem 8G --time 150 -- \
  python3 tools/compat/k1-run.py --apk .cache/corpus/k1/apks/<apk> --name <pkg> --out .cache/k1/runs/<pkg>

# 5. aggregate
tools/compat/k1-analyze.py --markdown
```

Guards and hygiene, as required: every guest run is inside
`tools/art-runtime/run-exclusive.sh --task K1` and `tools/guarded.sh --mem 8G
--time N`; scratch is `.cache/k1/` and `.cache/art-locks/data-K1-*` (never
`/tmp`); socket path is `.cache/k1/s.sock` (43 chars); the loop refuses to start
when `/` is >85 % full or host RAM is ≥90 % used; guests get no network and no
APK is executed outside the ACOS sandbox.

**Honest note on the lock unit.** `--batch 4` releases the host ART lock after
every four apps, not every app. With a 24-minute holder in the queue, per-app
acquisition starves (the K1 app is re-queued behind every holder after each
app). A batch is one short guarded run (<1 min in practice), so other tracks get
the lock between batches. `--batch 1` restores strict per-app release; §9 lists
what was used for which apps.

## 4. Ranked walls

### W1 — missing `IActivityManager.getMemoryInfo` (transaction 77) — 1 app (Flutter)

* **first failing call**: `ActivityManager.getMemoryInfo(MemoryInfo)` from
  `io.flutter.embedding.android.FlutterActivity`'s Application startup →
  binder transact `android.app.IActivityManager` code 77 → the ACOS peer raises
  `ServiceError::UnsupportedAndroidApi` → the app's `onCreate` throws
  `java.lang.RuntimeException: … UnsupportedOperationException: unsupported
  Android API: android.app.IActivityManager code 77 (getMemoryInfo)`.
* **guest state**: `application_created=true`, `activity_resumed=false`,
  guest exit 1 after 202 ms; no frame.
* **likely ACOS component**: `crates/acos-services/src/ams.rs` (the
  `IActivityManager` dispatcher) with the transaction table in
  `crates/acos-aidl/src/generated/tables.rs:1701` (`getMemoryInfo`).
* **smallest plausible fix**: answer transaction 77 by writing an
  `ActivityManager.MemoryInfo` parcel (`availMem`, `totalMem`, `threshold`,
  `lowMemory=false`) from the guest's own `/proc/meminfo` and cgroup
  `memory.max`, then `reply.writeNoException()`. It is a read-only query; the
  values can be the guest's real numbers, so nothing is faked.
* **AOSP reference**: `frameworks/base/core/java/android/app/IActivityManager.aidl`
  (`void getMemoryInfo(out ActivityManager.MemoryInfo outInfo)`),
  `frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java`
  (`getMemoryInfo`), `android/app/ActivityManager.java` (`MemoryInfo.writeToParcel`).

### W2 — missing `IPackageManager.getPackageInstaller` (transaction 133) — 1 app

* **first failing call**: `PackageManager.getPackageInstaller()` in
  `com.aurora.store.AuroraApp.onCreate` → transact 133 →
  `ServiceError::UnsupportedAndroidApi` → `Unable to create application
  com.aurora.store.AuroraApp`.
* **guest state**: `application_created=true`, `activity_resumed=false`, exit 1
  after 248 ms.
* **likely ACOS component**: `crates/acos-services` package-manager dispatcher +
  `crates/acos-aidl/src/generated/tables.rs:9904` (`getPackageInstaller`).
* **smallest plausible fix**: return a binder implementing `IPackageInstaller`
  with the **empty** state — `getMySessions`/`getAllSessions` → empty array,
  `getInstallerPackageName` → null — and let unsupported mutating calls fail
  loudly. A store app reads sessions at startup; it does not need to install
  anything to render its first frame.
* **AOSP reference**: `frameworks/base/core/java/android/content/pm/IPackageInstaller.aidl`,
  `frameworks/base/services/core/java/com/android/server/pm/PackageManagerService.java`
  (`getPackageInstaller`), `…/pm/PackageInstallerService.java`.

### W3 — app NPE inside `Application.onCreate`, stack not in the evidence — 1 app

* **observed**: `com.dot.gallery` (Compose): `Unable to create application
  com.dot.gallery.GalleryApp: java.lang.NullPointerException: Attempt to invoke
  virtual method 'java.lang.Class java.lang.Object.getClass()' on a null object
  reference`; `application_created=true`, `activity_resumed=false`, exit 1 after
  184 ms.
* **first failing engine call**: **unknown** — the `session-exit.json`
  `guest_crash` line carries the exception message but not a stack. This is a
  *wall class* (a framework object the platform never returns null for is null
  under ACOS) that cannot be assigned without the stack.
* **smallest fix, evidence first**: in the guest's crash publisher
  (`crates/acos-art/guest/java/dev/acos/art/LaunchMain.java`, the `ACOSLAUNCH
  {…}` line; `session-exit.json` writer in `crates/acos-art/src/launch.rs`),
  include the top ~20 stack frames (and the last logd lines) in
  `guest_crash`/a new `stack` field. One rerun then names the null-returning
  call; the framework peer is the likely owner (`ContextImpl.getSystemService`,
  `PackageManager` sugar, or `ActivityThread` state).

### W0 — static surface: `<activity-alias>` launchers are invisible to `acos inspect` — 4/42 (9.5 %), not blocking

`org.wikipedia`, `com.dot.gallery`, `net.mullvad.mullvadvpn`, `org.fdroid.basic`
declare their launcher as an `<activity-alias>` (themed icon) targeting the real
activity. `acos inspect` reports `launcher_activity: null` for all four.
* **why launch still works**: the ART launch path resolves aliases through
  `acos_services::manifest_resolve::launcher_activity`
  (`crates/acos-art/src/launch.rs:4780`), which handles aliases; `acos inspect`
  uses `acos_apk::Manifest::launcher_activity()` (`crates/acos-apk/src/manifest.rs:229`),
  which scans only `<activity>` (no `activity-alias` parsing at all in
  `crates/acos-apk`).
* **impact**: an agent that plans from `inspect` (the documented first step) sees
  a launcher-less APK for ~10 % of real apps and may conclude it cannot be
  launched; capability reports inherit the same lie.
* **smallest fix**: parse `<activity-alias>` (name, `targetActivity`,
  `enabled`, icon/label, intent filters) in `acos-apk` and resolve the alias to
  its target in `launcher_activity()`, matching the launch path.
* **AOSP reference**: `frameworks/base/core/java/android/content/pm/PackageParser.java`
  (`parseActivityAlias`, `PackageParser.Activity` with `targetActivity`),
  `PackageManagerService` launcher resolution.

## 6. Engine gaps vs app-environment needs

Nothing in the measured set needed the network or Play Services: all three
failures are engine-side shim gaps that fire during `Application.onCreate`,
before any screen. That split is the reason these walls are worth fixing first:
they block an app that is otherwise fully offline-capable.

The corpus deliberately contains apps that *will* need network or GMS at
runtime (store/mail/chat clients). They are reported as `REQUIRES_GMS`/app
environment walls only if their launch reaches that call; a framework gap found
earlier in `onCreate` is an engine gap and is ranked above them.

## 7. What a pass and a failure mean here

* `first frame` = `acos_launch` returned `status: pass` with
  `stage_reached: first_frame` on real ART, within the 20 s budget.
* `tree`/`screenshot`/`tap` = the follow-up verbs returned `pass`; the tap is at
  the centre of the **first clickable node in the tree the app produced**, not a
  hardcoded coordinate, and the tree after the tap is captured too.
* `Application.onCreate` is split into **entered** (the guest's
  `application-created` marker: the framework handed the app object to the app's
  code) and **completed** (`activity_resumed`, or a launch pass). An app that
  throws inside `onCreate` counts as *entered but not completed* — this is why
  the funnel in §5 has both rungs.
* A failure whose `error.code` is `GUEST_EXITED` is **not** classified by that
  transport code. The guest's own `session-exit.json` supplies
  `guest_crash`, which carries the app-level exception and, for the shim-gap
  class, the exact `unsupported Android API: <interface> code <n> (<method>)`.

## 9. Status, limits and what is still running

* **First commit of this file**: 4/42 apps have a `report.json`
  (`chat.fluffy.fluffychat`, `com.aurora.store`, `com.beemdevelopment.aegis`,
  `com.dot.gallery`). The other 38 were queued behind other tracks' ART holds.
* **Lock unit actually used**: `--batch 42` for the pending run (one bounded
  hold, ≤15 min) after `--batch 4` proved starvation-prone behind
  `Z7-loop1` (1450 s hold). The batch of 4 completed in **6 s** of guest time,
  so a full-corpus batch is minutes, not hours. Every app still gets its own
  `acos serve` daemon, its own guest, and its own evidence dir; the lock is
  released after the batch.
* **Why this is slow, measured**: K1 acquisitions waited 236–484 s each while
  Z7 (1450 s holds), GL1 (400–458 s) and GR1 (300–400 s) held the host lock.
  Runs that did execute took 2–6 s per app (failures) and ~4 s (the pass).
* **Not attempted**: any engine fix (out of scope), any zygote path, any
  sandbox weakening, per-app ABI rebuilds.
* **Confounds**: `targetSdk` 35–37 apps are run against an API-34 framework;
  that is the same condition a real Android 14 device gives them, and the
  manifest records it per app. Flutter/RN apps are driven through the ART path
  on purpose (that is the measurement), so a failure inside the framework is
  recorded as a framework wall, not as "Flutter is unsupported".
