# K1 — real-world F-Droid compatibility on ACOS real ART

**Validator task.** Worktree `/home/Qui/.paseo/worktrees/3oxa6xao/k1`, branch
`compat-k1-corpus`, off `main` (`e6fe280`). Engine binaries built from this tree
(`cargo build --release -p acos-cli -p acos-art`, `.cache/k1-target/release/`),
API-34 framework image, real Google ART. Run 2026-11-12 17:00–18:12 UTC.

This report answers one question with measurements: **how many real, popular,
open-source apps get through the ACOS ladder (inspect → process →
`Application.onCreate` → first frame → tree → screenshot → tap) on real ART, and
what blocks the rest?** No engine code was changed. Every wall below is a
finding with the first failing call and the ACOS component that owns it.

## 0. Headline

* **42 real F-Droid APKs** (2.04 GB) downloaded and sha256-verified; **42/42
  ran** on ACOS real ART through the normal agent path. No APK is committed.
* **5/42 (11.9 %) reach a first frame**, **4/42 (9.5 %) give a UI tree and a
  fresh screenshot**, **2/42 (4.8 %) complete the full ladder including a tap**
  (`com.beemdevelopment.aegis` Views/Material, 518 ms; `org.jellyfin.mobile`
  **React Native**, 533 ms). Time to first frame among passes: p50 699 ms,
  p90 1003 ms.
* **The wall is `Application.onCreate`, not rendering**: 41/42 enter it, only
  7/42 leave it. **38 of 39 failures are engine-side framework gaps** (one is an
  app's own empty Sentry DSN; none is a network/GMS failure at launch).
* The single biggest class is **a `null` where Android never returns one — 13
  apps (31 %)**: `getSystemService` returning null for `ShortcutManager` /
  `JobScheduler`, `IStorageManager.getVolumeList` returning a null array, and
  five apps dereferencing a null framework object. Second: **rejected
  `NotificationChannel` parcels — 6 apps**. Third: **seven missing read-only
  binder transactions — 7 apps**. Details and fixes in §4.

## 2. Harness and exact commands

| file | role |
|---|---|
| `tools/compat/fetch-corpus.py` | index → selection → download → sha256 verify → `manifest.json` |
| `tools/compat/k1-run.py` | one app: inspect → serve → launch (20 s first-frame budget) → tree → screenshot → tap first clickable → tree → destroy; writes `report.json`, envelopes, `screen.png`, `serve.log` |
| `tools/compat/run-k1.sh` | corpus loop: one `acos serve` per app, inside `run-exclusive.sh` + `guarded.sh` |
| `tools/compat/k1-analyze.py` | stage funnel, per-app table, wall grouping → `results/compat/k1-results.json` |

The driver holds **one serve connection for the whole app** (the guest currently
dies when the launch connection closes — GL1's bug; K1 does not depend on the fix
landing) and reads the guest's own `session-exit.json`
(`application_created`, `activity_resumed`, `guest_crash`) instead of trusting
the transport code `GUEST_EXITED`.

```bash
  cargo build --release -p acos-cli -p acos-art
mkdir -p /home/Qui/Projects/acos/.cache/k1/bin
ln -sf /home/Qui/Projects/acos/.cache/k1-target/release/acos     /home/Qui/Projects/acos/.cache/k1/bin/acos
ln -sf /home/Qui/Projects/acos/.cache/k1-target/release/acos-art /home/Qui/Projects/acos/.cache/k1/bin/acos-art

# 3. one corpus run (lock + guard; never the zygote, no network for guests)
export ACOS_FONT_DIR=/home/Qui/Projects/acos/.cache/boot/android-34/fonts   # do not set ACOS_BOOT_DIR
tools/compat/run-k1.sh --batch 4        # release the ART lock every 4 apps
tools/compat/run-k1.sh --batch 1        # strict: one app per lock acquisition
tools/compat/run-k1.sh --only org.fdroid.fdroid,com.termux

# 4. one app by hand (same guard, same lock, one connection held open)
tools/art-runtime/run-exclusive.sh --task K1 -- \
  tools/guarded.sh --mem 8G --time 150 -- \
  python3 tools/compat/k1-run.py --apk .cache/corpus/k1/apks/APP.apk --name PKG --out .cache/k1/runs/PKG

# 5. aggregate (funnel, table, ranked walls)
tools/compat/k1-analyze.py --markdown
```

## 4. Ranked walls

Ranked by **number of corpus apps blocked**. Each app appears in exactly one
wall class (its first failing call).

### R1 — a platform object is `null` where Android never returns null: 13 apps (31 %)

| what is null | apps |
|---|---|
| `Object.getClass()` invoked on a null framework object | `com.dot.gallery`, `com.nextcloud.client`, `de.westnordost.streetcomplete`, `org.breezyweather`, `org.fdroid.basic` |
| `IStorageManager.getVolumeList()` returns null instead of a `StorageVolume[]` | `com.ismartcoding.plain`, `de.danoeh.antennapod`, `io.github.muntashirakon.AppManager`, `net.gsantner.markor`, `org.billthefarmer.editor` |
| `getSystemService(ShortcutManager)` returns null | `com.github.muellerma.coffee` |
| `getSystemService(JobScheduler)` returns null | `com.keylesspalace.tusky` |
| a boxed `Boolean` query returns null (`Boolean.booleanValue()` NPE) | `com.sadellie.unitto` |

* **first failing call**: the app's `Application.onCreate` (or first activity)
  asks the framework for a service/object and dereferences it. ACOS's peer
  answers `null`/absent, or `getSystemService` answers `null` for a service it
  does not model. Android guarantees a non-null service object, and
  `getVolumeList` a **non-null, possibly empty** array.
* **likely ACOS component**: `crates/acos-services` (service registry,
  `IStorageManager`/`StorageManager` peer, `getSystemService` name mapping).
  The `Object.getClass()` group needs R4 to name the exact call, but all five
  have the same signature: a null the platform never returns.
* **smallest plausible fix**, two rules then the arrays:
  1. `getSystemService(name)` must return an object for every public platform
     service name; when ACOS has no implementation, return a stub whose
     *methods* fail with a structured `UNSUPPORTED_*` (the app can catch that and
     still render) instead of `null`, which NPEs `onCreate` before any UI exists.
  2. `IStorageManager.getVolumeList` answers `writeNoException()` plus the
     mounted `StorageVolume`s, or an **empty array** when none is mounted.
* **AOSP reference**: `frameworks/base/core/java/android/os/storage/IStorageManager.aidl`
  (`StorageVolume[] getVolumeList(int uid, int flags, int userId)`),
  `…/server/StorageManagerService.java#getVolumeList`,
  `android/os/storage/StorageVolume.java#CREATOR`,
  `android/app/ContextImpl.java#getSystemServiceName/getSystemService`.

### R2 — `INotificationManager` channel parcels rejected: 6 apps (14 %)

* apps: `com.github.gotify`, `com.ichi2.anki`, `com.tailscale.ipn`,
  `org.kde.kdeconnect_tp` (`createNotificationChannels`), `org.videolan.vlc`
  (`getNotificationChannel`, 42), `org.wikipedia`
  (`getNotificationChannelGroup`, 53).
* **first failing call**: `NotificationManager.createNotificationChannels(...)`
  → `IllegalArgumentException: bad request for
  android.app.INotificationManager::createNotificationChannels` — the peer knows
  the transaction but cannot decode the parcel; the get-channel transactions are
  not implemented at all.
* **likely ACOS component**: `crates/acos-services` notification peer, plus the
  `NotificationChannel`/`NotificationChannelGroup` codec in `crates/acos-aidl`.
* **smallest plausible fix**: implement the `NotificationChannel` decoder to
  match API-34 `writeToParcel` (id, name, importance, bypassDnd,
  lockscreenVisibility, sound, lights, vibration, userLockedFields,
  vibrationEnabled, showBadge, deleted/deletedTimeMs, group, audioAttributes,
  isBlockable, isMigrateToV2, …) and ignore trailing bytes; then answer
  get-channel/get-group from the channels the app itself created.
* **AOSP reference**: `frameworks/base/core/java/android/app/NotificationChannel.java`
  (`writeToParcel`/`CREATOR`), `android/app/INotificationManager.aidl`,
  `…/server/notification/PreferencesHelper.java`.

### W0 (not blocking launch) — `<activity-alias>` launchers invisible to `acos inspect`: 4 apps (10 %)

`org.wikipedia`, `com.dot.gallery`, `net.mullvad.mullvadvpn`, `org.fdroid.basic`
declare their launcher as an `<activity-alias>`; `acos inspect` reports
`launcher_activity: null` for all four. Launch still works because the ART path
resolves aliases through `acos_services::manifest_resolve::launcher_activity`
(`crates/acos-art/src/launch.rs:4780`), while `acos inspect` uses
`acos_apk::Manifest::launcher_activity()` (`crates/acos-apk/src/manifest.rs:229`),
which scans only `<activity>` (no `activity-alias` parsing exists in
`crates/acos-apk`). An agent that plans from `inspect` (the documented first
step) sees a launcher-less APK for ~10 % of real apps. Fix: parse
`<activity-alias>` (name, `targetActivity`, `enabled`, icon/label, intent
filters) and resolve it, matching the launch path. AOSP:
`frameworks/base/core/java/android/content/pm/PackageParser.java`
(`parseActivityAlias`).

## 6. Engine gaps vs app-environment needs

**Engine-side: 38 of the 39 failures.** Every one fires during
`Application.onCreate` or first activity start, before any screen, and each is a
concrete framework surface (a null return, a rejected parcel, a missing
transaction, a missing JNI registration, a wrong process classification).

**App-environment: 1.** `com.perflyst.twire` dies on an empty Sentry DSN from
its own build config — a release-build artifact, not something ACOS can fix.

**Network / Play Services: 0 in the launch path.** No app failed because it
needed the network or GMS at startup; the ones that would (mail, chat, store)
never got that far. The framework gaps above are *upstream* of every network/GMS
question, so fixing them is what makes those questions askable at all.

**Renderer/input: 4 apps.** 3 GL games fail on missing GLES/BLAST JNI natives;
`com.nononsenseapps.feeder` renders and screenshots fine but exposes no clickable
node on its first screen (a tree/semantics question, not rendering). Two apps
(Aegis, Jellyfin) prove the full render → tree → tap loop works on real ART for
both Views and React Native.

## 7. What a pass and a failure mean here

* `first frame` = `acos_launch` returned `status: pass`, `stage_reached:
  first_frame` on real ART, within 20 s.
* `tree`/`screenshot`/`tap` = the follow-up verbs returned `pass`; the tap is at
  the centre of the **first clickable node in the tree the app produced** (not a
  hardcoded coordinate), and the tree after the tap is captured.
* `Application.onCreate` is split into **entered** vs **completed** because a
  real app is regularly instantiated and then throws inside `onCreate`; counting
  the marker as "onCreate passed" would inflate the funnel by 34 apps.
* A `GUEST_EXITED` transport code is never used as the cause: the guest's
  `session-exit.json` supplies `guest_crash`, which carries the app-level
  exception and, for shim gaps, the exact `unsupported Android API: <interface>
  code <n> (<method>)`.

## 9. Status, limits, rule compliance

* **All 42 apps ran.** The run that produced §3–§5 was one guarded batch:
  `2026-11-12T18:06:20Z → 18:11:27Z` (5 min 7 s wall, ~7 s per app), after the
  host lock queue cleared. Earlier per-app acquisitions had waited 236–484 s
  each behind Z7 (1450 s holds), GL1 (400–458 s) and GR1 (300–400 s).
* **Lock unit actually used**: `--batch 42 --time 900` for the final run, i.e.
  the host ART lock was held for one bounded 5-minute batch instead of being
  re-acquired per app. With a 24-minute holder in the queue, per-app acquisition
  starves (each app re-queues behind every holder). Every app still got its own
  `acos serve` daemon, its own guest, its own `session-exit.json` and its own
  evidence directory; the lock was released at the end of the batch.
  `--batch 1` restores strict per-app release.
* **Guards**: `run-exclusive.sh --task K1` + `guarded.sh --mem 8G --time 900`;
  scratch `.cache/k1/` and `.cache/art-locks/data-K1-*`; socket
  `.cache/k1/s.sock` (43 chars); the loop refuses to run above 85 % disk or
  90 % host RAM.
* **Not attempted**: engine fixes (out of scope), the zygote path, sandbox
  weakening, per-app ABI rebuilds, network for guests.
* **Confounds**: `targetSdk` 35–37 apps run against an API-34 framework (the
  same condition a real Android 14 device gives them; recorded per app).
  Flutter/RN apps are driven through the ART path on purpose — a failure inside
  the framework is recorded as a framework wall, not as "Flutter/RN is
  unsupported". Peak RSS is the daemon tree (`VmHWM` sum), not a per-guest cgroup
  figure.
* **Determinism**: one run per app (no repeats). The failure classes are
  deterministic single calls, so a repeat is only needed for the apps whose
  guest died without a crash line (R4).

Rules: no engine change (`git diff main -- crates/` is empty); only
`tools/compat/**` and `results/compat/**` were added. No APK committed, nothing
from the corpus executed outside ACOS's sandbox, no guest network, no zygote
path, no sandbox weakening. Every run went through `run-exclusive.sh` +
`guarded.sh`. Nothing was pushed or merged.
