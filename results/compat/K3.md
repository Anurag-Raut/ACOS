## 1. K3b — the PMS error class (cheap, two apps)

**Root cause.** `IPackageManager.getPackageInfo`/`getApplicationInfo` for a
package that is not installed answered with a **parcel exception**
(`EX_ILLEGAL_ARGUMENT` carrying ACOS's structured "unknown service name"). That
is not what the platform does: the image's PMS returns a **null**
`PackageInfo`/`ApplicationInfo` and the *client* raises the exception app code
catches — `ApplicationPackageManager.getPackageInfoAsUser`
(`frameworks/base/core/java/android/app/ApplicationPackageManager.java`):

```java
PackageInfo pi = getPackageInfoAsUserCached(packageName, flags, userId);
if (pi == null) throw new NameNotFoundException(packageName);
```

Sending an exception instead of the null left apps in a `catch
(NameNotFoundException)` that never ran, and their first failure was
`IllegalArgumentException` from ACOS, not the app's own recovery path.

**Fix (`PMSNULL`).** `PmsService` answers a **typed null** for an unknown
package on both calls (`Value::TypedObject(Parcelable::Null)`); the framework's
own client turns it into `NameNotFoundException`. `getPackageUid` already
answered `-1`, which is the same contract. Nothing else changed: the app's own
package still resolves.

**Before → after.**

| app | K2 first failing call | K3 first failing call |
|---|---|---|
| `org.videolan.vlc` | `getPackageInfo("com.google.android.gsf")` → "unknown service name" | `InflateException` on `ConstraintLayout` in `activity_onboarding` (layout/theme, not PMS) |
| `org.fdroid.fdroid` | same class (PMS error) | `IPackageManager.getSystemAvailableFeatures` (code 99) → now answered (§2.5); next is an app-level `exit 10` with no crash line |

Both now complete `Application.onCreate` and reach the launch transaction.
`checkService` for an unknown name was already `null`
(`ServiceHost::check_service` → `Ok(None)`); K3 verified that path is the one
the apps take and that no other name lookup raises.

## 2. K3c — deliver the app's own providers through the framework

**Root cause.** The exec path's `LaunchMain.buildBindApplicationRequest` sent an
**empty** `ProviderInfoList`
(`ProviderInfoList.fromList(new ArrayList<>())`). `ActivityThread` therefore
never ran `installContentProviders`, so no `<provider>` of the APK existed:
androidx.startup's `InitializationProvider` never ran (element's
`ProcessLifecycleInitializer cannot be initialized lazily`), WorkManager had no
provider, FileProvider did not exist, and Sentry's
`SentryInitProvider`/metadata path had nothing to read.

**Fix (`PROVIDERS`).** The host parses the APK's providers from the same typed
manifest model PMS answers `getProviderInfo` from
(`acos-services::pms::PmsState::from_apk`) and passes them to the guest as one
record per `<provider>` (`class|authorities|permission|exported|grantUri`).
Records whose `android:process` is not this process are dropped, which is the
filter `AMS.generateApplicationProvidersLocked` applies with
`queryContentProviders(processName, uid, …)`. `LaunchMain` builds real
`ProviderInfo` objects (authorities joined with `;`, `applicationInfo` = the
same `ApplicationInfo` the bind request carries) and the framework does the
rest:

```
ActivityThread.handleBindApplication
  → installContentProviders
      → AppComponentFactory.instantiateProvider(cl, info.name)
      → provider.attachInfo(context, info)      // ContentProvider.onCreate
  → IActivityManager.publishContentProviders    // real AMS transaction
```

No provider is called by hand, and the stock order is preserved: providers are
created after `Application.attachBaseContext` and before
`Application.onCreate` (that is where `handleBindApplication` puts them).

**Two walls this exposed (both fixed here, both real Android behaviour):**

1. `publishContentProviders(IApplicationThread, List<ContentProviderHolder>)`
   arrives as an `ArrayList`, so the decoded AIDL table recorded the **erasure**
   `java.util.List` and the dispatcher had no element codec. `codec` now decodes
   that transaction with the declared element class
   `android.app.ContentProviderHolder` (`read_args_override`), which is
   transcription of the AIDL declaration, not a guess.
2. `BaseBundle.writeToParcelInner` writes an **empty** bundle as a single `0`
   int with no `BNDL` magic ("special case for empty bundles"). ACOS's reader
   demanded the magic and returned `bad Bundle magic 0x0`, which killed
   `installContentProviders` after the providers had already been created. The
   reader (and writer) now implement the empty case.

**Before → after (the apps this moved).**

| app | K2 | K3 |
|---|---|---|
| `org.videolan.vlc` | static-init/PMS wall | providers install; `activity_onboarding` layout inflate |
| `org.fdroid.fdroid` | PMS error class | providers install; `getSystemAvailableFeatures` |
| `com.termux` | platform layout inflate (line 46) | unchanged next wall, but providers now present |
| `io.element.android.x` | `ProcessLifecycleInitializer cannot be initialized lazily` | **`InitializationProvider` runs**; next wall is `<meta-data>`: Sentry's `SentryInitProvider` needs the app's `io.sentry.dsn` metadata and PMS sends no `metaData` Bundle |

**Also answered while measuring K3b/K3c (neutral on the funnel):**
`IPackageManager.getSystemAvailableFeatures` (code 99) now returns a
`ParceledListSlice<FeatureInfo>` built from the same feature table
`hasSystemFeature` answers (`android.content.pm.FeatureInfo` codec added). It
moves `org.fdroid.fdroid` past the unsupported call; fdroid's next failure is
an app-level `exit 10` with no Java crash line (same class as anki's K2 exit),
so it still does not reach a frame.

The element result is the honest remainder of K3c: the provider *delivery* is
correct (the provider's `onCreate` is what raises the DSN error), and the next
wall is **manifest `<meta-data>`** (`acos-apk` parses none; `ApplicationInfo`
and `ProviderInfo` metadata Bundles are empty). That is a named, sized
follow-up, not a hidden failure.

## 3. K3a — the next walls, classified rather than crashed

The brief allowed the cheap ones and demanded an honest classification plus a
cost for the rest. What the corpus shows after K3b/K3c:

| wall | apps | why it is not a shim | cost |
|---|---|---|---|
| GL / BLAST natives (`EGLImpl._nativeClassInit`, `BLASTBufferQueue.nativeCreate`) | `com.shatteredpixel.shatteredpixeldungeon`, `io.anuke.mindustry`, `org.supertuxkart.stk` | needs a real EGL/GLES driver and a `BufferQueue`/`BLAST` producer, not a symbol stub: the games then require shaders, textures and a GPU-side swap chain | large (weeks); must stay `UNSUPPORTED_ANDROID_API` naming `android.opengl`/`BLASTBufferQueue` |
| WebView provider | `com.libreweatherrn`, `de.tutao.calendar` | the framework refuses to load a WebView provider in a process it believes is privileged; the honest fix is the provider discovery path (`WebViewFactory.getProvider`) plus a real Chromium provider | large; classify as `UNSUPPORTED` capability `android.webkit.WebView` |
| AndroidKeyStore | `com.dot.gallery`, `com.tailscale.ipn`, `org.quantumbadger.redreader` | `KeyStore.getInstance("AndroidKeyStore")` needs the keystore2 provider **and a keymaster/software key store**; answering keys with fabricated material would break the core promise (the app would think it had attested keys) | large; a read-only shim that only raises the documented `KeyStoreException` is what the app already gets today |
| manifest `<meta-data>` | `io.element.android.x` (+ any app reading DSN/keys from metadata) | needs metadata parsing in `acos-apk` and a `Bundle` in the `ApplicationInfo`/`ProviderInfo` replies | small-medium (next K3 candidate) |
| layout/theme inflation (`ConstraintLayout`, `<unknown>`) | `org.videolan.vlc`, `com.termux`, `com.github.gotify` | R2's track (resource/inflation), not a service wall | owned by R2 |

K3 therefore does **not** fake any of these. Each app's evidence names the
capability in its own crash line, and the funnel counts it as blocked, not as a
pass.

## 5. Limits and rule compliance

* Changed: `crates/acos-services` (`pms.rs`, `codec.rs`, `parcelable.rs`,
  new test), `crates/acos-apk` (one manifest attribute:
  `android:grantUriPermissions`), `crates/acos-art` (`launch.rs` provider spec,
  `LaunchMain.providerList`), and `tools/compat/k1-analyze.py` (wall names).
  The sandbox, the network policy, the ART launch path and the untrusted-APK
  exec path are unchanged; APKs stay on the exec path, no zygote.
* Provider delivery is the **manifest's** provider set: nothing is invented, and
  a provider whose process is not this process is not installed here (exactly
  the AMS filter). Where the platform would need a real backend (keystore, GL,
  WebView) the run still fails with the app's own exception naming the
  capability.
* Corpus APKs only in `.cache/corpus/k1`; runs and gates in `.cache/k3`; no APK
  or full frame committed. Host RAM stayed under the 90 % ceiling (peak
  recorded in the run log).
* Confound: targetSdk 35–37 apps still run against an API-34 framework, as on a
  real Android 14 device.
