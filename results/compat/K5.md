## What changed since the pre-merge checkpoint

1. **APK signing certificates (fix-first, done + tested).**
   - v1 block reads are capped: 1 MiB absolute, 200× deflate ratio, and a
     capped `read_to_end` because the zip size field is untrusted. Violations
     are `APK_SIGNING_MALFORMED`.
   - `PackageInfo.signatures` is **one leaf cert per signer**, not the first
     signer's chain; v2/v3/v3.1 iterate every signer.
   - Highest present scheme wins; a malformed higher scheme is an error, never
     a lower-scheme fallback. v1 is used only when no block scheme exists and
     the signer is found by `SignerInfo` issuer+serial.
   - `Apk::signing_certificates_error` records a rejection; PMS sees empty, not
     wrong.
   - `acos-apk` lib: **14/14** (incl. malicious oversized block, ratio and
     lying-reader caps, v3-over-v2, malformed-v3 no-downgrade, chain-vs-leaf,
     v1 sid selection).

     `PackageInfo.CREATOR`** in `acos-runtime/tests/parcelable_java.rs` (1/1)
     and re-emits identical bytes. The ART guest's

### 1. The `KeystoreRefusal extends Error` deviation is REMOVED

K5b justified `KeystoreRefusal extends Error` with a measurement, not a design:
`javax.crypto.Cipher` performs **delayed provider selection**, so when our SPI's
`engineInit` threw, the JCA tried the next provider and Conscrypt performed the
operation the key forbade. The orchestrator's security review rejected carrying
that deviation, and AOSP does not need it: `AndroidKeyStorePrivateKey`/
`SecretKey` are **opaque** (`getEncoded()`/`getFormat()` return `null`), so no
other provider can initialise with the key object at all.

Reproduced from the image's own bytecode (`dexdump` on
`framework/classes3.dex` and `core-oj/classes.dex`):

- `android.security.keystore2.KeyStoreCryptoOperationUtils.getInvalidKeyException`
  — `KM_ERROR_KEY_EXPIRED (-25) -> KeyExpiredException()`,
  `KM_ERROR_KEY_NOT_YET_VALID (-24) -> KeyNotYetValidException()`,
  `LOCKED/UNINITIALIZED/KM_ERROR_KEY_USER_NOT_AUTHENTICATED (-26) ->
  UserNotAuthenticatedException()`, `KEY_NOT_FOUND/KEY_PERMANENTLY_INVALIDATED ->
  KeyPermanentlyInvalidatedException()`, default
  `InvalidKeyException("Keystore operation failed", e)`.
- `…getExceptionForCipherInit` — `KM_ERROR_INVALID_NONCE (-52) ->
  InvalidAlgorithmParameterException("Invalid IV")`,
  `KM_ERROR_CALLER_NONCE_PROHIBITED (-55) ->
  InvalidAlgorithmParameterException("Caller-provided IV not permitted")`.
- `javax.crypto.Cipher.tryCombinations`/`chooseProvider` — the **first**
  provider's exception is remembered and rethrown, and a provider's service is
  skipped when `Provider.Service.supportsParameter(key)` says no. That is the
  second half of the AOSP mechanism: `AndroidKeyStore*Provider` registers
  `SupportedKeyClasses`, so the platform provider is never offered a keystore
  key.

What changed in `crates/acos-art/guest/java/dev/acos/art/SoftwareKeyStore.java`:

- `StoreSecretKey`/`StorePrivateKey` carry **only the alias** — `getEncoded()`
  and `getFormat()` return `null`. The material is reachable only inside the
  provider, by alias, from the entry map (`materialSecret`/`materialPrivate`),
  and only `GuardCipher`/`GuardMac`/`GuardSignature` use it. Public keys stay
  ordinary X.509 public keys (`StorePublicKey`, AOSP does the same).
- `KeystoreRefusal` is deleted. Refusals throw the AOSP types/messages above
  (`KeyNotYetValidException()`, `KeyExpiredException()`,
  `InvalidKeyException("Keystore operation failed", KeyStoreException(code,
  detail))`, `InvalidAlgorithmParameterException("Caller-provided IV not
  permitted")`). `android.security.KeyStoreException(int,String)` is `@hide`
  (flagged BLOCKED), so it is constructed reflectively — the guest has no
  hidden-API enforcement (K5b experiment 1).
- `GuardService.supportsParameter` returns true only for `SoftwareKey`s
  (AOSP's `SupportedKeyClasses`), so `Cipher.getProvider()` is honest on both
  paths and the guard never shadows Conscrypt for foreign keys.
- New `GuardSignature` SPI (RSA/ECDSA encodings) so signing with an opaque
  private key still works through the store's material.
- `Store.engineSetKeyEntry` rejects our own opaque keys / null-encoded keys
  instead of storing a zero-length key.
