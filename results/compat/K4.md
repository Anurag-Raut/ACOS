## 1. K3d — manifest `<meta-data>` → `PackageItemInfo.metaData` (`GET_META_DATA`)

**Root cause.** `acos-apk` parsed no `<meta-data>` at all, so the typed manifest
model had nothing to carry, PMS wrote `Value::Bundle(None)` into the `metaData`
slot of every `PackageItemInfo` subtype, and no reply ever contained the Bundle
the platform puts there. With K3c's provider delivery the wall was visible and
app-specific: `io.element.android.x` died in `SentryInitProvider` (`DSN is
required`), `org.billthefarmer.editor` and `com.libreweatherrn` died in
`FileProvider.attachInfo` (`Missing android.support.FILE_PROVIDER_PATHS
meta-data`), all *after* the providers had been created correctly.

**Fix, at the lowest layer and in the platform's own order.**

1. `crates/acos-apk/src/manifest.rs` — a typed `<meta-data>` model
   (`MetaDataEntry { name, value: MetaDataValue }`), parsed from
   `<application>`/`<activity>`/`<service>`/`<receiver>`/`<provider>`. The value
   rules are transcribed from `.cache/aosp/base/.../PackageParser.java`
   `parseMetaData` (tag android-14.0.0_r75, line 5597):
   `android:resource` is peeked **first** and stored as `putInt(name,
   resourceId)`; otherwise `android:value` is `putString` (TYPE_STRING),
   `putBoolean` (TYPE_INT_BOOLEAN), `putInt` (TYPE_FIRST_INT..TYPE_LAST_INT —
   int dec, int hex **and the four colour types**) or `putFloat` (TYPE_FLOAT);
   every other type — including a reference in `android:value` — is not stored
   (what `RIGID_PARSER=false` logs and skips).
2. `crates/acos-services/src/pms.rs` — the entries ride on `AppInfo`,
   `ActivityInfo`, `ProviderInfo` and `ServiceInfo`; every
   `to_parcelable_with_flags` writes them into the `metaData` slot **only when
   the call's `flags` (a `long` on API 34) has `PackageManager.GET_META_DATA`
   (`0x80`)** — the `copyNeeded`/`generate*Info` rule of `PackageParser`.
   `getPackageInfo` propagates the same flags into its nested `ApplicationInfo`.
   Covered calls: `getApplicationInfo`, `getPackageInfo`, `getActivityInfo`,
   `getServiceInfo`, `getProviderInfo`, `resolveContentProvider`.
3. `crates/acos-art/src/launch.rs` — the PMS now publishes the APK path the
   **guest** can open, `/data/app/<name>.apk`, as
   `ApplicationInfo.sourceDir`/`publicSourceDir`
   (`PmsState::set_guest_apk_path`, `ServiceHost::install_package_from_apk_as`).
   This was the second half of the FileProvider failure and it is not obvious:
   `androidx`'s `FileProvider` re-resolves its own authority with
   `resolveContentProvider(authority, GET_META_DATA)` and then calls
   `PackageItemInfo.loadXmlMetaData` →
   `PackageManager.getResourcesForApplication` →
   `ResourcesManager.getResources(sourceDir…)`. With the host path in
   `sourceDir` the guest logged

   ```
   W/ResourcesManager: failed to preload asset path '<host>/…/org.billthefarmer.editor_196_1.96.apk'
   java.io.IOException: Failed to load asset path '<host>/…/editor.apk'
   E/ResourcesManager: failed to add asset path '<host>/…/editor.apk'
   ```

   and the app reported `Missing android.support.FILE_PROVIDER_PATHS
   meta-data` — the Bundle was already correct at that point (the PMS trace in
   §1.2 below proves it), the *resources* were not reachable.
4. `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java` — the bind request's
   `ApplicationInfo.metaData` carries the `<application>` metadata
   (`context.getApplicationInfo().metaData`, which is how Sentry reads
   `io.sentry.auto-init`), and each bind `ProviderInfo.metaData` carries the
   `<provider>`'s own entries (encoded by `meta_spec`/`meta_spec_escape`,
   decoded by `metaBundle`/`metaUnescape`).

   *Fidelity note:* a device's AMS builds the bind provider list with
   `STOCK_PM_FLAGS | GET_PROVIDERS` (no `GET_META_DATA`), so its bind
   `ProviderInfo.metaData` is `null` and providers read their metadata back
   through `Context.getPackageManager()` — which is the path that actually
   matters here (`FileProvider`, `androidx.startup`, Sentry) and which PMS now
   serves. ACOS additionally fills the bind record because it only exposes what
   the app's own manifest declares and it keeps `ProviderInfo.metaData`
   truthful for a provider that reads it inside `attachInfo`. Measured effect:
   none of the corpus apps behaves differently because of this field (the ON/OFF
   A/B in §3 is dominated by the PMS path).

## 4. K3e — not a marshal bug: the driver split a `BR_*` command

**Evidence.** With providers on, `net.cozic.joplin` (7 providers) and
`io.element.android.x` (6 providers) died in
`IActivityManager$Stub$Proxy.publishContentProviders` with
`java.lang.RuntimeException: Unknown error` from `BinderProxy.transactNative`,
and the guest log carried

```
E/IPCThreadState: *** BAD COMMAND -847180016 received from Binder driver
E/IPCThreadState: *** BAD COMMAND 916513200 received from Binder driver
```

`BAD COMMAND` is libbinder's `IPCThreadState::executeCommand` default branch
(`.cache/aosp/native/libs/binder/IPCThreadState.cpp:1499`): the bytes it reads
from the driver's read buffer are not a command.

**Root cause.** `publishContentProviders` exports one binder per provider. Each
newly exported node makes the driver pend `BR_INCREFS` + `BR_ACQUIRE`
(2 × 20 bytes). libbinder reads through **one fixed 256-byte Parcel**
(`IPCThreadState` ctor: `mIn.setDataCapacity(256)`, `talkWithDriver`:
`read_size = mIn.dataCapacity()`), and the kernel driver never copies a
*partial* command — a command either fits or stays queued. ACOS's `flush_pend`
copied `min(pend_len, read_size)`, so 7 providers (7 × 40 + 8-byte
`BR_TRANSACTION_COMPLETE` = 288 bytes) were cut **inside the 7th `BR_INCREFS`**;
the leftover pointer word was then read as a command. The Rust peer never saw a
marshal problem: `E3G_DEBUG=1` shows `REQ seq=46 code=31 … size=10740/64`
(64 offset bytes = 8 flat objects) answered with a 4-byte reply, and the correct
`RSP`.

**Fix.** `crates/acos-binder-peer/native/binder_driver.c`: `flush_pend` walks
`br_cmd_len()` — the header plus the payload of exactly the commands this driver
pends (`BR_TRANSACTION_COMPLETE`/`BR_FAILED_REPLY`/`BR_NOOP`/`BR_SPAWN_LOOPER`/
`BR_DEAD_REPLY` 4 B, `BR_INCREFS`/`BR_ACQUIRE`/`BR_RELEASE`/`BR_DECREFS` 20 B,
`BR_TRANSACTION`/`BR_REPLY` 68 B) — and copies only whole commands, leaving the
remainder queued for the next call: the kernel's invariant, restored.

**Before → after.** joplin: from *no process-start rung* (crash during provider
installation) to **first frame + tree + screenshot** (1269 ms); element no
longer dies in `publishContentProviders` at all (it has 6 providers), and
several apps whose provider sets are large (7 for joplin) are unaffected now.

**Measured, not reasoned:** the same crash is reproducible by keeping the old
`flush_pend` and running any app with ≥7 exported provider binders; the fix
changes no other byte path (the corpus OFF arm is unchanged, §2).

## 6. Limits and follow-ups

* **`<instrumentation>` metadata** and `<meta-data>` on elements ACOS still does
  not model are not parsed; no corpus app reads one.
* **`acos-runtime` (non-ART)**: `pms_java` materialises `ApplicationInfo` through
  the Java bridge, so its `metaData` stays `null`. The ART path (the corpus) is
  the one measured here; wiring the runtime path is a separate, mechanical job.
* **`PmsState` keeps two `ApplicationInfo` copies** (`app` and
  `package.application`) and both are updated by `set_guest_apk_path`; a third
  copy would silently reintroduce the host path. Worth collapsing into one
  record when the PMS model is next touched.
* **Driver test harness**: `flush_pend` is C inside the NDK-built preload, so the
  fix is proven by the reproducer and the corpus, not by a unit test. A tiny C
  harness (synthetic `pend`, assert only whole commands are copied) is the
  follow-up named in E5.9.
* New walls the corpus named this round (all app-level, all classified by the
  app's own exception): `IPackageManager.isInstantApp` (anki),
  `IActivityManager.getIntentSenderWithFeature` (k9),
  `IActivityClientController.setTaskDescription` (tusky),
  `IUserManager.getProfileType` (breezyweather),
  `IPackageManager.canRequestPackageInstalls` (files),
  `IConnectivityManager.requestNetwork` (client),
  `setRequestedOrientation` (app), conscrypt X.509 parsing (redreader).
