## 3. Blockers fixed (the owned area: Flutter session + `acos-jni` Flutter bits)

Four real product defects were exposed and fixed; the first three would affect
**any** framework app, not just this fixture.

### 3.1 The APK's own AOT snapshot was shadowed by the shared engine dir

`FlutterSession::launch` staged `libapp.so` from `opts.lib_dir`
(`.cache/flutter-1/lib-x86_64`) and only extracted the APK's copy when the file
was *absent*. That directory already held the W169-A probe's `libapp.so` **and**
`libapp_probe.so`, and `flutter_backend::flush_options` set
`prefer_probe_snapshot = lib_dir/libapp_probe.so.is_file()` — so every product
Flutter launch ran the **probe** snapshot. The fix (`crates/acos-jni/src/flutter_session.rs`,
`crates/acos-mcp/src/flutter_backend.rs`): never read the snapshot from the shared
dir; always stage `lib/<abi>/libapp.so` out of the APK. `prefer_probe_snapshot`
is now scoped to the raw probe fixture only (`flutter-hello.apk`, whose shipped
snapshot has no semantics and is exercised through the instrumented
`libapp_probe.so`); every other APK is authoritative. `ensure_libs` now only
extracts the engine.

The same `/proc/self/maps` gap (§3.2) also broke the W93-A confinement harness
(`flutter_hello.rs`), which never granted `/proc/self`; the harness profile now
grants it too, so `cargo test -p acos-jni --test flutter_hello` is 2/2 again.

### 3.2 The confined child could not read `/proc/self/maps`

On the first framework semantics update the engine called
`NewDirectByteBuffer` inside `PlatformViewAndroidJNI`. ACOS validates the
caller-owned range against `/proc/self/maps`; Landlock denied it, so the JNI host
threw `IllegalArgumentException: NewDirectByteBuffer: address … is not a readable
host mapping`, the engine aborted at
`platform_view_android_jni_impl.cc(1385) Check failed:
fml::jni::CheckException(env)`. Fix
(`crates/acos-mcp/src/session_backend.rs`): grant the Flutter child's own
`/proc/self` read-only (the Landlock wrapper adds `EXECUTE` on `/proc` only, so
no other process is exposed).

### 3.3 The product child never exported `ACOS_BOOT_DIR` → no glyphs

The engine's Skia font manager opens `/system/etc/fonts.xml` and `/system/fonts/*`
by absolute path; the native-loader translates those onto the extracted boot tree
named by `ACOS_BOOT_DIR`. The W130-A *harness* set it, the product confined child
did not (`session_backend` only added the boot tree to the Landlock read list), so
a real framework app laid out correctly but rendered **zero glyphs**. Fix
(`crates/acos-jni/src/flutter_session.rs`): the session exports
`ACOS_BOOT_DIR` from the boot dir it already resolves. Before/after:

| | before | after |
|---|---|---|
| `ACOS Counter`, `Count: 0`, `Increment`, `Add an item`, `alpha/beta/gamma` | absent | **rendered (Roboto)** |

### 3.4 Missing Material ripple shader

The hand-crafted `flutter_assets` omitted `shaders/ink_sparkle.frag`, so the first
tap raised `Unhandled Exception: Asset 'shaders/ink_sparkle.frag' not found` in
the framework. `tools/build-flutter-app.sh` now takes the assets from
`flutter build bundle --release`, which emits the compiled shaders,
`NativeAssetsManifest.json`, the real `AssetManifest.bin` and `NOTICES.Z`. The
exception is gone.

## 4. Blockers remaining (recorded, not papered over)

### 4.1 Semantics tree is empty (framework never builds one)

The driver does enable semantics — `acos logs` diag reports
`semantics_requested=true seq=0 java=seq=0 enabled=true bytes=0 strings=0
err=null`, i.e. `FlutterJNI.setSemanticsEnabled(true)` succeeded and the
`SemanticsCapture` delegate is installed. But the engine delivered **zero**
`updateSemantics` calls. The root cause is structural: the driver instantiates a
raw `FlutterJNI`, not a `FlutterView`/platform view, so the engine's
`PlatformViewAndroid`/`AccessibilityBridge` connection that drives the Dart
`PlatformDispatcher.onSemanticsEnabledChanged` callback (and hence
`SemanticsBinding`) is absent. The W169-A probe only appeared to work because it
called `PlatformDispatcher.updateSemantics` itself. Consequence: `acos observe
--tree` = 0 nodes and `acos tap --text …` has no node to resolve (coordinate taps
work). Fixing this needs a real platform view in the driver, or a Dart-side
`SemanticsBinding.ensureSemantics()` opt-in — both out of this wave's scope.

### 4.2 `acos type` does not reach the Flutter session

`acos type` → `acos_text` → `session_backend::call_text`, which only checks the
**native child / framework session table**, never `self.flutter` (unlike
`call_tap`/`call_observe`, which do). It therefore returns `UNSUPPORTED_BACKEND:
cannot type text: the runtime is not booted`. Even with the routing fixed,
`FlutterSession::text()` is `Unsupported`: Flutter text input needs the
`flutter/textinput` platform channel (a `TextInputPlugin` or a
`StandardMethodCodec`-based driver that captures `TextInput.setClient` and sends
`TextInputClient.updateEditingState`); the `FlutterJNI`-only driver has none.

### 4.3 Post-tap frame is not re-published

After the tap the app log proves the state change
(`flutter: ACOS_APP increment counter=1`), but `frame_seq` stays 1 and
`acos frame-diff` reports the two PNGs identical (`differing_pixels=0`). This is
the W149-A software-sink republish issue in the confined child (the compositor
frame store is `acos-render`/`acos-wm`, declared in flight for W185-A/W186-A and
not touched here). The tap is therefore evidenced by the Dart log, not by a
second frame.

## 5. Reproduce

```bash
# 1. build the real app APK (SDK via env)
FLUTTER_SDK=$PWD/.cache/flutter-sdk/flutter \
  tools/build-flutter-app.sh fixtures/apps/flutter-counter \
  fixtures/build/apps/acos-counter.apk

# 2. drive it through the product path
export ACOS_SESSION_SOCKET=$PWD/.cache/w189a.sock
./target/debug/acos serve --json &                 # or let launch auto-start one
./target/debug/acos launch fixtures/build/apps/acos-counter.apk \
    --flutter --keep --reference --json
./target/debug/acos observe --screenshot /tmp/frame0.png --json
./target/debug/acos tap 540 470 --json             # Increment button centre
./target/debug/acos logs --json                    # ACOS_APP increment counter=1
./target/debug/acos observe --tree --json          # 0 nodes (see §4.1)
```

The Increment button is at physical `(540, 470)` (logical `(216, 188)`, dpr 2.5);
`Count: 0` renders at the same geometry as the W130-A reference.
