## 2. NEW gap (root cause of "dialog cannot be dismissed"): `match_parent` measured at 2× the display width

The dialog's button panel is laid out **off-screen**:

```
ButtonBarLayout  [0,606,1080,754]
  Space          [64,  880,  618,  880]
  Button 'Cancel'[1172,628, 1403, 754]    <- x outside the 1080-px display
  Button 'OK'    [1634,628, 1865, 754]
```

`1080 = display width`, `2160 = 2 × 1080`. The same 2× signature appears on the
`Toolbar`'s `match_parent` child in every app
(`ActionMenuView [2160, 128, 2160, 275]`). So the dialog itself is fine; a
`match_parent` child of a `wrap_content`/`EXACTLY`-measured parent is measured with
twice the available width somewhere in measure propagation (ButtonBarLayout /
LinearLayout secondary-pass or `AlertController`'s `buttonPanel` measure spec).

Because the tap point is `((left+right)/2) = 1287 > 1080`, `hit_test` finds no window
and the CLI reports `ELEMENT_NOT_FOUND`. **This is a measure/layout bug, not an input
bug**, and it is the blocker for every remaining dialogs-menus interaction (2–7).

**Not fixed here:** the measure path is not in this wave's owned crates and needs a
`View.measure`/`MeasureSpec` trace (where 2160 enters), which is a full wave on its
own. Recorded with the exact evidence above.

* `AbsListView.onTouchEvent` ACTION_DOWN posts `mPendingCheckForTap` with

  `mTouchMode` to `TOUCH_MODE_DONE_WAITING`; `performItemClick` then runs from the

  or pump cut-off between DOWN and UP would drop it (W161-A's
  `unscheduleTraversals` runs after *every* input frame — worth checking whether it
  also cancels a listener-only traversal the ListView needs).
* `smoothScrollToPosition` needs the `Scroller`/`OverScroller` + `Choreographer`
  frame loop on virtual time; this wave did not touch `fw_vsync`.

two-line rows (`row_title`/`row_sub`) with a `SCROLL` action.

## 5. DatePicker `TypedArray.getString` NPE — root cause identified, not fixed

Chain from `results/app-matrix/datepicker-probe-logs.json` (unchanged, still the best
evidence):

```
java.lang.NullPointerException
  android.content.res.TypedArray.getString
  android.widget.TextView.readTextAppearance
  android.widget.TextView.<init>
```

AOSP API 34 `TypedArray.getString` (line 274 of the framework source):

```java
} else if (type == TypedValue.TYPE_STRING) {
    return loadStringValueAt(index).toString();      // NPE here
```

and `loadStringValueAt`:

```java
final int cookie = data[index + STYLE_ASSET_COOKIE];
if (cookie < 0) {
    if (mXml != null) value = mXml.getPooledString(data[index + STYLE_DATA]);
} else {
    value = mAssets.getPooledStringForCookie(cookie, data[index + STYLE_DATA]);
}
return value;                                        // null -> .toString() NPE
```

`readTextAppearance` is fed by
`theme.obtainStyledAttributes(attrs, styleable.TextView, …)` — a **hybrid**: the
`AttributeSet` comes from the layout XML (`mXml != null`) but the *found* values come
from the theme/style bags in `resources.arsc`. ACOS's
`res/theme.rs::null_or_raw_typed_value` writes **every non-reference value** with
`asset_cookie: -1` and `string: None` ("route string reads through the parser's own
`StringBlock`"). That is correct for a value taken directly from the start tag, but
**wrong for a value taken from a style/theme bag**: its `data` is an index into the
**ARSC package string pool**, so `mXml.getPooledString(data)` reads the *XML* pool at
that index, finds nothing, returns `null`, and `getString` NPEs. `null_or_raw_typed_value`
cannot tell the two apart because `fill_outputs` merges all sources into bare
`HashMap<u32, ResValue>` (`xml_attr_map`, `collect_style(defStyleAttr)`,
`collect_style(defStyleRes)`, `theme.values`) and drops provenance.

**Fix sketch (principled, matches `ResTable::ResolveReference`):**

1. `theme.rs`: keep provenance per source (`SourceKind::XmlTag` vs
   `SourceKind::ResTable(source_index)`), e.g. `sources: Vec<(SourceKind,
   HashMap<u32, ResValue>)>`. For a non-reference value from `ResTable(i)`, emit
   `asset_cookie = i as i32 + 1`, `data` unchanged, and `string =
   table.global_string(bytes, data)` for `TYPE_STRING` (already implemented in
   `manager.rs::build_typed_value` — reuse it). `XmlTag` values keep cookie `-1`.
   This is exactly what AOSP `Res_value` carries: `assetCookie` identifies the
   `ApkAssets` the string index belongs to. `retrieve_attributes`/`resolve_attrs`
   have the same split (`resolve_attrs` is theme-only → never cookie `-1`).
2. `fwk_res.rs`: implement the second half of the cookie path,
   `ApkAssets.getStringFromPool(I)Ljava/lang/String;` (AOSP routes
   `getPooledStringForCookie` → `ApkAssets.getStringFromPool`, not through
   `StringBlock`). The ARSC string pool is already parsed
   (`res::arsc::ResTableIndex::global_string`, `res::strpool::StringBlock`), so this
   is a small native. Without it the cookie `>= 0` branch would hit an unbound native
   (`UNSUPPORTED_ANDROID_API`) instead of the NPE.

Both halves are required; doing only (2) leaves every style string unreadable, doing
only (1) turns the NPE into an unbound-native error. Not landed in this wave: it is a
resource-engine change (`acos-framework-natives/res` + `acos-vm/natives/fwk_res`) that
needs its own regression tests (`theme_resolution.rs` fixture with a style-bag string),
and ~15 min of wave time remained after the input triage. **Owner: `res` (next wave).**
