# W179-A — the framework "2× window offset" is a `RenderNode` transform bug (fixed)

**Date:** 2026-11-11. **Worktree:** `.cache/wt-w179a` @ `af4ab94` (clean committed
HEAD; the main tree has since moved to `8e8d49d`, the patch still applies).
**Binary:** `.cache/target-w179a/debug/acos` (and `release/acos` for dexprogs),
`CARGO_TARGET_DIR=.cache/target-w179a`, `CARGO_PROFILE_DEV_DEBUG=0`,
`CARGO_BUILD_JOBS=2`, `tools/guarded.sh`, host RAM < 90 %. **No commit, no
`git stash`.**

W173-A concluded the framework `LinearLayout.layoutVertical`/`View.transform*`
bytecode was stock and left the fix to "the VM/framework measure↔layout
boundary". That owner was wrong: the layout (`mLeft`/`mTop`) is **correct**, and
the framework bytecode is stock — the 2× is introduced by **our `RenderNode`
native returning a transform matrix that contains the node's layout position**,
which `View.transformFromViewToWindowSpace` then adds a second time. Fixed at the
root, with a unit + end-to-end regression test. `dialogs-menus` `Cancel` now
taps through on the W171-A reproduction.

## 2. Root cause (direct probe, not inference)

I temporarily taught the tree walker to print `getLeft`/`getTop`,
`getLocationInWindow` and `getLocationOnScreen` side by side (probe removed from
the final diff). On the pre-fix binary:

```
class                         getLeft/getTop   getLocationInWindow   getLocationOnScreen
DecorView                        0 / 0              (0, 0)               (0, 128)
ActionBarOverlayLayout           0 / 0              (0, 0)               (0, 128)
content FrameLayout              0 / 147            (0, 294)  <-- 2×147  (0, 422)
LinearLayout                     0 / 0              (0, 294)             (0, 422)
count TextView                  42 / 42             (84, 378) <-- 2×189  (84, 506)
inc Button                      42 / 106            (84, 506) <-- 2×253  (84, 634)
reset Button                    42 / 232            (84, 758) <-- 2×379  (84, 886)
"Counter" TextView              42 / 28             (84, 56)  <-- 2×28   (84, 184)
ActionMenuView                1080 / 0              (2160, 0) <-- 2×1080 (2160, 128)
```

`getLeft`/`getTop` are **single and exactly the ART geometry**. Only the
window/screen transform doubles.

Cause: `acos-render::render_node::RenderNode::local_matrix()` folded the layout
position into the transform, and `gfx_node::{n_get_transform,n_get_inverse}`
returned it to Java as `RenderNode.getMatrix()`:

```rust
// pre-fix RenderNode::local_matrix()
m.set_translate(self.left as f32 + self.translation_x,
                self.top  as f32 + self.translation_y);
```

`View.transformFromViewToWindowSpace` (stock API-34 bytecode) already applies the
position itself:

```java
if (!hasIdentityMatrix()) getMatrix().mapPoints(position); // adds (left,top)
position[0] += mLeft;
position[1] += mTop;                                       // adds it again
```

`hasIdentityMatrix()` was also false for **every** positioned view because it
was derived from the same position-bearing matrix, so the double-add always ran.
Hence the clean 2× on `mLeft`/`mTop` with single sizes.

Ruled out along the way:
* **IR/quickened superinstructions (W136-A/W145-A):** `ACOS_EXEC=interp`
  produced byte-identical doubled bounds.
* **Tree exporter double-accumulation:** the walker calls the framework's
  `getLocationOnScreen` once per node (the `parent_x+left` path is only a
  fallback) and the framework's own numbers are doubled.
* **`LinearLayout.layoutVertical` / `View.layout`/`setFrame`:** `getLeft`/
  `getTop` prove the layout pass is single and correct.

## 3. Fix

`crates/acos-render/src/render_node.rs`

* new `transform_matrix()` — translation / rotation / scale about the pivot,
  **without** `left`/`top`; this is what Java's `RenderNode.getMatrix()` must
  return, and what `has_identity_matrix()` must test.
* `local_matrix()` keeps `left`/`top` composed with the transform — the renderer
  uses it to place a child node inside its parent's canvas, so **rendering is
  unchanged**.
* shared `compose_matrix(base_x, base_y)` helper preserves the exact existing
  composition order.

`crates/acos-vm/src/natives/gfx_node.rs`

* `nGetTransformMatrix` (`n_get_transform`), `nGetInverseTransformMatrix`
  (`n_get_inverse`) and `nHasIdentityMatrix` (`n_identity`) now use
  `transform_matrix()`.

## 5. `dialogs-menus` `Cancel` tap (W171-A reproduction)

Fresh session, daemon at a private `ACOS_SESSION_SOCKET`,
`fixtures/build/apps/dialogs-menus.apk`:

| step | before W179-A | after W179-A |
|---|---|---|
| tap `Alert dialog` | dialog shown (`state_changed:true`, `windows:2`) | same |
| `Cancel` bounds | `[1172,628,1403,754]` — off-screen (`right > 1080`), `ELEMENT_NOT_FOUND` | `[586,397,817,523]` — on-screen |
| tap `Cancel` | never delivered | `accepted:true`, `state_changed:true`, **dialog dismissed (`windows 2→1`)** |
| tap `OK` (second open) | n/a | `accepted:true`, `state_changed:true`, `status = "Dialog confirmed"` |

**Residual (separate bug, not the transform):** after dismissing and re-opening
the `AlertDialog`, the re-opened window is compact —
`DecorView [0,128,776,618]`, `AlertDialogLayout [42,170,734,576]`,
`Cancel [240,439,471,565]` — and **neither** `OK` nor `Cancel` receives a tap
(`state_changed:false`, `windows` stays `2`). `acos-wm::compute_frame_for`
returns the full `app_bounds` for a `WRAP_CONTENT`/`WRAP_CONTENT` window, so the
WM's input-routing frame and the framework's compact window do not agree on the
origin/size. First open is fully fixed; the re-open frame is a WMS follow-up.

## 8. Hand-off

1. The 2× is `RenderNode.getMatrix()`/`hasIdentityMatrix()` including the layout
   position; Java `View.transformFromViewToWindowSpace` adds `mLeft`/`mTop`
   anyway. Fixed; `getLocationInWindow` now equals the ART geometry at the top of
   every screen.
2. Remaining vertical deltas in the app matrix are **text metrics** (`count`
   64 px vs ART 51 px), not layout — the next text wave should chase that.
3. `compute_frame_for` returning `app_bounds` for a `WRAP_CONTENT` window makes a
   re-opened `AlertDialog` compact in the framework tree but full-screen in the
   input dispatcher; its buttons then never receive a tap. Separate WMS bug.
