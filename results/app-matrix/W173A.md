## 1. Dialog / ActionMenuView / ButtonBarLayout: root cause is a uniform 2× on
window-relative **layout offsets** (mLeft/mTop), not on sizes and not (only) on
`getLocationOnScreen`

### 1.1 It is the real layout, not the tree walker

`view_tree::walk` derives `bounds = [sx, sy, sx+getWidth(), sy+getHeight()]` from
the framework's own `View.getLocationOnScreen`. The counter probe is decisive:
`tap --text Increment` (which taps the **reported** centre) increments the app's
counter (`increment value=1`), so the view that the *input hit-test* sees is at
the reported (doubled) position. Input hit-testing uses `mLeft/mTop` directly
(`ViewGroup.transformPointToViewLocal`), so `mLeft/mTop` themselves are doubled.
The walker is correct; the layout is doubled.

### 1.2 Evidence (counter, same 1080×2400 @420dpi device)

```
DecorView            [0,128,1080,2337]
  ActionBarOverlayLayout [0,128,1080,2337]
    FrameLayout content  [0,422,1080,2484]     # action-bar bottom is 275; ART puts content at 275
      LinearLayout       [0,422,1080,2484]
        TextView count   [84,506,105,551]      # padding 16dp=42px expected -> 84 (=2x)
        Button  Increment[84,596,353,722]      # advance 45 -> 90 (=2x); height 126 (single, = ART)
        Button  Reset    [84,848,315,974]      # advance 126 -> 252 (=2x)
    Toolbar               [0,128,1080,275]
      TextView           [84,212,273,275]      # centered mTop 42 -> 84 (=2x)
      ActionMenuView     [2160,128,2160,275]   # right edge 1080 -> 2160 (=2x)
```

The dialog shows the same signature on every container:

```
AlertDialogLayout [0,128,1080,515]           # height = 113+126+148 = 387 (single sum)
  topPanel        [0,128,1080,241]           # mTop 0
  contentPanel    [0,354,1080,480]           # mTop 226 = 2*113
  buttonPanel     [0,606,1080,754]           # mTop 478 = 2*(113+126)
    ButtonBarLayout [0,606,1080,754]
      Space spacer  [64,880,618,880]
      Button Cancel [1172,628,1403,754]      # x = 2*586; right 1403
      Button OK     [1634,628,1865,754]      # x = 2*817
```

Rules that hold across every probe: the window origin (`DecorView` at
`[0,128]`) is **not** doubled; every `mLeft`/`mTop` offset below the window is
doubled; `getWidth()`/`getHeight()` (and therefore the drawn size) are single.
`AlertDialogLayout`'s own height is the **single** sum of its children, i.e. the
measure pass accumulates once while the layout pass advances the cursor twice.

### 1.3 What was ruled out

* The framework bytecode is stock: `dexdump` of
  `.cache/boot/android-34/dex/framework/classes4.dex` shows
  `android.widget.LinearLayout.getNextLocationOffset` is `const/4 v0, 0; return v0`,
  and `layoutVertical` advances the cursor once
  (`add-int v20, v20, v0` with `v0 = childHeight + bottomMargin + getNextLocationOffset`).
* `View.transformFromViewToWindowSpace` / `getLocationInWindow` / `getLocationOnScreen`
  (classes4.dex) add each ancestor's `mLeft/mTop` exactly once and subtract scroll;
  there is no double-add in the transform.
* The window frame is correct: `acos-wm::compute_frame_for` returns
  `app_bounds = [0,128,1080,2337]` for the WRAP_CONTENT dialog, and the dialog
  `DecorView` is exactly that. `DisplayInfo`/`densityDpi` are the reference
  (`logical_width 1080`, `420`), `Configuration.densityDpi = 420`,
  `fontScale = 1.0`, and the button size `126 px = 48 dp × 2.625` is single, so
  this is **not** a dp→px double conversion and **not** a `widthPixels = 2×` bug.
* Tapping candidate "true" (undoubled) positions `(586,378)`, `(701,441)`,
  `(895,441)` never dismisses the dialog; tapping the reported `(1287,691)` is
  off-display. This confirms the doubling is in the layout that hit-testing uses.

**Owner for the fix:** the VM/framework measure-layout boundary (why a correct
`layoutVertical` produces doubled mTop while `measureVertical` sums once). W171A's
`MeasureSpec` hypothesis is not supported by the evidence: sizes are single,
positions are uniformly doubled. This needs a `View.measure`/`View.layout`
execution trace, which is a wave of its own.

## 2. DatePicker `TypedArray.getString` NPE — implemented

### 2.1 What was changed

W171A §5 diagnosed: a `TYPE_STRING` taken from a **style/theme bag** was written
with `assetCookie:-1`, so `TypedArray.loadStringValueAt` read it through the
**XML** `StringBlock` (`mXml`), which is `null` for
`obtainStyledAttributes(styleRes, attrs)`, returned `null`, and `.toString()`
NPE'd. The engine dropped the provenance of every value.

Implemented in `crates/acos-framework-natives`:

* `res/theme.rs` — new `TaggedValue = (Option<usize>, ResValue)` /
  `TaggedMap`. `None` = XML start tag (cookie `-1`); `Some(source_index)` =
  style/theme bag in `AssetManager::sources[source_index]` (cookie
  `source_index + 1`). `collect_style` now tags every entry with the source
  index returned by `AssetManager::lookup_with`; `Theme.values`, `merge`,
  `rebase`, `get_tagged`, `resolve_theme_attributes`, `apply_style`,
  `resolve_attrs` and `fill_outputs` all carry the tag. A new
  `res_table_typed_value` writes `asset_cookie = source_index + 1` and (for
  `TYPE_STRING`) `string = pooled_string(source_index, data)`; the XML path
  keeps `null_or_raw_typed_value` unchanged.
* `res/manager.rs` — `AssetManager::pooled_string(source_index, idx)` decodes
  the ARSC global string; the now-unused `bag_for` was removed.

### 2.2 The second half of the W171A sketch is not needed

W171A §5(2) proposed a new native
`ApkAssets.getStringFromPool(I)Ljava/lang/String;`. Dumping the actual API-34
classes dex (`.cache/boot/android-34/dex/framework/classes.dex`) shows
`ApkAssets.getStringFromPool:(I)Ljava/lang/CharSequence;` is **pure Java**:

```
iget-object v0, v1, ApkAssets.mStringBlock
if-eqz v0 -> return null
monitor-enter v1
invoke-virtual {v0, v2}, StringBlock.getSequence:(I)Ljava/lang/CharSequence;
```

`mStringBlock` is built by the `ApkAssets` constructor from
`nativeGetStringBlock(mNativePtr)`, and `StringBlock.getSequence` bottoms out in
`StringBlock.nativeGetString` — both already bound in
`acos-vm/src/natives/fwk_res.rs` (`apk_get_string_block`, `sb_get_string`).
`AssetManager.getPooledStringForCookie(cookie, index)` is likewise Java
(`getApkAssets()[cookie-1].getStringFromPool(index)`). Writing a new native would
have added an unbound-API surface for no reason. The fix is therefore only the
cookie provenance above.

### 2.3 Regression test

`crates/acos-framework-natives/tests/theme_resolution.rs::
style_bag_string_keeps_its_asset_cookie` applies
`android:style/TextAppearance.StatusBar.EventContent.Title` (`0x01030068`), whose
`android:fontFamily` (`0x010103ac`) is a raw `(string8) "sans-serif-light"`, and
asserts `type == TYPE_STRING` and `assetCookie == 1`. It would fail on HEAD
(HEAD writes `assetCookie == -1` for every non-reference value).

**Residual uncertainty (honest):** the DatePicker dialog itself was never
reached end-to-end — the `date` button's `onClick` does not run on either the
W171A or the W173-A binary (§1.4 #5), so the fixed path was verified at the
resource-engine level, not through an actual `DatePickerDialog` inflation.
