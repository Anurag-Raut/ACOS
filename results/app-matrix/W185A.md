## 1. Text metrics: the `top`/`bottom` gap

### 1.1 Ground truth from the exact reference emulator

I booted an `android-34;google_apis;x86_64` AVD at 1080x2400 @420 dpi (the exact
`art-api34-x86_64` tier) and ran a probe APK that logs `Paint.FontMetrics(Int)`
and measures a `wrap_content` `TextView`:

```
ACOSPROBE size=36.75 fm{top=-38.8136,asc=-34.09424,desc=8.972168,bot=9.959106,lead=0.0}
                fmi{top=-39,asc=-34,desc=9,bot=10,lead=0}
ACOSPROBE textview wrap h=49 w=20 padT=0 padB=0 compoundT=0 compoundB=0
ACOSPROBE default textsize=37.0 h=51            <- Widget.DeviceDefault.TextView
ACOSPROBE sp14    textsize=36.75 h=49
```

Two facts:

* `fmi.top`/`fmi.bottom` are **not** `ascent`/`descent`; they are the face
  bounding box scaled (`head` yMax 2163, yMin -555 at upem 2048):
  `top = floor(-yMax*scale)`, `bottom = ceil(-yMin*scale)`.
* The theme's default text size resolves with `getDimensionPixelSize`
  (round to nearest px): `14sp * 2.625 = 36.75` becomes **37 px**, and only then
  `bottom - top = 11 - (-40) = 51`, the ART `count` height.

### 1.2 Fix

`crates/acos-render/src/text/mod.rs`:

* `font_metrics_for` now mirrors `SkFontHost_FreeType.cpp::generateFontMetrics`:
  `ascent = -hhea.ascender*scale`, `descent = -hhea.descender*scale`,
  `top = -head.yMax*scale`, `bottom = -head.yMin*scale`,
  `leading = max(0, hhea.lineGap)*scale`.
* `From<FontMetrics> for FontMetricsInt` now mirrors
  `GraphicsJNI::set_metrics_int`: `top` floors, `bottom` ceils, and
  `ascent`/`descent`/`leading` round half up (`floor(x + 0.5)`); previously
  `ascent` floored and `descent`/`leading` ceiled.

## 2. WMS frame: `WindowLayout.computeFrames`

`crates/acos-runtime/src/wms_java.rs` already decoded the six `relayout` ints
(`requestedWidth, requestedHeight, viewVisibility, flags, seq, lastSyncSeqId`)
but only used `ints[4]` (the sync seq). `acos-wm::compute_frame_for` returned
`app_bounds` for any `WRAP_CONTENT`/`WRAP_CONTENT` window, so a re-opened
`AlertDialog` was full-screen to the input dispatcher and compact to the client.

Fix (`crates/acos-wm/src/wms.rs`):

* `compute_frame_for_requested(display, params, requested_width, requested_height)`
  is a direct transcription of
  `frameworks/base/core/java/android/view/WindowLayout.java::computeFrames`
  for the fullscreen, `compatScale == 1` case:
  `MATCH_PARENT` → parent extent; `WRAP_CONTENT` → the client-requested
  measured size; fixed → verbatim; then `Gravity.apply` inside the parent frame
  and `Gravity.applyDisplay` to keep the window on-screen. `app_bounds` is the
  parent/display frame (it is the display content area already inset by the
  system bars).
* `WindowManager::relayout_with_requested` stores and uses the requested size;
  `relayout` delegates with `UNSPECIFIED_LENGTH` (the framework's first-layout
  path), so all existing callers are unchanged.
* `WmsState::relayout_with_requested` recomputes the frame **and** feeds the
  same frame to `InputDispatcher::update_frame`, so hit-testing and the client
  layout agree. `wms_java.rs` passes `ints[0]`/`ints[1]` for both `relayout`
  and `relayoutAsync`.
