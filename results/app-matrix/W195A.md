## 1. Code changes

### 1.1 `VelocityTracker` natives (`crates/acos-vm/src/natives/fwk_input.rs`)

The seven natives API 34 declares (`nativeInitialize`, `nativeDispose`,
`nativeClear`, `nativeAddMovement`, `nativeComputeCurrentVelocity`,
`nativeGetVelocity`, `nativeIsAxisSupported`) over a per-pointer sample ring
(bounded at 20 samples, 100 ms horizon, reset on `ACTION_DOWN`). The estimator is
a recency-weighted least-squares fit of position over time, evaluated in
pixels/second; `computeCurrentVelocity(units, maxVelocity)` applies AOSP's
unit scaling (1000 = px/ms, 0 = px/s) and magnitude clamp. That is the contract
`AbsListView.trackMotionScroll`/`FlingRunnable` consume — it is not claimed to be
bit-identical to AOSP's `LSQ2`/`impulse` strategies, and the doc comment says so.

### 1.2 Popup-window input receiver (`crates/acos-runtime/src/wms_java.rs`, `fwk_surface.rs`)

* `IWindowSession.getWindowId(IWindow) → IWindowId`: returns a stable synthetic
  binder per window. The framework only ever calls the local `asBinder()` on it;
  without a reply, `ViewRootImpl.setView` dies on the strong-binder read and the
  popup never registers an `InputEventReceiver`, so a correctly routed tap has
  nowhere to go.
* `SurfaceControl.nativeAddTransactionCommittedListener(J, listener)`: recorded
  on the `TransactionRecord`; `nativeApplyTransaction` invokes
  `onTransactionCommitted()` once (then clears), which is the software-compositor
  equivalent of SurfaceFlinger committing synchronously.

### 1.3 Tap delivery is one batch again (`crates/acos-runtime/src/session.rs`)

`do_split_tap` → a single `inject_tap` (DOWN+UP in one `InputEventReceiver`
drain). The split existed only because the DOWN used to throw inside
`VelocityTracker`; with that native implemented, the intermediate pump is
harmful (it relayouts the popup that was just shown). `inject_tap_down`/`up`
remain in `acos-services::input` — they are exercised by their own unit tests and
are still the right primitive for a long-press or drag.

### 1.4 AIDL nullable `CharSequence` (`crates/acos-aidl/src/decode.rs`, `generated/tables.rs`)

`try_nullable_cond` folds the idiom whose branch precedes the marker write:

```text
if-eqz vA, else
  const/4 vB, #1 ; invoke-parcel writeInt(vB) ; <value write> ; goto end
else:
  invoke-parcel writeInt(vB)   // vB == 0, hoisted above the branch
end:
```

→ `WireOp::Cond { marker: I32, ops: [value] }`, and `TextUtils.writeToParcel`
is classified as `Cond { marker: I32, ops: [Str8] }` (its wire form is
`int32 flag` + `string8` for a non-`Spanned` value). Regenerated
`tables.rs` (`cargo run -p acos-aidl --example gen`) — the fix corrects **7**
methods that were previously mis-decoded as `I32, I32`
(`IApplicationThread.bindApplication`, `IKeyguardDismissCallback.dismiss`,
`IKeyguardService` code 59, `IUiModeManager` code 126,
`INotificationManager.enqueueTextToast`, `IPackageManager.setHarmfulAppWarning`,
`IInputMethodSession` code 7). Coverage stays 106/107 (99.1 %) fully decoded;
the only remaining unknown is the `bindApplication` map, unchanged.

### 1.5 Toast surfacing (`acos-services`, `acos-runtime`)

* `declared::NotificationService` records a `ToastRecord { package, text,
  duration_ms, shown_at }` from the real `enqueueTextToast` request and answers
  with no exception (what a real NMS does — the toast is the system's to show).
  `enqueueNotificationWithTag`/`cancelNotificationWithTag`/channel creation stay
  `UNSUPPORTED_ANDROID_API` (no status bar).
* `ServiceHost` keeps that state so the runtime — which plays the system-UI role
  in a single-process ACOS — can read it (`set_notification_state` /
  `notification_state`).
* `Runtime::pump` → `emit_platform_events()` writes one `AcosToast` log record
  per new request: `{"event":"toast","text":"Hello from ACOS",
  "package":…,"duration_ms":2000}`.
* `view_tree::append_toasts` appends the visible toast as a
  `android.widget.Toast` node (real text, standard `GRAVITY_BOTTOM` frame:
  48 dp tall, 64 dp above the nav bar) so `observe --tree` and `tap --text` see
  what the user sees. It expires after the requested duration
  (`LENGTH_SHORT` 2 s / `LENGTH_LONG` 3.5 s), so it is not a permanent fake node.
  `acosvm::natives::os_log::push_record` was added so host code can write into
  the same stream `acos logs`/`acos events` read.

### 1.6 Tests

* `app_matrix_interaction.rs`: all 5 `#[ignore]`s removed; the popup/spinner
  tests now warm and retry the open exactly like the passing guard tests (a
  bounded retry, still asserting the real tree/log change). The toast test also
  asserts the structured `AcosToast` event, not just the node.
* `services_t38.rs`: `enqueueTextToast` is no longer expected to be unsupported —
  it asserts the recorded text/duration (and keeps asserting that posting a
  status-bar notification is still `UNSUPPORTED_ANDROID_API`).
* `aidl.rs`: `layout_spot_checks` pins the `enqueueTextToast` argument layout
  (the doubly-conditional `Str8`), so the decode cannot regress silently.
* `fwk_input.rs`: unit tests for pixels/second scaling, stationary/single-sample
  zero, and unit scaling + `maxVelocity` clamping.

## 5. Hand-off

1. **Nothing is left ignored in `app_matrix_interaction`.** If a future wave
   adds a scenario, keep the "assert a live tree/log change" discipline.
2. **VelocityTracker is an estimator, not AOSP's strategies.** It is
   dimensionally correct (px/s) and monotone, which is what the widgets branch
   on; if a fixture ever depends on exact fling distance, the gap will show up
   in fling *distance*, not in click/scroll delivery.
3. **`TextUtils.writeToParcel` models the non-`Spanned` case only.** A
   `Spanned` toast text (`Toast.setText(Html.fromHtml(...))`) decodes with the
   inner marker false, and `char_sequence_arg` reports the text as absent rather
   than guessing. Implementing span marshalling (`ParcelableSpan[]`) is the
   follow-up if an app needs it; the parse currently stops at the same point
   AOSP's `Parcel.readCharSequence` would need the span bundle.
4. **Toast rendering is the system-UI role, played in-process.** ACOS has one
   process, so the runtime renders the recorded `enqueueTextToast` request as a
   `TYPE_TOAST`-shaped overlay (standard gravity/duration) and emits
   `{"event":"toast",…}`. No text or geometry is synthesised; if ACOS ever grows
   a system process, this moves there unchanged.
