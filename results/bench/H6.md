# H6 — Stage 1 baseline and the reproducible regression bench (pre-H2)

**Status:** measured, accepted. One command now measures every tracked ACOS
metric on the current build and compares it with a stored baseline.
**Build:** branch `bench-h6-baseline`, commit `32a0708fcca3` (main after the GL1
merge), release, `acos` sha256 `5d42c4f09ab14f37ab7b2eda89e241a1bf9a00f26c881d42e8658c329463d9fb`.
This is **pre-H2**: H2's early-GC default landed on main after this build, so the
memory and loop numbers here are the pre-H2 baseline. `ACOS_STRICT_SETTLE` is
the tree default (event, P11). Nothing under `crates/` was changed.
**Artifacts:** `results/bench/BASELINE.json`,
`results/bench/baseline-20261112T200322Z.{json,md}`,
raw per-phase samples in `results/bench/run-20261112T200322Z/`,
tool `tools/bench/acos-bench.sh` + `tools/bench/acos_bench.py`.

## 1. What was built

```
tools/bench/acos-bench.sh            # orchestrator: build, groups, lock, merge, compare
tools/bench/acos_bench.py            # phase measurements + merge + thresholds + compare
```

Every ART phase is its own lock acquisition, so the host-wide lock is never held
across the whole bench:

```
tools/art-runtime/run-exclusive.sh --task H6 -- \
  tools/guarded.sh --mem 8G --time <N> -- \
  python3 tools/bench/acos_bench.py --bundle <phases> ...
```

Full bench = 3 groups per repetition, each < 10 min under the lock:
`latency,cold` (8G/420s), `loop1,loop5,p11,scenarios` (8G/540s),
`memory` (16G/600s). It reuses `benchlib.py` (stats, cgroup/PSS, host gate),
`d2_warm.py` (`Serve`, `WarmSampler`, screenshot, survivors), `agent_loop.py`
(`Daemon`), P5's loop harness, P7's fadvise M3 cohort and P11's false-pass
harness. Engine code is untouched.

Exact commands:

```bash
# build (once)
ACOS_FONT_DIR=/home/Qui/Projects/acos/.cache/boot/android-34/fonts \
CARGO_TARGET_DIR=/home/Qui/Projects/acos/.cache/h6/target CARGO_BUILD_JOBS=6 \
  tools/guarded.sh --mem 10G --time 1800 -- \
  cargo build --release --offline -p acos-cli -p acos-art

# full baseline, 3 repetitions, accepted as results/bench/BASELINE.json
ACOS_FONT_DIR=/home/Qui/Projects/acos/.cache/boot/android-34/fonts \
  tools/bench/acos-bench.sh --reps 3 --accept --no-build \
  --target-dir /home/Qui/Projects/acos/.cache/h6/target

# compare a stored run with the accepted baseline (exits non-zero on regression)
tools/bench/acos-bench.sh --from-run results/bench/baseline-20261112T200322Z.json \
  --compare results/bench/BASELINE.json

# CI subset (measured 3m03s under the lock, queue excluded)
tools/bench/acos-bench.sh --quick --no-build --target-dir /home/Qui/Projects/acos/.cache/h6/target
```

`--compare` gates on **p50** (p95 is printed but not gated) against a per-metric
threshold stored in the baseline: `max(category floor, 2 × worst rep-to-rep
deviation)`, capped at 40 %, plus an absolute floor (2 ms latency, 0.5 MiB
memory, 0.2 CPU points). Thresholds and per-rep p50s are in every metric row.
`--quick` does not measure memory/M3/N=5 and labels itself `mode: quick`;
`loop_n1` uses the same 22 loops so its throughput stays comparable.

## 3. CPU and wakeups (new measurements)

Idle, 60 s window after the sessions' first frames, summed over the `acos serve`
tree (guests included), from `/proc/<pid>/stat` and
`voluntary_ctxt_switches` (perf is not available on this host):

| N | total CPU | per session | wakeups/s | per session |
|---:|---:|---:|---:|---:|
| 1 | 0.614 % of one core | 0.614 % | 34.0 | 34.0 |
| 5 | 2.442 % | 0.488 % | 90.5 | 18.1 |
| 10 | 4.465 % | 0.447 % | 160.9 | 16.1 |

Idle cost is **not** the limiting resource at N=10 (4.5 % of 32 cores), but
wakeups grow linearly (~16 s⁻¹ per session at N≥5, after P10 cut idle probe
walks 19.8 → 4.0/s). The 250 ms probe fallback and per-session timers are the
next CPU lever (old H4); at the current loop cost it is a Stage-2 item, not a
Stage-1 blocker. Active strict tapping burns **45.8 %** of one core for ~19 s.

## 4. Reliability note (found by the baseline)

The N=5 agent loop verified **74/75 tasks over the three repetitions** (rep 1:
24/25, reps 2–3: 25/25), **0 false passes** in all reps. The single failure was a
strict `assert` tree that did not read the post-tap `count` (`false_pass` stayed
0 — the task failed honestly). It did not reproduce. Treat it as an open
concurrency question (Backlog H16), not a settled regression; the per-task
failure record (pre/post text + step statuses) is kept from rep 2 onward.

Rep 3's `loop1/loop5/p11/scenarios` group ran with load1 5.8–8.2 (the only
`noisy` phases, 4/21); its p50s still landed within 2 % of reps 1–2, so the
derived thresholds already include one loaded repetition. All other phases had
load1 ≤ 3.1. Queue waits were 0–1802 s (the lock was saturated by other agents);
every acquisition stayed under the 10-minute budget.

## 5. The three biggest remaining bottlenecks (verified tasks/s/GiB-min)

From the measured loop (counter, strict, N=1, 1438 ms p50):

| rank | step | p50 | share of loop | cause / next lever |
|---|---|---:|---:|---|
| 1 | tap → settled (strict) | **926–940 ms** | **65 %** | the framework Button press/elevation `ValueAnimator` keeps drawing ~0.9 s after every tap; event settle follows the real draw sequence, so it waits it out. Lever: agent-controlled `animations:off` (P12, in flight) or strict only for assertions (fast for navigation). Expected loop ≈0.55 s, +2.3× tasks/GiB-min. |
| 2 | per-session memory | **98 MiB** | GiB denominator | cgroup anon+shmem is flat 97.3/98.0/97.7 at N=1/5/10. Lever: shared uncompressed boot image (B3, −13.6 MiB/session, opt-in, owner ASLR decision), then ART post-first-frame trim / zygote CoW (Z6: −25…60 % at N≥5; security F1 open). Each 14–50 % memory cut is a 1.15–2× multiplier on tasks/GiB-min. |
| 3 | reset → correct screen | **342 ms** | **23.7 %** | fresh ART boot + framework + Activity (~175 ms readiness) + stop (12 ms) + strict bind. Lever: zygote/shared boot image or a fast reset for non-asserting steps. Expected −150–200 ms (−10…14 % loop). |

The other loop steps for completeness: inspect/tree/assert 41.1 ms each (8.7 %
total, already event-settled from 151 ms), screenshot PNG 30.1 ms (2.1 %), IPC
0.4 ms. Cleaning the three trees to fast reads would buy ~6 %; the three items
above are 10–50× larger.

## 6. Limits

* Pre-H2 build: H2's early-GC default (merged after this branch) is expected to
  move memory and loop numbers; re-run the same command on merged main.
* `M6 fast` is the only row that looks worse than its old value (+7.7 %) and it
  is inside the derived 14 % threshold, with one rep at 197 ms — an A/B under the
  lock is needed before calling it a regression.
* `M7 fast` is +0.24 ms in absolute terms (0.2 → 0.44 ms); the threshold cap
  (40 %) would flag a raw compare, so the baseline records it as a tie in the
  report. It is sub-millisecond either way.
* Pss and cgroup rows are separate types by design; do not compare them.
* The quick subset omits memory/M3/N=5; a quick-vs-full compare prints those as
  `missing`, never as regressions.
