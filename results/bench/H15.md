# H15 — where M6 reset's 333–343 ms goes, and the one safe win in it

Status: **measured; the 25 % target is NOT reached, and the budget says why.**
Real ART, release build, branch `perf-h15-reset` off `main` `1ce336b`.
0 false passes in every arm (M6 24/24 per arm; loop 100 % verified in 8 cohorts).
One change is implemented **in this worktree (uncommitted, per the 60-minute
checkpoint instruction)**: a cached cgroup capability probe (≈7 ms per launch;
pooled fast reset −1.4 % p50 / −7.7 % p95, strict tie). Everything else measured
here is a *finding*, not a change.

## 1. Result in one table

M6 = one `acos_reset` on a held `acos serve` session, animations **on** (the
product default), 3 reps × 8 resets = 24 per arm, host load1 0.71–2.43,
interleaved A/B (base `1ce336b` vs `1ce336b` + the fix) in one lock window.

|---|---|---|---|---|---|
| **M6 strict, base** | **343.1** | 358.6 | 326.2 | 358.8 | 24/24 |
| **M6 strict, fixed** | **341.1** | 347.8 | 309.0 | 357.1 | 24/24 |
| **M6 fast, base** | **211.1** | 226.4 | 195.9 | 227.8 | 24/24 |
| **M6 fast, fixed** | **202.9** | 213.0 | 176.1 | 227.4 | 24/24 |

- strict **−0.6 %** (inside rep noise; the same arm measured 333–350 ms across
  the day and 342–391 ms under load1 5–8),
- fast **−3.9 % (−8.2 ms)** in this window; the separate focused fast A/B
  (§6) measured −15.9 ms, and one later 2-rep window tied — see §6 for all
  four windows. Pooled over **every** fast reset measured today (96/arm):
  **211.1 → 208.2 ms p50, p95 231.0 → 213.3**, i.e. the change helps but the
  size depends on host load and is not the 8 ms every time.

**The `acos` (engine) binary is byte-identical between the two arms**
(`fc53a8bc…`): `acos-cli` does not depend on the `acos-art` crate, and this item
changes only the *launcher* (`acos-art`, `8fe2633d…` → `e5d85445…`) and its guest
dex. The A/B variable is exactly the change.

The strict reset is not launch-bound: **142 ms of its 341 ms is the strict
frame bind**, and 117 ms of that is a framework animator run that strict mode
must wait for by design (§4). That is the whole explanation.

## 2. Phase breakdown (strict, animations on)

Instruments (all pre-existing or trace-only, inert unless set): the engine's
`DM6_RESET_TRACE` split (`stop_ms` / `relaunch_ms` / `bind_ms`,
`crates/acos-cli/src/engine/art.rs`), the launcher's `ACOS_ART_INPUT_TRACE`
(`elapsed_us pid=… HOST|GUEST …`, `crates/acos-art/src/launch.rs`) — which
carries the guest's own `ACOSLAUNCH MARK` chain with host receipt times — and
new H15 trace-only additions: the guest's `in_touch_mode` probe field and, behind
`P10_PROBE_ANIM_TRACE=1`, the *identity* of the ANIMATION-queue callbacks
(`AnimationHandler`'s callback list, §4).

| # | phase | strict on | strict off | fast on | what it is |
|---|---|---:|---:|---:|---|
| 1 | guest stop (`stop_ms`) | 13 | 12 | 13 | `{"cmd":"close"}` → child reaped → process group proven empty (`kill(0)`/`/proc`) |
| 2 | relaunch (`relaunch_ms`) | 185–188 | 160–171 | 188 | spawn → `acos-art` ready line (below) |
| 3 | strict frame bind (`bind_ms`) | **142** | 50 | 0 | the `tree` command the reset issues after the relaunch |

## 3. What the strict bind's 117 ms is *not*

`D-M6` (2026-11-12) blamed a 150 ms quiet window + a 60 ms PNG encode in the
bind. Both are gone; the bind is now the P12 event rule. H15 re-measured it and
found the remaining cost is a **fresh Activity's own framework animators** that
keep the app redrawing for ~117 ms after `onResume`:

```
HOST settle event generation 0->1       (resume+17)
GUEST anim_callbacks android.animation.AnimationHandler$1,ValueAnimator dur=450
      mListeners=[RippleAnimationSession$AnimatorListener],
      ValueAnimator dur=7000 mListeners=[RippleAnimationSession$3],
      AnimatorSet mListeners=[StateListAnimator$1], ValueAnimator dur=80
      mUpdateListeners=[RippleDrawable$$ExternalSyntheticLambda0]
...
HOST settle event generation 6->7       (resume+119)
HOST settle event ready gen=7 draw_seq=7 confirm_ms=24   (resume+139..160)
```

`RippleDrawable`/`RippleAnimationSession` sessions (80 ms enter, 450/7000 ms exit)
and the `Button` `StateListAnimator` run on every relaunch, in touch mode
(`in_touch_mode true` in the guest sample), with no input. Each frame increments
the guest's `draw_seq`, and the strict rule requires *the same draw* to stay
newest for the 24 ms confirmation window — so strict waits for the animator run
to finish. With `animations: off` (P12/H14) the scale is 0, the animators do not
run, and the same bind is **50 ms** (close to the 41 ms an *idle* session pays).

**Do those frames change anything the agent can see?  No.** Four PNG captures
taken inside the window (first at reset+0 ms, then every ~45 ms) are
**byte-identical** to the capture taken 1 s later:

```
shot 0: sha=629611dfe28b7ce0 bytes=9545882 capture_ms=24.6
shot 1: sha=629611dfe28b7ce0 bytes=9545882 capture_ms=24.9
shot 2: sha=629611dfe28b7ce0 bytes=9545882 capture_ms=25.7
shot 3: sha=629611dfe28b7ce0 bytes=9545882 capture_ms=24.4
late : sha=629611dfe28b7ce0 bytes=9545882 capture_ms=24.5
```

So the strict rule as written waits for **redraw quiescence**, not for picture
stability: an idle-but-animating surface redraws the same pixels 7 times and
strict waits all of them out. This is the single largest removable block in M6,
and it is *not* removable without changing the documented strict rule
(`draw_seq` stability) — see §8.

## 4. Inside the stop (13 ms)

13 ms is `close` → guest exits (≈5 ms: logd flush + looper stop) → reap (a
blocking waiter thread, not a 50 ms poll — D-M6's quantisation is gone) → the
group-empty proof (`kill(-pgid, 0)`, `/proc` fallback). Overlapping it with the
new launcher's host-side setup is worth ≤ 10 ms (the host setup before
`guest-exec` is 0–10 ms at the stage clock's 10 ms granularity) and needs a
spawn/stop handshake, so it was **not** taken: the invariant "one ART guest at a
time" would then depend on a new synchronisation path for a 3 % prize.

## 5. The change that shipped: cache the cgroup capability probes

`RunCgroup::prepare` ran **two `systemd-run --user --scope … true` probes on
every guest start** (can a scope be created at all; does this systemd know
`MemoryOOMGroup=`). Measured on this host: 4.2–4.9 ms + 2.2–2.8 ms ≈
**6.5–7 ms per launch**, for facts that are constant for a boot.

Now cached (`crates/acos-art/src/cgroup.rs`): in-process `OnceLock`, then a
stamp file `<ACOS_ART_DATA>/cgroup-capability.json` keyed by the kernel **boot
id**, written with `publish_atomic` (temp + rename; a concurrent launcher never
reads a torn file). Stale/corrupt/other-boot → the probes run as before. A
stale *positive* cannot create an unbounded run: `confirm()` still reads back
the run's own cgroup `memory.max`, `memory.swap.max` and `pids.max` before the
guest may continue, and a scope that cannot be created fails at spawn. Unit
test `capability_stamp_is_boot_scoped_and_never_guesses` pins the
boot-id/garbage/missing-key cases.

Evidence (standalone `acos-art launch --until activity-resumed`, same data root,
stamp deleted before each cold run):

| arm | launch wall (3 runs) | `stage guest-spawned` |
|---|---|---|
| cold (probes) | 170, 166, 150 ms | 40, 30, 20 ms |
| warm (stamp) | 151, 141, 152 ms | 20, 20, 30 ms |

on this host `oom_group=false` (this systemd rejects `MemoryOOMGroup=`), which
is exactly what the per-launch probe used to find — the cached value changes no
behaviour, only the cost.

**The fast-reset A/B is mixed, and is reported as such.** Four windows, same
protocol, base and fixed arms interleaved inside each window:

| window | reps × resets | load1 | base fast p50 | fixed fast p50 | Δ |
|---|---|---|---:|---:|---:|
| `m6-on` | 3 × 8 | 2.9–5.3 | 217.8 | 209.2 | −8.6 |
| `m6-on2` | 3 × 8 | 0.71–1.34 | 211.1 | 202.9 | −8.2 |
| `fast-ab` | 4 × 8 | 1.09–2.11 | 210.2 | 194.3 | **−15.9** |
| `m6-final` (final binaries) | 2 × 8 | 1.96–4.29 | 211.0 | 210.6 | −0.4 (tie) |
| **pooled, all fast resets** | 12 × 8 = 96/arm | — | **211.1** | **208.2** | −2.9 (−1.4 %), p95 231.0 → 213.3 |

The mechanism is not in doubt (two `systemd-run` invocations of 4.2–4.9 ms and
2.2–2.8 ms are removed from every launch, and the standalone launcher drops
166 → 151 ms median), but the *measured* reset-level effect swings from 0 to
16 ms with host load and rep noise, so the honest claim is **“≈7 ms per launch,
−1.4 % on a pooled fast reset”**, not −3.9 % flat.

## 8. Why 25 % is not reachable, and what it would cost

Budget of the 341 ms strict reset, and what each block can yield:

| block | ms | can it drop? |
|---|---:|---|
| stop | 13 | ≤ 10 ms only with a spawn/stop handshake (new synchronisation on the "one guest at a time" invariant) — rejected on risk/benefit |
| cold ART boot + framework init to `onResume` | 186 | **no** without a warm process: 77 ms is `fork/exec` + bwrap + cgroup + ART runtime init + boot-image map, 46 ms is `BIND_APPLICATION`, 18 ms the first traversal. Zygote/warm pool is **declined by the owner**; the H13 shared boot image changes it by ≤ 10 ms (measured 203→190 ms `fixed`, and it costs +3.6 s on the first launch of a serve) |
| framework animator run after `onResume` | 117 | only by changing the strict rule (§4) — see below |
| strict 24 ms confirmation | 24 | it *is* the strict rule; not a target |

So the removable part of a **default** (animations on prompt) strict reset is
~7 ms (taken) + ~10 ms (rejected handshake). The 25 % target (85 ms) lives
inside the 117 ms animator block and cannot be taken without a semantics change:

**Option A (needs an owner decision): content-stable strict confirmation.**
Replace "the same `draw_seq` stayed newest for 24 ms" with "the same *C1
content* stayed newest for 24 ms". Evidence that this is the honest reading of
strict's intent: during those 117 ms the picture is byte-identical (§3), so the
current rule is measuring redraw cadence, not visible change. It stays as strong
for real animations (a press/elevation animation changes pixels every frame, so
the window restarts — `M8 strict` tap must stay ~956 ms and `animations: off`
must stay 131 ms, both are gates). Prize: **−117 ms strict M6 (−34 %)**, loop
**−8 % (animations on) / −22 % (animations off)**. Cost: a cheap content hash
(the compositor's `capture_composite` is 10–30 ms, too slow per draw; it needs an
async fnv1a of each stored buffer on the surface-client path), and the rule
change itself.

**Option B (harness, not product): let the agent loop's reset step use
`settle: fast`** (as it already does for the tap it uses to set up the reset).
`fast` binds the relaunched guest's first traversal; the *next* loop step
(observe/assert) is strict and is what backs the verdict. Prize: −142 ms/task
(−10 % on, −28 % off). This changes what the loop measures, so it needs an owner
decision, not a silent edit.

**Option C: zygote / warm pool** — the only way to cut the 186 ms boot; declined
(owner, 2026-11-12; H3).

## 9. Open risks

- **R1** `negative/offscreen-pager-wait` returned `GUEST_EXITED`
  (`LOOPER_THREW: java.lang.RuntimeException: Adding window failed` at
  `ViewRootImpl.setView`) once with the fixed binary; it failed *closed* with a
  named code and did not reproduce in 3 further fixed runs (nor 3 base runs,
  all `TIMEOUT`). Same shape as the open R2a Gaten crash class, not attributable
  to this change (nothing here touches window add); recorded rather than hidden.
- **R2** The capability cache trusts a per-boot stamp. A host whose systemd
  loses the ability to create scopes *inside* one boot would now fail at
  `spawn`/`confirm` (fail closed, different error text) instead of before the
  spawn. No path returns "no cgroup".
- **R3** The `anim_callbacks` / `in_touch_mode` diagnostics add ~90 lines of
  guest Java (reflection, off by default behind `P10_PROBE_ANIM_TRACE`; the
  `in_touch_mode` field is one boolean in the probe JSON). They exist so the next
  agent can re-identify an animator without this investigation.
- **R4** All M6 numbers here are single-host, single-image (API 34 x86_64,
  software hwui). The 117 ms animator run is a property of *this* image + this
  substrate's `RippleDrawable` behaviour; on a device it may not run at all —
  which would make strict reset ~225 ms there. Not measurable without the phone
  (out of scope for this item).
