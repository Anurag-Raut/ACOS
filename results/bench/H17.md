# H17 — concurrent reset/relaunch reliability at N=10: two shared-input races

Status: **fixed on `fix-h17-n10-reset`** (not merged). Real ART, release build,
`art-reference`. 0 false passes everywhere.

## 1. What was broken

In the P5 verified agent loop with 10 concurrent sessions under one `acos serve`
(`tools/bench/acos-bench.sh --phases loop10`), tasks failed with
`steps.reset.error = GUEST_EXITED` and follow-on `tap`/`observe` `INTERNAL`, at
14–50/50 verified (B2, E3.2/E3.3). The idle 10-session memory phase was clean, so
the fault was in the concurrent launch/reset path, not capacity.

Two *different* mechanisms were found, both of them the same class: **a file
shared by every session of the cohort was rewritten in place (truncate + write)
while another process was reading or mapping it.**

| # | symptom in the loop | who died | code seen | actual cause |
|---|---|---|---|---|
| 1 | `reset` fails ~34–730 ms after the relaunch starts, or a launch fails | the **fresh** guest, before its first frame | `GUEST_EXITED` `exit status: 1` (or 126) | `<data>/seccomp/landlock.plan` truncated by a concurrent launch → the guard constructor reads an empty plan and exits 126 (`ERR landlock=plan-missing`) |
| 2 | `tap`/`observe_tree`/`assert` fails mid-task, then the launcher exits 1 and the next verb is `INTERNAL: acos-art reply is not JSON` | the **running** guest | `GUEST_EXITED` `status exit status: 135` (= 128+SIGBUS 7; verified that `systemd-run --scope` reports a signal death as 128+signal) | `<data>/app/<apk>` (`fs::copy`, `O_TRUNC`) truncates the APK that ART/`AssetManager` has mapped → SIGBUS on the next page fault inside the mapping |

Both files are rewritten by **every** launch:

* `crates/acos-art/src/seccomp.rs::build_guest` calls
  `landlock::write_plan(<data>/seccomp)` on every launch (even on a build-cache
  hit); the old `write_plan` used `std::fs::write` (`O_TRUNC`).
  `<data>/seccomp` is `--ro-bind` into every guest and the guard constructor reads
  `/data/seccomp/landlock.plan` at start (`crates/acos-art/src/seccomp_guest.c`).
* `launch.rs` (and `app.rs`, `session.rs`) did
  `fs::copy(&opts.apk, <data>/app/<apk_name>)` on every launch. The guest argv is
  `/data/app/<apk_name>`, and ART maps classes/resources straight out of that APK.
  `fs::copy` is `O_TRUNC` + copy, so a concurrent guest's mapping loses its pages
  → SIGBUS; a starting guest can also map a half-written APK. (Second defect in
  the same line: two sessions launching *different* APKs with the same file name
  shared one path, so one session could be served the other's APK.)

`GL1`/`teardown` are not involved: the dm6 stop records show every stop taking the
`lifecycle` path with the session's own process group, and no `sigkill.group`
event fired in the failing reps. OOM is not involved: the guarded job cgroup
reported `oom_kill 0` in every sample and host `MemAvailable` stayed ≥ 47 GiB.

## 2. Root-cause chain (evidence)

Kept under `.cache/h17/` (deleted after the write-up; the tables below are the
record).

**Mechanism 1 — torn Landlock plan** (before-fix build, `loop-diag-on`, load1
8.45/9.35/8.07, 3 × 50 tasks):

* 3 of the 70 launch run trees kept with `ACOS_ART_KEEP_RUN=1` have
  `out/seccomp.log` = exactly `ERR landlock=plan-missing` (every other run has
  `OK landlock=active abi=10 rules=15 skipped=0` / `OK guard=active insns=83`).
  The guard fails closed with exit 126; those guests never reach a first frame.
* p5 records them as `reset` → `GUEST_EXITED` after 186–730 ms (the relaunch
  attempt) or `observe_tree` → `GUEST_EXITED` 70–81 ms (the guest died on start).
* The failure lands on whichever launch overlaps another launch's plan rewrite;
  with 10 sessions resynchronised by the task barrier their resets arrive
  together, which is why whole reps collapse (33/50) and others are clean (50/50).

**Mechanism 2 — truncated mapped APK** (`before-on-quiet`, load1 2.60; and
`before-off`, load1 1.10):

* `agent 1 idx 100002 reset … GUEST_EXITED … status exit status: 135`
  (before-on-quiet, 249.8 ms) and
  `agent 1 idx 100004 assert … GUEST_EXITED … the guest ended while binding the
  tree (status exit status: 135)` (before-off, 81.3 ms), plus the same 135 on a
  mid-tap in `before-on-quiet` (`tap 775 ms`). 135 = 128+7: the guest process
  tree died of SIGBUS, i.e. a fault inside a file mapping whose backing file was
  truncated.
* The launcher then finishes its non-ok outcome and exits 1 (`liveness.dead`,
  exit_code 1, no signal); the engine's next verb reads the closed stdout and
  reports `INTERNAL: acos-art reply is not JSON …` (the `INTERNAL` follow-on B2
  saw), then the session is dead for the remaining verbs.
* The only host file rewritten in place per launch that a *running* guest maps is
  the APK. `stat` of the fixture is 12.7 KiB, so the torn window is short — but
  the copy is issued by every one of the 10 resets in a burst, while all the
  other guests are actively probing trees and drawing, so a fault lands
  eventually; it hit 3 guests inside one second in `loop-diag-on` r3.

**Second symptom — the 0.009 ms fast-reset error** (`arm-off-r1`, load1 10.4,
M6 fast 20/20 bad): this is **not** a distinct bug. On a session id that has no
live guest, `acos_reset` answers from the session table without touching ART:

```
acos_reset wall_ms=0.116 status=error code=SESSION_NOT_FOUND
  message: no live ART session `never-launched`; acos_reset needs a launched session
  hint:    Call acos_launch with this base.session_id first …
```

(reproduced with a serve on a fresh socket; `tap`/`observe` answer the same in
0.017–0.035 ms). The M6 loop calls `launch(...)` **ignoring its return value**, so
when that one launch failed (a transient launch failure, the class fixed here) the
next 20 taps/resets were all fast `SESSION_NOT_FOUND` refusals. The refusal is
correct and specific; the reporting bug is the harness dropping the launch error.
After the fix the same latency phase under load shows M6 fast 20/20 measured
(§5.5).

## 3. The fix

Lowest responsible layer: the **publication of shared inputs**, not the reset
scheduler.

1. `acos_art::publish_atomic(path, bytes)` (`crates/acos-art/src/lib.rs`): write a
   sibling temp file and `rename(2)` it into place; no-op when the bytes already
   match. A reader keeps the old inode (complete) or gets the new one (complete);
   an `mmap` is never invalidated by a truncate. Used by:
   * `landlock::write_plan` — `<data>/seccomp/landlock.plan` (mechanism 1),
   * `Props::write` — `<data>/acos.properties` (read by every guest's property
     shim; same torn-read class),
   * `ArtRoot::write_apex_info_list` — `<data>/apex-info-list.xml` (same class).
2. The APK is **owned per run** (`crates/acos-art/src/app.rs::stage_apk`):
   `launch`, `render-app` and `session` stage their own copy inside their private
   run root and `--ro-bind` it over `/data/app/<name>`. The shared
   `<data>/app/<name>` is now only a mount point, written **once**
   (`ensure_apk_mountpoint`) — bwrap cannot create a file inside a read-only bind
   — and never rewritten. This removes the truncation (mechanism 2) and the
   cross-session same-name APK race at the same time; the guest argv/`sourceDir`
   path is unchanged (`/data/app/<name>`).
3. Diagnostics (kept): `session-exit.json` now carries `guard` (the seccomp/
   Landlock line, `ERR` line on failure) and `notes` (cgroup + isolation notes),
   so an exit-126/1 guest states *why* instead of only its exit code. This is how
   the bwrap mount-point error and the `ERR landlock=plan-missing` line became
   readable in the records.

`cargo build --release` on the branch; no behaviour change to replies other than
the extra evidence fields.

## 4. Regression tests (deterministic)

`crates/acos-art/src/lib.rs` (unit tests; both fail on the pre-fix code, pass
after — verified by temporarily restoring `fs::write`):

* `publish_atomic_never_truncates_a_live_reader` — a reader that already has the
  file open must still see the old, complete bytes after a publish; identical
  bytes do not change the inode; no temp files are left. Pre-fix: the held fd
  sees 0 bytes (the `plan-missing` class).
* `publish_atomic_is_atomic_for_a_concurrent_reader` — two reader threads
  re-open/read a 64 KiB file while 300 publishes alternate two payloads; every
  read must be exactly one of the two. Pre-fix: `torn read: 0 bytes` on the first
  iterations.
* `stage_apk_leaves_the_previous_copy_intact` — re-staging an APK leaves a
  previously opened copy complete (the `SIGBUS` class).

## 7. Limits and follow-ups

* The before/after comparison at *high* load is load-confounded: the before-on
  high-load rep (load1 8.45) is not matched by an after rep, because raising host
  load deliberately would perturb the other agents on the box. The quiet-load
  comparison is load-matched (1.1–2.6 both sides) and the mechanism is proven by
  the exit codes/guard logs, not only by the rate.
* `INSTALL.md`/`docs/ERROR_CODES.md` already promise that an exit-126 with a guard
  `ERR` re-classifies to `SECCOMP_UNAVAILABLE`; the launch path only does that
  when the guest otherwise reached its stage. With the race fixed the exit-126
  path should not fire; the record now carries `guard`/`notes` so any future one
  names its cause. A dedicated re-classification is a follow-up, not needed for
  this packet.
* The harness bug (M6 ignores `launch()`'s result, so a failed launch shows up as
  20 × fast `SESSION_NOT_FOUND`) is worth fixing in `acos_bench.py` so a launch
  failure is never attributed to reset. Not changed here (tool owner is B2/H6).
* Both defects were also present in `render-app` and the old `session` route
  (same two lines); they are fixed there too.
