### 3.1 Every delta, explained

**1. Memory: −32.1…−32.8 MiB per session (−32.8…−33.5 %), the only real change. H2.**
M1 idle cgroup anon+shmem 98.93 → **66.52 MiB**; M2 97.35/98.03/97.66 →
**64.96/65.22/65.59 MiB** at N=1/5/10; ΣPss per session at N=5/N=10 107.7/94.2 → **76.8/62.6 MiB**
(−28.7 %/−33.5 %). The absolute saving matches H2's own A/B (ΣPss −28.8…−30.6 MiB/session at N=5/N=10,
−28.9…−30.4 at N=1) and Z7's mechanism: one `VMRuntime.requestConcurrentGC()` right after the first
live frame returns the guest's own region space. The cgroup anon+shmem number moving by the same
absolute amount (not just Pss) is the stronger statement: this is freed anonymous memory, not shared-file
accounting. `M2 Pss N=1` (−8.4 %) stays inside its 14 % band by construction: at N=1 one session carries
the whole boot-image/framework file share, so a per-session heap saving is a small fraction of it.

**2. Nothing else moved by more than noise — including everything P12 changed.** M7 strict
41.10 → 41.14 ms, M8 counter strict 955.7 → 956.1 ms, M8 form strict 947.8 → 944.7 ms, tap ack 5.0 →
5.0 ms, teardown 12.0 → 12.0 ms, loop N=1 −1.0 %, loop N=5 +0.6 %, tasks/GiB-min +1.1 %/+0.5 %,
verified rate 1.000 at both N (pre-H2 was 74/75 at N=5). P12's contribution is **semantics and
evidence, not milliseconds**: strict settle is now event-only with no quiet escape hatch (the bench
records `bound:"strict-event"` on every strict row), the pixel guard is off by default while
`pixels_changed` is stated on every strict input/tree row, and `acos verify` fails a timed-out settle
step (the `p11-progress-timeout` scenario is an honest `timeout` verdict, and P11 reports 5 honest
timeouts per rep, 0 false passes). P11's event settle was already the pre-H2 default, which is why
M7/M8 strict did not move again.

**3. The two "worse" latency rows are the host, not the build.** `M4 strict +8.75 %`,
`M4 fast +16.4 %`, `M8 counter fast +26.8 %` all come from repetition 2, whose `latency` phase ran at
load1 6.0→11.1 (V1, K3, W7 and P12/K2 runs of other agents queued and ran through it). Per-rep p50s:
M4 fast 203.2 / **408.3** / 174.9 ms and M8 counter fast 66.6 / 52.1 / **44.3** ms. The clean
repetition ties pre-H2 exactly (M4 fast 174.9 vs 174.6; M8 fast 44.3 vs 44.3; M4 strict 323.7 vs
309.0). Because of that spread the derived threshold for both rows capped at 40 %, so the pooled delta
is reported as `within noise` rather than a regression — and the honest reading is "unresolved under
load, no evidence of a change". The same applies to idle CPU (N=5 +13 %, N=10 +18 %, rep spread
4.9–6.3 % at N=10, wakeups unchanged to ±0.5 %) and to `M3 +1.3 %`, `M5 +2.4 %`.

**4. H2 did *not* move tasks/GiB-min in this bench (283.5 vs 280.5, +1.1 %), and that is not a
contradiction of H2.** The bench's denominator is the integral of cgroup `memory.current` over the
cohort, which includes the per-task **boot transient** (page cache from reading the image/dex plus the
fresh guest's startup peak, measured peak 251–680 MiB depending on the phase mix) — not the steady-state
region space H2 returns. H2's own +37 %/+54 % were measured with a whole-tree **ΣPss** integral over
1-minute cohorts (E2.10). Both numbers are right; they answer different questions. Practical
consequence for the Backlog: at the current loop shape, memory per session is no longer the GiB
denominator — **the boot transient is** (see §5.4 and the re-ranked Backlog).

**4b. The GiB denominator decides whether H2's win is visible at all.** The bench's headline
`tasks/GiB-min` divides by the integral of cgroup `memory.current` (page cache included); the label-matched
variant divides by cgroup **anon+shmem** only. H2 moved the two differently:

| loop | tasks/GiB-min (cgroup, page cache included) | tasks/GiB-min (anon+shmem) |
|---|---:|---:|
| N=1, pre-H2 → current | 280.5 → 283.5 (+1.1 %) | 621.2 → **905.3 (+45.7 %)** |
| N=5, pre-H2 → current | 664.0 → 667.6 (+0.5 %) | 577.9 → **865.8 (+49.8 %)** |

The 32 MiB/session H2 returns is anon memory; the boot transient's page cache is untouched, so a
denominator that counts page cache cannot see the win, and one that counts anon+shmem reports it at the
same magnitude H2 claimed (+37 %/+54 % with ΣPss). **Both numbers are in the new baseline**
(`loop_n{N}_tasks_per_gib_min` and `..._net`); the anon+shmem variant is the one to quote when the
question is "does this change the agent-visible footprint".

**5. Reliability.** 63/63 verified loop tasks at N=1 and 75/75 at N=5, **0 false passes**; H6's
1-in-75 strict-assert flake (H16) did not reproduce. P11 settle-lab 0/105 false passes (3 reps × 12
cases × reps), 12/12 `p11-*.yaml` scenarios as expected (the negative control is a `timeout`).
Teardown 162/162 `verified:true`, `lifecycle`.

**6. Host load.** 9 of 21 phases are recorded `noisy` (load1 > 4 at the moment of the phase):
rep 1 `cold`/`latency`/`memory` (6.1–8.3), rep 2 `cold`/`latency`/`loop1`/`loop5` (4.2–11.1), rep 3
`loop1`/`loop5` (5.5–6.0). All other phases were ≤ 3.8. Queue waits 0–133 s (pre-H2 had 0–1802 s);
MemAvailable 45–47 GiB, never below the 90 % RAM guard. Every acquisition finished under the 10-minute
lock budget (max group wall 219.6 s).

### 5.2 Tasks per GiB-minute: the honest answer, in both denominators

The H14 arms bundle the latency phase before the loops in one guarded acquisition, so the loops inherit
that cohort's page cache in the cgroup integral — `tasks/GiB-min` (page cache included) in `arm-*.json`
is **not** comparable with the bench (49 on / 140 off in the arms vs 283.5 in the bench) and is biased
inside the arm pair too (the on arm's latency phase is 3× longer, so it inherits more). The
**anon+shmem** variant is page-cache-free and label-matched with the bench's own N=1/N=5 rows (the arm's
on N=1 median 901 vs the bench's 905.3 is the cross-check), so it is the one to read here:

So, in the label-matched denominator, animations off is not a wash: **5.8× at N=1 (901 → 5239),
~5.0× at N=5 (793 → 3942) and ~8.7× at N=10 (438 → 3798)** — medians of three interleaved reps, with
one caveat each (off `loop5` r3 is the 64 s straggler cohort of §5.3, excluded from the median's
use; the on `loop10` arm has two unreliable reps). Reason: the task
shrinks by 2.7× while its memory time-integral shrinks by more — with the animator gone the session
spends less wall time at its post-boot high-water mark, and the per-task anon+shmem integral falls
(≈37 MiB average on → ≈21 MiB off at N=1). The page-cache-inclusive denominator says "no gain" only
because it is dominated by file cache charged to the cgroup (≈95 MiB average on a clean acquisition,
≈600 MiB in a bundled one), which the animator does not touch.

The central objective therefore reads: **animations off is a 2.7× latency/throughput win and a ~5.5×
win in verified tasks per GiB-minute of agent-visible memory.** It still does not change the product
default, and it converts the loop from tap-bound to reset-bound (48 %), which is where the next lever is.
It also means the metric to watch in the Backlog is the anon+shmem integral, not `memory.current`.

### 5.3 Correctness, false passes, reliability

* **0 false passes in every arm** (P5 asserts the post-tap count and the reset's `state_reset`,
  `data_cleared`, newer frame; the counter reached 42/42 taps; the form error text is exact). `rr`
  strict rows report `settled:true` and `pixels_changed:true`.
* Verified rate per rep — on arm: 95/100/100 % (N=1), 72/96/100 % (N=5), 28/100/84 % (N=10); off arm:
  95/100/100 %, 100/100/96 %, 92/100/98 %. All failures are honest (`GUEST_EXITED` — the guest process
  died during reset/observe; no false pass, the failure record carries the steps). The **N=10 loop is
  not reliable on either arm** (on 14/50 and 42/50 in two of three reps, off 46/50 and 49/50), and the
  off `loop5` r3 rep shows the same thing at N=5 in a different shape: 24/25 with one `reset`
  `GUEST_EXITED` after 930 ms, and one 1.47 s task, which stretched that cohort's wall to 64 s (its
  GiB-min value 78 is an artefact of the stall, not a memory effect).
* Off-arm `latency` rep 1 ran at load1 10.4 and its fast-reset cohort failed 20/20 with near-zero
  replies (`reset` returns an error immediately when the fresh guest cannot start). That rep is
  reported, not deleted; it is why the off M6 fast column shows a 0.009 ms row.
* Off arm rep 4 (`arm-off-r3`) and the loop-only reruns are recorded in `.cache/b2/h14/`.

### 5.4 What H14 settles

Accepted as the agent-facing mode for functional checks, executed **without touching the default**:
`animations` stays `on` unless the caller asks for `off`, every reply states which mode ran, and
`off` is launch-time only. The measured effect is 7.34×/8.35× on strict taps, 1.37× on a warm launch,
1.25× on a strict reset and 2.71–2.84× on the agent loop, with 0 false passes. Not accepted as a tasks/GiB-min improvement: no evidence of one, and a
mechanism for why there is none (the boot transient becomes the whole task).

## 6. New findings to carry into the Backlog

1. **N=10 verified-loop failures (`GUEST_EXITED`)** in a P5 loop with 10 concurrent sessions under one
   serve, on both arms (on 14/50 and 42/50 verified in two of three reps; off 46/50 and 49/50),
   0 false passes. The same failure appears once at N=5 (off r3). The idle 10-session metric suite
   (memory phase) is clean, so this is a concurrency/lifetime question in the reset path, not a capacity
   wall.
   Evidence: `arm-on-r1` (36/50 failed), and the failure records in each `.cache/b2/h14/run-arm-*/…/loop10.json`
   (`steps.reset.error = GUEST_EXITED`, `tap`/`observe` follow-on `INTERNAL`).
2. **Reset fails fast under host load** (`arm-off-r1`, load1 10.4: 20/20 fast resets returned an error
   in 0.009 ms). H9 (input queue stall under load) and this share the "load makes a launch/relaunch
   path fail" shape; worth one A/B on a quiet host before calling either a product bug.
3. **The GiB-min denominator is transient-bound.** H2 bought 32 MiB/session of steady state and moved
   the loop's tasks/GiB-min by +1.1 %. Anything that only shrinks idle memory will not move the
   central objective; the boot/relaunch working set will (H15/zygote, B3's shared image).

## 7. Limits and notes

* The orchestrator's merge step was re-run standalone (`acos_bench.py --merge … --accept-baseline`)
  on the same raw run dir: the shell script was edited while it was executing, so the running copy
  stopped before its own merge. All 21 phase documents were already written; the merged document,
  thresholds and accepted baseline come from the same code path the script calls.
* 9/21 phases are marked noisy (host load from four concurrent agents). Only repetition 2's `latency`
  phase is materially distorted; per-rep p50s are in the table so the reader can see it.
* `teardown_ms` pools latency and memory phases, so its "rep p50" list has 6 entries (2 phases × 3 reps)
  while latency rows have 3. Pre-existing behaviour of the tool.
* Pss and cgroup anon+shmem rows are label-matched and never mixed; `M2 Pss N=1` is high by
  construction (the single session carries the whole file share).
* H14's off-arm P11 corpus was not re-run with `animations:off` (P11's harness has no switch); the
  scenarios were (`--animations off`).
* N=10 loop numbers are only from the H14 arms (the bench does not include `loop10` in its default
  groups). The arms' page-cache-inclusive GiB-min is invalid as noted; the anon+shmem variant is not.
* A dedicated loop-only A/B (loops as the first phase of their own acquisition, page-cache-inclusive
  GiB-min comparable) was queued behind four other agents and stopped to release the lock: the
  anon+shmem variant already answers the question without it. Its slot: `--groups
  "loops:loop1,loop5,loop10:16G:400"`, one line in `.cache/b2/logs/h14-loops2.sh`.
* Nothing here changes a product default: `animations` stays on, early GC stays on, settle stays
  event-only strict.
