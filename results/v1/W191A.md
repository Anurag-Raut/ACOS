## 1. Interaction pump (hello-views tap after type)

Reproduced on the product path: `tap` after `type` logged
`greet name=World clicks=1` and then ran the VM to the 120 s wall-clock limit.
The handler worked; the *traversal* did not stop. Root cause: the pump chased
the framework's repeating timers — the `EditText` cursor blink (500 ms) and the
vsync-driven `Choreographer.doFrame`; in the interpreter each vsync frame is a
full ~1 s traversal (W180-A measured **118 frames / 113 s**).

Two rejected attempts, kept in the log for the next session:

1. a virtual-time *advance* budget — still timed out (the advance itself reaches
   the next vsync);
2. `run_scheduler_due` alone — the vsync eventfd is *immediately readable*, so
   frames still ran.

The fix is a **frame budget**, not a skip: the input dispatch still happens, the
click handler still runs, and `render_frame_now()` still draws the result. Only
the animation frames beyond the third are dropped, which leaves the eventfd
quiet so `nativePollOnce` parks and the scheduler returns. Tap: 113 s → 5.2 s.

## 2. hello-jni symbol resolution

`verify --native` reported `UNSUPPORTED_NATIVE_SYMBOL stringFromJNI` while
`readelf --dyn-syms` and `acos native-inventory` both listed
`Java_dev_acos_fixtures_hellojni_MainActivity_stringFromJNI`. Instrumenting
`resolve_native` showed `libs=[]`: **no library was loaded at all**, so the
symbol search had nothing to search. `load_library_impl` was reached for
`stats_jni`, `javacrypto`, `framework-connectivity-jni`,
`framework-connectivity-tiramisu-jni` — and never for `hellojni`.

`classes.dex` does contain `const-string "hellojni"` + `System.loadLibrary` in
`MainActivity.<clinit>`. The `<clinit>` was never executed: the framework
instantiates the launch `Activity` through reflection, and `Class.newInstance()`
/ `Constructor.newInstance0()` allocated the instance and called `<init>`
**without** `initialize_class` (JLS 12.4.1 requires it). With that fixed the
load runs, `libhellojni.so` maps, `JNI_OnLoad` registers `registeredEcho`, and
every JNI result matches: `stringFromJNI=Hello from native C`, `add(20,22)=42`,
`sumArray([1,2,3,4,5])=15`, `javaCallbackResult=42`,
`voidCallback=from-native`, `registeredEcho=echo!`,
`throwFromJNI caught=thrown from native`.

Reaching the assertions needed two more framework edges, both real blockers
behind the symbol error: `nativeAddTransactionCommittedListener` (ViewRootImpl
blocks the resume on it) and `nPurgePendingResources` (called by the relaunch
path). Both are recorded in the diff table.

## 4. 1.7 recreate / save-restore

`RelaunchActivityItem` does not exist in the extracted API-34 boot image (it is
`ActivityRelaunchItem`), so the item was not available. The path implemented is
the framework's own sequence, invoked directly:

```
ActivityThread.prepareRelaunchActivity(token, …, MergedConfiguration, …)
ActivityThread.handleRelaunchActivity(record, PendingTransactionActions)
  -> handleRelaunchActivityInner: performPauseActivity -> callActivityOnStop(saveState=true)
     -> handleDestroyActivity -> handleLaunchActivity
ActivityThread.handleStartActivity(record, actions, null)
ActivityThread.handleResumeActivity(record, false, false, false, "relaunch")
```

Three details that took measurement rather than guesswork:

* the token must be the **live** record's (`mActivities.keyAt(0)` picks a stale
  one — the launch leaves three records in this build — so the live record is
  selected by a non-null `activity` field);
* `handleRelaunchActivity` returns a *temporary* record; `handleStartActivity`
  and `handleResumeActivity` need the live one re-read via `getActivityClient`;
* `handleResumeActivity` alone resumes an activity that never started, so
  `handleStartActivity` must run between (without it the log shows
  `onCreate → onResume`).

Observed log (real framework output, `AcosFixture`):

```
onPause
onStop
onSaveInstanceState clicks=2
onDestroy
onCreate
onStart
onResume
```

and the recreated tree reads `clicks: 2` in both directions. Back finishes the
activity with `onPause → onStop → onSaveInstanceState clicks=2 → onDestroy`.

## Known limits of the interaction pump

The pump now runs only already-due work plus at most 3 vsync frames, and
`input_after_pump` falls back to the pre-W191-A bounded virtual-time pump when
nothing changed. Two consequences worth knowing:

* a *consecutive double tap* on the same widget can report
  `state_changed = false` on the second tap (the tap rule requires tree **and**
  screenshot to change); both `v1-recreate` and `v1-reset` put a `capture`
  between clicks for that reason, which is evidence, not a weakened assertion;
* an animation longer than the budget (`smoothScrollToPosition`) may not
  complete, which is the `list_scroll_button…` regression above.
