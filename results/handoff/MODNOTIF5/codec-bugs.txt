(the fixture's notify() crashed) and fixed at the cause.

(a) android.media.AudioAttributes — 8 bytes over-read
-----------------------------------------------------
Old spec (MODNOTIF3, from a linear reading of the DEX):

  Int usage/contentType/source/flags/? + StringArray + Str16 + Int + Bundle

Wire of a real Notification.Builder notification (offset 212 in the capture):

  000000d0: ffff ffff 0100 0000 0500 0000 0400 0000   marker, usage=5, contentType=4
  000000e0: ffff ffff 0008 0000 0000 0000 0000 0000   source=-1, flags=0x800,
                                                      parcelFlags=0 (FLATTEN_TAGS clear),
                                                      String[] tags (count 0)
  000000f0: 47f8 ffff ffff ffff ...                    -1977 = ATTR_PARCEL_IS_NULL_BUNDLE
                                                      (no bundle body follows)

  i.e. 4 (marker) + 5*4 + 4 (tags) + 4 (null-bundle sentinel) = 32 bytes.

  The old list read an extra Str16 + Int + Bundle = 12 bytes instead of 4 -> +8.

  Field trace of the broken read (positions relative to the argument):
    field 16 Cond(AudioAttributes) at 212 (now 252) -> 40 bytes consumed (should be 32)
    field 17 LongArray             at 252 (now 256) -> LongArray(Some([]))  (wire: -1/null)
    field 18..21 Int               at 256..272      -> 0,0,0,0
    field 22 Cond(PendingIntent)   at 272           -> Err(NotABinder { offset: 276, ty: 4294967295 })

  AOSP writer: base/media/java/android/media/AudioAttributes.java:1349-1368
  Fix: curated read_audio_attributes/write_audio_attributes (branches on FLATTEN_TAGS;
  bundle only after ATTR_PARCEL_IS_VALID_BUNDLE = 1980).

After the fix the same capture decodes all 45 Notification fields and consumes the
notification exactly; the trailing 4 bytes of the capture are the `userId` argument.

(b) Parcel.writeValue length prefix counts the stripped stability records
-------------------------------------------------------------------------
With AudioAttributes fixed, the last field failed:

  field 44 ArraySet at 1516 (now 1608) -> Err(BadReply { detail:
    "VAL_4 body consumed 80 bytes but declared 84" })

Capture at the ArraySet (count 2, first element):

  000005ec: 0200 0000 0400 0000 5400 0000 1900 0000   count=2, VAL_PARCELABLE(4),
                                                      declared=84, name len=25 (incl NUL)
  000005fc: 6100 6e00 ... 7400 0000                     "android.app.PendingIntent"
  00000630: 852a 6273 1300 0000 1f00 0000 0000 0000     flat_binder_object (BINDER, id=31)
  00000640: 1f00 0000 0200 0000                         ... + 4-byte stability, then the
                                                        next element's VAL_PARCELABLE tag

The framework's 84 counts the 4-byte stability record; peer::import_parcel strips it, so
the imported body is 80. Fix: the import records every rewritten object offset
(Parcel::register_object) and check_value_length accepts exactly 4 bytes per object
inside the body (read_value_length's bound allows the same, so a forged length is still
refused — asserted in a_value_length_prefix_counts_the_stripped_stability_records).
