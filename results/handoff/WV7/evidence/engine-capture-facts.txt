WV7 measured facts: how this pinned engine (chrome-headless-shell 157.0.8103.78,
--enable-begin-frame-control) does and does not produce pixels.

Method: crates/acos-webview/tests/scratch_render.rs (temporary, deleted) spawned
the engine bare, emulated a 900x560 device-pixel View (343x213 CSS px,
deviceScaleFactor 2.625) and printed the PNG's IHDR size for each capture route.

A  HeadlessExperimental.beginFrame {screenshot:{format:png}}   -> 343x213  (CSS px)
C  Page.captureScreenshot {fromSurface:true, ...}              -> TIMEOUT (never answers)
D  Page.captureScreenshot {clip:{...,scale:2.625}}             -> TIMEOUT
E  Page.captureScreenshot {fromSurface:false}                  -> TIMEOUT
H/I/J Page.startScreencast + beginFrame, metadata.deviceWidth   -> 343 (CSS px),
      PNG 343x213, both with maxWidth=900x560 and maxWidth=0

Conclusion: this engine cannot emit a device-resolution frame under begin-frame
control. `beginFrame`'s screenshot is CSS-sized and ignores deviceScaleFactor;
`Page.captureScreenshot` is unavailable; the screencast also carries CSS pixels.
(An earlier probe that seemed to show 900x559 was reading the emulation of a
previous probe step: with width=900 CSS the screencast is 900 px wide.)

WV7 therefore: frames come from Page.startScreencast (real compositor surface,
one HeadlessExperimental.beginFrame per `render`, acked in the pump), and the wire
reports the frame's real pixel size. A device-resolution PNG needs an engine whose
capture path honours deviceScaleFactor; this one has none.
