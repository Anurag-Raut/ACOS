## 1. What is implemented (current state)

### 1.1 Guest uid = application uid (default on)

Files: `crates/acos-art/src/lib.rs`, `crates/acos-art/src/launch.rs`.

- Active runs (`Sandbox::active_run_root().is_some()`) execute inside
  `bwrap --unshare-user --uid 10192`; `bwrap` maps inner 10192 onto the host
  caller’s uid, so the guest sees `/proc/self/status` uid 10192 while host
  files stay accessible.
- `10192` is `acos_services::pms::FIXTURE_UID`. PMS/AMS answers are hard-coded
  to that uid (`pms.rs`), so `ACOS_ART_GUEST_UID` accepts **only** `host`
  (explicit A/B, old behaviour) or `10192`. Any other numeric or malformed
  value is `Error::InvalidGuestUid` (`INVALID_GUEST_UID`) — **there is no silent
  fallback to host uid 1000 (`SYSTEM_UID`)**.
- `launch.rs` forwards `ACOS_ART_KEYSTORE` (and nothing else K5-specific)
  explicitly with `sb.env`, because bwrap `--clearenv` makes the guest
  environment exactly the `--setenv` list.
- The `application-created.marker` now records: `guest_uid`, `pms_uid`,
  `uid_map`, `status_Uid/Gid/Groups/CapEff`, `files_dir` + writability,
  `app_data_entries` (see `uidFacts()` in `LaunchMain.java`).
- **Why this exists:** the old guest ran as host uid 1000. API-34
  `WebViewFactory.getProvider()` refuses `ROOT/SYSTEM/SHELL/NETWORK_STACK/BLUETOOTH`
  uids with `UnsupportedOperationException: For security reasons, WebView is
  not allowed in privileged processes`. That system-only branch is unreachable
  for a real app; the uid change removes the lie. It does not make WebView
  work (see §4.3).
- **Not host-level isolation.** gid/groups remain the host caller’s (measured
  984), the inner uid maps to host 1000, and there is no new host confinement.
  Each session gets a fresh `/data/app-data` bind; a previous session’s
  directory is not mounted, but no adversarial cross-session read test was run.

### 1.2 Software AndroidKeyStore provider (OPT-IN, default off)

Files: `crates/acos-art/guest/java/dev/acos/art/SoftwareKeyStore.java`,
`LaunchMain.java`, `crates/acos-art/src/launch.rs`.

- `LaunchMain.main` installs provider `"AndroidKeyStore"` before app code
  (the position the zygote uses on a real device) **only when
  `ACOS_ART_KEYSTORE` is `on`/`1`/`software`**. Default/unset/`off` leaves the
  honest failure `KeyStoreException: AndroidKeyStore not found`.
- Session-private storage: `<dataDir>/acos-keystore/entries.properties` under
  `/data/app-data/<pkg>` (per-run bind). Keys never cross sessions because the
  directory does not.
- Supports `KeyStoreSpi`, AES/HmacSHA256/HmacSHA1 `KeyGenerator`, RSA/EC
  `KeyPairGenerator`, alias persistence.
- Refuses `setUserAuthenticationRequired(true)` and `setStrongBoxBacked(true)`
  with `InvalidAlgorithmParameterException`; it does **not** claim
  hardware/TEE/attestation support.
- **Not done (K5b):** `KeyInfo` security level (currently plain exportable
  keys), purposes/modes/padding/validity validation, import
  `ProtectionParameter`, generated RSA/EC certificate chains, persistence
  error propagation, 0600 permissions/retention policy, reset/restart/crash/
  SIGKILL/concurrent-session/identical-alias tests.
- Earlier targeted real-ART smokes with the shim **on** (pre-merge tree):
  `io.element.android.x` first frame 1534 ms + tree + screenshot;
  `com.dot.gallery` first frame 2504 ms + tree + screenshot. With the default

### 1.4 Real APK signing certificates

Files: `crates/acos-apk/src/signing.rs`, `crates/acos-apk/src/apk.rs`,
`crates/acos-services/src/pms.rs`, `.../parcelable.rs`.

- **Bounded parsing (security-relevant):** v1 signature blocks are read with
  `MAX_SIGNATURE_BLOCK_BYTES = 1 MiB`, `MAX_SIGNATURE_BLOCK_RATIO = 200`
  (declared uncompressed / compressed), and a `take(MAX+1)` read. The zip
  size field is untrusted, so the declared size is checked *and* the actual
  stream is capped. Violations are `APK_SIGNING_MALFORMED`; a `.RSA/.DSA/.EC`
  entry is only a v1 block if its matching `META-INF/<stem>.SF` exists.
- Certificate caps: `MAX_CERT_BYTES = 128 KiB`, `MAX_TOTAL_CERT_BYTES = 1 MiB`.
- **Signer semantics:** `Signature[]` is **one leaf certificate per signer**,
  not the first signer’s whole chain. v2/v3/v3.1 iterate **all** signers and
  take the first cert of each signer’s `certificates` sequence (leaf first);
  chain members are deliberately skipped.
- **No silent scheme downgrade:** highest present scheme (`v3.1 → v3 → v2`)
  is authoritative; a present-but-malformed higher scheme returns an error and
  never falls back to v2/v1. v1 is used only when the block has none of those
  schemes. v1 identifies the signer by `SignerInfo` issuer+serial
  (`certificate_issuer_serial`); a subjectKeyIdentifier `sid` is refused
  (`None`) rather than returning the wrong cert. Most corpus APKs are
  single-signer F-Droid/JAR blocks using issuer+serial.
- `Apk::signing_certificates_error: Option<String>` records why an array is
  empty; PMS sees an empty array rather than a wrong one.
- `pms.rs` writes `PackageInfo.signatures`; `parcelable.rs` has the
  `android.content.pm.Signature` spec (`writeByteArray`), matching the image’s
  `Signature.writeToParcel`.
- Tests: `acos-apk` lib **14/14**, including: chain-vs-leaf per signer,
  v3-over-v2, malformed-v3 no-downgrade, oversized block, v1 sid selection,
  and apk.rs cap tests (declared size, ratio, reader that lies about size).

## 4. Open defects / named walls

### 4.1 RedReader `PackageInfo.signatures` — ART `DECODE_ERROR` (K5c)

- Symptom: `java.security.cert.CertificateException …
  OPENSSL_internal:DECODE_ERROR` in
  `org.quantumbadger.redreader.common.AndroidCommon.getPackageInfo` (line 57,
  stack points at `CertificateFactory.generateCertificate`) during
  `Application.onCreate`.
- Host reply evidence: `.cache/k5/pmsreply.bin` (2408 bytes) contains the exact
  832-byte F-Droid DER at offset 1500; `.cache/k5/pmscalls.log` shows both
  `getPackageInfo` calls (flags `0x10000000` and `0x40`) with the same cert;
  `openssl x509 -inform der` parses it; the Java `PackageInfo.CREATOR` test
  parses it.
- Therefore the Rust framing is **not** the explanation. Remaining hypotheses,
  untested:
  1. the guest decodes a **different** `PackageInfo` than the captured reply
     (cached/earlier call, another class loader, a reply template path);
  2. the peer byte pipe truncates/corrupts a >2 KiB marshalled reply
     (2408 bytes is larger than the small replies exercised elsewhere);
  3. an ART-vs-VM difference in `Parcel`/`Signature` (less likely; same
     framework dex).
- Next action: instrument the guest’s **received** reply bytes for
  `getPackageInfo` and compare the exact byte range with `pmsreply.bin`;
  add a >2 KiB PMS reply transport test. Do not “fix” by suppressing the
  exception.

## 5. Things tried that did NOT work (and why)

1. **Assuming the cert DER was malformed.** `openssl x509 -inform der` and the
   real `PackageInfo.CREATOR` both parse it; the bytes in the reply are
   byte-identical. The bug is not our DER.
2. **Assuming the `Signature` typed-array framing was wrong.** Verified in the
   boot dex that `Parcel.createTypedArray` also reads a presence word via
   `readTypedObject`; the host writes `count=1, presence=1, len=832, DER`.
   Replaying through the real CREATOR passes. Chasing presence/framing was a
   dead end.
3. **Host reply dump hooks** (`ACOS_DBG_PMS_REPLY`, `ACOS_DBG_PMS_CALLS`). They
   confirmed the reply is correct and were removed. They did not explain the
   ART error.
4. **Guest-side signature probe** (`ACOS_DBG_SIG`, writing
   `/data/out/sigprobe.txt`). First it did not run because bwrap `--clearenv`
   dropped the env (fixed by forwarding in `launch.rs`); after forwarding it
   still produced no file/output, cause never found. Removed before the
   checkpoint. This is a loose end: the guest-side decode was never directly
   observed.
5. **Keystore `off` seam initially didn’t work** because `ACOS_ART_KEYSTORE`
   was not forwarded through `--clearenv`; fixed, then the default was changed
   to opt-in per the advisor.
6. **`guest_uid` silently parsed invalid values to `None`** (host uid

7. **Keystore default-on.** It got element/dot.gallery frames but the advisor

8. **Wrong corpus APK filenames** for uid/joplin runs (`editor_3_1.3.apk`,

   `org.billthefarmer.editor_196_1.96.apk` and

## 7. Why this needs security + fidelity review (not just gates)

K5 changes **identity, security-state answers, key storage, and code-signing
data**, and it does so for every app. Gates exercise fixtures; they cannot show
that the platform never lies to an app or leaks across sessions. Before merge:

1. **Keystore honesty.** Default must stay off until K5b. If enabled: prove
   `KeyInfo` reports a software security level (no hardware/TEE/attestation
   claim), generated keys are not silently exportable where the API promises
   non-exportability, `setUserAuthenticationRequired(true)` /
   `setIsStrongBoxBacked(true)` fail (they do), and import `ProtectionParameter`
   is honoured or rejected. Test reset/restart/crash/SIGKILL/concurrent
   sessions/identical aliases across packages. Check file mode 0600 and crash-run
   retention (kept trees otherwise retain key material).
2. **Session isolation.** Keys must never be readable by another session. The
   per-run `/data/app-data` bind is the mechanism; test it adversarially
   (plant a key/file in session A’s host dir, attempt to open it from session
   B). Do not claim host isolation: gid/groups are host-shared and the inner
   uid maps to host 1000.
3. **Signature semantics.** Confirm against AOSP
   `ApkSignatureSchemeV2/V3Verifier` and `PackageParser`: `Signature[]` count
   and order for multi-signer APKs, v3 rotation/lineage, v1 `SignerInfo` SKI
   ids, and the “no downgrade” rule. The implementation is non-verifying
   detection, not cryptographic verification — say so. The decompression caps
   (1 MiB, 200×, capped stream) and 128 KiB/cert cap are the zip-bomb defence;
   fuzz the block parser with malformed lengths/signers and assert no panic/
   huge allocation.
4. **Trust/restrictions.** Reads must match a real no-credential, no-MDM device
   (they do by construction), and every mutation/listener must fail explicitly
   rather than pretend success. Re-check the boot-image transaction numbers and
   reply shapes after any framework bump; `requestPermission` is void in API 34
   and must not grow a payload.
5. **uid.** `bwrap --unshare-user --uid 10192` maps the inner uid to the host
   caller; verify no setuid helper/path in the guest turns that into host
   privilege, that `/proc/self/uid_map` cannot be rewritten, and that PMS/AMS
   only ever answer 10192. The override validation must stay fail-closed.
6. **RedReader honesty.** If the ART `DECODE_ERROR` remains, do not suppress it
   or fabricate a certificate; it is an open compat wall (K5c), not a pass.
