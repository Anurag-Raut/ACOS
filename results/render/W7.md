## 1. Where the carve was

The pre-W7 app window was carved in two places that had to agree:

| layer | file:line | what it did |
|---|---|---|
| guest display facts | `crates/acos-art/guest/java/dev/acos/art/LaunchMain.java:2821` | `APP_H = PANEL_H - STATUS_INSET - NAV_INSET`; this becomes `DisplayInfo.appHeight`, so the framework believes the app owns only the application area |
| WMS frame | `crates/acos-wm/src/wms.rs:742` (`compute_frame_for_requested`, `let window_bounds = display.app_bounds;`) | every app window frame was the application area |
| display model | `crates/acos-wm/src/display.rs:183` (`custom`, `app_bounds = Rect(0,status,width,height-nav)`) | built that application area from the geometry config |
| WMS state | `crates/acos-services/src/wms.rs` (`WmsState::new`) | constructed the `DisplaySpec` from `ACOS_DISPLAY_OVERRIDE` |

Because the frame already excluded the bars, `InsetsState.calculateInsets(mWinFrame, …)` (AOSP
`InsetsState.java:256/270`, `InsetsSource.calculateInsets`) had no status/nav source **inside** the
frame and returned zero. That is why changing `--nav-inset` alone could not move Gaten's footer.

## 2. Change

* `ACOS_WM_INSETS=carve|report` (`acos-wm::display::InsetsMode`), plus
  `acos launch --insets` and `acos-art launch --insets`. At W7 `carve` was the default and
  `report` opt-in; **W7b (ADR-0026 decision 6) flipped the default to `report`** and added a
  per-scenario `insets:` field so each scenario pins its model.
* `report` uses AOSP `WindowLayout.computeFrames` semantics: the frame starts at the full display
  and is reduced only by the client's `fitInsetsTypes`/`fitInsetsSides`. `PhoneWindow.generateLayout`
  sends both as 0 for a non-floating window, so an Activity gets the full display; a floating dialog
  keeps the default `systemBars()` fit and stays in the application area. DecorView then consumes the
  reported insets for a non-edge-to-edge app; an edge-to-edge app applies them itself.
* The guest derives `DisplayInfo.appWidth/appHeight` from the same selector, and
  `reference_merged_configuration` reports the full-display dp size under `report`.
* `acos-verify` publishes `display_origin: [0,0]` and a display-sized `app_size` under `report`.
* New fixture `fixtures/apps/insets-probe` (edge-to-edge, targetSdk 35) prints
  `getRootWindowInsets()` status/nav/systemBars/systemGestures, the decor frame, the screen frame and
  WindowMetrics as text. Scenarios: `scenarios/w7-insets-report.yaml` (must pass under `report`) and
  `scenarios/w7-insets-carve-negative.yaml` (must fail under `carve`).

### 4.1 The one report-arm gate failure: `w42-back-frame`

The strict hash for the final first-Activity frame differs by **one anti-aliased row**: display
`y=283`, 122 pixels, green channel 210 vs 211. The second region and every other frame in the
scenario are byte-identical; the difference is deterministic across three report runs. It is a
1/255 Skia edge-blend change from drawing the same hierarchy in a 1080x2400 window rather than the
1080x2209 carved window, not a semantic layout change. A strict RGBA8 hash cannot accept it, and
loosening the hash would weaken a gate, so `report` stays opt-in and the default stays `carve`.

## 6. W7b addendum (ADR-0026 decision 6)

`report` is now the build default. `carve` remains selectable through
`ACOS_WM_INSETS=carve`, `acos launch/verify --insets carve` and a scenario's
top-level `insets: carve`. The two W7 regression scenarios pin their model, so
neither can pass or fail because of an ambient default (the carve negative
would otherwise become a false pass once the default flipped). `w42-back-frame`
was re-blessed: only its final first-Activity region-1 hash changed, and a
pixel diff against the carve arm shows the change is exactly the one known
anti-aliased display row (display y=411, 122 pixels); every other pixel in the
overlapping display area is identical. The proof is in
`results/handoff/W7B.md`.
