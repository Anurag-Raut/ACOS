# R3 — Native-crash evidence on the product path, and the Gaten post-first-frame SIGSEGV

Debugger task. Worktree `/home/Qui/.paseo/worktrees/3oxa6xao/r3`, branch `fix-r3-gaten-segv`,
off `main` `b551dfa`. Same read-only Gaten APK as GR1/GR2
(`/home/Qui/Projects/acos/.cache/gaten/gaten-dev-f344272-x86_64-release-unsigned.apk`,
sha256 `e04c7ffc…`); Gaten source and APK untouched. Every ART run through
`tools/art-runtime/run-exclusive.sh --task R3` + `tools/guarded.sh`, scratch in `.cache/r3/`
(loop artefacts in `.cache/r3/loop/`, crash fixtures in `.cache/r3/crashtest/`).

**One-line verdict: the failure was undiagnosable by construction — the guest had no crash
handler at all, `session-exit.json` carried only the signal number, and teardown deleted the run
directory. A guest killed by a signal now reports the fault address, `si_code`, the faulting
thread and the runtime's own symbolised native backtrace, and keeps its run tree. The Gaten
`1/10` SIGSEGV did **not** recur in 40 post-change launches (20 with early GC on, 20 with
`ACOS_ART_EARLY_GC=0`), so its root cause is not named here — the next occurrence will be.**

## 0. Where this run started, and what the evidence actually was

`results/render/R2.md` §2 recorded one Gaten launch in ten lost to
`GUEST_KILLED_BY_SIGNAL` (`guest_signal: 11`), between the first frame and the next observation,
no OOM. `results/gaten/GR2.md` saw the same shape as a white screen. R2's own words: *"the failing
run's per-run directory was removed by the loop's own `session destroy`, so there is no
tombstone/`stderr_tail` for launch 7; the signal is known … the stack is not."*

Re-reading R2's retained artefacts (`.cache/r2/loop/run7/04-logs.json`) confirms it: the exit
record was `{"code":"GUEST_KILLED_BY_SIGNAL","guest_signal":11,"guest_crash":null}` with
`logd_tail`/`stderr_tail` fields present but empty of anything from a crash, because nothing in
the process ever looked at the fault.

### 0.1 Why nothing looked at the fault (three separate reasons, all in ACOS)

| # | mechanism Android uses to report a native crash | state on the ACOS ART guest before this task |
|---|---|---|
| 1 | bionic's debuggerd handler (`debuggerd_init` from the linker, `system/core/debuggerd/handler/`) | **absent**: this image's `ld-android.so` is built with `liblinker_debuggerd_stub` (`bionic/linker/Android.bp`), not `libdebuggerd_handler_fallback`; `libc.so` installs none. Verified: no `Fatal signal`/`tombstone`/`debuggerd` strings in `ld-android.so`. |
| 2 | ART's own unexpected-signal dumper — `*** *** ***` / `Fatal signal … fault addr …` / `Thread: <tid> "<name>"` / registers / `Backtrace` with mapped libraries (`art::HandleUnexpectedSignalCommon`) | **suppressed by ACOS**: `Runtime::InitPlatformSignalHandlers` (`art/runtime/runtime_android.cc`) only installs it when `getenv("ANDROID_ROOT")` is **not** exactly `/system`. ACOS set `ANDROID_ROOT=/system` (`crates/acos-art/src/lib.rs`, `Sandbox::new`). |
| 3 | the launcher keeping the run tree for a debugger | **deleted**: `RunDir::drop` removes the tree on every path (S4's "scratch is scratch"), and the session-exit record kept only `guest_signal`. |

So a `SIGSEGV` ART declined (not a managed NPE, not a stack overflow) went
`FaultManager` → libsigchain → `SIG_DFL` → the kernel killed the process and the only trace left
was `signal 11` in the exit record. Nothing was mis-reported; there was simply no reporter.

## 1. What was added (product path, on by default)

### 1.1 ART's own crash dump, turned back on (one deliberate value)

`crates/acos-art/src/lib.rs` now exports `ANDROID_ROOT=/system/` to the guest
(`android_root_for_guest()`), with the trailing slash as the whole point: every framework
concatenation still resolves (`/system//framework/…`, `/system/fonts`, `$ANDROID_ROOT/` prefix
checks), and the runtime's own dumper is installed because the value is not the literal
`/system`. `ACOSART_CRASH_DUMP=0` restores `/system` exactly (A/B seam). The eight gates below
were re-run under `/system/` to prove the framework sees no difference.

The dump is produced by the runtime that owns the maps and the unwinder, not by a handler we
wrote; the output is the same block a device gets:

```
*** *** *** *** *** *** *** *** *** *** *** *** *** *** *** ***
Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR) fault addr 0x0
OS: Linux 7.2.11-arch1-1 (x86_64)
Cmdline: <unset>
Thread: 15 "acos-launch-wat"
Registers:
    rax: 0x00000000acc0dead  …  rip: 0x00007f47 …
Backtrace:
    #00 pc 00007f47  /data/lib/libacos_binder_driver.so (Java_dev_acos_art_Nat_crashTest+39)
```

### 1.2 A minimal chained handler for the machine-readable facts

`crates/acos-binder-peer/native/binder_driver.c` gained
`Java_dev_acos_art_Nat_installCrashHandler`, called once from `LaunchMain.main` **after**
`initAndroidRuntime` so the runtime's handlers are already in front of it. It appends to ART's own
chain with `AddSpecialSignalHandlerFn` (libsigchain, the same API `FaultManager::Init` uses), for
`SIGSEGV/SIGBUS/SIGILL/SIGFPE/SIGABRT`, and the handler:

* is async-signal-safe: `write(2)`, `getpid`, `gettid`, `prctl(PR_GET_NAME)`, one 320-byte stack
  buffer, no allocation, no locks; an alternate signal stack is installed once at startup;
* prints `ACOSCRASH {"signal":11,"code":1,"fault_addr":"0x0","pid":…,"tid":…,"thread":"…"}` — the
  fields that must never depend on the unwinder succeeding;
* returns `0` ("not handled") so the chain continues to ART's dumper and then to the previous
  handler: **the process still dies of its own signal**, so `GUEST_KILLED_BY_SIGNAL` and the
  existing failure taxonomy are unchanged;
* refuses to call ART's dumper itself: the runtime's dumper begins
  `MutexLock mu(Thread::Current(), …)` and takes a *second* fault on a thread the runtime does not
  know (measured — the first attempt produced a tombstone of `art::Mutex::ExclusiveLock` instead of
  the guest's fault). Chaining instead of calling is what makes the reported fault the real one.

### 1.3 The evidence the launcher keeps

* `crates/acos-art/src/crash.rs` (new, with 4 unit tests) parses both sources into one structured
  record and never fabricates a field: `ACOSCRASH` JSON for the primary facts, ART's dump for
  `signal_name`, `code_name`, `fault_addr`, `thread{tid,name}`, the register block and the frames.
  Frame lines are parsed tolerantly (`#NN pc <hex>  <map> (<sym>+<off>)`, `offset 0x…`, or a bare
  pc for an unmapped address).
* `session-exit.json` gains `native_crash` (the record above) and `native_crash_path`; the raw dump
  is written verbatim to `<out>/native-crash.txt` and the structure to `<out>/native-crash.json`, so
  a parser gap can never destroy the evidence.
* `crates/acos-cli/src/failure.rs` passes `native_crash`/`native_crash_path` through
  `details.session_exit`, so the agent sees the fault address, thread and frame in the failing reply
  itself.
* **A signal death keeps its run tree** (`run.keep()` in `launch.rs` and `session.rs`); every other
  outcome still removes it, so S4's leak guarantee is unchanged for crashes-by-exit-code. The S6
  test that asserted "signal death cleans up" was updated to the new contract (tree kept, no process
  still names it).
* `ACOSLAUNCH_CRASH_TEST={segv,abort,main,thread}` is a diagnostic seam (forwarded by `launch.rs`,
  read only by the launch guest) that faults the guest after `activity-resumed` — the deterministic
  fixture the crash-evidence test uses.

## 2. Root cause: what is proven, and what is not

**Proven (the diagnosability defect).** A guest killed by a signal had three independent reasons to
leave nothing (§0.1) and did. After this change the same fault produces §1.1's dump and §1.3's
record. Demonstrated with a deterministic fault on the launch guest
(`ACOSLAUNCH_CRASH_TEST=segv`, one store to an unmapped page on the watcher thread):

```
native_crash.summary = SIGSEGV (11) fault_addr=0x0 in thread 15 "acos-launch-wat":
                       /data/lib/libacos_binder_driver.so (Java_dev_acos_art_Nat_crashTest+39)
```

**Not proven (the Gaten crash itself).** The 1/10 SIGSEGV did not recur: **0 crashes in 40
post-change Gaten launches** (§3). At n=40 a true 1/10 rate would show zero crashes with
probability 0.9⁴⁰ ≈ 1.5 %, so the rate is either genuinely lower on this build (merged `main`
`b551dfa`, different host load than R2's five-agent hour) or the event is rarer than 1/10 — the
sample cannot separate those. What the change guarantees is that the next occurrence names its
library, thread and offset instead of vanishing. It is *not* a fix for the crash; nothing in this
task changed the guest's drawing, threading or native code paths.

No Gaten source or APK was touched, and nothing was patched speculatively.

## 3. Reproduction attempt: 40 launches, two arms

Loop: `launch → 2 s → tree → screenshot → 5 s → tree → logs → destroy`, evidence copied
(`session-exit.json`, `native-crash.*`, frames, markers) before/after destroy.

| arm | n | `first_frame` | tree carries `Set up Gaten` | guest signal deaths | frames |
|---|---|---|---|---|---|
| default (H2 early GC **on**, the product default) | 20 | 20/20 | **20/20** | **0** | 20/20 |
| `ACOS_ART_EARLY_GC=0` (H2 ruled out as a cause) | 20 | 20/20 | **20/20** | **0** | 20/20 |

Crash rate: **before 1/10** (R2 §2, same APK, same worker) and 2/6 white-screen launches in
`GR2.md` §4; **after 0/40** (both arms). Wall clock: 40 launches in 7 min 15 s including the 7 s
per-launch settle, i.e. ~11 s/launch. Artefacts: `.cache/r3/loop/on2/run1…20` and
`.cache/r3/loop/egcoff/run1…20` (gitignored).

Early GC is **not** implicated: the 20 `ACOS_ART_EARLY_GC=0` runs are as clean as the 20 default
ones, and no crash in either arm means H2 can be ruled out as *necessary* (it was never a
candidate for *sufficient* either — the defect is native).
