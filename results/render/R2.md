## 1. What was added (committed, diagnostic only, off by default)

`ACOSLAUNCH_GEOM_TRACE=1` (forwarded by `crates/acos-art/src/launch.rs` to the guest) makes
`LaunchMain` start a read-only watcher thread that samples **every size the app can observe** and
prints/writes one line per change to `<run>/art-frames/geometry-trace.txt`:

```text
ACOSGEO t=<ms> app_dm=1080x2292@400 app_cfg=432x917@400 smallest=432 orient=1 \
  sys_dm=1080x2292@400 sys_cfg=432x917 smallest=432 \
  win_metrics=[0,0][1080,2400] win_insets=status:108 nav:0 \
  decor=1080x2292 measured=1080x2292 at=0,108 \
  win_frame=[0,108][1080,2400] vr_wh=1080x2292 vr_layout_requested=false
```

That is the surface the task asked for: `DisplayMetrics`, `Configuration` (`screenWidthDp`,
`screenHeightDp`, `smallestScreenWidthDp`, `densityDpi`, orientation), `WindowManager` window
metrics + insets, the decor's measured/laid-out size and screen origin, and
`ViewRootImpl.mWinFrame` / `mWidth` / `mHeight` (what the last `relayout` reply actually said).
Field reads only: scalars and framework getters, no mutation, and no `Surface` monitor (the W6
deadlock documented in `probeViewRoot`).

No product behaviour changes: the trace runs only when the variable is forwarded.

## 3. What was *not* reproduced, and what that means

The `+1080 px` fragment offset did not occur in 10 launches. Two facts matter for the next attempt:

1. **A wrong first measure is not what the geometry trace shows in a good launch.** Every correct
   run samples `app_dm`/`app_cfg`/`win_metrics`/`win_frame` consistently with the launch geometry
   from the first sample (100 ms after `activity-resumed`) onward: `app_dm=1080x2292@400`,
   `app_cfg=432x917@400 smallest=432`, `win_frame=[0,108][1080,2400]`, `decor=1080x2292 at=0,108`.
   There is no second, different width and no re-layout. So if W6/a is a WMS/Configuration race it
   is **inside the first ~100 ms** (before the trace's first sample) — the trace must start at
   `application-created`, not at `activity-resumed`, to catch it. That is the first change for the
   next run and it is a 5-line move of the `startGeometryTrace` call site.
2. **The +1080 offset is the pager's page pitch.** GR1 measured the onboarding pager at
   `[270,128][1350,2337]`; GR2 measured the off-screen Analytics page at `x=1080..2160`. A layout
   that places *sibling* views one page pitch away is what a `Pager`/`Animated.View` translation
   does. Two ACOS-side inputs can produce it: (a) a `WindowManager`/`Configuration` width that is
   2× the window for one measure pass (nothing in the trace shows it, and the launch `Configuration`
   is built once from `ACOSLAUNCH_WIDTH`, so this would need the *window* frame to disagree with the
   launch configuration — the trace's `win_frame` vs `app_cfg` pair is what would show it), or
   (b) a first traversal at the *previous* run's or the *default* geometry with the framework
   re-laying out afterwards. Neither is proven; both are directly visible on the next run because
   the trace records every change with a timestamp.

Not patched in Gaten (read-only) and nothing in ACOS was changed on speculation.

## 4. A — the per-view canvas: why there is no small correct change (owner decision)

### 4.1 What the framework guarantees, and what the guest actually runs

* Hardware-accelerated Android: `View.draw(Canvas)` (`View.java:3394` in
  `.cache/aosp/frameworks/base/core/java/android/view/View.java`) sees
  `canvas.isHardwareAccelerated() == true` and takes the `updateDisplayListIfDirty()` path:
  `mRenderNode.beginRecording(width, height)` returns a `RecordingCanvas` **sized to that view**,
  the view's drawing is recorded as a display list, and `drawDisplayList` replays it. That is why
  `canvas.getWidth()` inside `View.onDraw` equals the view's width on a device — and why
  react-native-svg's `ViewBox.getTransform` (which feeds `canvas.getWidth()` into the viewBox
  scale) is correct there.
* The ART guest: `FLAG_HARDWARE_ACCELERATED` is deliberately absent
  (`LaunchMain.buildAppInfo`, P4b §4), so `ViewRootImpl` has no `ThreadedRenderer` and
  `performDraw` calls `drawSoftware()` → `mSurface.lockCanvas(dirty)` → a stock Skia software
  `Canvas` over the CPU-mapped `GraphicBuffer` for the **Surface** (window size + surface insets).
  Every view draws into that one canvas, in window coordinates and at window size. Measured on
  the guest (`results/gaten/evidence/GR1/svg-probe.json`): `view=270x116 canvas=1080x2292
  canvasIsViewPx=false scale=0.2357` (correct would be `0.0589`). The wordmark's 2.5× ink and the
  Analytics screen's window-sized SVG are the same arithmetic.
* There is no framework software path with per-view semantics. `View.draw(Canvas)` only consults
  `mRenderNode` when the canvas is a hardware canvas; a `RecordingCanvas` can be produced by
  `RenderNode.beginRecording(w, h)` on *any* canvas-less node, but replaying the resulting display
  list requires HWUI's `RenderThread`/`Skia` GPU backend, i.e. the very path that is missing.

### 4.2 Why enabling the flag is not the small change it looks like

`ACOSLAUNCH_APP_FLAGS=0x02000000` (the GR1 experiment) does not fail in *our* code — it fails
because the ART guest's `ThreadedRenderer` natives come from the **stock** `libhwui.so` in the
sysroot (`.cache/art/sysroot/system/lib64/libhwui.so`), not from ACOS. `android.graphics.HardwareRenderer.preload()`
starts a `RenderThread`, which creates a `SkiaOpenGLPipeline` (EGL + GLES) and, on this image, a
`BLASTBufferQueue` consumer per surface. ACOS has no GPU and no EGL/GLES driver for the ART guest
(`crates/acos-gles` is a software GLES implementation used by the Rust VM path, and the Rust VM's
`gfx_hwui.rs`/`gfx_node.rs` — a `RenderNode`→display-list→`acos-render` replacement — are **acos-vm
natives**, unreachable from a real ART process that resolves its natives from bionic). So (ii) is
"port the RenderNode/HardwareRenderer implementation into a `libhwui` shim the ART guest can load" —
that is the GR1 §5.2(A) item and it is not small: a JNI-compatible `HardwareRenderer`+`RenderNode`
+`DisplayList` surface, a `RenderThread` with a frame clock, and the rasteriser handoff into the C1
buffer. It also lands *below* C1 composition (allowed by the boundaries — C1 is not replaced — but it
is a new native ABI surface for every app).

### 4.3 The one bounded proposal (not implemented: over budget, needs the decision)

Smallest change that makes `canvasIsViewPx=true` **without** a GPU, keeping C1 composition:

1. Keep the guest's software window canvas as the compositor hand-off (no change to the draw path
   that C1 consumes, so T03/w54 baselines cannot move).
2. In the guest, drive the framework's **own** software display-list route per view rather than
   reimplementing it: for every `View` whose `onDraw` is reached with a window-sized canvas, call
   `View.draw` on a *nested* software `Canvas` created from a `Bitmap` sized
   `view.getWidth() × view.getHeight()`, translate by `-view.getLeft(), -view.getTop()`, and blit
   the result into the window canvas at the view's position. That preserves per-view semantics by
   construction (including `clipRect`/`getClipBounds`), needs no RenderNode, and is a
   `ViewGroup.dispatchDraw` override installed by the launch guest (framework subclass, not an app
   patch).
   * **Cost:** ~250–400 lines of guest Java + a per-view `Bitmap` allocation story (reuse pool) and
     a blit per view; measured on the fixture before anything else. Rasterising text twice per frame
     is the risk: Gaten's welcome screen has ~40 text views, so the estimate is a **1.5–3× draw
     cost on text-heavy screens** — acceptable for verification, wrong for a product claim.
   * **Risk:** correct but not framework-native (a subclass, not the framework's own dispatch); it
     changes nothing about `RenderNode`s, so a library that uses `View.setLayerType`/`RenderNode`
     directly (e.g. `Lottie`, `Reanimated`'s native drawing) still sees window pixels. It also
     silently changes every existing pixel baseline unless gated (off by default, opt-in per launch).
   * **Alternative considered and rejected as "not small":** an interposed `libhwui` (option ii)
     or a `Canvas.getWidth()` shim (dishonest — it lies to *all* callers instead of fixing the
     contract, and it does not fix clipping).
3. Acceptance stays `scenarios/svg-viewbox.yaml` green **and** T03/w54 byte-identical, which is why
   the proposal must be opt-in and measured before it becomes a default.

**Recommendation:** do not take (ii) inside a rendering task; take §4.3 only with an owner decision,
because it changes the drawing model for every app and has a real per-frame cost. Until then the
honest state is: wordmark/SVG stay window-sized on the ART guest (documented, red scenario kept),
and Gaten is verified through the tree + a capture whose element geometry is known to be off for
SVG/`canvas.getWidth()` consumers only.
