## Standing rules (all tracks)

- The existing ART engine keeps working throughout. Reuse AOSP/Google components wherever practical.
- No fake successes, stale frames, incomplete UI trees or weakened assertions. Tap acknowledgement is never treated as success.
- At most **5 concurrent agents**. Each task is limited to **one hour**, with escalation if exceeded.
- ART runs only through `tools/art-runtime/run-exclusive.sh` + `tools/guarded.sh`, which serialises measurements so the tracks cannot skew each other.
- Host RAM stays under 90%. Disk is checked at every health check and pruned at 85% or above. Scratch goes in `.cache/`, never `/tmp`.
- Untrusted APKs stay on the existing exec/sandbox path until a new sandbox passes security review.
- Escalate to the owner: architecture changes, security changes and verification-semantics changes. There is no production migration without measured evidence and owner approval.

## Track 1: Zygote-style shared ART (architecture)

**Goal:** one pre-initialised ART core that forks many independent, lightweight app sessions, using Google's real ART/Zygote mechanisms (`-Xzygote`, ZygoteHooks, preload, fork/specialise). Independent apps are never put inside one shared Java process.

**Why:** measured per-session cost is about 114 MiB (`results/art-runtime/D-M2-MEASURE.md`):

| Item | Per session | Note |
|---|---|---|
| Java heap | 39.0 MiB | private |
| Boot image | 26.3 MiB | private: the compressed image is decompressed in every session |
| Graphics buffers | 18.3 MiB | must stay private |
| Daemon PNG retention | ~10 MiB | being fixed in O2 |
| Launcher (our services + C1) | 7.3 MiB | |
| malloc | 5.8 MiB | |

Nothing initialised is shared today. Evidence and inventory: `results/art-runtime/D-M2-INVENTORY.md`. The advisor's review is summarised in the owner report on 2026-11-12.

**Plan:**
1. Standalone Zygote prototype: init once, preload, fork with Android's hooks, copy-on-write.
2. Measure real memory at N = 1, 5, 10 and 20, separating shared from private and including the Zygote process. Also measure launch speed and CPU.
3. Validate correctness and isolation: each child's heap, app data, Binder identity and UI state; GC, threads, repeated launches and teardown; sandbox isolation without losing copy-on-write.
4. Run real apps: counter, then form, dialog, then Gaten. Real rendering, input, screenshots and tree verification.
5. Three-way comparison: (a) optimised current ART, (b) shared boot image without Zygote, (c) Zygote copy-on-write.

**Gate:** production integration only if the result is at least **25% better for the whole system** than the *optimised* current implementation, with no loss of correctness, security or compatibility. The owner sees the advantages, disadvantages, risks and measured gains before any final change.

**Estimate (not yet measured):** each added session costs about 58–78 MiB instead of about 104 (after O2). Versus the optimised current version, that saves about 15–33% at N=10 and 19–38% at N=20; there is no gain at N=1. Clearing the gate depends on how much of the 39 MiB heap is pre-app framework state.

## Track 2: Performance (agent-facing latency)

**Goal:** make ACOS feel nearly instantaneous to an AI agent. Common operations should take tens of milliseconds, ideally under 50 ms.

| Operation | Target | Before (2026-11-12) |
|---|---|---|
| Tap delivery and acknowledgement | ≤ 20–30 ms | (not reported correctly: ack matching bug) |
| Tap → usable updated UI state | ≤ 50 ms ideal, < 100 ms | 1.14 s (counter), 295 ms (form) |
| Fresh screenshot (M5) | ≤ 30 ms ideal, < 50 ms | 80 ms |
| Fresh UI tree with text (M7) | < 50 ms ideal, < 100 ms | 252 ms |
| Reset → first correct screen (M6) | < 300 ms | 682–703 ms |
| Warm app launch | minimise; benchmark separately | not measured |
| End-to-end agent verification | minimise total wall time | 62.84 verified tasks/GiB-min (N=10) |

**Approved:**
- **Fast vs strict observation split.** Agents may navigate on fresh, possibly mid-animation frames, which are labelled as such. Strict settled-frame verification stays the default for assertions and pixel checks.
- Independent low-risk optimisations.

**Not allowed:** disabling real Android animations.

**Rule:** keep a change only if it brings a measured benefit, with no regressions and zero false passes.

**Known root causes:**
- **M5:** the PNG encoder's crc32 takes 43 ms and adler32 16 ms, both slowly written. Starting `md5sum` costs 10 ms, and the pixel hash 7 ms. (`results/art-runtime/D-M5.md`)
- **M8:** the button ripple animation keeps the 150 ms "screen is quiet" timer open for about 860 ms. The real tap takes about 20 ms. Leftover acknowledgements are miscounted. (`results/art-runtime/W59.md`)
- **M6:** an unneeded screenshot plus a 150 ms settle (238 ms), a hard-coded 200 ms sleep, and polling every 50 ms when the app exits in about 5 ms (105 ms). (`results/art-runtime/D-M6.md`)

## Track 3: Long-term session architecture (study, no redesign yet)

**Owner request (2026-11-12):** find the best long-term architecture for lightweight, independent Android sessions. Reduce the per-session overhead the Zygote still duplicates: the stand-in stub, the per-session launcher/ServiceHost/Binder/C1, ART copy-on-write erosion, duplicated threads/caches/buffers. Consider alternatives, not "everything in one process" (contention, cross-session leakage, single point of failure). Compare options with measured fixed + incremental memory at N = 1/5/10/20, startup, CPU, isolation and reliability. Keep the working implementation intact; recommend, do not commit to a redesign.

**Options compared:**

| | Shape | Main risk |
|---|---|---|
| A | Today: launcher per session + exec | highest memory |
| B | Zygote + full per-session launcher (Z4) | duplicated host |
| C | Zygote + launcher forked from a warm host template (separate processes, CoW host) | shared ASLR layout in hosts too |
| D | Zygote + one shared control plane hosting N ServiceHost/C1 | contention, leakage, one failure domain |
| E | Zygote + session services inside each app child | weaker app/service trust boundary |
| F | Small shared control plane (routing, lifecycle) + per-session service processes (C) | complexity |
