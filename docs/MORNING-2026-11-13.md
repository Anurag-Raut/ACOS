## 3. Decisions for you

1. **Zygote (Z7).** Recommendation: **do not adopt now.**
   - With early GC on the normal path (H2, now shipped), the zygote adds +38–40 % memory at N=10. At N=5 it adds only +22–25 %, which misses the 25 % gate.
   - It completes fewer tasks per minute (30 vs 39), because the prototype resets the whole group of sessions together.
   - It failed the security review for untrusted APKs.
   - Revisit only as a persistent zygote with per-session forks for trusted apps, which is an architecture change.
2. **Pixel guard (P12), decided overnight, please confirm.**
   - Strict settle no longer requires pixels to change.
   - Freshness is still proven: the probe is newer than the action, the guest is idle, a draw happened after the action, plus a 24 ms confirmation.
   - Each reply states `pixels_changed`.
   - It is never more permissive than main was before. `ACOS_STRICT_SETTLE_PIXEL_GUARD=on` restores the old rule.
3. **Gaten SVG sizing: plan ready for your approval (Codex-led research).** Every SVG icon on Gaten Home is drawn ~2.5× too large. **Measured cause: a bitmap density mismatch, not a missing per-view canvas.** In ACOS a new Bitmap defaults to 160 dpi while the canvas and `DENSITY_DEVICE` are 420, so the stock framework scales bitmap draws by 420/160 = 2.625×. Fixture evidence: a 60×60 default bitmap renders 158×158; a density-aligned one renders 60×60; a 100×100 canvas ruler is exact. react-native-svg already draws each SvgView into its own bitmap, so this is the path Gaten hits (strongly supported; the Gaten-specific A/B is not done yet). Still open: *why* the bitmap default is 160. **Source-level lead (not yet runtime-confirmed):** AOSP `ActivityThread` sets `Bitmap.setDefaultDensity(160)` and density-compat mode when the app's `ApplicationInfo` lacks `FLAG_SUPPORTS_SCREEN_DENSITIES` (0x2000), and `ConfigurationController` then skips the device density. The probe app's flags (0x10800046) lack it, so ACOS's package parsing probably drops the `<supports-screens>` defaults. If confirmed, the fix belongs in the parser, not in Bitmap. The old "hardware" launch flag was the wrong bit, so no HWUI path ever ran; the image has gfxstream drivers, not a standalone SwiftShader.
   - **Proposed PR1:** minimal fix to initialise the bitmap default density, plus a regression test and a Gaten region-by-region A/B against the Moto G35.
   - **Proposed PR2 (only if residual differences remain):** a hardware-renderer (HWUI) path.
   - R4's per-view canvas experiment is shelved, not merged. **Nothing is implemented until you approve.**
   - Local research evidence (gitignored scratch, not committed): `.cache/render-research-plan/REPORT.md` (analysis; **§8 is the authoritative measured density appendix** and supersedes earlier "unmeasured" wording), `.cache/render-research-hwui/REPORT.md` (acceleration flags, backend inventory), logcat `.cache/render-research-plan/out/logs/logcat.txt` line 54+, frame `.cache/render-research-plan/out/art-frames/live-frames/acos-c1-layer3-frame-279-g279-c3.png`. The probe scenario itself ended TIMEOUT (not a pass); the pixel/log measurement is the evidence.

4. **Screens that never stop drawing (Gaten welcome/onboarding).** They never strict-settle. GR3 wrote 4 options with false-pass analysis (results/gaten/GR3.md §4.3). **Recommendation (mine, and the Codex advisor's): explicit navigation-only `settle: fast`, then a strict `wait_for`/fresh capture before any claim**. This is what is merged now, opt-in per step, and the guard makes it fail closed. "Settle when content stops changing" (option A) stays an experiment, not the default: Gaten's pending retry keeps the guest busy anyway, and same-pixel redraws or A→B→A changes are hard to rule out. Please confirm.

6. **Reset in the agent loop (H15).** 117 of the 342 ms strict reset is waiting out button ripples that change no pixel. Options: let the bench loop's reset step use `fast` (−142 ms/task, then the next step proves state strictly), or try option A above. Neither is default today. Recommendation: allow `fast` for reset in the loop harness only, reported as a separate benchmark protocol. Your call.

5. **Shared boot image default (H13).** `shared-aslr` saves 10–12 MiB per session (≈ −17 %) at N≥5, keeps image ASLR per serve, and passed all gates with 0 false passes. The price is a one-time 3.6 s image build at the first launch of each `acos serve` (cold start 409 ms → 4.1 s for that one launch). Recommendation: make it the default **only for long-lived `serve` deployments** (many sessions per serve) and keep `lz4` for one-shot CLI runs, or first try an offline relocator that removes the 3.6 s. Your call; nothing changed by default.
