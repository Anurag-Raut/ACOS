# ACOS plan, 2026-11-16, revision 2 (supersedes sections 5 to 7 of STATE_AND_PLAN_2026-11-15)

Revision 2 follows the owner's review: three releases only; every service module
ships in one release; the phone must have real internet; WebView must be a real
engine, and the host machine may provide it. Major decisions are made here, by
the orchestrator with the owner, and are not left to implementers.

Inputs: the agent feedback log (`~/.claude/acos-feedback/ACOS_AGENT_FEEDBACK.md`;
no PDF exists on disk), the Gaten floating-button verification (ACOS covered about
15% of that change), and a code check of the sandbox (`--unshare-net`, a seccomp
filter that allows only `AF_UNIX` sockets, CPU rendering with no GPU stack, about
50 services registered lazily in `crates/acos-services/src/registry.rs`).

Standing rules: root cause and finished features; 0 false passes; `unsupported`
is structured, never a silent stub; max 5 agents; pi + DeepSeek implementers
(`deepseek-v4-pro` thinking high for framework internals, security and verdict
work; `deepseek-v4.1-flash` thinking high for the rest); a fresh Opus-medium
reviews security and verdict-semantics changes only.

## 3. v0.4.0: service modules

### 3.1 The model (decided)

A **module** is a unit that owns some Android system pieces and is attached to or
detached from a session. Today's services become the `core` module, which is
always attached, so nothing regresses.

- **Manifest** per module: id, what it provides (ServiceManager names, broadcasts,
  content providers, windows, system apps), what it requires (modules, host
  tools), profiles, RAM and startup budget, security class, control operations,
  and whether it can be attached live (`hot`) or only at launch.
- **Profiles**: `off` (the framework takes the real missing path and every reply
  says the module is off), `stub` (fixed, documented answers), `scripted` (the
  agent drives the state), `real` (a real implementation).
- **Interface** (Rust, in `acos-services`): `attach(host, profile, config)`,
  `detach()`, `control(op, args)`, `report()`. It plugs into the existing
  `ServiceHost::register` seam. Detach removes every registration, thread, fd and
  socket.
- **Unattached names** answer with a tombstone that returns
  `UNSUPPORTED_ANDROID_API` naming the module and the attach call. Never a silent
  null that looks like a working phone, never a fake success.
- **Agent API**: `acos_launch {services: [{id, profile, config}]}`, the same
  `services:` block in scenario YAML, `acos_services {op: attach|detach|list|status}`
  for live sessions (only `hot` modules), `acos_service_ctl {module, op, args}`
  for scripted state.
- **Verdicts** list the attached modules and profiles in the envelope, the summary
  line and `verdict.json`. A pass that relied on `stub` or `scripted` says so. An
  assertion that needs a module that is `off` is `unsupported`, never `pass`.
- **Docs**: `acos_capabilities` and the `acos_help` limits section are generated
  from the module registry (root-cause fix D).
- **Conformance kit** every module passes: manifest valid; attach and detach twice
  returns RAM, threads and fds to baseline; honest-report test; a negative test;
  density at N=20 within the manifest budget.

"ADR" is an Architecture Decision Record, a short document in `docs/decisions/`
that fixes a design choice and its reasons. ADR-0029 records this model. It is a
document, not a module.

### 3.2 Shared foundations (built first, everything depends on them)

1. **Module framework** (section 3.1).
2. **Window layer stack.** Extend compositor C1 from one app window to an ordered
   stack of windows with real types and z-order (application, dialog, application
   overlay, accessibility overlay, system dialogs, notification shade). This
   absorbs ROT9 (layer pool). Needed by accessibility overlays, permission
   dialogs, the shade, the second app and multi-window.
3. **Multi-process sessions.** A second app (or an `android:process` component)
   runs as its own ART process forked from the session's zygote, in the same
   sandbox. The Rust service layer routes binder transactions between the guest
   processes. It already plays the system_server role, so it is the broker. Package
   manager and intent resolution see every installed package in the session.
   Loading a second app into the first app's process was rejected because it is
   wrong fidelity.
4. **Host broker.** One ACOS-owned host process per server for things that run on
   the host (the network relay and the shared Chromium below). The guest reaches
   it only through a socket ACOS creates. No raw host interface is exposed to the
   guest.

### 3.3 Decisions per module

**Network (real internet, decided).**
- `real` is the **default profile**: the phone has working internet like a real
  phone. `offline` and `scripted` are opt-in, for failure-path tests and
  reproducible runs.
- Transport: the session keeps its own network namespace, and **pasta** (from
  passt, the rootless networking used by Podman) gives it a NATed interface.
  The seccomp filter allows `AF_INET`/`AF_INET6` only when the network module is
  attached.
- Host safety: no route to host loopback or the LAN gateway by default
  (`--no-map-gw`). That keeps `acos view`, the MCP daemon and anything else on
  127.0.0.1 unreachable. Host ports are reachable only when named explicitly (for
  example Metro on 8081 in v0.5.0).
- DNS: Android's resolver talks to netd over `/dev/socket/dnsproxyd`. ACOS serves
  that socket (netd replacement) and resolves through pasta.
- TLS: ship the AOSP CA store (`/system/etc/security/cacerts`) in the image.
- Framework state: connectivity reports a validated internet network.
  `ConnectivityManager`, `NetworkCallback`, `TrafficStats` and `WifiManager`
  connection info are consistent with it.
- Agent controls (`hot`): go offline or online mid-session, add latency or loss,
  and record traffic to a HAR file through an optional proxy.
- Packaging: pasta is bundled in the ACOS install as a static binary (GPL-2,
  shipped with its licence), so no system package is needed; `acos doctor` checks
  it.
- Fresh Opus security review before merge.

**WebView: the host's Chromium as the engine (decided, behind a 2-day spike gate).**

Options:

1. *Android System WebView APK inside the guest.*
   - Pros: the exact engine phones use.
   - Cons: it needs a separate sandboxed renderer process and draws through a
     hwui GPU functor, and ACOS renders on the CPU with no GPU stack. It would
     cost roughly 150 to 250 MiB per session, and every session pays it again.
2. *Host Chromium as the engine (chosen).* ACOS ships its own WebView provider (the
   framework's `WebViewFactory` loads a provider package; ACOS supplies one). The
   provider implements `android.webkit` (`WebView`, `WebViewClient`,
   `WebChromeClient`, `WebSettings`, `CookieManager`) by driving a pinned headless
   Chromium on the host through the DevTools protocol:
   - Rendering: deterministic frames are painted into the View's canvas at the
     View's size and density.
   - Input: touch, scroll and IME text go through the DevTools input methods.
   - JavaScript: `evaluateJavascript` is mapped to evaluation in the page.
     `addJavascriptInterface` is mapped to page bindings with a shim, so calls go
     both ways.
   - Callbacks: request interception gives `shouldOverrideUrlLoading` and
     `shouldInterceptRequest`, and `file:///android_asset` and `content://` URLs
     are served from the APK.
   - Identity and network: the WebView user agent is used, and the page's traffic
     follows the session's network profile.
   - Web content in the UI tree: the page's accessibility tree is merged into the
     ACOS UI tree as virtual nodes, so agents tap and assert web content by text.
     No phone WebView gives agents that.
   - Cost: one Chromium per host, shared by all sessions (one browser context per
     session, the shared-core idea), costing about 40 MiB per page instead of
     150+ MiB per session.
   - Engine version: it is a real Blink engine, pinned (Chrome for Testing
     `chrome-headless-shell`, downloaded by the installer with a checksum). The
     verdict names the engine version. It is not the phone's exact WebView build,
     and `fidelity` says so.
   - Isolation: Chromium runs in its own bwrap sandbox.
3. *Scripted pages only.* Rejected: the owner wants a real engine.

Spike gate (2 days, before the full build): the Gaten or a sample app loads a real
HTTPS page, a JS-bridge round trip works both ways, a tap on a web button by text
works, a frame takes under 50 ms, and an extra session with a WebView costs at most
60 MiB. If the gate fails, fall back to option 1 and accept the per-session cost.

**Accessibility (the Gaten floating bubble), decided.**
- Real `AccessibilityManagerService` behaviour, not a stub.
- Enabling a service is a launch config (`services: [{id: "accessibility", config:
  {enable: ["com.gaten/.GatenAccessibilityService"]}}]`), the equivalent of the user
  switching it on in Settings. ACOS writes the secure setting and binds the
  service, and `onServiceConnected` runs.
- Service connection:
  - window list and node search through each window's interaction connection
  - `performAction` and global actions (back, home, recents, notifications)
  - `dispatchGesture` through the input path
  - `takeScreenshot` from the compositor frame
  - event delivery (window state, content changed, view clicked) from the app's
    `AccessibilityManager` calls
- `TYPE_ACCESSIBILITY_OVERLAY` and `TYPE_APPLICATION_OVERLAY` windows come from the
  layer stack (3.2.2), so the bubble draws, drags and clamps above the app.
- FLAG_SECURE is honoured in `takeScreenshot`, as on a phone.

**Intents and the second app, decided.** Covered by the multi-process foundation:
- a second APK installed in the session
- implicit intent resolution across all packages, with a real chooser window for
  share sheets
- a minimal ACOS launcher and Settings stub as system apps, so "go home" and
  settings intents have honest targets
- media session state shared across apps, for Gaten's pause and resume

**Notifications and permissions, decided.**
- A real notification shade window (layer stack) that agents can open, read and tap.
- Runtime permission dialogs are real system windows that agents answer with
  `tap`, or pre-grant through config.

**Rotation and multi-window, decided.** Real configuration changes (activity
recreation or `onConfigurationChanged` as declared) and display resize through WMS.

**Location, sensors, camera (scripted feeds), decided.**
- Location: a GPS track or a single fix fed by the agent, with providers and
  geocoder answers.
- Sensors: scripted accelerometer, gyroscope, light and proximity values through
  the native sensor service.
- Camera: Camera2 backed by a still image or video file as the frame source.
- These can never be "real" in a sandbox; `scripted` is the honest top profile.

**Telephony, Bluetooth, biometrics, and the long tail (wifi scan, NFC, USB,
vibrator, usage stats, wallpaper, print, search, device policy, role, dropbox,
carrier config), decided.**
- Telephony: scripted SIM state, incoming SMS and call events.
- Biometrics: a scripted prompt result (success, fail, cancel).
- Bluetooth: an empty or scripted device list.
- Everything else is `stub` with an honest report. A stub is never presented as a
  real device feature.

### 3.4 Real-app proof per module (the v0.4.0 acceptance)

| Module | Proof |
|---|---|
| network | an RN app fetches a real HTTPS API, then the agent goes offline mid-session and asserts the app's error state |
| webview | a page with a JS bridge, a tap by web text, and a navigation intercept |
| accessibility | **Gaten floating bubble**: bubble appears after the service is enabled; drag, edge clamp, idle fade, remove target, `takeScreenshot` lookup, TalkBack custom action |
| second app + intents | Gaten media pause and resume with a second media app; a share sheet that lands in a second app and returns |
| notifications + permissions | app posts a notification, agent opens the shade and taps it; app asks a permission, agent grants and denies |
| rotation | Gaten bubble position restored after rotation |
| feeds | a location track moves a marker; a sensor value changes a view; a camera preview shows the supplied image |
| long tail | per-module honest-report tests |

### 3.5 Work order and agents (max 5)

1. **Phase 1 (foundations, in parallel):** module framework and conformance kit;
   window layer stack; multi-process sessions; network; WebView spike.
2. **Phase 2:** accessibility and overlays; notifications and permissions;
   WebView full provider (if the spike passes); intents, second app and system apps.
3. **Phase 3:** rotation and multi-window; feeds; long tail; generated docs (D);
   integration on the `modules` branch; all gates; the real-app proofs; density
   check.

Each workstream has one owner agent, its own worktree, a brief with the acceptance
command, and `docs/AOSP_REFERENCE.md`. Security reviews by a fresh Opus-medium:
network, host broker and Chromium sandbox, accessibility (screen capture and
gesture injection), and the verdict changes from module profiles.

### 3.6 Risks

- **Size.** v0.4.0 is the largest release so far. Integration happens continuously
  on one branch, and nothing ships until every module meets its proof (owner rule).
- **Multi-process binder routing** is the deepest change. It gets the
  `deepseek-v4-pro` agent and an early end-to-end test (two processes, one bound
  service).
- **Host Chromium fidelity** differs from a phone's WebView build. This is
  mitigated by the spike gate and a `fidelity` note in every verdict, with the
  Android WebView APK as the fallback.
- **Real network** reduces reproducibility. Every verdict records the network
  profile, and scenarios that need determinism set `scripted`.
