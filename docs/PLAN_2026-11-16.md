## 2. Service modules: the building-block system

### 2.1 What a module is

A module is one unit that owns a set of Android system pieces and can be switched
on or off per session. It plugs into the existing `ServiceHost` (today
`crates/acos-services/src/registry.rs` registers about 50 names with lazy
factories; `host.register(name, descriptor, factory)` is already the seam). Nothing
about the current services changes at first: today's behaviour becomes the
`core` module set and the default.

Each module ships:

- **Manifest** (`module.toml`, also generated into `acos_capabilities`): id,
  version, what it `provides` (ServiceManager names and descriptors, broadcasts,
  content providers, system apps or windows), what it `requires` (other modules,
  host capabilities such as network or a device node), supported **profiles**,
  RAM and startup budget, security class, control operations.
- **Profiles**: `off` (the framework sees the honest missing path and the reply
  says so), `stub` (fixed documented answers), `scripted` (the agent drives state:
  set a network response, feed a sensor value, post a notification), `real` (a
  real implementation, only where reviewed).
- **Lifecycle**: `attach(host, profile, config)`, `detach()`, `control(op, args)`,
  `report()`. Detach must leave no thread, fd, socket or registration behind.
- **Conformance tests** (a shared kit every module must pass): manifest valid;
  attach then detach twice leaves RAM, threads and fds at baseline; reports
  honestly (an unattached or `off` service never returns a silent null or fake
  success: `UNSUPPORTED_ANDROID_API` names the module and the attach call); a
  negative test; and a density bench at N=20 sessions.

### 2.2 How agents use it

- Attach at launch: `acos_launch {apk, services: [{"id":"network","profile":"scripted"}, ...]}`
  (also in scenario YAML as a `services:` block, so a verify run is reproducible).
- Attach and detach on a live session: `acos_services {"op":"attach|detach|list|status", ...}`.
  Only modules marked `hot` allow this (pure state modules: network, notifications,
  location, sensors, permissions). Modules that need a process or window layer
  (second app, WebView, accessibility, overlays) are `at-launch` and say so in the
  manifest. We state this plainly instead of faking hot-swap.
- Drive scripted state: `acos_service_ctl {"module":"network","op":"respond","args":{...}}`.
- Verdicts record the attached set. `verdict.json` and the summary line carry
  `modules: [network:scripted, ...]`; a pass that depended on a `stub` or `scripted`
  module says so in its `fidelity` note, and an assertion that needs a module that
  is `off` returns `unsupported`, never `pass`.
- `acos_capabilities` and `acos_help` limits are generated from the module
  registry. This is also the root-cause fix for track D.

### 2.3 Module list and build order (owner: all wanted)

Order is by how many real failures each unblocks and by dependency.

| Wave | Module | Hot? | Unblocks | First honest profile | Acceptance proof |
|---|---|---|---|---|---|
| 0 | `core` + module framework | n/a | everything | all current services as `core`, tombstones for known-missing names | attach/detach leak test passes; capability report generated; N=20 density unchanged |
| 1 | `network` | yes | connectivity-dependent apps, API clients | scripted (agent-defined responses, DNS, latency, failures); `real` opt-in later with security review | a React Native app fetch is answered by a script and the failure path is asserted |
| 1 | `intents` (package manager sees more than the app under test) | no | share sheets, pickers, browser, camera app, deep links | stub target activities + routing table | an app share action lands on a scripted target and the result returns |
| 1 | `second-app` | no | media pause/resume, foreground-package logic | second APK in the same session, one foreground at a time | two-app scenario switches foreground and asserts both |
| 2 | `notifications` + `permissions` | yes | notification posting and grants, runtime permission dialogs | shade state readable and tappable, grant dialog as a real window | app asks permission, agent grants or denies, app reacts |
| 2 | `webview` | no | any app with a WebView | scripted pages first (content-only); real engine only after a size and security assessment | page loaded from a script is asserted in the tree |
| 3 | `accessibility` + `overlay-windows` | no | Gaten floating bubble, TalkBack-style actions, takeScreenshot | real accessibility service binding, `TYPE_ACCESSIBILITY_OVERLAY` windows in the compositor layer pool | **Gaten FAB bubble: drag, clamp, idle fade, remove target** (the 85% that ACOS could not verify) |
| 3 | `rotation` + `multi-window` | no | geometry restore, fold logic | rotate and resize through WMS | rotate then assert restored position |
| 4 | `location`, `sensors`, `camera` | yes | map, motion, scanner apps | scripted feeds (GPS track, accelerometer, a still or video frame source) | a feed drives a visible change |
| 5 | `telephony`, `bluetooth`, `biometric`, `wifi`, `nfc`, `usage-stats`, `wallpaper`, `print`, others on the gap list | mostly yes | long tail | `stub` with honest reports, `scripted` where an app flow needs it | per-module report test |

A module is "done" only when its acceptance proof runs against a real app, not a
unit test. Modules that cannot be made honest stay `off` and are listed as
unsupported with a reason.

### 2.4 Design decisions needed from the owner

1. Approve this module model as ADR-0029 (extends ADR-0008, "start only what a task needs").
2. `network` `real` profile: allow it at all? It lets guest apps reach the host network. If yes it needs a security review and an allow-list. Recommendation: scripted first, `real` later and opt-in only.
3. `webview`: the real engine is large (hundreds of MB, extra processes). Recommendation: scripted content first and decide the real engine after measuring.
4. Which first real proof matters most: the Gaten bubble (wave 3) or network and intents (wave 1)? Recommendation keeps wave 1 first because it proves the framework cheaply, then goes straight to wave 3 before waves 4 and 5.

## 3. Hardening tracks (each one finished root-cause fix)

Run in parallel with module work when agent slots allow.

1. **B: Verdict provenance and strict inputs.** Put scenario path (absolute), scenario sha, APK sha, engine and attached modules into the envelope, the summary line and `verdict.json`. Reject unknown arguments on every MCP tool and CLI command. One engine vocabulary shared by YAML and flag, one default constant used by help and code. Warn when the scenario `app:` differs from `--apk`. Needs verdict-semantics review.
2. **A: Settle semantics.** Content stability as a first-class settle mode for every wait, assertion and action reply; replies state the mode used; a timed-out settle is never a plain pass; `animations` on MCP verify. Needs verdict-semantics review.
3. **C: Reply budget.** One reply rule for all tools: hard cap, compact default answering "what is on screen", file path for the rest, same rule in verify artifacts (full tree persisted per step), logs default filtered.
4. **D: Docs from code.** Generate limits, capabilities, tool cheat sheet and the "not visible is not absent" and coordinate-origin text from the same registry; a test fails when docs and code disagree. Depends on module wave 0 for the capability table.
5. **E: Handled vs sent.** The input dispatcher reports whether a handler consumed the event; replies carry `handled`, auto-asserted taps are documented.
6. **F: Front-door parity.** `acos guide [topic]`, `session list` text output and ids, positional destroy, absolute paths in `repro.json`, readable selector errors, `replay_pid*.log` triage and `.gitignore`.

## 5. How the work is run

- Agents: at most 5 at once. Wave 0 and track B start first and in parallel:
  1. module framework design note + ADR-0029 draft (read-only, then owner approves), then implementation;
  2. track B (provenance and strict inputs);
  3. track A (settle), after B's envelope fields land, because both touch the reply and verdict shape;
  4. track C (reply budget), independent;
  5. a reviewer slot kept free for verdict and security reviews.
- Each agent gets its own worktree, a self-contained brief, the acceptance command,
  and `docs/AOSP_REFERENCE.md`. ART runs go through `tools/art-runtime/run-exclusive.sh`
  and `tools/guarded.sh`; RAM stays under 90%; disk is pruned at 85%.
- Worktree cleanup (merged branches) and the parked backlog (ROT8b/ROT9 Back fixes,
  GUESTEXIT0, ZPROD8, METRO1..8, ABCHECK, viewer follow-ups) stay as in the earlier
  state doc; ROT8b joins v0.3.0 only if it passes its own full verification.
